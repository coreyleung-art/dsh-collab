# 技术判断沉淀：P2-4 帧索引落地评估（2026-09-05）

> 来源：mbp-ops 重启后代码级核实 · 结论：**暂缓 P2-4 runtime 大改动**（已获用户确认）
> 归类：考古闭环 M2（全量物化内存失控）的治理边界澄清

---

## 一、核心发现（代码级证据，0.1.1-rc.2）

### 1. 首开会话读路径 = inspect（不走 readFrom/loadStoredFrom）
- `api-remotes/lib/index.js:86`：客户端打开会话 → `persistence.inspect(sessionId)`
- `coordinator.inspect` → `prepareCore` → `backend.loadStored(id)` **全量**
- 与官方 #4416 描述的 master 分支（history 尾页走 readFrom）**不同**——本机 rc.2 是 inspect 主路径

### 2. inspect 必须全量物化（架构硬约束）
- `prepareCore` 需要全量 events 做：`adoptStoredEvents` + `interruptedTurnClosers` + `sessions.prepare(seed: balanced)` surface 重建
- `SessionLogScanner` 严格校验事件 seq 从 0 连续（`event.seq !== this.events.length`）→ **consumer 不能跳帧**
- → 帧索引无法让 inspect "只解尾部帧"（seq 全序校验依赖全量解码）

### 3. loadStoredFrom hook 只服务 readFrom（非首开主路径）
- `coordinator.readFromCore:938`：backend 提供 loadStoredFrom 才走后缀读
- readFrom 用于翻页/历史恢复/长会话滚动——**非"首开会话"瓶颈**

### 4. 帧索引对 inspect 的真实收益 = 仅 decode 调度开销
- 官方实测全量 430ms 中 decode 仅 ~78ms；parse ~200ms / snapshot ~148ms 才是大头且**不可避免**
- → 帧索引在当前架构下对冷开会话**收益有限**

---

## 二、结论与决策

**暂缓 P2-4 大 runtime 改动**。原因：
1. 主瓶颈（inspect 全量物化）是架构约束，非帧索引能解
2. loadStoredFrom 实现的收益仅覆盖非主路径（翻页/恢复）
3. 投入产出比低，且动 persistence 核心写路径风险高

**已生效的治理**：P2-3（preparedSessionCacheSize 5→2）重启后 RSS 859→280MB——通过**减少常驻**而非"免解码"降内存，是当前架构下的正确杠杆。

**未来若要做 inspect bounded**：需改 coordinator/surface 语义（T2-2b 设计的 L4，官方 roadmap mid-term）——那是大工程，等官方上游方向或专门立项。
