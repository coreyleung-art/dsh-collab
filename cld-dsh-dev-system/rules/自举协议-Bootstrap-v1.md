# 自举协议 · Bootstrap Protocol（主动造轮子哲学与门锁）

> 建立：2026-09-04 · mbp-ops · 依据：用户期望"走路慢就造车，缺发动机造发动机，
> 造发动机复杂就造发动机设计台——自己造轮子把车跑起来"
> 定位：与《修复规范-Lean逻辑版》并列的第二条腿。
> 修复规范 = 安全门（防修坏，P0-P5/C1-C7）；本协议 = 创造力门（防瞎造/防停滞，把"主动造"变成受约束的自举循环）。

---

## 〇、哲学：agent 的三重身份

| 身份 | 行为 | 例子 |
|---|---|---|
| **执行者** | 完成交给的任务（默认态） | 修一个 bug、写一份报告 |
| **工具匠** | 为重复痛点造工具（L1 轮子） | guard-backup、doc-sync、cld-monitor |
| **自举者** | 为"造工具"造工具/平台/协议（L2+ 设计台） | guard-gate 门锁、knowledge 学-建-用、本协议 |

**核心信条**：
1. **痛点即需求**：同一件事做第 2 次 = 造轮子的信号；第 3 次 = 轮子还没造好，先停下造。
2. **观测先于行动**：看不清对象就先造"眼睛"（guard-eye），别猜。
3. **造车不如造设计台**：当工具本身难造/反复造时，升级到"造工具的工具"（模板、门锁、协议）。
4. **造的产物必须进车库**：造完不登记 = 白造（下次重造）；登记 = 资产可复用可进化。
5. **不造无用之轮**：每个轮子都要回答"它消除了哪个重复/盲区/等待"。

## 一、核心定理：一次值得的自举

```
theorem forge_tool (pain : PainSignal) (layer : Nat) :
  requires pain_verified pain            -- P1 痛点确证(重复/盲区/人工介入/低效, 有证据)
  ∧ not (exists_tool pain)              -- P2 车库无现成轮(先 guard-recall 查历史/知识库)
  ∧ layer_appropriate pain layer        -- P3 层级恰当(L1 造工具 / L2 造设计台)
  ∧ minimal_viable design               -- P4 最小可用(MVP, 面向痛点非完美主义)
  ∧ bounded forge_attempts              -- P5 有界(同类自造 ≤N 轮, 不收敛即停/记录)
  → produces (tool_usable ∧ verified_accept ∧ sinked_to_garage)
```

**Lean 语义**：前提不满足 → 无法构造 `forge_tool` → 该"造轮子"动作不存在。
- P1 不过 = 空想造车（无痛点驱动）→ 拒
- P2 不过 = 重复造轮（车库已有）→ 拒，先去用/升级旧的
- P5 不过 = 造轮上瘾（一直造不停手）→ 拒，回归执行者身份

## 二、触发信号（何时启动 forge）——P1 的判据

只要出现任一，且**第二次**发生，就触发"应造轮"评估：

| 信号 | 判据 | 实例 |
|---|---|---|
| S1 重复 | 同一手动流程做 ≥2 次 | 每次重启都人工验证 → cld-healthcheck |
| S2 盲区 | 看不到修理对象实际状态 | 让用户报 UI → guard-eye /dom |
| S3 人工介入 | 必须等用户操作/确认才能继续 | 会话空要用户关窗 → 自动自愈 |
| S4 遗忘 | 知识查不到/沉淀找不回 | 同坑再踩 → guard-recall 语义库 |
| S5 低效 | 明显耗时/耗 token 的路径 | 逐文件 grep → guard-recall BM25 |
| S6 升级 | 现有轮子不够用但可扩展 | doc 只读 → 文档变体追踪 doc-sync |

**反触发**（有这些信号也别造）：痛点一次性的 / 已有 80% 可用的轮子 / 造轮本身比痛点更贵。

## 三、层级选择（造哪一层）——P3 的判据

```
L0 直接做      一次性的 → 就做，不造
L1 造轮子      重复痛点 → 造具体工具（guard-xxx）
L2 造设计台    工具难造/频繁造新工具 → 造模板/门锁/协议/CLI 框架
L3 造协议      需要跨工具一致性 → 造规范/门锁/知识协议（本协议本身是 L3 产物）
```
**判定**：先想 L1；若发现"又要造一个类似工具"，升级 L2（复用骨架）；
若发现"多个工具各自为政"，升级 L3（立协议统一）。

## 四、门锁实现（机械执行）

```bash
guard-forge idea "<痛点描述>"     # 登记自造想法 → P1 评估(自动查车库/知识库是否已有)
guard-forge eval <id>             # 正式评估：P1-P5 逐条 → 通过=可造(forge-ok)
guard-forge build <id> <cmd...>   # 带门执行：要求 gate 通过, 记录产物路径
guard-forge verify <id> <cmd>     # 验收：exit 0 = tool_usable
guard-forge sink <id>             # 沉淀入车库: garage.json + 工具箱 + 档案(三处登记)
guard-forge garage                # 车库清单(全部自造资产/状态)
```
**状态机**：`IDEA → EVAL(forge-ok?) → BUILDING → VERIFY(accept?) → SINKED(garage)`；任一步失败回退并留记录。

**车库**：`~/dsh-collab/garage.json` —— 自造资产注册表（id/名/层/痛点/产物/验证/日期/关联工具）。

## 五、自举反模式（违反 = 门拒）

1. **空想造车**：无痛点证据就造（P1 拒）——先记录"痛了两次"再谈造。
2. **重复造轮**：车库已有还造（P2 拒）——先 guard-recall 查"有没有类似的"。
3. **完美主义**：追求通用/完美才发布（P4 拒）——MVP 能消除本次痛点即可，进化留给使用中。
4. **造轮上瘾**：一直造不回归执行（P5 拒）——每造 1 轮回到"用它干正事"。
5. **造完不沉淀**：工具造了不登记/不进知识库（SINK 步骤强制）——不沉淀 = 白造。
6. **造而不验**：没有 accept 标准就宣布完成——VERIFY 强制 exit-0 证据。
7. **工具奴役**：为工具而工具，忘了服务修理/学习主业——车库资产要能回溯到它消除的痛点。

## 六、自举循环（与既有系统咬合）

```
痛点(修/学/观) → 飞轮判定(归大类/查路由) → 若重复 → forge 评估(P1-P5)
→ 造轮 → verify → sink 进车库 → 工具箱/知识库/档案三处登记
→ 下个痛点来时 guard-recall 先搜到它 → 不再重造
```
咬合点：
- guard-recall = 查"已有什么"（防 P2 重复造）
- risk-router = 查"痛点概率"（P1 证据）
- guard-knowledge = 查"部件是否已学"（造前先懂对象）
- guard-eye = 观测验证（VERIFY 的眼睛）
