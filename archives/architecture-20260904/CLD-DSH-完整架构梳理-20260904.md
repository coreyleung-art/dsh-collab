## 二、CLD 桌面壳（②层）架构详解

### 2.1 启动流程（main.js:700 start()）
```
app.whenReady → start()
  ├─ buildMenu() 构建菜单
  ├─ traceBoot() 读上次退出标记 → 写本次 boot 标记 + 心跳
  ├─ setInterval(writeHeartbeat, 30s)  心跳线程
  ├─ resolveStartupMode()  模式决策（见 2.2）
  ├─ 若 remote 模式 → waitForHttpReady(remoteUrl) → createWindow
  └─ 若 local 模式：
       ├─ awaitServerUrl() 准备 URL 解析
       ├─ spawnDsh(runtime)  ← 核心：拉起 dsh 子进程（见 2.3）
       ├─ startReloadServer()  ← 31888 热重载
       ├─ runDoctor()   ← 会话健康扫描
       └─ 等 URL → createWindow(url)  加载 GUI
```

### 2.2 模式决策（main.js:272 resolveStartupMode）
```
CLD_REMOTE_URL / CLD_BIND_HOST 环境变量 → 直接决定
→ 否则读 ~/.cld/config.json（mode/remoteUrl/remember）
   ├─ mode=remote + remember → CFG.remoteUrl
   ├─ mode=local  + remember → local 默认
   └─ 否则 askMode() 交互弹窗 → 写回 config.json
```
CFG 来源（main.js:199）：`CLD_REMOTE_URL / CLD_BIND_HOST / CLD_PORT / CLD_HEADLESS / CLD_TRUSTED_HOSTS` 环境变量。

### 2.3 spawnDsh 子进程模型（main.js:321，架构核心）
```js
dshArgs = ["--expose-internals", bin, "web", "--port", "0"]
        + (bindHost ? trusted-host 列表 : [])
child = spawn(process.execPath, dshArgs, {
  env: { ...process.env, ELECTRON_RUN_AS_NODE: "1" },  // ← 关键
  cwd: os.homedir(),   // 会话按 $HOME 分组
})
```
- **CLD 用自身二进制 + ELECTRON_RUN_AS_NODE=1 派生 dsh** → dsh 是真 Node 子进程
- stdout 解析 `dsh web: http://127.0.0.1:<port>` → 窗口加载
- **exit 处理（关键缺陷点）**：`child.on("exit")` → 弹错框 → `app.quit()`

### 2.4 看门狗/退出留痕（架构缺陷源）
```
文件：~/.cld/logs/{exit-marker.json, heartbeat.json, crash-reason.log, dsh-web.log}
启动：traceBoot() 读上次 marker：
      cleanExit!=true → 记 "DID NOT EXIT CLEANLY"
      cleanExit=true  → 记 "exited cleanly"
退出：before-quit → traceExit("quit") → 写 cleanExit:true
      process exit → traceExit("process-exit")
```
**❌ 架构缺陷（本次治理重点）**：
- 看门狗**只跟踪主进程生命周期**，不检查 child.exit code/signal
- dsh 子进程 OOM（SIGABRT）→ child.on("exit") → app.quit() → before-quit → **记 cleanExit:true**
- ⇒ 子进程崩溃被系统性误判为 clean exit（09-04 1856 OOM 实证）
- 修复点：child.on("exit") 处若 code≠0/signal 非空 → 写 crash marker（绕过 quit 路径）

### 2.5 热重载（31888）
- `startReloadServer()` 起 localhost:31888，POST /reload → `reloadDsh()`
- reloadDsh：杀旧 child → spawn 新 → 窗口刷新（壳不退出）

### 2.6 doctor（会话健康扫描）
- `runDoctor()`（main.js:663）：spawn doctor 脚本（ELECTRON_RUN_AS_NODE）
- 逐会话检查 session.jsonl.zstd 完整性（healthy/corrupt 统计，doctor-state.json）
- **每次启动全量解压 189 会话** → 4GB 堆峰值的直接来源之一

## 五、会话子系统（⑤层）全链路

### 5.1 服务链（依赖序，来自 dump 树）
```
session（核心：append-only 事件日志，唯一事实源）
  → session-persistence-jsonl（zstd 多帧落盘）
  → session-query-sqlite（搜索/查询/分页）
  → session-projection（派生视图缓存）
  → session-projection-cache（写检查点）
  → session-telemetry-otel（可选遥测，默认 DISABLED）
```

### 5.2 存储布局
```
~/.dsh/sessions/
  └─ --Users-coreyleung--/          ← 按工作区 cwd 分组
       └─ session-<uuid>/
            └─ session.jsonl.zstd   ← 单文件 append-only（137MB 最大）
格式：checksummed concatenated Zstandard frames（每 append 批次一帧）
      帧可独立定位（实测 302,413 帧/137MB，平均 477B/帧）
```

### 5.3 读路径（内存治理关键）
```
打开会话 → SessionCorpus.load(id)
  ├─ live 会话 → 快照内存 events（不碰磁盘）
  └─ 持久化会话 → inspectPersisted() 整文件 zstd 解压
       → events.map(structuredClone)  ← 全量驻留（OOM 源）
readEvent 窗口只控返回条数，底层数组全量
```

### 5.4 缓存机制（官方 + 实测）
| 机制 | 官方文档 | 实测 |
|---|---|---|
| preparedSessionCacheSize | config-catalog:1916 "Defaults to 5" | SessionPreparations LRU 容量 5 |
| 每 id 一份冷缓存 | persistence.md:101 revision 键 | — |
| zstd 多帧 | "concatenated Zstandard frames" | ✅ 302,413 帧 |
| LRU 逐出 | 官方留白 | touch/evict 队头淘汰 |

### 5.5 崩溃恢复（官方语义）
- 持久化层不截断/不重写：读方修复（interruptedTurnClosers）
- 尾帧撕裂 → 只丢不完整残帧
- 版本不匹配 → SessionFormatUnsupportedError fail-closed

## 九、架构结论（治理锚点）

| # | 架构事实 | 治理含义 |
|---|---|---|
| 1 | dsh 是 ELECTRON_RUN_AS_NODE 子进程 | 堆上限走子进程 execArgv 或 --js-flags；NODE_OPTIONS 无效（官方白名单） |
| 2 | 看门狗只看主进程退出 | **补 child exit code 检测**（缺口①修复点） |
| 3 | 打开会话=全量解压驻留 | **帧索引**（官方多帧格式支持随机访问） |
| 4 | doctor 启动全量扫描 189 会话 | 4GB 峰值源；应只读帧头/stat |
| 5 | 插件 31 层 link 到用户源码 | 版本漂移风险源（@linxin666 案例） |
| 6 | 协作设施独立进程 | CLD 崩溃可远程诊断（本次即如此） |
| 7 | main.js 退出=弹框+app.quit 无分级 | OOM 与正常退出同路径 → 信号失真 |

## 十、内存治理目标架构（你的模型：磁盘扩展临时内存通道）

### 10.0 模型表述

你提出的模型——**「临时调用硬盘来扩大内存通道」**——在系统层面有成熟对应物（虚拟内存/swap、tiered memory、JSON-Mmap），其本质是：

> **内存只保留"热"数据，冷数据留磁盘；通过"索引/映射"按需换入，而不是把整份资源物化进 RAM。**

映射到 DSH 会话场景，就是要把「会话历史」从 **原子对象**（当前：打开=整文件解压全量驻留，见 §5.3）改成 **可分页资源**（热帧在内存、冷帧在磁盘、帧索引定位、按需解压）。

### 10.1 现状 vs 目标（对照）

| 维度 | 现状（§5.3，OOM 源） | 目标（你的模型落地） |
|---|---|---|
| 打开会话 | 整文件 zstd 解压 → 全量 events 驻留（137MB→数GB） | 只建/读帧索引（KB 级），解压目标窗口帧（MB 级） |
| 内存驻留 | 整份会话事件对象 | 帧 LRU 缓存（热帧），其余留磁盘 |
| 冷读代价 | 每次冷读 1.8s + 全量内存尖峰 | 索引定位 <1ms + 单帧解压（~477B 输入 → ~KB 输出） |
| 多会话并发 | N 会话 × 全量 = 线性爆炸（本次 1856 OOM） | N 会话 × 帧窗口 = 与活跃窗口相关，可预测 |
| 磁盘角色 | 只是持久化终点（写完不管） | 既是持久化终点，也是**内存扩展层**（冷帧驻地） |

### 10.2 目标架构图（新增会话读路径）

```
┌─ 打开会话（当前：全量物化） ─────────────────────────┐
│  readEvent(seq, before=50, after=50)                  │
│    → SessionCorpus.load(id)                           │
│    → inspectPersisted() 整文件 zstd 解压 ← ✗ OOM 源    │
│    → events[0..N] 全量 structuredClone 驻留           │
└───────────────────────────────────────────────────────┘

┌─ 打开会话（目标：你的模型 = 帧索引 + 按需换页） ──────┐
│  readEvent(seq, before=50, after=50)                  │
│    → 查帧索引 .idx（磁盘侧或内存侧，KB 级）            │
│      帧号 = binarySearch(seq → 帧偏移表)              │
│    → 若目标帧不在 LRU 帧缓存（内存）                   │
│       → 磁盘 seek 到帧偏移 → 单帧 zstd 解压（~KB）     │
│       → 入 LRU 帧缓存（热帧驻留，冷帧逐出）            │
│    → events[seq-50 .. seq+50] 从命中帧组装             │
│   内存：帧索引 + LRU 热帧 ≈ MB 级（与会话大小无关）    │
│   磁盘：session.jsonl.zstd = 冷帧驻地 = 内存扩展层     │
└───────────────────────────────────────────────────────┘
```

### 10.3 与系统级模型的映射（论文依据）

| 你的模型概念 | 系统对应物（论文/文档） | DSH 落地点 |
|---|---|---|
| 磁盘扩内存 | OS 虚拟内存 / tiered memory（ZeroSwap/AdaSlice） | session.jsonl.zstd 作冷层 |
| 页表/定位 | mmap 页表 / zstd 帧偏移表 | **帧索引**（302,413 帧实测可定位） |
| 缺页换入 | demand paging | 单帧按需解压 |
| 热页缓存 | LRU buffer manager（DB 论文） | 帧 LRU 缓存 |
| 内存映射直读 | JSON-Mmap（NeuroJSON） | 可选：mmap 索引头/帧头 |

### 10.4 关键可行性（已在 §5.2/5.4 实测背书）

1. **格式支持**：DSH 官方 = "concatenated Zstandard frames"，帧天然独立 → 帧索引不改存储格式（config-catalog:1849 官方原文）
2. **实测**：137MB 会话 = 302,413 帧、平均 477B、边界可顺序定位（偏移 0/159/307/405/817…）
3. **readEvent 本就是窗口读取**（官方 readWindowMax=50）→ 只需把"底层全量数组"换成"按帧换页"，上层 API 不变

### 10.5 实施层级（对应治理路线 T1/T2）

| 层 | 改动 | 效果 |
|---|---|---|
| T1 配置层 | preparedSessionCacheSize 5→2（cordis.patch.yml） | 减已关闭会话缓存驻留（治标） |
| T2 帧索引层 | ① 写路径记录帧偏移 ② 读路径查索引按需解压 ③ 帧 LRU | **治本**：打开任意大会话 MB 级 |
| T2+ mmap 层 | 索引侧文件 .idx 伴生落盘（重启免重建）；可选 mmap | 冷启动免扫描 |

### 10.6 目标态内存画像（估算）

| 场景 | 现状 | 目标 |
|---|---|---|
| 打开中枢会话（137MB/54万行） | 全量解压 ~数GB + 1.8s | 索引 ~KB + 窗口帧 ~MB + <50ms |
| 同时开 10 会话 | 10 × 数GB = 必 OOM | 10 × MB = ~百MB |
| doctor 启动扫描 189 会话 | 全量解压 1.43GB → 4GB 峰值 | 只读各帧头/stat → MB 级 |
