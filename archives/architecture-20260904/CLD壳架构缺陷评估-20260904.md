# CLD 桌面壳架构缺陷评估（系统级）

> 评估：mbp-ops · 2026-09-04 · 基于 app.asar main.js 源码逐行审查 + 09-04 六次 OOM 实证
> 性质：从「壳架构设计」维度审查 CLD（Electron main），非 dsh 侧——识别壳自身放大/掩盖故障的结构性缺陷
> 方法：每个缺陷给出 main.js 行号证据 + 触发路径 + 实测影响 + 修复方向 + 严重度

## 缺陷总览（按严重度排序）

| # | 缺陷 | 严重度 | 一句话 |
|---|------|--------|--------|
| S1 | 崩溃信号系统性失真（子进程崩溃记 clean exit） | 🔴 致命 | 看门狗只看主进程 |

## S1 · 崩溃信号系统性失真（最严重）

**代码证据**：
- `child.on("exit")`（main.js ~382-397）：弹错误框 → `app.quit()`，**不检查 code/signal**
- `app.on("before-quit")`（main.js ~841）：`traceExit("quit")` → 写 `cleanExit:true`
- 触发链：dsh OOM(SIGABRT) → child exit → app.quit() → before-quit → **cleanExit:true**

**实测影响**（09-04 16:32 PID 1856 OOM）：
- crash-reason.log 记录 1852/1856 为 "clean exit"——与实际 SIGABRT 矛盾
- 看门狗（外部重启/告警）以为一切正常 → **灾难信号丢失**
- 人工排查被误导（先排除"正常退出"才怀疑 OOM）

**架构根因**：CLD 把「子进程生命周期」与「自身生命周期」耦合——子进程退出直接驱动主进程退出，而退出标记只反映主进程视角。**违背 DSH postmortem/0004 纪律**："进程归因需 exit code + 精确 stderr 行合取"。

**修复方向**（最小）：
```js
child.on("exit", (code, signal) => {
  if (quitting) return;
  const crashed = code !== 0 || signal !== null;
  if (crashed) writeCrashMarker({ code, signal, tail }); // 新增：绕过 quit 路径
  ...
});
```
让 `traceExit("crash", code, signal)` 写 `cleanExit:false + reason:"dsh-crash" + code/signal`，且 before-quit 不再覆盖。

## S2 · 无进程故障域隔离

**代码证据**：
- spawnDsh 单子进程（main.js:345），无 UtilityProcess/worker 隔离
- child.on("exit") → `app.quit()`（main.js ~392）→ **整个 CLD 退出**

**实测影响**：
- dsh 一次 OOM = GUI 全没（用户看到"崩了"）
- 与协作设施（黑板/桥，独立进程）形成反差——它们不受影响，唯独 CLD 单点

**架构对比**（Electron 官方推荐）：utility-process.md 强调"子进程崩溃不影响主进程"的故障域隔离；CLD 未用。dsh 内部倒是用了 worker（subagent/workflow），但**壳层到 dsh 之间没有隔离层**。

**修复方向**：
- 壳持有 dsh 崩溃 → 不退出，弹重试/自动重启（见 S4）
- 远期：高内存组件（会话加载/doctor）移 worker，主进程瘦身

## S3 · 启动即峰值（spawn dsh + doctor 并发）

**代码证据**：
- `start()`（main.js ~780）：`spawnDsh(runtime)` 后**立即** `runDoctor({fix:true})`
- runDoctor 全量扫描 189 会话（每次启动解压 1.43GB → 4GB 峰值）
- 两者并发 → **dsh 启动加载 + doctor 全量扫描同时吃内存**

**实测影响**：
- 正是 53030/61327/1481 启动后 3-13 分钟 OOM 的放大器
- dsh 本身要跑 doctor 之外的插件树加载，内存竞争

**修复方向**：
- doctor 改为**读帧头/stat**（元数据预算，官方 coldBlankProbe 思路）
- 或 doctor 延迟到 dsh 稳定后、且低峰执行
- 或 doctor 与 dsh 启动错峰（串行化）

## S4 · 崩溃无自动恢复

**代码证据**：
- child.on("exit") → dialog → app.quit()（无 spawn 重试逻辑）
- 无 restart 计数/退避/看门狗自动拉起（对照：collab 层有 com.dsh.cld-auto-relaunch launchd，但那是壳级）

**实测影响**：
- 每次 OOM 后 CLD 停摆，靠用户手动/我们远程 open 拉起
- 06:45→09:26→…多次 OOM 间服务不可用

**修复方向**：
- 壳内加 child 重启策略：崩溃 → 等 3s → 自动 respawn（计数 + 退避，>N 次才弹人工）
- 与 S1 结合：写 crash marker 后自动重启，而非 quit

## S5 · 无 crashReporter / 内存趋势（观测盲区）

**代码证据**：
- main.js 全文件无 `crashReporter.start`、无 `getHeapStatistics` 周期采样、无 `child-process-gone` 监听
- 崩溃证据全靠 macOS 系统 DiagnosticReports（.ips）+ 侥幸的 GC 尾部日志

**实测影响**：
- OOM 前只有 last few GCs（2 条），**无内存增长曲线** → 无法区分泄漏 vs 突发
- 无 crash dump → Electron 崩溃（非 JS OOM）无现场

**修复方向**（Electron 官方 API 现成）：
- `crashReporter.start({uploadToServer:false})` 在 ready 前（main.js start 最早处）
- `setInterval` 采样 `process.getHeapStatistics().usedHeapSize/heapSizeLimit` 落盘（复用 heartbeat 机制）
- `child.on("exit")` + `app.on("child-process-gone")` 按 reason 分诊（oom/crashed/killed）

## S6 · 日志单文件无轮转

**代码证据**：
- `openLogStream()` → `appendFileSync(dsh-web.log)`（main.js ~56-82）
- 无大小/日期轮转、无保留策略

**实测影响**：
- dsh-web.log 163 次 boot 挤一文件（321KB 尚可，长期必膨胀）
- crash-reason.log / heartbeat 混排，boot 边界靠 `===== CLD boot` 分隔

**修复方向**：
- 简单：启动时按日期/大小 rotate（`dsh-web-YYYYMMDD.log` 或超 5MB 轮转）
- 保留最近 N 份，旧 crash 证据不丢失

---

## S7 · 退出路径无分级

**代码证据**：
- `traceExit(reason, code, signal)`（main.js ~153）但调用方只有 "quit"/"process-exit" 两种
- child 崩溃走 app.quit() → 也记 "quit"

**实测影响**：
- 归因信息（crash vs kill vs quit）在 marker 里不可分
- crash-reason.log 需要外部对照 .ips 才知真相

**修复方向**：traceExit 增加 reason 枚举：`quit | process-exit | dsh-crash | dsh-killed`，marker 完整记录。

---

## S8 · env 全量透传子进程

**代码证据**：
- `env: { ...process.env, ELECTRON_RUN_AS_NODE: "1" }`（main.js:345 及 doctor spawn）
- 主进程所有环境变量（含 launchctl setenv 的 NODE_OPTIONS）透传

**实测影响**：
- 我们 setenv 的 NODE_OPTIONS 确实传给了 dsh（ps 可见）——但被 Electron packaged 白名单拦截（另论）
- 风险：无关环境变量影响 dsh 行为（漂移难排查）

**修复方向**：显式白名单 env 子集（HOME/PATH/必需项），而非全量透传——但这会改变当前 NODE_OPTIONS 可传状态，需权衡。
