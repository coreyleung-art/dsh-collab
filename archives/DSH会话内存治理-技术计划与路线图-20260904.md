# DSH 会话内存治理 · 完整技术计划与路线图

> 编制：mbp-ops · 2026-09-04 · 版本 v1.0
> 问题域：Mac mini CLD 反复 OOM（SIGABRT），根因 = 打开/扫描会话时解压后事件全量驻留内存
> 技术方向：用户提议「用硬盘扩展临时内存通道」→ 泛化为「会话历史可分页化/按需解压」

---

## 〇、执行摘要

| 项 | 内容 |
|---|---|
| 目标 | 让任意大小会话（含 54 万行/137MB 压缩的中枢会话）打开时不触发 OOM，内存占用从 GB 级降到 MB 级 |
| 核心思路 | 会话历史从「原子对象（全量解压驻留）」→「可分页资源（帧索引 + 按需解压 + LRU 页缓存）」 |
| 总工期 | 三阶段：T0 行为治理（立即）→ T1 配置治理（1-2 天）→ T2 机制改造（2-4 周评估+实施） |
| 关键可行性证据 | 中枢会话文件 = 302,413 个独立 zstd 帧（平均 477B/帧），帧边界可顺序定位 → 帧索引方案不依赖格式变更 |

## 一、问题定义与量化基线

### 1.1 症状
- CLD 反复 `FATAL ERROR: JavaScript heap out of memory`（2026-09-04 单日 6 次 SIGABRT）
- 崩溃栈统一指向 `AfterMkdirp` / GC last-resort（堆打满）
- 8.4GB 堆扩容后缓解，但**打开多会话场景仍可触顶**（估算见下）

### 1.2 根因链（已代码级确认）
```
打开会话 → SessionCorpus.load()
  ├─ live 会话 → 快照内存 events（不碰磁盘）
  └─ 持久化会话 → inspectPersisted() 整文件 zstd 解压
       → events.map(structuredClone)  ← 全量事件数组驻留
readEvent 的 before/after 窗口只控制"返回多少条"，底层 events 数组是全量的
```

### 1.3 量化基线（Mac mini 实测）
| 指标 | 数值 |
|---|---|
| 会话总数 | 189 个（共 585MB 压缩） |
| 全量解压原始文本 | 1.43 GB |
| JSON 对象化内存（3-5× 放大） | **4.3 ~ 7.2 GB** |
| 最大会话 fa1f9150 | 137.6MB 压缩 / 54.7 万行 / 1.82s 全量解压 |
| 其 zstd 帧数 | **302,413 帧**（平均 477B/帧，每帧=一个 append 批次） |
| 帧边界定位 | magic `0xFD2FB528` 顺序扫描可行（实测偏移 0/159/307/405/817…） |
| 当前堆上限 | 默认 4GB → 已临时扩至 8.4GB（NODE_OPTIONS） |

## 二、方案设计（三层递进）

### 方案 A · 行为治理（零改造 / 立即可用）
**策略**：同时保持打开的会话 ≤ 5 个（匹配 DSH 原生 LRU 容量设计）
**产出物**：
1. 会话打开纪律说明（写进 Mac mini 运维 SOP）
2. 会话体积体检脚本 `session-size-audit.sh`：列出 Top-N 大会话供决策
**效果**：内存驻留可压到 1-2GB；**局限**：靠人工纪律，非机制保障

### 方案 B · 配置治理（原生支持 / cordis.patch.yml）
**改动**（profile web 层）：
```yaml
- id: session-persistence-jsonl
  config:
    preparedSessionCacheSize: 2      # 默认 5 → 2：已关闭会话的 LRU 缓存更少
    compression: zstd                 # 显式保留
- id: session-query-sqlite
  config:
    readWindowMax: 50                 # 保持：事件读取窗口上限
    defaultLimit: 20
```
**验证**：`dsh --profile web --dump-config` + boot 冒烟 + 内存采样
**效果**：减少"已关闭会话"的缓存驻留；**局限**：**打开的会话仍全量驻留**（机制层未变），治标

### 方案 C · 机制改造（治本 / 核心计划）
**目标**：会话历史可分页化——打开大会话只解压目标窗口帧

#### C1 · zstd 帧偏移索引（推荐首做，改动最小）
**原理**：DSH zstd 容器天然多帧（每 append 批次一帧）。新增**帧索引**：`帧号 → (字节偏移, 字节长度, 首事件 seq, 尾事件 seq)`。
- **写路径**：append 批次写盘时顺带记录帧偏移（增量，O(1) 内存）
- **读路径**：`readEvent(seq, before, after)` 查索引 → 只解压 `seq-before..seq+after` 覆盖的帧 → 丢弃其余帧
- **冷启动**：无索引时先全文件扫 magic 建索引（302,413 次 find，预计 <500ms，一次性）

**关键设计决策**：
| 决策点 | 选项 | 选择 | 理由 |
|---|---|---|---|
| 索引存储 | 内存 vs 磁盘侧文件 | 磁盘伴生文件 `.zstd.idx`（或 sqlite 表） | 重启不重建，免冷扫 |
| 帧粒度 | 现有帧 vs 重新分帧 | 沿用现有帧 | 零格式变更 |
| 解压缓存 | 无 / LRU N 帧 | LRU 64 帧（≈30KB 输入） | 翻页时相邻帧命中 |
| 兼容 | 旧文件无索引 | 惰性构建 + 缓存到侧文件 | 无缝升级 |

**改动面**（评估）：
- `dsh-session-persistence-jsonl`：写路径记录帧表 + 读路径按需解压（核心 ~200-400 行）
- `dsh-session-query`：`SessionCorpus.load` 保持接口，底层换分页读（~100 行）
- **风险**：persistence 是 DSH 核心写入路径——需充分回归（append/repair/doctor/快照）

**预期收益**：
- 打开 137MB 中枢会话：全量 1.82s + 数 GB → 按需 <50ms + MB 级
- doctor 启动扫描：只需读各帧头部而非整包解压
- 彻底解除"同时打开会话数"的内存约束

#### C2 · SQLite 事件落库（备选 / 与已有基建对齐）
DSH 已有 `session-query-sqlite`（search 用）。扩展为事件权威存储：写入同步灌库，读取走 SQLite 分页。
- 优点：查询/窗口天然分页，绕开 zstd 容器
- 缺点：写入双写成本、存储翻倍、改造面大于 C1；**作为 C1 不可行的备胎**

#### C3 · OS 层 swap 调优（仅兜底，不建议主动依赖）
macOS swap 已被动撑到 19GB；调大 swap 上限会伤 SSD 且掩耳盗铃。仅记录不实施。

## 四、风险与回滚

| 风险 | 等级 | 缓解 |
|---|---|---|
| persistence 改造破坏写入 | 高 | T2 纯原型隔离；T3 灰度 + 全量回归 + 侧文件可删 |
| 帧索引与旧文件不兼容 | 中 | 惰性构建 + 无索引时回落全量读 |
| 按需解压引入延迟抖动 | 低 | LRU 帧缓存 + 预取相邻帧 |
| auto-index 类外部进程再吃内存 | 高 | 维持定时器卸载（已做）+ 恢复前改流式 |
| 8.4GB 堆掩盖问题（推迟暴露） | 中 | 监控 RSS 趋势而非只看崩溃 |

**回滚**：
- T1：删除 patch 条目即还原（已备份）
- T3：删除帧索引侧文件 → 自动回落旧全量路径（写路径先行、读路径可后切）
