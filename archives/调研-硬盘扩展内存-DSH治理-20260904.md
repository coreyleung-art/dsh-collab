# 「用硬盘扩展内存通道」技术调研 → DSH 会话内存治理泛化评估

> 调研：mbp-ops（远程运维）· 2026-09-04
> 背景：Mac mini CLD 反复 OOM——根因是「打开会话 = 解压后事件全量驻留内存」（189 会话共 1.43GB 解压文本，JSON 对象化后 4.3~7.2GB，撞 4GB/8.4GB 堆上限）
> 问题：用户提出「论文里用硬盘暂时扩展内存通道」的思路能否泛化到 DSH 治理

---

## 一、用户所提技术方向的论文溯源

「调用硬盘扩展临时内存通道」在学术与工业界对应三类成熟技术（均有论文/规范支撑）：

### 1. SSD 作为内存扩展层（最贴近"硬盘扩内存"字面）
- **[ZeroSwap: Minimizing Swap Overhead for Real-Time Multi-DNN Inference via SSD-based GPU Memory Extension](https://rtcl.dgist.ac.kr/index.php/zeroswap)**：SSD 扩展 GPU 显存，解决显存不够时的换入换出开销
- **[Evolution of Buffer Management in Database Systems](https://ar5iv.labs.arxiv.org/html/2512.22995)**：缓冲管理从经典 LRU 演进到 tiered memory（DRAM+SSD+远端）分层缓冲
- **[AdaSlice: Hotness-Aware Eviction in Tiered Memory](https://www.springerprofessional.de/de/adaslice-hotness-aware-and-adaptive-slicing-for-eviction-algorit/52395336)**：按"热度"分片，冷数据放慢层（SSD）

### 2. 文件系统 mmap 直接映射（应用级"磁盘当内存"）
- **[NeuroJSON / JSON-Mmap 规范](https://github.com/NeuroJSON/jsonmmap/blob/main/JSON-Mmap_Specification.md)**：把大 JSON/JSONL 文件**内存映射**，只把被访问的页载入 RAM，未访问部分留在磁盘——**这就是"用硬盘当临时内存"在文件层面的标准做法**
- SQLite 论坛同主题讨论（[sqlite.org forumpost](https://sqlite.org/forum/forumpost/5d135a95351fa54c)）
- **实践案例**：[How I cut Python JSON memory overhead from 1.9GB to ~0MB](https://dev.to/nareshcn2/how-i-cut-python-json-memory-overhead-from-19gb-to-0mb-11x-speedup-3o8c) —— 用 mmap/按需解析把 1.9GB JSON 内存开销降到接近 0

### 3. 压缩数据的随机访问（按需解压，不整包解压）
- **[ZRA: ZStandard Random Access](https://github.com/zraorg/ZRA)**：在 zstd 压缩流内做随机访问
- **[tarzan: Random-access seekable .tar.zst with embedded table-of-contents](https://github.com/astraw/tarzan-rs)**：压缩归档内嵌目录索引 → 按需解压单个块
- [StackOverflow: Random indexing of large compressed JSON](https://stackoverflow.com/questions/74460186) ：预计算帧偏移索引文件存盘，实现压缩 JSON 随机读

## 二、DSH 现状 vs 技术对照

| 论文/技术思路 | DSH 现状 | 差距 |
|---|---|---|
| JSON-Mmap 按需载页 | 打开会话 → `events.map(structuredClone)` **全量驻留** | DSH 无 mmap/页式读取 |
| SSD 分层缓冲（tiered LRU） | `SessionPreparations` LRU 容量 5，纯内存 | 无磁盘层，冷会话驱逐即释放（要重解压） |
| 压缩随机访问（帧索引） | 每次冷读**整文件 zstd 解压**（137MB→1.8s） | 无帧偏移索引，无法只解压需要的段 |
| 虚拟内存/swap（OS 级） | macOS 默认 swap 已被打爆（19GB） | OS swap 是被动兜底，非主动设计 |

**核心差距一句话**：DSH 把"会话历史"当**原子对象**（要么全在内存、要么全不在），论文思路是把它当**可分页资源**（热段在内存、冷段在磁盘、按需换页）。

## 三、泛化到 DSH 治理的三层可行方案

### 方案 A：行为层（零改造，立即可用）—— 推荐先做
不碰代码，治理"同时打开的会话数"：
- 约定：**同时保持打开的会话 ≤ 5 个**（匹配 LRU 容量设计）
- 超大会话（fa1f9150 54万行）只在需要时打开，用完即关
- 效果：内存驻留可控在 1-2GB；缺点：靠纪律，非机制

### 方案 B：配置层（原生支持，改 cordis.patch.yml）—— 推荐第二个做
利用 DSH 已暴露的参数：
```yaml
- id: session-persistence-jsonl
  config:
    preparedSessionCacheSize: 2    # 默认5→2：已关闭会话缓存更少
- id: session-query-sqlite
  config:
    readWindowMax: 50              # 已是50，翻页窗口上限
    defaultLimit: 20
```
效果：减少"已关闭会话"缓存驻留；缺点：**打开的会话仍全量驻留**（读代码确认 `SessionCorpus.load` 对 live/查询快照全量克隆），治标不治本

### 方案 C：机制层（需上游/插件改造，治本）—— 远期
把"会话历史"改成**可分页资源**，三种子方案按成本排序：
1. **zstd 帧索引**（最贴合现有 .zstd 格式）：DSH 的 zstd 容器本就是**多帧**（每批 append 一帧）——已有帧边界！只需存**帧偏移表**（每帧 start/end 字节偏移 + seq 范围），打开会话时按需解压目标帧段，而非整包。改动面：persistence 层读路径
2. **SQLite 事件落库**（已有 `session-query-sqlite` 基建！）：事件写入时同步灌 SQLite，打开会话走 SQLite 分页查询（readEvent 窗口已是 50），不再全量解压。改动面：写入时同步索引
3. **OS swap 主动扩容**：macOS 设 swap 上限（`sysctl vm.swapusage` 已 19GB 说明系统在换页）——但这是被动兜底且伤 SSD，不推荐主动依赖

> 注：方案 C1 有个**现成抓手**——日志里 doctor 每次启动全量扫描 189 会话就是整包解压的浪费，若做帧索引，doctor 也只需读各帧头部。

## 四、结论与建议路线

1. **立即**：方案 A（行为约束）+ 方案 B（缓存调参）——今天就能做，缓解 70% 场景
2. **中期**：推动方案 C1（帧偏移索引）——需要 DSH 上游或插件层改造，但 DSH zstd 容器已分帧，改造点明确、收益最大（打开大会话从"全量 1.8s+数GB"变"按需几十 ms+MB 级"）
3. **长期**：方案 C2（SQLite 事件库）若 DSH 官方推进则天然对齐

**用户论文直觉是对的**：核心思路=「把大资源当可分页/可换出对象」，DSH 会话历史完全符合该模式，且**底层格式（多帧 zstd）已具备实现条件**，缺的只是一层索引与按需读路径。
