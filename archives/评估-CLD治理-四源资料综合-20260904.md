## 一、CLD 问题的重新定位（资料对照后）

### 1.1 三个已确证的硬事实
1. **Electron packaged app 拒绝 NODE_OPTIONS 传堆参数** —— 官方 environment-variables.md 明示白名单仅 `--max-http-header-size`/`--http-parser` → 我们此前的 8GB 堆注入从未生效（GC 上限恒 4001MB 佐证）
2. **正确通道是启动 argv `--js-flags` 或子进程 execArgv** —— 官方 command-line-switches.md（`--js-flags` 须启动时传入 main）
3. **CLD 的 dsh 是 ELECTRON_RUN_AS_NODE 子进程** —— 该模式=真 Node，`execArgv` 可行（E.2 结论）

### 1.2 核心矛盾（论文视角）
DSH 官方客户端设计（web-client.md:40-46）= **惰性 Session + 单连续事件窗口 + 物理代替换 + page 补缺口**——**CLD 的"打开会话=全量事件驻留"违背官方客户端意图**。三篇 harness 论文（empire-convergence）确认行业共识 = append-only 可回放会话记录 + **上下文渐进披露**，CLD 全量物化是反模式。

## 二、五条治理建议（综合 4 源，按优先级）

### 建议 1 ★★★★★：会话历史"按位置随机访问"（帧索引，即原 T2 方案）
- **证据**：DSH 官方 = "checksummed **concatenated** Zstandard frames"（config-catalog 1849-1854）→ 多帧是官方格式；Log-is-Agent 主张日志按索引 k 定位任意前缀 L₁:ₖ；web-client 官方=惰性+窗口
- **落地**：帧偏移索引（302,413 帧实测可定位）→ 打开会话只解压目标窗口帧
- **结论强化**：原 T2 方案从"自研 hack"升级为"符合官方架构意图 + 论文共识"的正路

### 建议 2 ★★★★★：崩溃可观测性接入 Electron 官方通道
- **证据**：crash-reporter.md（ready 前 start/uploadToServer:false/本地留档/extra 键限 39B/127B）；child-process-gone reason 分诊（oom/memory-eviction）；getHeapStatistics（usedHeapSize/heapSizeLimit **预警**）
- **落地**：CLD main.js 启动第一行接入 crashReporter + 内存三件套周期落盘 → **修复"崩溃信号失真"缺口① + 消灭"无内存趋势"缺口③**
- **对应**：正是我们评估的日志优化缺口，官方有现成 API

### 建议 3 ★★★★：日志/进程归因遵循官方 postmortem 纪律
- **证据**：DSH postmortem/0004 = "进程归因需 exit code + 精确 stderr 行**合取**，共享前缀不是协议"——CLD 看门狗把子进程 OOM 记成 clean exit 正是违反此纪律
- **落地**：看门狗补子进程 exit code 检测（缺口①的机制解法）+ 结构化归因

### 建议 4 ★★★★：跨会话记忆"选择性持久化"（SSPM 启示）
- **证据**：SSPM 实证"全量历史完成率最低 71% vs 选择性 96%"——全存既费内存又伤质量；trace anchoring 危害
- **落地**：CLD 会话列表/上下文注入不整段回灌，按 SSPM 四类（task/data-schema/tools/output）压缩；配合 compaction（官方已有 thresholdRatio 0.8/retainRatio 0.16）

### 建议 5 ★★★：快照级事务边界（MemTxn 启示，中期）
- **证据**：MemTxn = ARIES 谱系：写前持久化 recovery intent → 崩溃整表回滚 O(活动 key 数)
- **落地**：DSH 会话写入跨 checkpoint 时持久化 recovery intent；崩溃后校验回滚（官方持久化层已有 interrupted closers 读方修复，可补快照层）

## 三、Swift 侧评估（用户点名）

Swift 资料（TSPL）对 CLD 治理的启示——**CLD 生态中的 Swift 组件**（CLDVoiceIME、菜单栏工具）与 dsh 主进程是不同语言栈，但 Swift 的内存纪律有参照价值：

| Swift 概念 | 对 CLD 治理的映射 |
|---|---|
| ARC（AutomaticReferenceCounting） | CLD 侧对应 V8 GC——Swift 的"引用生命周期显式化"提醒：DSH 的 LRU/会话引用应**显式断开**（close 即释放），而非依赖 GC 兜底 |
| MemorySafety（独占访问/越界编译期拦截） | 提醒：会话事件的"写者独占"（SessionHandle 单写者）是官方已内建的内存安全边界——治理时应利用而非绕过 |
| Deinitialization（确定性释放时机） | CLD 会话关闭应走确定性 disposer（DSH 官方 defensive-patterns "Dispose must reach quiescence"）而非等待 GC |
| Concurrency（结构化并发/任务取消） | 长会话加载应支持取消（AbortSignal 已在 DSH 读路径） |

**结论**：Swift 侧主要提供**工程纪律参照**（显式释放/确定性生命周期），直接可执行项不多——CLD 是 Electron/Node 栈，治理主战场在 Electron 通道与 DSH 架构意图。

## 三-bis、CLD 壳架构缺陷评估（独立文档摘要）

> 详见 `architecture/CLD壳架构缺陷评估-20260904.md`（8 缺陷，逐条行号证据）

**壳层 8 缺陷 vs 前文建议的关联**：
- S1 崩溃信号失真 + S7 退出无分级 → **建议 2/3** 的落点（crashReporter + 归因合取）
- S2 无故障域隔离 + S4 无自动恢复 → **建议 5**（UtilityProcess 隔离 + 崩溃重启）
- S3 启动即峰值 → **建议 1**（帧索引使 doctor 变轻）的附带收益
- S5 无内存趋势 → **建议 2**（getHeapStatistics 采样）
- S6 日志无轮转 → 可观测性基础
- S8 env 透传 → NODE_OPTIONS 无效的又一佐证（传了但被白名单拦）

**结论**：壳层缺陷与 dsh 侧内存问题是**双层叠加**——dsh 会 OOM（内存治理），壳把 OOM 藏成 clean exit 且不恢复（壳缺陷），观测不到趋势（可观测性缺失）。三者需**同批治理**，缺一不可。

## 五、结论

1. **资料拉取证实并升级了治理方案**：CLD 的 OOM/日志问题不是"本地特例"，而是**违背了 DSH 官方客户端架构意图 + Agent harness 行业共识**（append-only + 惰性物化 + 渐进披露）
2. **三条立即可行**（官方 API/文档背书）：Electron crashReporter 接入、内存三件套采样、看门狗补子进程检测
3. **一条中期正路**：帧索引（T2 升级版）——从格式（官方多帧）到意图（随机访问）全部有据
4. **两条认知修正**：NODE_OPTIONS 扩容永远无效（官方白名单）；"全量历史"既是内存负担也是质量负担（SSPM 71% 反证）

**建议下一步**：按建议 2（Electron 可观测性接入）优先实施——官方 API 现成、直接修复灾难信号失真、半天可落地。
