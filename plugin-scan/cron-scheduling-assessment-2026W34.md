# cron 集中调度：现成方案 vs 自研评估

> 背景：C2（cron #28 集中定时调度落地，约 0.5 天）已批准，按调研优先制度先完成「现成调度能力」评估闭环，确认无现成可满足再实施自研。
> 三要素判定口径（本次评估核心）：
> 1. **掉线补跑**：宿主/GUI 关闭、断网、错过触发时，任务是否仍能被补执行或至少可检知；
> 2. **跨会话**：任务定义与状态是否不依赖某个浏览器标签页/某次会话存活；
> 3. **持久化**：任务清单/执行历史/日志是否落盘（重启不丢、可审计）。

## 1. 候选方案清单（本机实证）

| 方案 | 形态 | 现成性 | 三要素现状 |
|---|---|---|---|
| A. dsh-task-board | Web GUI 插件，localStorage 5 段 cron，可驱动 agent 会话 | ✅ 已装 | 掉线补跑 ✗（标签页关闭即错过）；跨会话 ✗（localStorage 单浏览器）；持久化 △（localStorage 可留存但不可审计） |
| B. launchd 用户定时 | macOS 系统级定时（LaunchAgent） | ✅ 已装（本机已有 journal 等定时项） | 掉线补跑 △（错过后不自动补，但服务常驻可靠）；跨会话 ✅；持久化 ✅（plist + 系统日志） |
| C. bus-bridge | launchd 常驻守护 + bus 队列（~/.dsh/bus-bridge、bus-queue） | ✅ 已装 | 掉线补跑 △（队列可暂存消息，超时任务可 failed）；跨会话 ✅（守护进程）；持久化 ✅（队列/日志落盘） |
| D. chicheng-cron（候选插件） | 服务端常驻 cron（待验证） | ⏳ 未装，需验证三点 | 未知：需确认「服务端常驻 / 不依赖 GUI / 掉线补跑」 |
| E. 自研集中调度器 | 原生 setInterval / 自建调度服务 | 自研（最后手段） | 可做到全满足，但需 0.5-1 天开发 + 维护成本，且与 B/C 重叠 |

## 2. 需求画像（建议先确认）

集中调度要解决的真实诉求（决定选型）：
- 任务类型：定时调研/报告、定时运营动作、心跳/巡检、内容发布排期？
- 运行要求：必须「浏览器关闭也跑」吗？是否可接受「依赖 launchd 常驻底座」？
- 审计要求：任务执行历史是否需要集中查看（决定是否需要持久化清单/日志中心）？

## 3. 结论与推荐路径

1. **优先组合现成（推荐，无需自研集中调度器）**：
   - 定时/周期任务 → **launchd（B）或 bus-bridge（C）为常驻底座**，任务定义持久化为 plist/JSON + 日志；
   - GUI 编排/手动触发 → dsh-task-board（A）保留，但**不作为唯一调度源**；
   - 关键任务（运营/发布/告警）→ 用 B/C 承载 + 执行后回写状态文件，实现「跨会话 + 可审计」；
   - 掉线补跑：对重要任务由 C 的队列/幂等机制补偿（超时 failed + 重试窗口），无法满足时按任务重要性评估。
2. **chicheng-cron（D）**：若其具备「服务端常驻 + 免 GUI + 掉线补跑」则等价于 B+C 组合，可作为候选替换；由供应链按三点验证后决策（验证成本 < 自研）。
3. **自研（E）仅当**：B/C/D 均不满足「掉线补跑 + 跨会话 + 持久化」组合诉求时立项；届时按论文筑基出方案论证（调度器属成熟工程，参考 SOA/任务队列既有模式，无需新论文，但需书面「现成方案为何不满足」交 HR 把关）。

## 4. 落地建议（给 0e84e65c）

- 第一步（今天可做）：把现有 launchd 定时项 + bus-bridge 能力盘点成「任务登记表」（任务名/触发/当前承载/补跑需求）；
- 第二步：对照本评估，标出「必须集中调度」的任务子集（预计 <20%）；
- 第三步：对子集选 B 或 C 承载（建议 C 因已有队列/幂等/审计），dsh-task-board 降级为辅助编排；
- 若第三步发现缺口 → 再评估 D，最后才 E。
- 预计落地 0.5 天内完成第一步+第二步，第三步视子集大小。

## 5. 待确认项

- 用户/运营侧是否要求「浏览器完全关闭也能跑全部定时」（决定 A 是否淘汰为主源）；
- 是否有任务需要秒级精度（launchd 最小粒度受限，需 minute 以上？）；
- 掉线补跑的最长可接受窗口（决定 C 队列 TTL/重试参数）。
