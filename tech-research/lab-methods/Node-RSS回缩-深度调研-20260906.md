# Node/Electron RSS 不回缩 · 深度调研报告（2026-09-06）

> mbp-ops · 缘起：mac-mini dsh RSS 3.6GB 高位驻留（不 OOM 但不健康）
> 目的：调研业界对"Node/Electron 长驻进程 RSS 不归还 OS"的解决方案，定我们的落地方向

---

## 一、问题确认（本机实测）

- dsh 进程 RSS 稳定 3.6GB（非泄漏性缓涨，是驻留高位）
- 系统 swap=0、inactive 8GB 空闲 → 无真实内存压力
- V8 完整 GC 后 RSS 可从峰值大幅回缩（本地实测 1239→46MB）
- memory-trend 只监控壳(162MB)，**对 dsh 子进程是盲区**

## 二、业界共识（调研来源）

### 1. V8/Node 设计使然（非 bug）
> V2EX 共识：**"V8 不愿意把内存释放给 OS，倾向于自己管理"**——这是正常行为。
> V8 维护已分配堆，峰值后 RSS 不主动归还；heap 内部有上限管理。

### 2. Electron 特有：shared V8 cage（关键机制）
> [dyad electron-workers 规则（源自大型 app 内存崩溃调查）](https://github.com/dyad-sh/dyad/pull/3868)：
> - **Electron 的 pointer-compression cage 让所有进程共享 ~4GB heap**
> - worker OOM 会 SIGABRT 杀掉整个 app
> - 官方文档未明说进程级范围——是实测发现
>
> **与我们场景直接相关**：dsh 3.6GB 逼近共享 cage 上限（4GB），
> 之前设的 `--max-old-space-size=8192` 可能未真正作用于 cage（cage 硬上限 ~4GB）。

### 3. 主动 GC 是可行手段（本地已验证）
> - `--expose-gc` 暴露 `global.gc()`；Electron 下实测**放行**（非白名单拦截项）
> - 完整 GC 耗时 39ms（1GB 驻留下），周期调用无感知
> - `NODE_OPTIONS=--require <gc-timer.js>` 注入定时 GC **实测成功**

### 4. 其它方案（业界提及）
> - **jemalloc**：V2EX 有人提，但"好像没什么用"（Node 内部堆不由 jemalloc 管）
> - **--max-old-space-size 调低**：约束堆上限但不促归还
> - 进程重启：最彻底但业务中断
> - [Cribl Node 22 内存分析](https://cribl.io/blog/understanding-node-js-22-memory-behavior-and-our-upstream-contribution/)：Node 22 的 RSS 行为与 20 有差异（与我们观察的版本相关）

## 三、方案评估（结合调研）

| 方案 | 机制 | 可行性 | 风险 |
|---|---|---|---|
| **A. 定时完整 GC**（--expose-gc + require gc-timer）| V8 主动回收→RSS 回缩 | ✅ 本地全验证 | GC 39ms 无感知 |
| B. jemalloc | 外部分配器 | ❌ 业界反馈无效 | — |
| C. 调低 max-old-space | 约束堆 | ⚠️ 不促归还 | 可能过早 OOM |
| D. 定期重启 dsh | 进程重建 | ⚠️ 彻底但中断 | 业务抖动 |

**结论**：方案 A（定时 GC）是业界共识 + 本地验证的最优解。
但**需先确认 cage 上限问题**——若 dsh 真受 4GB cage 限制，8.4GB 堆设置是无效的，
那 3.6GB 已很接近硬顶，定时 GC 只能缓解不能根除（除非换 Node 启动方式绕 cage）。

## 四、下一步（待决策）

1. **确认 cage 假设**：查 dsh 实际 heap_limit（v8.getHeapStatistics 经 dsh API 或 doctor）
2. 若 cage 4GB 属实 → 方案 A 定时 GC 作为**缓解**（RSS 3.6→~1GB）
3. 根治需评估：Electron 启动 Node 的方式能否禁用 cage（`--no-pointer-compression`? 需查 Node 版本支持）

## 六、cage 假设最终确认（2026-09-06 实测铁证）

### 实测数据（CLD 二进制 ELECTRON_RUN_AS_NODE 直测）
| 场景 | heap_size_limit |
|---|---|
| 默认 | **4192MB** |
| --max-old-space-size=8192 | **4192MB**（无效）|
| --max-old-space-size=4096 | **4192MB**（无效）|
| 参数直传 | **4192MB**（无效）|

### 业界佐证
- **vscode #127105**: typescript.tsserver.maxTsServerMemory=8192 但 heap_limit 恒 4GB（同 bug 类，官方确认）
- **electron #35032**: pointer compression 默认启用"不打算改"，超 4GB 需自编译（v8_enable_pointer_compression=false）

### 认知修正（重要）
1. **dsh 实际可用堆 = 4GB cage 硬顶**——之前 launchctl 设 8.4GB **从未生效**（Electron 忽略）
2. dsh 3.6GB = 已用 90% cage——危险但未崩
3. **OOM 修复真正功臣 = P1 自动重启 + P2-3 减驻留**（非扩容！）
4. 根除(自编译 Electron)不可行(用官方 CLD.app)

### 可行治理（4GB cage 内）
1. 定时 GC 缓解（RSS 3.6→~1GB，已本地验证可行）
2. 减驻留继续（P2-3 已做；inspect bounded 是架构约束）
3. cld-monitor 增加对 dsh RSS 的监控（现只监控壳=盲区）

## 七、GC 误判误删风险审查（2026-09-06 代码级）

### 审查问题：定时 GC 会误删会话吗？
**结论：不存在误判误删路径**（机制保证）

### 核查证据
| 机制 | 位置 | GC 触发? | 结论 |
|---|---|---|---|
| WeakRef | cordis Logger fiber 元数据(index.js:636) | 弱引用可回收 | 🟢 无(仅日志来源追溯, 与会话无关) |
| FinalizationRegistry | dsh-session / dsh-session-persistence | **0 处** | 🟢 无 GC 回调删数据路径 |
| Symbol.dispose | SessionPreparation(index.js:599) | 否(显式 using/调用方释放) | 🟢 无 |
| preparations invalidate/discard | 显式(日志变更/提交时 839行) | 否 | 🟢 无 |

### 两层误删区分
1. **内存移除**(GC 回收无引用缓存) → 磁盘数据在(zstd fsync), 重读恢复 = 安全
2. **数据删除**(需 FinalizationRegistry/终结器回调) → dsh 无此机制 = 不存在

### 为什么安全
- 会话每次 append = writeFile + handle.sync()(fsync 落盘), 不靠内存保命
- 活跃 Session 被 coordinator/sessions Map 强引用 → GC 永不回收
- GC 只回收"纯垃圾"(无引用历史对象) = 正是 3.6GB 里可安全清的部分
- 真正删除只走显式代码路径(用户删/日志变更 invalidate), 与 GC 无关

### 结论
定时 GC 无会话误删风险。唯一"可回收"的是 prepared LRU 缓存(容量2, 淘汰重读磁盘即可)
