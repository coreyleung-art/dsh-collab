## 〇、目标与方法

**目标**：在隔离环境复现历史 OOM 崩溃场景，验证内存治理（P2-1 帧索引尾部窗口）前后差异；并把此前修理中的**核心判断固化为可执行断言**反向验证。

**黑箱约束**（满足用户要求）：
1. 全程 MBP 本地运行，**零进程侵入** macmini 生产 CLD
2. 真实会话仅 `scp` 只读副本（sha1 校验一致），原始文件零写入
3. 崩溃模拟 = **受限 heap 子进程**（`--max-old-space-size`），OOM/SIGABRT 只杀实验进程自己
4. 零第三方依赖（仅 node:zlib / node:v8 / node:child_process）

**双路径模拟**：
- `full` = 现状 runtime 冷读：整文件读 → 全帧解压 → 逐行 parse → 事件对象驻留（含 structuredClone 放大）
- `tail` = P2-1 治理后：帧扫描 → 只解尾部 200 帧 → 窗口事件驻留

## 一、崩溃复现结果（核心证据）

### 场景：多会话叠加物化（6 真实会话 = 276MB，模拟 doctor/boot 同时打开多个会话）

| heap 硬顶 | full（现状） | tail（治理后） |
|---|---|---|
| **512MB** | 💥 **SIGABRT 崩溃**（15.4s 后被杀） | ✅ 存活 199ms，峰值 **33.8MB** |
| 1024MB | ✅ 存活 23.8s，峰值 768MB | ✅ 存活 156ms，峰值 33.9MB |

### 场景：单会话中枢（137.7MB / 302,559 帧 / 最大真实会话）

| heap 硬顶 | full | tail |
|---|---|---|
| 512MB | ✅ 存活，峰值 383MB | ✅ 64ms，峰值 22.5MB |
| 1024MB | ✅ 存活，峰值 383MB | ✅ 56ms，峰值 22.7MB |
| 2048MB | ✅ 存活，峰值 385MB | ✅ 56ms，峰值 21.9MB |

**反向证实**：单会话即便 137MB 中枢也不崩（峰值 385MB < 512MB 顶）→ **OOM 根因确为多会话叠加/全量物化场景**，与历史诊断一致（6 次崩溃多发生在 doctor 扫描/多会话场景）。

## 五、结论与意义

1. **崩溃可复现**：6 会话全量物化在 512MB 堆顶 SIGABRT——与历史 CLD 崩溃（JS heap OOM / SIGABRT）同信号同机制
2. **治理结构性有效**：tail 同限存活且内存降 23x、速度升 152x（与 P2-1 POC 54-250x 及 T2-2b 设计 ~500x 自洽——本实验含 parse/驻留全链，收益略低于纯解码 POC，符合预期）
3. **反向验证了修理判断**：单会话不崩 → OOM 根因是多会话叠加；断言套件可长期回归（任何未来修复可先在此跑断言）
4. **实验室即"评估台"**：后续 L1-L3 落地前可在本实验室预演（把真实 runtime 的 loadStoredFrom 逻辑接入 oom-sim 的 tail 路径），量化验证后再上生产

## 六、遗留与限制

1. **retained 统计在多文件 GC 后失真**（V8 堆统计怪癖，3 文件起 retained 报 2.9MB）——本报告以 **peakHeap + 崩溃 outcome** 为硬指标，retained 仅单/双文件可信；后续可改用 process.memoryUsage.rss 采样曲线替代
2. 模拟器的 full 路径未含 **surface 投影重放**（官方 #4416 R3/R4）——真实 runtime 的内存可能更高；但治理收益方向与量级已被证实
3. 单会话 137MB 需要 6+ 会话叠加才复现崩溃 → 建议后续把"同时打开会话数"纳入 mac-mini 运维监控（现有 SOP 已含 ≤5 纪律）
