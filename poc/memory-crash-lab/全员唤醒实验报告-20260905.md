## 二、关键发现

### 1. 内存表现（治理验证）
- 峰值 **4532MB** 逼近历史 OOM 区（4GB）但**无 OOM 崩溃**（P1 扩容 8.4GB 生效）
- 高位平台 4.4GB 持续 ~5min 稳定——大量会话驻留但**有界**
- 与黑箱实验室预测一致：多会话叠加是内存大头

### 2. ⚠️ 意外发现：resolveUrl 竞态 bug（壳崩溃，非 OOM）
exit-marker 明确记录：
```
pid 71861 DID NOT EXIT CLEANLY
reason: uncaughtException
error: TypeError: resolveUrl is not a function
  at app.asar/main.js:440 (Socket data handler)
```
**根因**：P1 的 `reloadDsh()` 把 `resolveUrl=null`（539 行）→ 重载间隙旧 stdout 缓冲仍输出 "dsh web: URL" 行 → 440 行无条件调 null → TypeError 崩壳。
**触发**：16:44 全员唤醒期（可能是重载 + 高负载竞态）。

## 三、修复（v0.6.1 · Lean 五道闸全过）

- **改动**：stdout handler 440 行加 `if (resolveUrl)` 保护（null 时仅记录 URL，重载会重新 await）
- **门禁**：P0 留证 ✅ / P1 备份(165833) ✅ / P2 受限区 ✅ / P4 沙箱打包+语法 ✅ / pre-mortem ✅ / guard-gate 全过 ✅
- **部署**：新 asar sha `20880594794c3355`（182279B）已替换 + 重签
- **登记**：v0.6.1

## 四、结论与后续

1. **治理有效**：4.5GB 峰值不 OOM（对比修复前 4GB 必崩）——P1 扩容 + P2-3 正确
2. **全员唤醒仍推高内存**：4.4GB 高位驻留 = 大量会话全量物化（架构约束，P2-4 已评估暂缓）
3. **发现 P1 引入的竞态** → 已修复（v0.6.1）——这正是"实验发现生产 bug"的价值
4. **本地网 SSH 在重负载后不稳**（Tailscale 通）——观察项，可能与系统网络栈压力有关

## 五、建议
- 重启应用 v0.6.1（等用户窗口）
- 全员唤醒场景建议分批（避免瞬时 4.5GB），或作为已知边界记录
- stability-watch 持续跟踪新进程基线（当前 301MB）
