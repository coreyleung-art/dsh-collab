# P2-1 帧索引 MVP POC · 对比测试报告

> mbp-ops · 2026-09-05 · 独立原型（零第三方依赖，仅 node:zlib 内置 zstd）
> 目录：`~/dsh-collab/poc/session-frame-poc/`（本地 MBP 运行，**绝不触碰 macmini 原始会话**）
> 代码：lib/frame-scan.js（独立 zstd 帧扫描器）、lib/synthetic.js（合成会话生成器）、bench.js（基准 runner）

## 〇、结论

**P2-1 帧索引方案在 MVP 原型上验证成立且收益巨大**：打开会话取最近一页（尾部 ~0.3-1.6% 帧），解码耗时从 **365-383ms → 2-7ms**（加速 **50-250x**），解码量降到原来的 1% 以下。真实 macmini 会话副本与官方 #4416 实测模型（24,005 帧冷读 430ms）**量级吻合**，证明本原型可作后续 runtime 落地（`loadStoredFrom` 补丁）的验收基准。

## 一、方法（隔离实验环境）

1. **零接触原始会话**：真实样本仅 `scp` 只读副本到本地 `data/`，sha1 校验一致（`385f063d…`）；测试只读副本
2. **零第三方依赖**：仅 Node 25 内置 `node:zlib`（原生 ZstdCompress/Decompress）+ 自写帧扫描器（移植官方 `scanZstdFrames` 逻辑，~80 行）
3. **两条路径对比**：
   - 路径 A（现状/runtime 冷读）= readFile 整文件 + 扫全部帧 + **解压全部帧**（官方 #4416 实测的 430ms 就是这段）
   - 路径 B（P2-1 帧索引）= readFile + 扫全部帧（仅读帧头定位边界）+ **只解压尾部 N 帧**（帧索引 sidecar 落地后的等价行为）
4. 每样本 7-9 轮取中位；输入全程只读

**模型交叉验证**：真实 14.1MB/27,608 帧冷读 365ms ≈ 官方 #4416 实测 8.84MB/24,005 帧 430ms（官方样本解码明文更大）；合成 50 万事件 ~380ms ≈ 官方外推 46 万事件 ~5.8s 中的解码/parse 段（官方含 JSON.parse+快照，本 POC 只测 IO+解压段）→ **量级吻合，模型可信**。

## 三、结论解读

1. **全量解码成本随文件线性增长**（126帧→62,501帧：1.4ms→383ms），页大小完全不约束 IO——证实官方 R1/R2 根因
2. **帧索引（尾部窗口）成本 ≈ 常数**（与总帧数几乎无关：12,501 帧与 62,501 帧都是 ~2ms）：只解需要的帧
3. **帧扫描本身很便宜**（0.2-1.5ms，仅读帧头 magic/descriptor，不解压）——`scanZstdFrames` 提供的 `{start,end}` 偏移表可直接做 `.idx` sidecar 数据源（P2-4 前置）
4. 真实 dsh 帧（带 checksum、真实内容冗余）与合成样本结论一致 → 不依赖数据特性

## 四、与官方 #4416 路线图对位

| 官方项 | 本 POC 证据 | 落地映射 |
|---|---|---|

## 六、遗留与建议

1. **POC 未含 JSON.parse/structuredClone/投影重放段**（官方 430ms 中 parse ~200ms/快照 ~148ms）；落地 `loadStoredFrom` 后这些也只需处理窗口内事件 → 增益同比放大，但建议落地后全链复测
2. 建议下一步：T2-2b 设计（写路径帧表埋点 + `.idx` sidecar 一致性方案），达标后再动 runtime（当前 CLD 生产环境刚重启稳定，不宜立刻打 persistence 补丁）
3. 与本次孤儿 tool_calls 修复共享经验：**都在读取侧做容错/优化、不碰历史数据**——本 POC 全程只读佐证该原则可行
4. bench.js 可在 macmini 本地重跑以获得该机 CPU 的绝对数字（当前为 MBP 数字，相对加速比两者一致）
