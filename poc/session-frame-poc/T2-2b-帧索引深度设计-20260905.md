## 一、背景事实（代码级锚定，2026-09-05 核实）

| 事实 | 位置/证据 |
|---|---|
| 会话日志 = header 帧 + 每 append 批一帧的 zstd 多帧文件 | jsonl lib `encodeMaterialization`/`encodeEventBatch` |
| **写端天然埋点**：`appendLines` 先 `stat` 得 `before` size，再 `writeFile(content)` → 帧字节偏移 = `before`，长度 = `content.length` | jsonl lib:1200-1217 |
| **写端已知 seq 范围**：append 的 `events` 数组事件 seq 连续（`next.seq !== prev.seq+1` 检测） | dsh-session lib:818 |
| packed chunks：storage record 带 `seq0`+payload，展开后多事件 | dsh-session lib:877,929 |
| 帧边界可不解压扫描：`scanZstdFrames` → `{frames:[{start,end}], tornStart}` | jsonl lib:503 |
| coordinator `loadStoredFrom` hook **已就绪**：backend 提供即只读后缀 | persistence lib:938-951 |
| 冷开 inspect/prepare 走 `backend.loadStored` **全量**（loadStoredFrom 不经过） | persistence lib:986-987 |
| 崩溃恢复已有：`rollbackAppend`（写失败 truncate 回 before）、`repair`（torn tail truncate） | jsonl lib:1220-1240 |

**核心设计洞察**：与官方 #4416 open question「sidecar 如何与日志事务一致」不同——本设计**不需要跨文件事务**：
写路径的 `before size` + `events seq` 在**同一同步点**可得，sidecar 条目是日志追加的**纯函数**。崩溃在「日志已写/fsync 完成但 sidecar 未写」之间时，读路径检测到 sidecar 落后于日志即可自愈重建尾部条目。

## 二、`.idx` sidecar 格式设计

### 2.1 文件与布局
- 伴生文件：`<log-path>.idx`（如 `session.jsonl.zstd.idx`），与日志同目录
- **二进制追加式**（非 JSONL——每帧一条定长/变长记录，避免重复解析）
- 结构：
```
[8B magic] "DSHIDX01"
[4B version] = 1
[8B headerEndByte]   # header 帧结束偏移（恒 = 首事件帧起点）
[8B logSizeSnapshot] # 写满时日志字节数（崩溃检测用，见 §4）
--- 每帧一条记录（append 时追加） ---
[8B startByte][8B endByte][4B firstEventSeq][4B lastEventSeq]   # 定长 24B/条
[4B trailingCRC]  # 覆盖本记录，防半写（可选第 2 版）
```
- 记录定长 → 尾部截断检测：`sidecarSize % 24 != 0` 即 torn → 丢弃末条

### 2.2 为什么存 firstSeq/lastSeq 而非行号
- packed chunk 一条 storage record 展开为多个事件（`seq0..seq0+n`），行号无法定位事件
- 写端 `events` 数组是**展开后**事件 → 直接取 `events[0].seq` 与 `events.at(-1).seq`（O(1)）
- 事件 seq 全局连续单调 → sidecar 记录天然有序，可二分

## 三、写路径埋点（增量、O(1)、无额外 IO 放大）

### 3.1 埋点位置：`appendLines` 成功后（现有代码 hook）
```
appendLines(meta, events) {
  content = encodeEventBatch(events)        // 1 帧
  before = stat(path).size                  // 已存在
  writeFile(content); sync()
  // ===== 新增埋点（同一 async 函数内、sync 之后）=====
  index.appendRecord({
    startByte: before,
    endByte: before + content.length,
    firstEventSeq: events[0].seq,
    lastEventSeq: events.at(-1).seq,
  })
}
```
- `index` = 内存中当前会话的 sidecar 写入器（见 3.3）
- **materialization（首写）**：`encodeMaterialization` 返回 `concat(headerFrame, eventFrame)` → header 帧 `[0, headerFrame.length]` 不建条目，首事件帧 `[headerFrame.length, total]` 建首条
- **repair/rollback**：truncate 日志后 sidecar 同步 truncate 到对应条目（见 §4）

### 3.2 写放大评估
- 每批 append 额外写 24B + 一次追加写（同文件系统、同目录）
- 可配置合并：`indexBatchMs`（默认 0 = 每批同步写）——崩溃一致性要求 sidecar 落后可自愈，故**允许延迟批写**以减 fsync 次数
- 日志 fsync 已存在；sidecar 独立 fsync 或复用同批（设计上 sidecar 允许滞后 → 不强求同 fsync）

### 3.3 SidecarWriter（每会话一个，挂在 coordinator state）
- 内存态：`{ logSize, records: [] }` + 打开句柄
- `appendRecord`：push 内存 → 可选延迟 flush
- `flush`：追加到 `.idx` + sync
- 会话 dispose/retire 时 flush

## 四、崩溃一致性协议（核心）

### 4.1 三条不变量
1. **日志先写**：日志 fsync 成功后才写 sidecar → sidecar 永不超过日志
2. **sidecar 可落后**：崩溃丢 sidecar 尾部条目 → 读时重建，不丢数据（日志是权威）
3. **帧原子**：日志单帧写失败已由 `rollbackAppend` 恢复；torn tail 由既有 `repair` 处理

### 4.2 读路径自愈（sidecar 落后检测与补齐）
```
openForRead:
  idx = readIdx()                  # 可能落后
  logSize = stat(log).size
  if idx.logSizeSnapshot < logSize:
    # 落后 → 从 idx 记录的最后 endByte 起 scanZstdFrames 日志剩余段
    tailFrames = scanZstdFrames(log[lastEndByte..])
    # 对每个新帧：解压该帧（仅这些尾部帧）得到 events → 提取 first/lastSeq → 追加索引
    rebuildTailRecords(idx, tailFrames)
    # 若有 torn tail：停在 tornStart（既有 repair 逻辑不变）
```
- 补齐只解**落后帧**（通常 1-几十帧），非全量 → 自愈代价 O(新帧数)
- 这是读路径**首次触碰文件时**做一次；后续 sidecar 已追上则跳过

### 4.3 双写竞态
- coordinator 已按 per-id 串行化写（`this.serialize(id, ...)`）→ 同一会话无并发 append
- 多进程（CLD 主 + doctor）同一日志：沿用现有 revision stat 检测（`readStableFile`），sidecar 同样以 logSize 为准做乐观并发校验，不一致即重建

### 4.4 删除/清理
- 会话日志删除时同删 `.idx`（跟随现有 lifecycle）

## 五、读路径对接（`loadStoredFrom` 实现）

### 5.1 服务范围与入口
| 入口 | 现状 | 本设计后 |
|---|---|---|
| `readFrom(id, fromSeq)` | hook 已就绪，缺 backend 实现 | ✅ 走 sidecar 定位 → 只读后缀 |
| `inspect/prepareCore`（冷开） | `backend.loadStored` 全量 | 本阶段**不动**（见 §7.2 后续项） |

### 5.2 loadStoredFrom 伪代码（jsonl backend 新增）
```
async loadStoredFrom(id, fromSeq, signal):
  path = locate(id); idx = ensureIdxUpToDate(path)   # §4.2 自愈
  if idx 无记录（旧文件无 idx）→ 走 §6 惰性构建
  rec = binarySearch(idx.records, firstSeq <= fromSeq <= lastSeq)  # 含 fromSeq 的帧
  if rec == null:                                    # fromSeq 超过全部记录(异常) 
    return loadStored(id)                            # 兜底全量
  buf = readFileRange(path, rec.startByte, logSize)  # ★ 部分读：仅从目标帧起
  # 只解 rec 起的帧（含 packed 展开、legacy 检测同现有 SessionLogScanner 逻辑）
  events = decodeFrames(buf, minSeq = fromSeq)
  return { meta: readHeader(path), events, revision }
```
- **部分读** `readFileRange`（open + read 从 offset 到 EOF）替代整文件 readFile → 这是与 POC 尾部窗口对齐的关键（POC 证明 54-250x）
- 兼容：若返回的 suffix 含 legacy 形状，coordinator `readFromCore` 已有回落逻辑（`needsLegacyPrefix` → 全量）

### 5.3 readFromCore 已有语义验证
```
if backend.loadStoredFrom !== undefined → suffix 读（本设计）
else → whole.events.slice(fromSeq) 全量兜底（旧 backend/无 idx 时）
```
→ sidecar 缺失时 backend 可抛"未索引"让 coordinator 走全量兜底，**优雅降级**

## 六、旧文件升级 / 惰性构建

### 6.1 场景
- 存量 189 个会话（585MB）无 `.idx`
- 升级后首次打开 → 需建索引

### 6.2 惰性构建（两档）
| 档 | 触发 | 成本 | 服务 |
|---|---|---|---|
| **轻档**（帧级，推荐默认） | 首次读某会话 | `scanZstdFrames` 全文件扫帧头：O(文件大小) 只读 magic/头，**不解压**（14MB 文件实测 ~1.5ms） | 尾部 N 帧窗口（POC 场景）够用：**无需 seq**，从尾部倒数 N 帧即可 |
| **全档**（seq 级） | 需要任意 fromSeq | 解压**每帧**提取 first/lastSeq：O(全文件解压)（14MB ~365ms 一次） | 任意 seq 定位 |

- **决策**：轻档先建（毫秒级、立即可用尾部页）；全档**后台渐进**（空闲时逐会话建，或在第一次 `readFrom(fromSeq<近尾)` 时按需补）
- 写入 `.idx` 缓存（`logSizeSnapshot` 绑定）→ 下次打开直接读，不重扫

### 6.3 格式演进
- 版本号在 magic 后；`SESSION_FORMAT_VERSION` 不变（sidecar 是伴生加速文件，非日志格式）
- 读端对无 idx/旧版 idx 全部容忍（回落全量或轻档重建）→ **升级/回滚双向安全**

## 七、实施分层与验收

### 7.1 分层（每层独立可交付/可回滚）
| 层 | 内容 | 改动面 | 风险 |
|---|---|---|---|
| L1 | 轻档惰性索引 + `readTailWindow`（内部，不接 coordinator） | jsonl backend ~150 行 | 低（纯新增读路径） |
| L2 | 写端埋点 + `.idx` 增量维护 | jsonl backend 写路径 ~80 行 | 中（写路径，需回归 append/repair/doctor） |
| L3 | `loadStoredFrom` 正式实现 + 对接 coordinator hook | jsonl backend ~120 行 | 中（读语义需全量回归） |
| L4 | inspect 冷开 bounded 化（后续课题，官方也列 mid/long） | persistence coordinator 层 | 高（surface 语义） |

### 7.2 验收基准（对接 P2-1 POC）
- 真实 14.1MB/27,608 帧会话：`readFrom(fromSeq=尾部-200帧)` < **10ms**（现全量 365ms）
- 重启后首开（无内存索引）：轻档构建 < **50ms**；全档 < **500ms**
- 回归：append/repair/doctor/快照/并发双写全通过；sidecar 损坏/落后自愈

### 7.3 风险表
| 风险 | 等级 | 缓解 |
|---|---|---|
| 写路径埋点破坏 append 原子性 | 高 | L2 单独交付；埋点在 sync 之后、失败只影响 sidecar（可重建）不触日志 |
| sidecar 与日志不一致 | 中 | §4 不变量：日志权威、sidecar 可落后可重建、logSize 校验 |
| 旧文件/无 idx 读 | 中 | 优雅降级全量 + 轻档先行 |
| 升级覆盖 runtime | 中 | 沿用 guard 备份/重放脚本模式（同孤儿修复） |
| packed chunks seq 语义 | 低 | 写端展开后取 seq，读端复用现有 SessionLogScanner 展开 |

## 九、设计机制端到端验证（2026-09-05 补录，真实会话副本）

在真实会话副本（14.1MB/27,608 帧/59,686 事件）上验证设计核心机制：

| 场景 | fromSeq | 二分定位 | 部分读 | 全量对比 | 事件集一致性 |
|---|---|---|---|---|---|
| 尾部窗口（取最近页） | 711500 | 62μs→帧#27596 | **0.98ms**（12帧） | 497ms | ✅ PASS 不丢不重 |
| 中部任意定位 | 700000 | 68μs→帧#27242 | **14.5ms**（366帧） | 467ms | ✅ PASS |
| 近头部（几乎全量） | 100 | 70μs→帧#10 | 505ms（27598帧） | 470ms | ✅ PASS |

**结论**：
1. 部分读事件集与全量解压后 filter **完全一致**（无正确性缺陷）——`loadStoredFrom` 语义可安全对接
2. 尾部窗口加速 **~500x**（0.98ms），且随窗口增大平滑过渡（近头部场景自然退化到全量成本，符合预期）
3. 二分定位 ~65μs 可忽略；帧边界表构建（全档）~500ms 一次性
