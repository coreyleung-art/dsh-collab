# 供应链工程第一原则 · 慢慢来，可能更快

> 提出：用户（2026-09-07）
> 维护：守链-mac-mini-依赖/供应链专员
> 定位：**一切依赖工作的根本节奏观**——不是过渡策略，是工作方式本身

## 核心原则

**不要追求"马上能用"，不要有"拿来即用"的倾向性。
记住一句话——慢慢来，可能更快。把基础打好。**

> ⚠️ 校准（用户 2026-09-07 补充）：这**不是**拒绝外部经验、不是闭门造车。
> 拿来本身没问题——吸收外部好的技术/经验是正当的（xberg 修复、CLD-004 方法论、
> sharp 升级等都是外部经验吸收的成功案例，不应否定）。
> 关键是：**判断力**——知道「拿什么、本地化后对长远真正有帮助」，而非无差别拿来 + 图快。

## 判断力标准（吸收什么值得本地化）

不是所有外部技术都要本地化，也不是都不该吸收。判断维度：

1. **是否长期高频依赖**：我们要持续用的核心能力 → 值得本地化打牢；一次性/边缘的 → 吸收用法即可不必自研
2. **是否脆弱不可控**：版本/构建/schema/发布失控反复坑我们 → 本地化；成熟稳定可信任的 → 吸收引用即可
3. **是否值得地基投入**：本地化后能否长期受益（可查/可补/可控）→ 值得慢工自研；反之吸收知识复用即可
4. **不否定外部经验价值**：方法论、最佳实践、CLD-004/xberg 等成功经验要持续吸收——吸收「智慧」和「代码」是两回事

**关键区分**：
- 吸收**知识/方法论/经验** → 永远欢迎（不问来源，对长远有帮助就学）
- 吸收**代码/依赖** → 选择性本地化（问"本地化后对长远是否更有帮助"，值得才自研，不值得就审慎引用）

## 这意味着什么（守链的理解与自我纠正）

过去我的隐性倾向（需纠正）：
- 「这个第三方崩了？先 patch 顶上，能跑就行」→ 短视止血，地基没修，下次还崩
- 「这个库功能好，吸收过来快点用」→ 仍是无差别拿来主义

但不能矫枉过正（另一极端，也需避免）：
- 「慢慢来 = 什么都不吸收、全自研」→ 错，会拒绝有价值的外部经验，闭门造车
- 「外部的东西都不可信」→ 错，xberg/方法论等成功经验正是外部吸收的成果

正确的做法：
- **有判断力地吸收**：先判断"这个拿来本地化对长远是否真有帮助"，值得才慢工自研，不图快
- **持续吸收智慧**：方法论/经验永远开放学习（不问来源，对长远有帮助就吸收）
- **本地化打地基**：确实长期依赖且可控性重要的 → 慢而稳地自研，一次打对（架构/测试/文档/结构门/持久化）

## 落地纪律

1. **拒绝快速止血优先**：发现问题先问"地基哪里歪了"，而非"怎么最快堵上"
2. **地基一次打对**：值得自研的模块——架构合理 + 测试全 + 文档齐 + 结构门 + 持久化，不赶工
3. **先判断再吸收**：吸收前问"本地化后对长远是否有帮助"——有帮助才自研，否则审慎引用或只学方法
4. **持续吸收智慧**：外部方法论/经验/成功案例永远开放学习，不因本地化而封闭
5. **不计算"工期快"**：评估看"是否稳、是否可长期维护"，不追求上线天数短
6. **崩过的是地基信号**：每次崩溃都是地基某处没打牢的提示，值得慢下来修根，不是快堵

## 与本地化战略的关系

- 本地化战略 = 方向（把第三方能力吸收为可控自研）
- **"慢慢来可能更快" = 怎么做**（不图快吸收，而是把每个自研地基打牢）
- 两者合一：**方向是本地化，方法是慢而稳地打地基**，最终根除"第三方反复坑"的病灶
