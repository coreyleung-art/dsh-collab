## 〇、为什么推进内存治理本身是高风险

内存治理的目标是解决上下文膨胀，但**实施动作全部落在 CLD 宿主配置面**：
改 `~/.dsh/.agent-presets/*/agent.cordis.yml`（compaction/pruner 挂载）、调 thresholdRatio、
可能触发 compaction 运行、最终可能重启 CLD 生效——每一类都触碰宿主，配置错误/资源尖峰即可拉崩整个 CLD。

## 三、预判信号清单（提前发现，非事后）

1. **内存压力**：`memory_pressure` >85% 判红（health-check.sh 已有，CLD-011）；swap 使用率 >90%
2. **Worker 线程数**：多会话并发时 heap 放大（C1 崩溃帧特征）
3. **cordis 配置校验**：改 preset 后 `dsh --profile <p> --dump-default-config` 必须零报错才可继续
4. **备份在位**：任何 .cordis.yml/.json 改动前先 .bak-*（C4 教训：所有修改均有 .bak-* 备份）
5. **重启前就绪**：守望 pre-restart 门（锁/进程/存档/bundle/通讯检查）
6. **崩溃留痕**：CLD-002 看门狗（exit-marker/heartbeat）安装后每次异常可归因

## 四、最小化模型原则（用户定论）

> 「理论先行，最小化模型，每一个突进纳入生产都要给我评估报告经我确认」

**每个纳入生产的突进，走五步**：
1. **理论先行**：先写变更说明+风险分析（本文档/评估报告），不动配置
2. **隔离验证**：/tmp/dsh-test-home 或单 preset 副本验证可加载（C4 用户定论）
3. **最小试点**：单会话/单预设小步实施，观察内存曲线与功能
4. **评估报告**：试点结果 → 影响/收益/风险/回滚 → 交用户
5. **人类确认**：GUI 审批通过才扩大/纳入生产（对齐 R027 人类开关锁 L3）

**禁止**：一次改多预设 / 未备份直改 / 内存高压期做重操作 / 未评估直接上生产。

## 五、回滚预案（每个突进必备）

- preset 改动：.bak-* 恢复 + dump-config 复验
- thresholdRatio：记录原值，回退单行
- 重启：启动前健康基线快照（health-check.sh 全绿才重启）
- 失败判定：崩溃/会话中断/工具大面积失效 → 立即回滚并走守望 pre-change 门复盘
