## 一、为什么需要这张表

本日发生过一次「连自己都分不清版本差异」的事故：

| 版本 | 口令集 | 差异 |
|---|---|---|
| `a6d8ee57`（15:52:19 推） | 4 条全轮换 | 林小调位被换成 `46v1-...` |
| **`ca24d469`（15:54:21 推）** | **仅轮换 2 条 + 恢复 1 条** | **林小调位恢复为原值** |

**中间版与最终版并存，且没有单一对照表** → 我一度无法判断「线上到底是哪一套」。
**根因**：口令槽位、版本、推送时序三者散落在不同卡片里，没有一处能一眼看全。

**本表解决这个问题**：以「槽位号」为稳定标识，口令值变化时只更新槽位指向的本机文件，**本表本身不含密钥材料，可以安全共享**。

## 五、凭据纪律（本日事故的直接产物）

### 5.1 不要做什么

| 禁止 | 原因 |
|---|---|
| **口令写入黑板卡**（key 或 value 任一侧） | 黑板跨设备同步 → 等于把钥匙贴在锁上 |
| **口令写入 agent_send 消息** | 消息进消息队列与会话记录 |
| **口令写入任何共享文档** | 同上 |
| **在回复卡里"引用"口令做说明** | **本日第二次泄漏就是这么发生的** —— 为了解释"哪条恢复、哪条轮换"，我把口令文本又写了一遍 |

### 5.2 应该做什么

| 做法 | 说明 |
|---|---|
| **只写槽位号** | 「S01 恢复原值」而不是「某条口令恢复原值」 |
| **口令只存在于单一文件** | `~/dsh-collab/data/device/access-passwords-v2.txt`，`chmod 600` |
| **口令只经私密渠道分发** | 用户 ↔ 明鉴 的会话；不经黑板/群/文档 |
| **卡内自带提醒** | 写卡时若命中口令形态，**拒绝写入**或强制告警 |

### 5.3 建议的结构性防线（待落 CP）

**凭据防火墙**：
- 拦截面：直接 PUT、`agent_send` 消息、任何同步语料
- 判据：命中高熵凭据形态（如 `xxxx-xxxx-xxxx` 小写字母+数字分组、`FL-XXX-####`）
- 动作：**拒绝写入**或**强制告警**
- **白名单**：凭据专用存储路径（`data/device/access-passwords*.txt`）允许

**为什么需要结构性防线而不是靠自觉**：本日共发生 **4 次**凭据复制。

| # | 怎么复制的 | 是否「有意写入」 |
|---|---|---|
| 1 | 原始泄漏（推送请求卡） | 是 |
| 2 | 我在闭环卡的说明文字里引用 | **否 —— 为了解释「哪条恢复」** |
| 3 | 我在回复卡里引用 | **否 —— 为了回答「能不能用」** |
| 4 | 协作者在回执中引用 | **否 —— 为了确认验证结果** |

**★ 结论：4 次里有 3 次不是「有意写入」，而是「为了说明这件事而引用」。**

> **谈论凭据这件事本身，就是凭据的复制机制。**

**推论**：只拦「写入凭据值」的防火墙**不够**；它必须同时拦「在说明性文字里出现凭据值」，否则**每做一次复盘就会再泄一次**。

**本文件的自律**：全文不含任何口令值、不写口令形态示例、不写槽位与口令的对应关系 —— 只写槽位号与事实。

## 六、本表的维护规则

1. **口令值变化时**：更新本机口令文件 + 更新本表「状态/备注」列，**但不在本表写出口令值**
2. **新增收件人**：优先用备用槽位（S04-S08），避免重加密
3. **必须重加密时**：先暂停推送 → 定稿口令集合 → 一次性重加密 → 填「口令变更影响」表 → 再推
4. **每张推送请求卡**：引用本表槽位号，不写口令值
