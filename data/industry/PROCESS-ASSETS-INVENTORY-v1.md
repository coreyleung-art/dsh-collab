## 二、P0：三个最该做的

### 2.1 全载体一致性扫描器 `consistency-scan.py` ★★★

**触发它的真实教训**：出让比例有 **3 个载体**（资金计划 markdown / 图表 JS `rounds()` / 相关方文件的估值表），我只搜了 markdown → 星桥挂 HOLD 抓到 **8 处旧值**。

**根因**：一个事实会在多处出现，而且**载体的形式不同**：
- 正文 markdown
- **图表函数里的字符串**（源码搜索搜不到，因为它是 JS 生成的 HTML）
- 另一份文档里的表格
- 派生版（合作方版/公开版）
- **生成的 HTML 产物**

**工具形态**：
```bash
consistency-scan.py --facts facts.json --roots <目录1> <目录2> ...
```
```json
// facts.json
{
  "出让比例.Pre-A": { "correct": ["10-20%"], "stale": ["10-15%"] },
  "出让比例.A轮":   { "correct": ["6-12%"],  "stale": ["15-20%"] },
  "口径.成都":      { "correct": ["700-800 家存量商家"], "stale": ["成都已经做出来的"] }
}
```
**输出**：每个 stale 值的命中文件 + 行号 + 上下文；每个 correct 值的覆盖面（确认已改全）。

**泛化到其他工作流**：
| 领域 | 用法 |
|---|---|
| **代码** | 常量/版本号/配置在多文件同步 |
| **文案** | 多语言词条一致性 |
| **合同** | 金额/期限/主体名称跨条款一致 |
| **数据** | 同一指标在不同报表的口径统一 |
| **发布** | 版本号在 package.json / README / CHANGELOG 一致 |

**为什么最有价值**：**这是本会话唯一一个"我改完了但其实没改完"的坑，而且只有外部扫描能发现。**

### 2.2 交付前逐字节验证 `verify-deploy.py` ★★★

**触发它的真实教训**：我用 `curl -w "%{http_code}"` 看到 200 就认为"上线了"。实际线上是**旧版本**（95,645B vs 本地 52,302B）。

**根因**：**200 只说明"服务了一个文件"，不说明"服务的是最新版本"。**

**工具形态**：
```bash
verify-deploy.py --map deploy-map.json
```
```json
// deploy-map.json
{
  "base": "https://example.com/",
  "pairs": [
    { "local": "index.html",            "url": "/flowernet/" },
    { "local": "welcome/index.html",    "url": "/flowernet/welcome/" },
    { "local": "taobao-brief/index.html","url": "/flowernet/taobao-brief/" }
  ]
}
```
**输出**：
```
  /flowernet/                本地 803022B  线上 803022B  ✅ cmp 一致
  /flowernet/welcome/        本地   8903B  线上   8903B  ✅ cmp 一致
  /flowernet/taobao-brief/   本地  52290B  线上  95645B  ⚠️ 不一致（线上是旧版）
```

**泛化到其他工作流**：
| 领域 | 用法 |
|---|---|
| **任何部署** | 静态站/CDN/对象存储/容器镜像 |
| **发布** | npm/pypi 包内容校验 |
| **同步** | 双仓（GitHub/Gitee）内容一致 |
| **备份** | 备份文件与源文件比对 |

**关键点**：**用 `cmp`（逐字节），不用状态码，也不用文件大小** —— 大小相同内容也可能不同。

### 2.3 多视角红队编排 `red-team.py` ★★★

**触发它的真实教训**：我在本会话手动派了 3 个红队（平台方视角 / 数据算术 / 表达可信度），**效果极好** —— 它们发现了：
- 造节被自己的排期表推翻（平台视角）
- 长期档少算 1723 家（算术）
- 内部改稿史外泄 2 处（表达）
- **「你敢把『我做不好就退』写进材料，我才敢把位置给你」**（平台视角的洞察）

**现状**：流程有效但**全靠手工**（手写提示词、手动合并报告）。

**工具形态**：
```bash
red-team.py <target-file> --perspectives platform,math,expression --out reviews/
```
**内置视角模板**（可扩展）：
| 视角 | 审查什么 | 输出要求 |
|---|---|---|
| `platform` | 对方视角：给不给我信心？我会问什么尖锐问题？ | 8-12 个必问问题 + 能否回答 |
| `math` | 每处数字实算 + 口径交叉核对 | 【算错】/【假设不同】/【无法核实】三分类 |
| `expression` | 元话语 / 此地无银 / 承诺姿态 / 空话 | 三档判定：必须改 / 可选 / **不要改**（防过度修改） |
| `legal` | 法律风险 / 授权链 / 合规 | 条款级建议 |
| `data` | 来源可核验性 / 口径标注 | 每个数字的来源与性质 |

**关键设计**（本会话验证有效的）：
1. **要求必须具体**：不说"这里不清楚"，要说"这句『…』没告诉我…"
2. **必须给可执行改法**：写出可直接替换的句子
3. **区分「必须改」与「不要改」** —— 防止过度修改
4. **要求报告 `units_reviewed`** —— 证明真的全读了
5. **发现冲突要标注**（多个红队对同一处判断不同 → 列出来让用户定）

**泛化到其他工作流**：
| 领域 | 视角替换 |
|---|---|
| **代码评审** | 安全 / 性能 / 可维护性 / 边界条件 |
| **方案评审** | 业务方 / 技术方 / 财务方 / 风控方 |
| **论文投稿** | Reviewer 1/2/3 不同倾向 |
| **合同** | 甲方律师 / 乙方律师 / 税务 |
| **产品发布** | 用户 / 竞品 / 客服 / 法务 |

## 三、P1：三个该补的

### 3.1 数字归属四问（审查标准，进 `stance-auditor`）★★★

**触发它的真实教训**：成都 750 家 —— 我写成「成都已经做出来的」，实际是**城市合伙人资格承接的类目存量**。

**这是一条可复用的审查标准，不是工具**。新增 P16：

> **P16 数字归属清晰性**
> 文中每一个数字，必须能回答四个问题：
> 1. **分母是什么**（比例类）
> 2. **分子是什么**（比例类）
> 3. **谁做的**（成绩类）—— 是我们做的，还是承接的/借用的/行业的？
> 4. **什么时候做的**（时效类）
>
> 任何一个答不上来的数字，标为"归属不清"，**不得进入对外材料**。

**泛化到其他工作流**：
- **尽调**：标的公司的"市场份额"是谁的口径
- **财报**：营收是并表的还是母公司的
- **研究报告**：引用的数据是原创的还是二次转引
- **绩效汇报**：成绩是本人做的还是团队/前任的

### 3.2 逐单元语义审查 `unit-review.py`（补完 `stance-line-review.py`）★★★

**触发它的真实教训**：关键词法在 BP 上报「12 项全通过」，逐单元审查发现 **570 项**。

**现状**：`stance-line-review.py`（197 行）能切块，但没有：
- 上下文附加（每个单元附前后 3 个）
- 审查员回报校验（`units_reviewed`）
- 结果合并与去重

**工具形态**：
```bash
unit-review.py <file> --split-by semantic --context 3 --out review-pack/
# → 生成 N 个审查任务包（每包含单元 + 上下文 + 提示词）
unit-review.py --merge review-pack/results/*.json --out FINDINGS.md
```

**关键设计**：
- **切单元按语义边界**：heading / table_row / list_item / code / para
- **每个单元附前后 3 个上下文** —— 单看一句看不出问题
- **提示词必须写**：「不要只报含敏感词的行；要报**读起来不对**的行」
- **要求回报 `units_reviewed`** —— 不看这个数就不知道审查员是否全读

**泛化**：合同逐条审 / 代码逐函数审 / 论文逐段审 / 法规逐条比对

### 3.3 界面三重验证 `verify-ui.py` ★★

**触发它的真实教训**：改两级菜单连续引入 **5 个 bug**，最后一个是 **`@keyframes` 缺一个 `}`** → 后面所有 CSS 被当成 keyframes 的一部分 → **整个侧栏样式静默失效**。我是靠「**截图哈希两次相同**」才发现不对劲的。

**工具形态**：
```bash
verify-ui.py <file.html> --checks render,hash,computed
```
三项检查：
1. **渲染截图** —— 能不能渲染出来
2. **哈希比对** —— 与上次截图比对；**哈希相同 = 没变化（可能是缓存，也可能是改动没生效）**
3. **computed style 查询** —— 关键元素的 `position` / `display` / `width` 是否符合预期

**为什么需要第 3 项**：**一个 `}` 的缺失让整个样式表失效，但页面"看起来还行"** —— 只有查 computed style 才能发现。

**泛化**：任何前端改动 / 邮件模板 / PDF 生成 / 报表渲染

## 四、P1：一个该做的（受众分层）

### 4.1 受众分层矩阵 `audience-matrix.json` ★★

**触发它的真实教训**：本会话反复调整「什么内容给谁看」：
- 平台版删掉：AI 工具实测数据 / 数据回流 / 账号线 / 合规技术细节 / 四跑法推演
- 股东版保留：股权 / 对赌 / 资金 / 出让比例
- 合作方版：删股东敏感，保留计划细节
- 对外通用版：只讲定位与方法

**这不是"删敏感词"，是「内容类型 × 受众」的矩阵**：

| 内容类型 | 股东 | 合作方 | 平台 | 公开 |
|---|---|---|---|---|
| 股权 / 对赌 / 资金 | ✅ | ❌ | ❌ | ❌ |
| 单位经济 / 毛利 | ✅ | ⚠️ | ❌ | ❌ |
| **我方内部操作方式** | ✅ | ✅ | **❌** | ❌ |
| **技术细节（设备/日志/采集）** | ✅ | ⚠️ | **❌** | ❌ |
| **我方自我推演 / 可能性评估** | ✅ | ⚠️ | **❌** | ❌ |
| 目标数字 / 承诺 | ✅ | ✅ | **❌** | ❌ |
| 定位 / 差异化 / 方法 | ✅ | ✅ | ✅ | ✅ |
| 资源诉求 | — | — | ✅ | ❌ |

**关键洞察**（本会话想通的）：

> **给平台的 = 只说「做什么、给谁带来什么、要什么」**
> **不给平台的**：① 我们内部怎么干活 ② 我们怎么想这件事 ③ 我们的技术细节
> **共同点**：平台不需要知道（知道了也不改变决策）；知道了可能有害（引发警惕 or 暴露底牌）

**泛化**：
- **API 文档分级**（公开 / 合作方 / 内部）
- **Wiki 分级**（全员 / 部门 / 管理层）
- **漏洞披露**（内部 / 厂商 / 公开）
- **产品路线图**（内部 / 客户 / 公开）

## 七、三条可以进治理哲学库的原则

**1. 逐行读才叫审查，搜关键词只是检索**
> 关键词匹配的是「含不含某个词」，审查要看的是「**读起来对不对**」——这两件事没有交集。
> 证据：同一份 BP，关键词法报 12 项，逐单元审查发现 570 项。

**2. 一个事实有多个载体，改一处不等于改完**
> 载体形式不同：正文 / 图表函数字符串 / 另一份文档的表格 / 派生版 / **生成的产物**。
> **只搜源码会漏掉 JS 生成的 HTML —— 因为那部分内容根本不在源码的搜索范围内。**

**3. 授权必须来自授权人本人**
> 我曾用「用户已确认」让协作方解除门禁。这条链必须终止 ——
> **一旦我能用"用户说"绕过闸门，闸门就形同虚设。**
