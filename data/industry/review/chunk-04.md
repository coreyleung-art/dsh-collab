# 逐单元立场审查任务

## 读者画像
读者是**股东（如橙果）**。他需要知道：自己的出资/权利/义务、公司结构、对赌与保障、各轮选项、退出路径。
他**不该看到**：他方（尤其是梁振宇）的私人资金安排、内部文档生产流程、内部工具代号与文件名、与本次合作无关的内部管理细节。
判定标准：这一行若被股东读到，会不会让他困惑/误解/知道不该知道的事？

## 审查要求（★ 必须逐单元通读，不得用关键词匹配代替阅读）

对下面**每一个审查单元**独立判读，给出：
1. `verdict`: `ok`（对该受众合适）/ `flag`（有问题）/ `suspect`（存疑，需人确认）
2. `reason`: 一句话说明**为什么**（读懂了这句话在讲什么，再判断）
3. `suggest`: 若 flag/suspect，给出**具体改法**（原文 → 建议）

**特别注意**（这些是过去用关键词法漏掉的类型，但不限于这些）：
· 说话人视角错误（把「我们」写成「你」、把公司决策写成个人安排）
· 对读者的知识水平假设错误（用了读者不可能懂的内部术语）
· 「此地无银」式表述（写「不包含X」反而暴露X存在）
· 内部生产痕迹（版本号、作者名、写作规范、模板来源、内部文件名）
· 口径不一致（同一事实在不同位置说法不同）
· 承诺越界（对读者作了不该作的承诺）
· 上下文错位（内容本身没问题，但放在这里给这个读者看不对）
· **任何你读出来觉得不妥的地方**——不要因为没有匹配到上述类型就判 ok

**不要**只报「含敏感词」的行；要报「读起来不对」的行。
**不要**放过任何一行：每一行都要过一遍。

L876 [heading] ### 四、依赖关系 relations（四条业务线互为输入）
L878 [para] 这一节最容易被误读：**四条线是"互为输入"，不是"四条并行产线"。**
L880 [code] ```
L881 [para] 代运营线 ──产数据──→ 软硬件数据线 ──训出工具──→ 工具提效回流代运营线
   │                        │
   ├───产数据─────────────→ 底座线（订单级数据沉淀）
   │                        │
   └─产现金/场景──→ IP 商品线 ←─反哺选品与定价── 底座线
L886 [code] ```
L888 [para] **读法**：**代运营产数据 → 数据训 AI 工具 → 工具卖出回流提效 → 底座积累 → 底座反哺选品与定价。** 每一环让下一环更强，也让上一环更省。
L890 [para] 由此得到一条资源分配纪律：**四条线抢预算时，优先保障"能让其它三条线变强的那个节点"，不做平均主义。**
L892 [para] 关键路径上有三个硬依赖，**断一个整条链停摆**：
L894 [list_item] 1. **数据可得性依赖合规**——采集必须合法且严格隔离个人信息（个人身份信息，如收货人手机号、地址）。触碰的处罚是《个人信息保护法》下的顶格处罚（最高为上一年度营业额 5% 或 5000 万元的双罚）。**这不是成本问题，是生死问题。**
L895 [list_item] 2. **工具可信度依赖真实场景**——代运营的规模天然限制工具线成熟的速度。
L896 [list_item] 3. **底座价值依赖前三线规模**——没有足够门店的数据，底座只是一堆样本。
