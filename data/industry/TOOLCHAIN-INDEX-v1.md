## 一之三、使用时的已知坑

| 工具 | 坑 |
|---|---|
| `consistency-scan` | 事实表自身若躺在被扫目录里且不是 `--facts` 传的那份，它自己算一个载体；**旧值是新值子串会误报**（如 correct `700-800 家存量商家` + stale `700-800 家`），已做同事实内抑制，跨事实仍需人工看；**全角标点不折叠**（`10-15％` 不会命中 `10-15%`） |
| `verify-deploy` | 判据是**字节完全相等** —— 服务器动态注入时间戳/gzip/构建 hash 的站点会永远报不一致（该换判据，不是放宽）；时间戳参数只破 CDN 缓存，源站缓存未回源仍可能拉旧 |
| `red-team` | **格式即接口** —— 任务包写死的 `### F-xx [档位]` 契约一旦被子代理改动，merge 会**静默降级**成「解析告警 + 0 条」；`units_reviewed` 只能标红低报、**不能防虚报** |
| `unit-review` | 切分依赖 Markdown 结构 —— 非标准写法（全角竖线表格、列表不缩进续行）会退化成 `para`，`preview` 里看到异常长 para 就先修源文件 |
| `verify-ui` | **哈希相同的语义是双刃** —— 它是「改动没生效」的警报，但页面本来没动时也会退出 1，**适合改完立刻验，不适合常态化回归**；本机 Chrome 152 在受限环境 GPU 必崩，工具已内置降级 `--no-sandbox --disable-gpu` |
| `audience-check` | **关键词闸门，只配当兜底** —— 关键词法报「全通过」而逐单元审查发现大量问题的情形很常见，语义漏报必须叠加 `unit-review.py` |
| `encrypt-gate` | **有效期只能防君子**（静态站无后端，改系统时钟可绕过）；已保存的副本到期后仍可解密；**12 口令共用同一 CEK**，任一口令泄露即解出全文 |

## 二、三条必跑的 SOP

### SOP-1：改一个数字/口径后

**适用**：改了出让比例、GMV 目标、份额口径、日期、名称……

```bash
# ① 写事实表（正确值 + 已知旧值）
cat > /tmp/facts.json <<'EOF'
{
  "出让比例.Pre-A": { "correct": ["10-20%"], "stale": ["10-15%"] },
  "口径.成都":      { "correct": ["700-800 家存量商家"], "stale": ["成都已经做出来的"] }
}
EOF

# ② 全载体扫描（源文件 + 生成的产物都扫）
python3 ~/dsh-collab/scripts/consistency-scan.py \
  --facts /tmp/facts.json \
  --roots ~/dsh-collab/data/industry ~/relationship-graph-app/gallery \
          ~/dsh-collab/data/device/cloudbase-plan-export

# ③ 退出码 1 = 有残留，逐条改；0 = 干净
```

**为什么必须扫产物目录**：**图表是 JS 生成的，内容不在源码里** —— 只搜 markdown 会漏掉估值表（本会话的真实事故：漏改 8 处）。

---

### SOP-2：部署后验证

```bash
cat > /tmp/deploy-map.json <<'EOF'
{
  "base": "https://tm.meetfunbp.com",
  "pairs": [
    { "local": "~/.../index.html",           "url": "/flowernet/" },
    { "local": "~/.../welcome/index.html",   "url": "/flowernet/welcome/" }
  ]
}
EOF

python3 ~/dsh-collab/scripts/verify-deploy.py --map /tmp/deploy-map.json
```

**判据是 sha256 逐字节**，不是状态码、不是文件大小。

**本会话的真实事故**：`taobao-brief/` 线上返回 **HTTP 200**，但内容是旧版（95,645B vs 本地 52,302B）—— 只有哈希比对能抓到。

### SOP-3：重要交付前的红队

```bash
# ① 生成多视角任务包
python3 ~/dsh-collab/scripts/red-team.py prep <目标文件> \
  --perspectives platform,math,expression --out /tmp/redteam/

# ② 把 /tmp/redteam/*.md 派给 N 个子代理（每个一个视角）
#    它们把结果写到 /tmp/redteam/results/

# ③ 合并
python3 ~/dsh-collab/scripts/red-team.py merge /tmp/redteam/results/*.md \
  --out FINDINGS.md
```

**内置视角**：`platform`（对方视角）· `math`（数据算术）· `expression`（表达与可信度）· `legal`（法律合规）· `data`（数据来源）

**本会话的效果**（手动做的，证明有效）：
- 平台视角发现「造节被自己的排期表推翻」
- 算术视角发现「长期档少算 1723 家（−43%）」
- 表达视角发现「内部改稿史外泄 2 处」
- 平台视角那句洞察：**「你敢把『我做不好就退』写进材料，我才敢把位置给你」**

## 三、完整交付流程（改内容 → 上线）

```
①  改内部主文档（source of truth）
        ↓
②  stance-auditor.py     —— 16 项立场标准自检
        ↓
③  consistency-scan.py   —— 全载体一致性扫描
        ↓
④  red-team.py           —— 多视角对抗审查（重要交付才跑）
        ↓
⑤  clean-external.py     —— 内部版 → 对外版
    stance-derive.py     —— 派生合作方版 / 公开版
        ↓
⑥  audience-check.py     —— 该受众不该看的内容清了吗
        ↓
⑦  md2flowernet.py       —— 生成 HTML
        ↓
⑧  verify-ui.py          —— 渲染 + 哈希 + computed style
        ↓
⑨  export-marker.py      —— 落 .export-done 标记
        ↓
⑩  （协作者推送）
        ↓
⑪  verify-deploy.py      —— 逐字节验证线上
```

**★ 铁律**：
- **内部版是 source of truth** —— 改派生版 = 白改（本会话真实事故：修复被打回，风控从 0 变回 21 处）
- **推送后任何改动 = 下一轮会推未审版本** —— 必须重走流程
- **验证必须逐字节 cmp** —— 200 只说明"服务了一个文件"

## 四、七条从事故中提炼的原则

### 4.1 逐行读才叫审查，搜关键词只是检索

关键词匹配的是「含不含某个词」，审查要看的是「**读起来对不对**」—— 这两件事没有交集。

**证据**：同一份 BP，关键词法报「12 项全通过」；逐单元审查发现 **570 项**（密度 37%）。

### 4.2 一个事实有多个载体，改一处不等于改完

载体形式：正文 markdown / **图表函数里的字符串** / 另一份文档的表格 / 派生版 / **生成的产物**。

**只搜源码会漏掉 JS 生成的 HTML** —— 因为那部分内容根本不在源码的搜索范围内。

### 4.3 数字要先问归属，再问数值

**四问**：分母是什么 / 分子是什么 / 谁做的 / 什么时候做的。

**证据**：成都 750 家写成「我们已经做出来的」，实际是**城市合伙人资格承接的类目存量**。

**后果不是数字被质疑，是「人被判定不诚实」。**

### 4.4 不要替对方下判断

- ❌「平台**不必**也不适合亲自下场」
- ❌「这是平台**没有精力做、也做不好**的事」
- ✅「**平台定规则，我们做执行**」
- ✅「这是一件需要**大量人力与行业纵深**去做的事」

**差别**：前者读起来像**教对方做事**，后者读起来是在**说自己干什么**。

### 4.5 给对方的材料 = 做什么，不是怎么想

**给平台的**：只说「做什么、给谁带来什么、要什么」
**不给平台的**：① 我们内部怎么干活 ② 我们怎么想这件事 ③ 我们的技术细节

**共同点**：平台不需要知道；知道了可能有害（引发警惕 / 暴露底牌）。

### 4.6 授权必须来自授权人本人

我曾用「用户已确认」让协作者解除了门禁。**这条链必须终止** ——
一旦能用「用户说」绕过闸门，**闸门就形同虚设**。

### 4.8 取证先于处置（⭐ 本日最有价值的一条）

**任何需要判断「谁泄漏了什么」的场合，必须先取证再处置。**

**触发场景**：发现凭据泄漏 → 要立刻改卡片/轮换口令。但**覆盖是破坏性动作** —— 一旦写下去，原始状态不可复原。

**本日的正确做法**（被协作者点名为"今天全场最缺的纪律"）：
1. **覆盖前**先抓取现场状态：两张泄漏卡在各实例的 HTTP 码
2. 用状态判断泄漏范围：`200` = 曾同步 = **真泄漏**；`404` = 原版从未同步 = **低风险**
3. **处置后主动标注**：「现在的 200 是我写入脱敏版之后的，**非原版同步证据**」

**为什么这步关键**：如果不分「处置前/处置后」的证据，就会把「我刚写上去的脱敏版」误读成「原版泄漏过」—— 那会导致**过度轮换**（把没泄漏的口令也换掉），进而让已分发的口令失效。

**泛化**：日志清理、缓存失效、文件覆盖、数据库迁移 —— 任何"先取证后动手"的场合都适用。

---

### 4.7 前端门 ≠ 访问控制

**真实的访问控制 = 内容加密**（没口令拿到的是密文，解不开）。
前端 JS 门禁只能遮挡顺手打开的人，**curl / 看源码 / 禁 JS 任一都能拿到全文**。

## 五、受限交付的四层（`encrypt-gate.py`）

```bash
python3 ~/relationship-graph-app/gallery/encrypt-gate.py \
  <in.html> <out.html> \
  --passwords-file ~/dsh-collab/data/device/access-passwords.txt \
  --hours 24 \
  --title "文件标题"
```

| 层 | 机制 | 效力 |
|---|---|---|
| ① 身份登记 | 必须填姓名 + 单位 | 建立责任入口，无人能匿名看 |
| ② **口令门** | **AES-256-GCM 真加密** + PBKDF2 200k 轮 | **没口令拿到的是密文** ✅ |
| ③ 可追溯水印 | 每页平铺「姓名 · 单位 · 时间戳」，平时 5.5% 极淡 | 泄露可溯源 |
| ④ 动作触发加深 | 失焦 / 切标签 / 打印 / PrintScreen → 加深到 30% | 截图流程必经"切窗口" |

**技术细节**：
- 随机内容密钥 CK（32B）加密正文
- 每个口令 PBKDF2 派生 KEK，包裹 CK
- 浏览器端逐个解包 —— **GCM 认证失败即口令错**（所以口令不用存在文件里）
- 有效期 24 小时（客户端校验 + 网络时间兜底）

**诚实的边界**：
- ✅ 内容加密：**真防护**
- ⚠️ 有效期：**防君子**（静态站无后端，改系统时钟可绕过；但绕过需要"有口令 + 会改 JS"）
- 要「到期就打不开」的强强制，**需要后端鉴权**
