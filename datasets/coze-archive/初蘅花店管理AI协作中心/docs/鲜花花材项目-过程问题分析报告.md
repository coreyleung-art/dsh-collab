## 二、核心问题清单

### 🔴 P0：历史数据覆盖率严重不足（最大瓶颈）

**现状**：v3汇总表共 7329 条记录，覆盖 2021-01 至 2026-06，但仅37个月有数据，**29个月完全空白**。

**关键缺口**：

| 时间段 | 缺失月份 | 严重程度 | 说明 |
|--------|----------|----------|------|
| 2025-02 ~ 2025-12 | 连续11个月 | 🔴 致命 | 几乎整年无数据，这是离现在最近的完整年度 |
| 2024-09 ~ 2024-12 | 连续4个月 | 🔴 致命 | Q3-Q4数据全空 |
| 2026-02 ~ 2026-03 | 2个月 | 🟡 重要 | 刚过去不久，应可补回 |
| 2021-03, 2021-06 | 2个月 | ⚪ 低 | 早期月度汇总，优先级低 |
| 2022-02 ~ 2022-08 | 连续7个月 | 🟡 重要 | 早期数据，但影响时间序列连续性 |

**根因**：Claw 执行数据采集时发现——**nyncj.km.gov.cn 的每日花卉价格页面从2026年1月中旬才开始发布**，之前没有每日花卉数据。这意味着我早期规划中"2023年起每日发布"的判断是**错误的**。

**影响**：数据覆盖率仅 56%（37/66个月），无法支撑可靠的价格波动因子建模。

---

### 🔴 P0：信息源判断偏差（规划失误）

**我的原始规划**：昆明市农业农村局（nyncj.km.gov.cn）2023年起每日发布斗南花市品类级批发价，静态HTML表格，爬取难度低。

**实际情况**：
- nyncj.km.gov.cn 的每日价格页面**仅从2026年1月中旬开始**才有花卉数据，之前几乎全是蔬菜/水产价格
- 该站列表页中，斗南花卉仅占约 **4%**，大量抓取工作浪费在无关页面上
- 2023-2025年的花卉数据实际分布在**呈贡区政府站**（kmcg.gov.cn）的月度统计表中，格式为 PNG 图片+HTML表格

**偏差原因**：
1. 我在规划时基于搜索结果中看到的 nyncj.km.gov.cn 个别花卉页面，**过度外推**为"2023年起每日发布"
2. 未在规划阶段实际验证数据源的时间覆盖范围
3. 将月度汇总表和每日发布页混为一谈

### 🟡 P1：采集策略效率低下

**Claw 的采集过程暴露的问题**：

1. **盲目全量抓取**：先启动子 session 抓取 nyncj.km.gov.cn 全部401页8015个URL，发现花卉仅占4%，大量资源浪费
2. **格式适配慢**：第11页起HTML结构不同导致脚本失败，调试了多轮才发现URL路径差异
3. **OCR截断问题**：用 read_image 直接读取大图片，输出频繁截断，后来才改为裁剪分块OCR
4. **月度表日期错位**：kmcg 发布月份与数据月份不一致（如2026-03 URL → 2026年2月数据），多次验证才发现规律
5. **多次"响应太长"中断**：Claw 至少2次因响应过长被截断，丢失上下文

**预估时间消耗**：从消息时间线看，Claw 从 05:13 到 06:44（约1.5小时）主要在做历史数据回填，但最终 v3 汇总表仍未完成——2024-09~12 和 2025年几乎全部缺失。

## 三、问题根因分析

### 3.1 规划与执行脱节

```
规划阶段（我负责）         执行阶段（Claw负责）
    │                          │
    ├─ 假设nyncj有2023+每日数据 ──→ 实际2026年1月起才有花卉
    ├─ 设计了完整数据规范    ──→ 品类命名/来源名称未统一
    ├─ 规划了6大因子群       ──→ 仅完成2个，其余4个未启动
    └─ 未验证源站实际覆盖    ──→ 花费1.5h回填，覆盖率仍仅56%
```

**核心问题**：我在规划时没有实际验证数据源的时间覆盖范围，导致后续执行方向偏移。

### 3.2 数据源体系认知迭代但未及时同步

| 阶段 | 认知 | 行动 |
|------|------|------|
| 初始规划 | nyncj.km.gov.cn = 2023年起每日数据 | 以此为唯一主力源 |
| Claw验证发现 | nyncj花卉数据仅2026年1月起 | 转向kmcg月度表+OCR |
| 当前实际情况 | 数据分布在3个站点，颗粒度不同 | 需要重新设计多源采集策略 |

**问题**：认知迭代了多次，但每次都是执行中"撞墙"才发现，缺乏规划阶段的提前验证。

### 3.3 项目文件管理混乱

| 问题 | 表现 |
|------|------|
| 多版本并存 | v1/v2/v3汇总CSV + ocr_monthly_data_complete.csv + 各月独立CSV |
| 目录结构未对齐规范 | 规划的 flower_price_db/ 目录结构未实际建立 |
| 过程文件未清理 | 月度统计表下有 monthly_html_all.csv / monthly_kmcg_html.csv / monthly_readimage_data.csv 等多个中间产物 |
| 核心数据 vs 过程数据未区分 | v3 汇总表直接放在项目根目录 |

## 四、改进建议

### 4.1 立即行动：数据源重新验证与补全

**最高优先级**：填补 2024-09 ~ 2025-12（16个月）的数据缺口。

实际可用的数据源及对应关系：

| 数据源 | 覆盖范围 | 颗粒度 | 格式 | 优先级 |
|--------|----------|--------|------|--------|
| kmcg.gov.cn 月度统计表 | 2023-2026 | 月度均价 | HTML+PNG | P0 |
| nync.yn.gov.cn 每日价格 | 2023-2026 | 日频 | HTML表格 | P0 |
| nyncj.km.gov.cn 每日价格 | 2026-01至今 | 日频 | HTML表格 | P1 |
| weihengtech.com 监测月报 | 2025至今 | 日/周/月 | PDF+图表 | P1 |

**建议路径**：
1. 先用 kmcg.gov.cn 补全所有月份的月度均价（解决覆盖率问题）
2. 再用 nync.yn.gov.cn 补充日频数据（解决颗粒度问题）
3. nyncj.km.gov.cn 仅用于 2026年1月至今的增量

### 4.2 数据规范化清洗

1. **统一来源名称**：映射为3个标准来源（kmcg月度表 / nync日价格 / nyncj日价格）
2. **统一品类命名**：建立映射表（月季→玫瑰，东方百合→百合），并保留 raw_name
3. **空品类修复**：对180条空品类记录做 raw_name 拆分
4. **目录重构**：按规划文档建立 flower_price_db/ 目录结构，迁移现有数据

### 4.3 增量采集系统建设

1. **移除 Fallback 模板**：花易来/花易宝的假数据立即清除
2. **改造成辉采集**：全量遍历7个核心分类页面
3. **配置定时任务**：每日增量采集 + KIFA月报月度采集
4. **监控告警**：页面结构变更检测、数据缺失告警

### 4.4 因子数据推进

按原规划分期路线：
- **二期（本周）**：接入心知天气API，生成 weather_daily.csv
- **三期（下周）**：抓取上期所原油期货数据 + KIFA月报供货量
- **四期（按需）**：昆明海关出口月报

### 4.5 规划流程改进

1. **规划阶段必须做源站验证**：对每个数据源至少检查3个时间点的实际页面
2. **规划与执行对齐会议**：在动手采集前，确认数据源的实际覆盖、格式、反爬策略
3. **数据质量门控**：每完成一个阶段的数据采集，做一次覆盖率+质量检查再继续

## 五、总结

| 维度 | 评价 |
|------|------|
| **规划质量** | 框架设计完整（6因子群×18因子），但数据源验证不足，导致核心假设错误 |
| **执行效率** | Claw 投入大量精力但策略反复调整，1.5小时回填仅达56%覆盖率 |
| **数据质量** | 品类命名混乱、来源名称不统一、77%缺高低价、29个月空白 |
| **体系完整度** | 因子设计+节日数据完成度好，但气象/供给/成本/出口因子全未启动 |
| **增量能力** | 每日采集系统尚未建成，实时监控为0 |

**一句话**：规划方向正确但地基不实——数据源验证失误导致整个采集链条效率低下，当前最紧迫的是用 kmcg + nync.yn.gov.cn 补全 2024-2025 的16个月数据缺口，然后建立增量采集闭环。
