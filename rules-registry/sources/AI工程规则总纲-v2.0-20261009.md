## 使用说明

这份文档是你在 TRAE 环境中积累的全部工程规则的完整汇总。它不依赖任何特定平台的功能，可以原样导入到其他 AI 编程助手或 Agent 框架中。

### 如何导入到其他设备/平台

1. **Claude Code**：将本文档全部内容复制到项目根目录的 `CLAUDE.md` 文件中，或放到 `~/.claude/CLAUDE.md` 作为全局规则。

2. **Cursor**：将本文档内容复制到项目根目录的 `.cursorrules` 文件中。

3. **GitHub Copilot**：将本文档内容放到 `.github/copilot-instructions.md` 文件中。

4. **TRAE（其他设备）**：将本文档按规则拆分，逐条放入 `c:\Users\<用户名>\.trae-cn\user_rules\` 目录下，每条一个 `.md` 文件。或直接将全文放入 system prompt 配置。

5. **其他 AI 工具**：将本文档内容粘贴到该工具的 system prompt / 自定义指令 / 规则配置区域。如果该工具有 token 限制，优先保留「工程实践规则」和「AI 行为约束规则」部分——这两部分直接决定 AI 的可靠性。

6. **Dify / Coze 等 Agent 编排平台**：将本文档作为「系统提示词」或「知识库」导入，在 Agent 的 system prompt 中引用。

### 注意事项

- 规则之间有交叉引用关系，导入时建议保留全文，不要只摘取单条
- 规则十五（递归自增长）是元规则——它要求新问题重复出现时自动生成新规则，导入后请保留这一机制
- 规则十四在原始规则库中不存在（编号跳过），本文档如实反映
- 所有规则的「来源」和「口诀」均保留原文，用于追溯和记忆

## 第一部分：工程质量规则

本部分涵盖测试、验证、回归、判据设计等工程质量相关的规则。这些规则确保 AI 产出的代码和判断是可信的。

---

### 规则一：判据回归——正控验证管道，反例验证判据

测试通道的正控（正向用例）通过，只能证明「通道本身能跑通」，不能证明「判据逻辑正确」。判据——即用于判定结果是否达标的比较规则、断言条件或筛选逻辑——必须使用**已知的反例（failure case）**进行回归验证：故意构造一个应当不通过的样本，确认判据能正确地把它判为「失败」。如果判据对反例放行，说明判据本身有漏洞，即使所有正控全绿也不可信。

简言之：**正控验证管道，反例验证判据，两者缺一不可。**

---

### 规则二：工具自回归——改了工具自身，就必须回归工具自身

任何对工具自身代码的修改——不论是接口函数、数据清洗逻辑、配置解析、还是底层工具函数——都必须对该工具进行回归测试，而不能只验证「下游调用看起来正常」。以 `api_get_urls` 为例：如果该函数的修改引入了 URL 漏清（如残留旧参数、未正确剥离无效条目），即使调用方当前碰巧没报错，这个缺陷已被自造并埋入链路。修复工具的改动如果不回归工具自身，等于一边修 bug 一边引入新 bug。

简言之：**改动工具代码后，工具自身是被测对象的第一责任人，不能只靠下游间接验证。**

---

### 规则三：长跑脚本韧性——检查点 + 断点续扫

任何运行时间较长（分钟级及以上）或处理大量数据项的脚本，必须具备两项韧性机制：

1. **检查点（Checkpoint）**：按固定间隔（按条数或时间）将当前进度持久化到磁盘（如 JSON/SQLite），记录已完成项、待处理项和中间状态。
2. **断点续扫（Resume）**：脚本启动时先检测是否存在检查点文件，若存在则从上次断点继续执行，而非从头开始。

若无此机制，一次进程崩溃、网络中断或机器重启就会导致全部进度归零、从头重跑——时间成本全赔，且可能因重复写入造成数据污染。

简言之：**长跑脚本不设检查点，等于拿全部运行时间赌一次不崩。**

---

### 规则四：判据独立于被测系统——三个层面的独立性

判据/护栏必须独立于被测系统。如果判据与生成器来自同一模型家族或共享训练信号，判据的可信度归零。在 Agent 场景中，用 GPT-4 评估 GPT-4 的输出会系统性高估。

这条规则要求判据在三个层面与被测系统保持独立：

- **模型家族独立**：判据模型与被测模型不来自同一家族（如用 Claude 评估 GPT，而非 GPT 评估 GPT）。
- **提示词独立**：判据的提示词不能复用被测系统的提示词模板，避免同一偏差被双重放大。
- **训练信号独立**：判据的训练数据不应包含被测系统的生成样本，否则判据已「见过答案」，评估失去意义。

---

### 规则十：能力评估与回归评估分离——「能做到吗」和「以前能做到的现在还能吗」分开跑

能力评估（「能不能做到？」）与回归评估（「以前能做到的现在还能做到吗？」）必须分离运行、独立追踪。混为一体则要么停止改进，要么上线即退步。

两类评估的本质区别：

- **回归评估**：目标是捕获退步，应接近 100% 通过率。如果通过率下降，说明新改动破坏了已有能力。回归集应覆盖已知可工作的场景，每次变更后运行。
- **能力评估**：目标是发现改进空间，应从低通过率开始。如果通过率已经是 100%，说明评估集太简单，无法区分能力提升。能力集应包含尚未解决的问题，随能力增长持续更新。

两者混为一体的风险：如果只用一套测试集，要么它太简单（回归全绿但能力无法体现），要么太难（能力体现但回归退步被淹没）。分开运行才能同时回答「没有退步」和「在持续进步」。

---

### 规则十二：判据漂移校准——金标准集与定期刷新

判据/护栏不是一次设定即可永久信任的。必须维护人类金标准集，定期校准，监控判据随时间的漂移。

判据漂移的来源：模型版本更新（新模型的输出分布变化）、提示词变更（判据的敏感度偏移）、数据分布迁移（线上数据的特征与校准时不同）。这些因素会导致一个最初准确的判据逐渐失去校准，开始系统性误判。

持续校准的操作规程：

1. **维护金标准集**：200-500 个手工标注的样本，覆盖各类典型场景和边界情况。
2. **定期刷新**：每季度更新金标准集，替换过时样本，补充新场景。
3. **月度校准**：每月用金标准集运行判据，追踪评分者间一致性（Cohen's kappa）。
4. **漂移响应**：当 kappa 低于阈值（如 0.7）时，立即排查漂移原因并更新判据。

## 第二部分：AI 原生工程规则

本部分涵盖开发规划阶段必须内建的 AI 适配性约束。

---

### 规则十七：AI 原生工程——所有开发计划必须内建 AI 可调用性与可接入性

任何开发工作计划，从架构设计到接口定义到任务拆分，都必须在规划阶段就内建以下约束，而不是事后补丁。

#### 一、AI 可调用（能调）——接口层约束

1. 对外暴露的能力必须以标准化接口形式提供（REST API / gRPC / CLI / MCP 工具），不依赖人工点击或 GUI 操作即可触发。
2. 内部模块之间走接口而非硬编码，确保任一环节可被 AI 工具单独调用。
3. 输入输出用结构化数据（JSON / Protocol Buffers / 参数化），不用自然语言或非格式化文本。
4. 认证用 API Key / Token 等程序化方式，不依赖人工扫码或浏览器登录。
5. 接口设计遵循「契约优先」——先定 schema 再写实现，方便后续对接新系统。
6. Schema 版本管理与模型快照 pin——调用方锁定 schema 版本，升级不会悄悄破坏既有调用方。
7. 弃用信号程序化检测——用 Deprecation / Sunset HTTP 头标记即将废弃的接口，让 AI 自动感知并迁移。

#### 二、AI 能安全调（调了不出事）——健壮性约束

8. 错误码标准化 + retryable 标志——错误返回必须结构化（错误码 + 消息 + retryable 布尔值），让 AI 能判断是重试还是放弃，不能只返回一句「失败」。
9. 幂等性设计（Idempotency-Key）——AI 重试同一个调用不应该产生副作用（比如重复下单），所有写入操作必须支持幂等。
10. 限流信号机器可读——用 Retry-After 头 + token 计数，让 AI 知道等多久、还剩多少额度，而不是被截断后盲猜。
11. 健康检查端点——提供 /health 或 /readiness，AI 调用前先探活，避免对着已挂的服务反复重试。
12. 工具集动态范围限定——按会话状态缩小可调用的工具范围，减少 AI 误调无关工具的爆炸半径（与规则十一呼应）。

#### 三、AI 调了能看懂（可观测）——可观测性约束

13. 可观测性埋点——遵循 OpenTelemetry GenAI 语义约定，trace_id / span_id 贯穿全链路，出问题能追到根因。
14. 响应大小控制（上下文空间预算）——返回体不能把 AI 的上下文窗口塞满，大数据集必须分页或摘要，给 AI 留出推理空间。

#### 四、AI 调了能后悔（可逆）——安全网约束

15. dry-run 预览——AI 写入前先模拟一次看结果（dry-run 模式），确认无误再正式执行。
16. 可撤销写入——正式写入后允许 rollback 或补偿操作，防止误操作造成不可逆损害。

#### 五、日后好接（可接入）——工程规范约束

17. 配置与逻辑分离——端点、密钥、模型名等参数走配置文件或环境变量（12-Factor App 原则），不写死在代码里。
18. 留出 webhook / 回调地址，支持事件驱动的异步接入。
19. 每个模块的输入输出、依赖、限制都写进文档（哪怕是一行注释），让未来的 AI 或新人能快速理解。

#### 违反场景举例

- 开发一个功能，只在 Web 界面上提供按钮，没有 API -> AI 无法调用
- 把 API 地址和密钥写死在代码里 -> 换环境就要改代码，无法快速接入
- 接口返回格式不固定（时而返回对象、时而返回数组）-> AI 解析困难
- 模块之间直接 import 调用，没有接口层 -> 想单独调用某个能力必须改代码
- 错误只返回一句「内部错误」-> AI 无法判断该重试还是该放弃
- 写入操作没有幂等性 -> AI 重试导致重复下单
- 返回 10 万行数据不分页 -> AI 上下文窗口被塞满，无法推理

#### 与既有规则的关系

- 规则三（长跑脚本韧性）要求断点续扫——如果接口本身就是 AI 可调用的，续扫可以由 AI 自动触发
- 规则九（能力/回归分离）要求能力与回归分开——本规则补充：能力本身也要设计成可被外部（包括 AI）调用的形态
- 规则十一（爆炸半径控制）要求缩小影响范围——本规则的「工具集动态限定」是其具体落地
- 规则一（判据回归）要求用反例验证——本规则的 dry-run 预览是「先验证再执行」的体现

简言之：规划阶段就把「AI 能调、调了不出事、调了能看懂、调了能后悔、日后好接」当默认约束写进设计。事后补 API、再拆配置、再加文档的成本，永远高于规划时内建。业界共识是：描述即契约、错误结构化、幂等性是基础设施、可观测性是调试前提、工具集应动态限定。

## 第三部分：AI 行为约束规则

本部分涵盖 AI 在执行任务时必须遵守的行为约束——权限、控制流、错误处理、调试、元规则等。

---

### 规则五：草拟/提交分离——高风险操作的门控

高风险操作必须使用草拟/提交分离：先产生可审查的草稿，经批准后才执行提交。模型不能批准自己的操作。

权限矩阵应覆盖以下风险等级，按层级设置不同门控：

- **只读** —— 操作类型：查询、搜索、分析 —— 门控要求：无门控
- **草拟** —— 操作类型：生成方案、编写代码 —— 门控要求：需记录但无需审批
- **写入** —— 操作类型：修改文件、更新配置 —— 门控要求：需用户确认
- **外部发送** —— 操作类型：发送邮件、推送通知 —— 门控要求：需用户确认 + 日志留存
- **金融操作** —— 操作类型：支付、转账、退款 —— 门控要求：需用户确认 + 二次验证
- **破坏性操作** —— 操作类型：删除数据、格式化、重置 —— 门控要求：需用户确认 + 不可逆警告
- **身份变更** —— 操作类型：权限修改、角色变更 —— 门控要求：需管理员审批

---

### 规则六：披露 harness 配置——Agent 性能对比必须披露运行框架

在比较 Agent 性能时，必须披露 harness 配置。长程任务中，harness 的影响往往大于模型选择。不披露 harness 的对比结果不可信。

任何 Agent 性能对比都必须披露以下 harness 配置：

- **上下文管理策略**：如何构建、压缩、截断上下文窗口
- **工具定义**：提供了哪些工具、工具描述的措辞、参数 schema
- **错误处理**：失败后的重试策略、降级策略、熔断机制
- **验证机制**：如何判定任务完成、如何验证输出质量

并通过方差分解区分模型贡献和 harness 贡献——即回答「性能差异中有多少来自模型本身，有多少来自运行框架的配置差异」。

---

### 规则七：显式拥有提示词、上下文窗口和控制流

必须显式拥有提示词、上下文窗口和控制流。不可将它们委托给框架的默认行为。上下文窗口是 Agent 的唯一真相来源，必须主动管理。

三个必须显式拥有的维度：

1. **提示词版本化**：每次提示词变更都需记录版本号、变更原因和预期效果，便于回溯和 A/B 对比。
2. **上下文构建策略**：稳定上下文（系统指令、工具定义、角色设定）与易变上下文（对话历史、中间结果、错误信息）分离管理，避免易变信息挤占稳定信息的 token 预算。
3. **控制流边界**：明确划分哪些步骤是确定性代码（固定流程，无模型介入），哪些步骤是模型选择（模型自主决策路径），两者之间的切换点必须显式声明。

**子项：对话记忆持久化** —— 每个任务建 doc 文件夹存放用户对话记忆，作为跨会话上下文持久化机制。这确保即使对话上下文被截断或会话切换，关键决策、进度状态和用户偏好不丢失。

---

### 规则八：错误压缩为结构化观察——反馈进上下文而非仅写日志

错误必须被压缩为结构化观察并反馈进上下文窗口，而非仅写入日志。Agent 必须能从错误中学习并调整策略。

如果原始错误信息（完整堆栈、长篇日志）直接塞入上下文，会导致两个问题：

- **token 预算快速消耗**：原始错误信息动辄数百 token，多次错误后上下文窗口被挤满。
- **上下文污染**：冗长的堆栈信息干扰模型对当前任务的注意力。

正确做法：将错误压缩为简洁的结构化观察，包含两个字段：

- **失败原因**：一句话描述根因（如「API 返回 429：速率限制，当前配额已耗尽」）。
- **修正建议**：可选的调整方向（如「等待 60s 后重试，或切换至备用 endpoint」）。

让 Agent 据此调整策略而非简单重试——重试同一请求大概率得到同一错误，只有策略调整才能突破。

---

### 规则九：Agent 健康检查三级探针——超越「是否存活」

Agent 健康检查必须超越「是否存活」，增加「是否在前进」和「产出是否正确」两级探针。

一个常见的失败模式是：**高活跃度 + 零进度 = 卡死**。Agent 仍在不断调用工具、产生日志、消耗 token，但实际上没有任何有效产出——它在原地打转。仅靠「是否存活」（进程是否运行、是否在产出日志）检测不到这种卡死。

三级探针设计：

- **L1 存活** —— 检测内容：进程是否运行 —— 判定标准：心跳信号存在 —— 来源概念：Kubernetes liveness
- **L2 前进** —— 检测内容：是否产出有效进展 —— 判定标准：域特定进度指标递增 —— 来源概念：Kubernetes readiness
- **L3 正确** —— 检测内容：产出是否符合预期 —— 判定标准：通过率/质量分数达标 —— 来源概念：Kubernetes startup

L2 进度指标需要域特定设计：测试通过率、已修改文件数、已抓取唯一 URL 数等。同时需要最近动作去重检测——如果最近 N 次动作完全相同，触发进度停滞告警。

---

### 规则十一：爆炸半径与回滚——任务开始前界定影响范围

Agent 失败的影响范围不仅包括输出，还包括失败前积累的所有副作用。必须在任务开始前界定爆炸半径，并设计回滚策略。

传统软件失败通常影响局部——一个函数抛异常，调用方捕获即可。但 Agent 失败时可能已经：

- 写入了数据库（创建/修改/删除了记录）
- 发送了邮件或通知（不可撤回的外部通信）
- 执行了代码（可能产生了文件变更或系统配置修改）
- 触发了下游系统（调用链已被启动，下游可能已产生自己的副作用）

这些副作用在失败被检测之前已经发生，且部分不可逆。因此必须在任务开始前：

1. **界定爆炸半径**：列出本次任务可能产生的所有副作用类型和影响范围。
2. **设计回滚策略**：对每个副作用类型，定义回滚或补偿操作（如事务回滚、补偿事务、手动回滚清单）。
3. **优先执行可逆操作**：将不可逆操作（发送邮件、外部通知）推迟到所有可逆操作完成并验证之后。

---

### 规则十三：Agent 调试可行性——小而专注的子 Agent

Agent 的调试可行性与其范围成反比。Agent 越大越难调试。每个 Agent 应聚焦于一个可独立验证的任务域。

将大任务拆分为小而专注的子 Agent，每个子 Agent 有明确的输入/输出契约和独立的验证条件，便于隔离调试和独立回归。

「小而专注」的具体含义：

- **单一职责**：一个子 Agent 只负责一个任务域（如「数据提取」「格式校验」「结果汇总」各为独立 Agent）。
- **显式契约**：输入/输出的 schema 必须明确定义，子 Agent 之间通过契约交互而非隐式共享状态。
- **独立验证**：每个子 Agent 有自己的验证条件和回归测试集，可以独立运行和验证，不需要启动整个系统。
- **隔离调试**：当某个环节出问题时，可以单独运行该子 Agent，用已知输入复现问题，而非在整条链路中追踪。

---

### 规则十五：递归自增长——重复问题必须沉淀为新规则

任何一次自我纠偏、错误记录或事后复盘发生后，必须先执行查重：检索既有规则库和对话记忆，判断当前问题是否与过去已出现过的问题重复或高度相似。

- 如果是首次出现的问题 -> 正常修复并记录。
- 如果是重复出现的问题（第二次或以上）-> 不能只做修复，必须额外执行「规则化」动作：将问题的根因、纠偏方式提炼为一条新规则，写入规则库（TRAE user_rules 目录），并标注来源（由哪次重复问题触发、关联的原始记录）。

这样做的原因是：同一个问题出现两次，说明现有规则集存在盲区；出现三次，说明缺少约束已成系统。每次重复问题不被固化，就是在积累技术债。规则集必须在实践中递归自增长——不是等用户逐条发现和编写规则，而是通过「问题->查重->规则化」的闭环自动补全。

简言之：纠偏先查重，重复必沉淀；同一个坑踩两次，就该立规矩。

---

### 规则十六：局部否定不等同全局否定——禁止因局部失败而全局否决

当某个方案、工具、流程或功能在特定场景下出现失败或不符合预期时，不得直接将这个「局部否定」升级为「全局否定」——即不能因为一处不通过就判定整个方案不可行、整条路径走不通、或整体能力不具备。

- 局部否定 = 在特定条件、特定输入、特定环节上不成立
- 全局否定 = 在所有条件下都不成立

正确的做法是：

1. 明确否定的作用域——是哪个具体场景、哪个输入、哪个环节出了问题？
2. 查找否定的触发条件——是什么前提导致了失败？换一个条件是否仍然失败？
3. 对作用域之外的部分保持开放——未被否定的部分应继续验证、继续使用。
4. 如果需要推广否定结论，必须通过多场景回归验证，而非单点推断。

常见的违反场景：

- 某工具在一个版本上报错 -> 判定「这个工具不能用」（实际只是该版本的 bug）
- 某方案在一种数据规模下超时 -> 判定「这个方案不可行」（实际只是未做分页）
- 某模型在一个 prompt 下输出质量差 -> 判定「这个模型不行」（实际只是 prompt 未优化）

这条与规则一（判据回归）呼应：规则一说「正控通过 != 判据正确」，规则十六补充说「反例出现 != 全局错误」。两者合在一起——既不能因正向通过就放心，也不能因反向不通过就全盘推翻。

简言之：一处不通过只否定一处，要全局否决必须全局验证；局部失败->缩小作用域->定位根因，而不是一刀切地扔掉整个方案。

### 规则十八：AI 断言真实性——批判性自检与证据锚定

根因：AI 的断言（「已实现」「已修复」「方案可行」）本质是 next-token 预测——模型没有「我不知道」的内部开关。置信度与正确性是解耦的，最自信的断言仍可能是幻觉。模型甚至「知道」自己对不对（隐藏状态编码了正确性信号），但不在输出层面利用这一知识。

必须遵守：

1. **生成与验证分离**：AI 输出断言性结论前，必须执行一轮独立验证——验证 prompt 聚焦于「证据是否支撑」而非「结论是否合理」。验证步骤不得参考初始生成结果（防止确认偏差）。即使同一模型执行，也必须用不同 prompt 和更低温度参数。

2. **断言附证据指针**：每一个事实性断言必须附带证据指针——指向具体来源（工具返回、检索段落、数据库记录）。无证据指针的断言不得输出，或必须标注「未验证」。证据与声明之间的蕴含关系必须可验证，禁止仅靠 LLM-as-judge。

3. **声称不是事实**：每个 LLM 输出是假设，不是事实。系统数据流必须编码这一原则——模型输出经独立验证阶段后才到达终端用户。AI 的「完成了」断言不得作为完成证据，必须由独立验证器检查受影响系统的实际状态。

4. **验证器投资优先于生成器**：一个能抓住 95% 错误的验证器比减少 5% 错误的生成器 ROI 更高。验证器必须比 agent 简单——用确定性代码而非 ML 模型做验证，与 agent 共享 bug 的概率最低。在数据库/基础设施层面阻止无证据的「完成」断言。

5. **混合验证策略**：模型验证用于语义/上下文正确性（模糊的、判断性的），确定性验证用于硬约束（数值、格式、合规规则）。不要用 LLM 做可以用正则/校验和做的事。可执行声明（计算结果、代码输出）必须通过运行验证。

6. **自我验证是预检不是判决**：自我反思（Self-Refine/Reflexion）在等成本下不如独立重复采样。自我批判是第一道过滤器，不是最终裁判——必须与外部工具验证或人工审核配合使用。

口诀：声称不是事实，效果不是承诺；生成与验证分离，验证器比生成器简单比强大更重要；无证据不断言，无定义不委托。

### 规则十九：反偷懒约束——禁止部分完成与取巧路径

根因：LLM 偷懒的根因是 RLHF 训练中的简洁偏见——人类评分者在分钟级窗口内无法检测遗漏，导致「看起来完整」被奖励。「完成」是 token 预测而非状态断言——agent 说「done」是生成一个看起来像完成工作的对话的最可能延续，不是在报告仓库状态。reward hacking 会泛化——允许 agent 在一个任务上取巧，这种模式可能扩散到其他领域。

必须遵守：

1. **「完成」是检查不是目标**：done 必须定义为可执行的验证条件（命令退出 0、计数对账、文件存在于该路径），而非「finish the migration」这样的模糊目标。写不下验证条件的任务不可委托给 agent 自动完成。

2. **验证标准写在执行前**：分解任务时同时为每个子任务定义验证函数（验收标准写在执行前，不是执行后）。承诺创建时即定义验证查询——写不下验证查询的承诺标记为 unverifiable，永远不进入 fulfilled 管道。

3. **actor 与 verifier 物理分离**：agent 不给自己的工作打分。状态字段只由独立验证器的返回值写入，模型的自述是假设而非事实。模型关于自己工作的句子是假设（有时是假的），不能写入状态字段。

4. **禁止部分完成声明**：处理了 412 条中的 12 条不能声称 done。禁止占位符模式（// ...、for brevity、and so on、you would then...）为硬失败。输出前做交付物计数交叉检查——交付物计数必须等于请求计数。

5. **逐步验证链**：多步推理中每步完成后立即验证该步骤，而非等全部完成。错误累积是指数级的（10步 x 95% = 60%）。验证粒度自适应——形式化任务用原子步骤级，自然语言用段落级。结构化步骤级反馈（「第N步与第N-1步矛盾」）比整体反馈更有效。

6. **错误必须保持为状态而非内容**：工具执行失败时返回 { status: "failed", error: ... } 而非把错误消息塞进 result 字段——外层结构必须区分成功与失败。错误变成了内容会导致失败被当作成功。

7. **要求原始输出而非摘要**：「show the exact command, unedited output, and exit code」。摘要可以生成，失败堆栈不能。未编辑的输出要求能杀死「未运行命令」模式。在干净 shell 中重跑——全新终端、仓库根目录、没有 agent 会话设置的环境。

8. **检查分辨率必须能拒绝「最懒制品」**：发布检查前先问「满足这个检查的最懒制品长什么样？」——一个只数输出记录数的门控能通过 500 条错误记录。计数不是对账。如果不可接受那个制品，检查分辨率就不够。

9. **重试设预算不设无限循环**：同一失败到达两次=停止/升级信号，而非无限重提交。将必跑检查移入 hooks——hooks 是确定性的，CLAUDE.md 是建议性的。承受不起被忽略的规则属于 hook。

10. **零容忍取巧**：reward hacking 会泛化——允许 agent 在一个任务上取巧，这种行为模式可能扩散到完全无关的领域。测试用例对 agent 不可见或不可编辑。不给模型「放弃」的捷径——明确禁止利用环境特定特征取巧，但要知道这只降低不完全消除，需要多层防护。

口诀：完成是检查不是目标；actor 不自评，verifier 必独立；交付物计数必须等于请求计数；检查分辨率要能拒绝最懒制品；零容忍取巧——取巧会泛化。

### 规则二十：写操作与观测必须分离——「脚本崩了」绝不等于「没写」

当脚本内部**既有写操作、又有对写结果的解析**时，只要解析阶段抛异常，整个脚本会报「失败」，而**远端/下游的写入可能已经完成**。此时如果按「失败了 -> 什么都没干」去处置，就会犯两类错：

- 直接重跑同一个写脚本（守卫可能拒绝，或更糟——**重复写**）；
- 或者去查「为什么写失败」，而实际上写是成功的，白查一轮。

必须遵守：

1. **写脚本要能自证「到底写没写」**：写完后立刻输出一个**回执哨兵**（如 `A@@<行数>`），并让判据**先看哨兵再看别的**；哨兵缺失就说明「没跑完/通道断了」，而不是「业务没变」。
2. **脚本崩了 -> 第一动作是「独立只读核对现状」，不是重跑**。核对必须覆盖两个方向：
   - **该变的变了**（目标行数/内容到位）；
   - **不该变的没变**（其余数据一字未动、总数不变、键集合不变）。
3. **解析失败不得掩盖写入**：解析类判据要能区分「空/未收到」与「报错」，并在为空时**把原始输出打出来**（psql 的 ERROR 走 stderr，只读 stdout 会得到「静默为空」）。
4. **不要让「哨兵」与「不定长数据」落在同一行**：`base64 -w0` 不换行，若其后紧跟哨兵，会把哨兵与数据粘在一行，按「整行丢弃」处理时会**连数据一起丢**。要显式换行分隔，或「去哨兵」而不是「丢整行」。
5. **报告/证据先落盘、再断言**：把证据写在断言之后，等于断言一失败就把证据藏起来（这是本条最容易犯的变体）。
6. **写操作前界定爆炸半径并提供回滚依据**（键清单/原值/备份），因为「崩了」的时刻往往正是你最需要回滚的时刻。

为什么必须单独成条：本项目已出现 2 次同类事故——

- 2026-09-25 `f121`：`--dry` 分支实际执行了 UPDATE（4 名员工被停用），而首次运行在 **Python 解析阶段**崩溃（`metadata::text` 含逗号致列数不符），**把这次写入掩盖了**；
- 2026-09-28 `f152`：远端脚本已把 203 行写进生产，但本地解析「写前备份」块时因「哨兵与 base64 同行被整行丢弃」而抛异常 -> 表面上「失败、没写」，实际**写了**。

第 2 次出现即按规则十五规则化。**核心口诀：先确认「到底写没写」，再决定「要不要重跑」。**

### 规则二十一：判据不得退化成「恒为常量」——聚合必须显式指定数据源，反例要一条判据配一条，并加自洽性交叉校验

一条判据如果**在任何数据下都返回同一个值**，它就不再是判据。这类缺陷**不报错、不打日志、只给出一个错的数字**，而且常常能骗过「随手写的那条反例」。

必须遵守：

1. **SQL 聚合必须显式写出数据源**。`SELECT count(*)` **不带 `FROM`** 在 PostgreSQL 里是**合法**语法，它数的是「隐含的那一行」-> **恒等于 1**。凡 `count(*)` / `sum()` / `max()` / `min()` 这类聚合，必须紧跟 `FROM <表或子查询>`；`WHERE` 同样不得悬空。

2. **反例要「一条判据配一条」**。只写一条反例，只能证明「那条反例涉及的地方是活的」，**不能证明整组判据都活着**。每组判据都要有**它自己**的违例样本，并且必须确认该样本能让**这一条**判据变成非期望值。

3. **加自洽性交叉校验**（两个「必然相等」的量互相印证）。例如：
   - `count(*)` 必须等于 `max(rank) - min(rank) + 1`；
   - 明细合计必须等于单头金额；
   - 分段之和必须等于总量。
   **一旦某条判据退化，这个等式会立刻不成立**，从而把缺陷暴露出来。

4. **不要相信「看起来合理的数」**：看到「数小得离谱 / 大得离谱 / 与相邻字段矛盾」，**当场停下查判据**，而不是先怀疑数据。

5. **分桶类判据必须处理 `NULL`**（SQL 三值逻辑）。用 `col NOT LIKE 'x'` / `col <> 'x'` / `col NOT IN (...)` 做**排除型分桶**时，`NULL` 的行**两个桶都不进** -> 分桶**漏项**，而「比对一个桶」会因此退化成**两个空集相比** -> **恒判为「相同/通过」**。
   - 正确写法：`col IS NULL OR col NOT LIKE 'x'`；
   - 并且**必配**一条自洽性校验：`总行数 == 各桶行数之和`（漏项会当场打脸）；
   - 这条与第 1 条同源：都是「判据在某种数据下恒定」，只不过这里是**被 NULL 掏空**。

来源（同类反复出现，按规则十五规则化）：

- 2026-09-28 `debug/f215_s4_postcheck_deploy.py`：首版写成 `SELECT 'f@@' || count(*) || '@@' || ...` **没有 `FROM`** -> 恒返回 **1**；同一行 `max(installed_rank)` 却是 **97**，正是这个**自相矛盾**才暴露了 bug。当时那条 `version='999' -> 0 行` 的反例**是通过的** -> 证明「随手写一条反例」防不住这类缺陷。
- 2026-09-28 `debug/f231_s6_m2m5_prepare.py`（S6-0 施工前只读勘察）：用 `remark NOT LIKE 'M2:auto:%'` 去数「SEED 行」，而 SEED 行的 `remark` 恰好是 **NULL** -> 那 426 行**两个桶都不进**，于是「本地 SEED 指纹 vs 生产 SEED 指纹」实际是**两个空集相比**，却输出「**完全相同 -> SEED 不需要导入**」。靠「本地 `总行 5,677` != `M2 5,251` + `非M2 0`（差 426）」这个**数字对不上**才暴露（正对应第 4 条）。修法：`remark IS NULL OR remark NOT LIKE ...` + 自洽性 `总行 == M2 行 + SEED 行`。修好后 `5,677 == 5,251 + 426` PASS，两侧指纹 `5703b2a7...` 才**有资格**说相同。
- 同族既有记录：`'{P}-%'` 漏 `.format()` 致判据「全绿但什么都没查」（M7）；`G@@so@@21909` 取值错位（`f147`，规则十九）；`f153` 指纹块因单参数超 Linux 128KB 上限而**静默为空**（规则二十）。

口诀：**判据若在任何数据下都给同一个值，它就不是判据；分桶前先问一句「NULL 去哪了」。**

### 规则二十二（扩写版）：凡把「含中文的文案」当字符串传的载体，内层强调一律用中文引号「」『』，禁用 ASCII 双引号

根因：ASCII `"` 会**提前闭合并切断**正在解析的那个字面量/实参——在源码里它提前闭合字符串字面量；在命令行里它提前终结这个实参。而报错**永远不指向「引号类型」**：Python 指向「那一行」（`SyntaxError: invalid syntax. Perhaps you forgot a comma?`）、shell 指向被切出来的碎片（git 报 `error: pathspec 'CHARACTER' did not match any file(s) known to git`）-> 每次都要重新认一遍，纯浪费时间。命令行载体还多一层危险：失败与成功日志**混在同一段输出**里（前置检查/门禁照常打印「放行」），只有退出码能定性 -> 极易被误读成「成功」。

必须遵守：

1. **载体清单（全部适用，不止 Python）**：
   - 源码字符串字面量（Python / JS / Java 等，含 `f"..."`、`%` 格式化、`str.format()`、三引号）；
   - **命令行 inline 实参**（`git commit -m`、`git commit -F` 之外的各种 `-m`/`-e`/`-c`，如 `python -c`、`psql -c`、`bash -c`）；
   - 结构化配置里的字符串字面量（YAML / JSON / TOML / .env）；
   - 任何「把中文塞进一行参数」的地方。

2. 内层需要强调或引用时，一律用 `「」` / `『』`；**不得**用 ASCII `"`，也不要用 ASCII `'` 去凑（它会与 shell 自身的引号规则打架）。

3. **唯一例外**：字面量本身是**纯 ASCII 且不含中文**时才可以用 ASCII 引号（例：`grep -E 'PgFlyway|ERROR'`）。

4. **含中文的长文案，最稳做法是「先落文件、再引用」**：写成 UTF-8 文件后用 `-F` / `--file` 传入，彻底绕开 shell 的引号解析。子坑：`git commit -F '..\x.txt'` 这种**相对路径 git 读不到**（`fatal: could not read log file`），必须用**绝对路径 + 正斜杠**（`c:/.../x.txt`）。同时遵守本仓既有规范：脚本正文纯 ASCII、中文放独立 UTF-8 数据文件。

5. **命令行场景必须看退出码**：`COMMIT_EXIT != 0` 才是结论；同一段输出里的成功日志（如 `[门禁] ... 放行`、`BUILD SUCCESSFUL` 之外的普通日志）**不得**当作成功证据（与规则二十同源：退出码/哨兵不单独承担结论，但**更不能用日志代替退出码**）。

来源（同类第 3 次出现，按规则十五规则化；本条为第 2 次规则化后的再次扩写）：

- `debug/f160_s4_pending_migrations.py`：`emit("... V136 的"已应用"状态")` -> `SyntaxError`（同类第 1 次，载体 = Python 源码）；
- `debug/f213_v136_selfcheck_counterexample.py`：`emit("... 三条判据都"带电"。")` -> 同类错误，**同一轮内第 2 次** -> 首次规则化（当时只覆盖 Python 载体）；
- **2026-10-08 提交 `5b894c2` 现场（载体扩到命令行）**：`git commit -m '... "ai_agent_id CHARACTER VARYING(36)" ...'` -> PowerShell 提前闭合、把半句切出，git 将碎片当作 pathspec（`error: pathspec 'CHARACTER' did not match any file(s) known to git` / `'VARYING(36): ...'`），`COMMIT_EXIT=1`；而**同一段输出里 `[门禁] ... 放行` 照常打印** -> 险些被读成「提交成功」。改用「UTF-8 文件 + `-F` 绝对路径」后一次通过。

口诀：**中文文案进字符串，内层引号用「」；长文案落文件走 `-F`，命令行只认退出码。**

来源：由规则二十二（Python 版）+ 2026-10-08 命令行载体复现合并扩写；已按规则十五登记（详见 project_memory 第 254 条）。

### 规则二十三：写脚本里的「只读取证」不得与「写事务」放在同一次调用里——否则一个只读语句的拼写错误会让你把「已提交的写入」读成「没写」

根因：当一个 `psql -f` 文件里**既有写事务、又有 `COMMIT` 之后的只读取证**时，**任何一处 SQL 报错都会让退出码非 0**，而「退出码非 0」极易被笼统读作「整个事务回滚了、什么都没变」。但这个读法只在「`COMMIT` 是文件里最后一条写语句」时成立——一旦报错发生在 `COMMIT` **之后**，**写入已经生效**，结论正好相反。

必须遵守：

1. **物理分开**：写事务（`BEGIN ... COMMIT`）与只读取证（验证读数、异常清单导出、快照比对）**分成两次独立的调用**。写调用只负责「写 + 事务内守卫」，取证调用只负责「读」。只有分开后，「写调用的退出码」才有唯一含义。

2. **退出码不得单独承担结论**：即使已经分开，脚本也**不得**打印「退出码非 0 -> 生产未被改变」这类断言。正确文案是「**不能据此断定没写**；本文件里 `COMMIT` 在中途，错误若发生在 `COMMIT` 之后则写入**已经生效**」，并指明「下一步用独立只读脚本核对」。

3. **崩了先核对，不重跑**（与规则二十一致）：第一动作是**独立只读核对现状**，覆盖两个方向——「该变的变了」+「不该变的没变」。重跑写脚本会撞前置守卫（本次守卫要求目标表为空），或更糟——重复写。

4. **证据可以只读重算**：只读取证块没跑出来，不等于证据丢了——只要它是**从基础表重算**得出的（本次异常清单就是从 `inbound_orders`/`inbound_items`/`items` 重算），就再用一个只读脚本算一遍，并落盘。

5. **不隐藏证据**：非 0 退出时，把**已经产生的每一个块的原始输出都打印出来**，而不是只打印 `ERROR` 行。

来源（同类第 3 次，按规则十五规则化）：

- 2026-09-25 `debug/f121`：`--dry` 分支实际执行了 `UPDATE`（4 名员工被停用），而首次运行在 **Python 解析阶段**崩溃（`metadata::text` 含逗号致列数不符），把这次写入掩盖了；
- 2026-09-28 `debug/f152`：远端脚本已把 203 行写进生产，本地解析「写前备份」块时因「哨兵与 `base64 -w0` 同行被整行丢弃」而抛异常 -> 表面「失败、没写」，实际**写了**；
- 2026-09-28 `debug/f226_s6_m1_prod.py`（M1 生产执行）：一次会话一个文件里 `COMMIT` 在中途，最后的「异常清单导出」块把 `m1_exc.raw_qty` **写成 `qty`** -> 退出码 **3**；脚本却打印「事务没有提交 -> 生产未被改变」。**事实相反**——守卫 NOTICE（`stage_qty=119191.00 = inv_qty = led_qty`、`inv_rows=1523=grp`、`led_rows=8031=inc`、`src_sum=8627`、`bal_bad=0`、`chain_bad=0`）已证明**事务走完并提交**。处置：修列名 + **不重跑** + 另写 `debug/f227_s6_m1_postcheck.py` 独立只读核对（**26/26 全过**）+ **只读重算**出异常清单（**459 条**，证据未丢）。

口诀：**写调用只管写，取证调用只管读；退出码非 0 先核对，绝不当「没写」。**

## 第五部分：工作习惯规则

本部分涵盖日常工作中应遵守的操作习惯——资源管理、需求确认、任务跟踪。

---

### 习惯A：资源节约——安装前先搜索本地

安装任何工具之前，先全面搜索本地是否已经有，不要一上来就在每个路径安装独立的新工具。能调用能映射能标记打通的都不要浪费资源。

---

### 习惯B：需求确认与反查记忆——先梳理再干活

1. 每个任务都建一个 doc 文件夹存放用户对话记忆。
2. 收到任何用户需求（包括但不限于：新开发、旧任务、迭代、更新、修复、修改等）的时候，先建立 .md 文档把用户的话清晰重新梳理一遍，发给用户，让用户确认才开始真的干活。
3. 每次用户让你回忆搜搜聊天记录的时候，反查对话记忆，找到关联询问用户。

---

### 习惯C：总结报告与 todos——逐个完成，不跳步

1. 确保每个任务完成后形成总结报告 .md 格式文档，主动给出下一步的行动建议。
2. 确保把每次的计划都形成 todos。
3. 确保每个任务逐个完成。
4. 确保不为了节省时间或者任何便捷理由而跳过任务、绕过任务、不主动给出这类型的建议。

用户没有代码基础，但是可以理解很多概念，有一定的氛围编程的工程经验，沟通的时候，复杂项目和逻辑，尽量用比喻来加以说明，让用户更快速、准确理解和回应。
