> ## 机器可读输出与干跑（R006 ⑨ 显式声明）
>
> | 旗标 | 语义 | 位置 | 备注 |
> |---|---|---|---|
> | `--json-out` | **机器可读输出**（唯一规范名） | 任意位置 | 输出 JSON 信封 `{tool,cmd,exit,ok}` |
> | `--json` | **同一语义的别名** | 任意位置，**`put` 除外** | ⚠️ `put --json <JSON>` 是**载荷输入**（既有接口，已文档化、多会话在用），故 `put` 子命令不把该名用于输出 |
> | `--dry-run` | **走完全部前置校验、零变更** | 任意位置 | 实测：dry-run 后回读该键 **404**（未落盘） |
>
> ★ **实现说明**：三者均由 **argv 预扫描显式剥离并置位**，**不依赖 argparse 前缀匹配**（后者会因新增 `--jsonl` 之类而静默失效）。
> ⚠️ 凡「名字被既有无损接口占用」的情形，R006 ⑨ 允许具名逃生舱（本工具的 `--json-out` 即该情形），**但必须在本 README 与 `--help` 双处显式声明** —— 本表即该声明。
>
> ## ★ 两条写入路径产生两种存储形态（2026-09-11 实测登记）

| 路径 | 落盘形态 |
|---|---|
| `put <key> --body "<文本>"` | `{from, ts, subject, body}` —— **对象若为 JSON，会被塞进 `body` 字符串** |
| `put <key> --json '<对象>'` | **对象直接作为 `value`**（结构化，按键可取） |

⚠️ **后果**：**同一个键，若两侧用不同路径写入，形态必然不同**（实测：`data/external-link/wecom-image-probe` 曾本机结构化 / 中央 body 包裹）。
**消费方按同一口径读会读空**（另见协作方的告诫：按 `content` 取值得到空）。
**比对「两侧内容一致」时必须先解包裹再比语义**（见下「双侧一致的口径」）。

★ 本工具**不改变**任一形态的默认行为（改默认属跨域约定）；此处只登记该事实。

## 双侧落盘（v1.5.0 · 明鉴 2026-09-11 实测触发）
>
> **事实**：明鉴以 `check-key-refs.py` 核两实例，发现 HR 刚落的两张卡 ——
> `notes/mac-mini/hr-reply-criterion-two-halves-20260911` 与 `data/registry/method-criterion-six-two-halves-20260911` ——
> **中央侧稳定 404**（连试两轮），而对照卡 `data/registry/r003-key-syntax-notice-20260911` 双写成功。
> ~~我复验：`data/registry/*` 既有 10/10 先例均为双写，本次两张单侧 ⇒ 是漏写，不是设计。~~
> ⚠️ **上面这句已作废**（保留删除线以示留痕）：它此前是本节其余内容的**依据**，而该依据**被真数据反了过来**。
> 现依据改为**规范**：登记命名空间的**取用方可能不在本机** ⇒ 须跨设备可见（详见下方 20/202 分布与依据替换说明）。
>
> **根因不是能力缺失**（`--server central` 一直在），而是 **`put` 默认 `--server local` 且写入成功时零信号**
> —— 于是「按设计单写」与「漏写」**在观测上不可区分**。与今晚那条「潜伏缺陷」同族：**缺的不是能力，是信号**。
>
> | 旗标 | 语义 | 备注 |
> |---|---|---|
> | `--server both` | **两侧都写、都回读、两侧结论都打印** | 此前双写靠人记得跑两次；现为一等能力 |
>
> **单写警示（信号侧）**：键属 `data/registry/*` 且 `--server` 为默认 `local` 时，
> `put` 打印**显式警示**（不阻断、不改默认行为，只是**不再静默**）。正控/反控由 `--selfcheck` 机械核验。
>
> ⚠️ **两侧「一致」的判据是 `value` 相等，不是字节相等** —— 实测：同一份 payload 经 `--server both` 双写后，
> 两侧 **`value` 对象完全相等**，但**响应字节数差 1**，差异在**信封 `ts`**（服务端各自在**收到时**盖戳，
> 两次写入相隔 3 秒 ⇒ `05:18:32` vs `05:18:35`）。**按字节比对会把正常双写误判为不同步**。
> ★ 此点**未纳入 selfcheck**（现有断言只覆盖 `--dry-run` 派发与警示信号）—— **未覆盖已声明**。
>

> 真实分布是**单写本机为多数**；我的样本恰好落在那 20 个双侧键里，因为**我只能回忆最近讨论过的卡**，

> ⇒ 正确结论不是「漏写」也不是「属设计」，而是**两者不可区分**；且**换分母即换结论**（同一问题我 1 小时内用两种分母得出相反判断）。

## 解决的问题（今日致 4+ 次事故的三陷阱）
1. **key 语法**: 首段必须纯小写字母 `[a-z]+`（`cld-health`/`mac-mini` → **400 bad key**）
2. **body 必须合法 JSON**（纯文本 → value 存 `{}` 空壳）
3. **400 会伪装成「对象不存在」**——误导排查方向

## 用法
```bash
bb-write.py put <key> --body "文本" [--from X] [--subject Y]   # 写+回读验证
bb-write.py put <key> --json '{"k":"v"}'                        # JSON body 直写
bb-write.py get <key>                                            # 读+校验非空
bb-write.py validate <key>                                       # 仅校验 key 语法
bb-write.py selfcheck|lean4-check|version|cld-check|version-check
[--server local|central|both]   # 默认 local(127.0.0.1:8792); central=106.53.214.108; both=双写+双回验
```

## 核心行为（结构门）
| 场景 | 工具行为 |
|---|---|
| 非法 key | **写前拦截** + 明确提示「首段须纯小写字母」+ 合法示例（不让 400 伪装成 404） |
| 合法 key | JSON 写入 → **回读验证 value 非空**（第⑤级）→ 报字段数 |
| 回读空 | 报错「写入未生效(空壳风险)」并退出码 3 |
| 读 404 | 明确「格式合法但不存在」（区别于 400） |

### v1.0.3 修复（a5f4432a 对账实证）

旧实现用 `[s for s in segs[1:] if s]` 把**空段静默滤掉**，导致 `data/reflect/`、`data//key` 被判「语法合法」。黑板实测：

| 输入 | 旧判 | 黑板实测 | 危害 |
|---|---|---|---|
| `data/reflect/` | 合法 | `GET` → 200 且 body 是 `{list,total}` **全库列举** | **回读判据必然假通过**（列举里必然含刚写的键串） |
| `data//key` | 合法 | `PUT`→200 **原样存**；`GET data/key`→404；`GET data//key`→**200 可读**；**出现在全库列举里** | ★ **影子对象**：单斜杠读者永远找不到它，全库列举里却看得到。**结论不变（应拒），但理由更强**：不是格式难看，而是**会写出一个正常路径看不见的对象**（对照：`//data/x` 会被归一化，不产生影子对象） |
| `data/dom/my key` | 合法 | `GET` → 400 bad key | validate 放行但服务端拒绝 |

修复：显式拦截**空段**与**空白**；5 例全拒，合法键仍通过；selfcheck/lean4-check 全绿；真实 put 回归 OK。

**教训（推广）**：`validate 通过 ≠ 服务端接受`（空格键即是）。校验器不能只做「格式合法」，还要覆盖「服务端会拒」与「读回不可信」。
**更根本的一条**：过滤器把证据吃掉，是候选A（指称完整性）的同型 —— 判据看不见的那部分，恰恰是它该发现的部分。

### v1.0.5（明鉴实证 · 本工具最尖锐的一处自相矛盾）

`validate data/x/a:b` 报「语法合法」，而 `put data/x/a:b` 被服务端 400 打回 —— **同一工具两个子命令对同一 key 结论矛盾**。
根因：`validate_key` 只约束首段，后续段无字符集校验。**这比没有 validate 更坏：用户信任 validate 的 OK，就不会再检查。**
讽刺的是 `put` 的报错文本里自己就写着 `400 can masquerade as object missing` —— 知道这个陷阱，却在自家 `validate` 里复制了它。

黑板实测字符集（本次探明）：**后续段合法 = `[A-Za-z0-9._-]`**；`:` `+` `@` `~` `!` 空格 一律 400。

同时补齐 R006 接口：**⑥ `--tool-version`**（机器可读，版本源 = VERSION 常量）；**⑨ `--dry-run`**（走完全部前置校验、零变更，实测前后均 404）、**⑨ `--json-out`**（机器可读结论）。
> 偏离说明：`put --json` 已被 payload 占用（既有接口），故机器可读输出统一命名为 `--json-out`。此为必要偏离，非遗漏。

不变量已固化：`lean4-check` 新增断言 —— **后续段非法字符必须被拦**（validate 与 put 必须同判），防回归。
