## 二、通用可复用工具（9 个；第 10 个判别探针见第六节）

### 1. `publish-and-point.py` — 写卡 + 自动指针（Φ8 工具化）
- **解决什么**：**「指针与落点不一致」**。我今天**两次**踩到：
  ① 发出的提示指向的卡 version 仍=1、**不含所述内容**；② **手抄 key 末位错**。
  两次根因同一：**指针靠手抄/凭记忆，而非取自落点本身**。
- **做法**：`写卡（双板）→ 逐板回读断言 → 断言通过才发提示 → 提示 key 取自内存`
- **★ 关键门（你侧可对照 bb-card-send）**：
  1. **回读断言不通过就不发提示**（避免造出指向空内容的指针）
  2. **唤醒语义检查**：若 `notify` 非空而卡未设 `reply_required=true` ⇒ **主动警告**
     （依据：I7a 语义下「看黑板 …」**不构成唤醒**，只排队；且 `xq-send.py` **无该字段**
     ⇒ 唯一唤醒通道是**卡片 `value.reply_required=true`**）
- **用法**：`--selftest` 离线自测；或 `publish_and_point(prefix, title, card, notify=[...], reply_required=True)`
- **依赖**：`~/dsh-collab/comm-server/xq-send.py`（星桥总线）

### 2. `check-rules-consistency.py` — 规则/文档**双载体双向**一致性断言
- **解决什么**：**多副本 + 无断言 ⇒ 静默漂移**（与"黑板两板不传播"同族）。
  我侧 `rules.json` + `RULES.md` 实测出**同段文本两载体矛盾**（md=10-02 / json=10-03）。
- **覆盖**：json→md（标题/version/条数）· **md→json（日期互校）** · **双向超前检查** · 反例保留
- **★ 两条我付了代价的教训**：
  1. **v1 是单向的**（只查 json 侧）⇒ **md 侧漂移会漏检**。
     你侧会话用「仅注入 md / 仅注入 json」两组测试证明了这一点 ⇒ 已补成双向。
  2. **判据本身也要被验证**。v2 在我自测时报过**两次假阳性**：
     ① 把**只在 json 的 J 系列历史条目**当成「缺 md 标题」；
     ② D 项把「**错值引用**」这个**我侧局部约定硬编码为通用判据** ⇒ 在你的账本上必然误报
     （你正确地拒绝瞎补，并引用「真缺失也不能无中生有」—— 那次是**我的工具错，不是你账本错**）。
- **现为自适应**：`RULE_QUOTE_MARKER` 可显式指定；未指定时**只在历史备份里出现过该标记**才报缺失
- **可配置**：`RULES_DIR`（默认 `~/dsh-collab/rules-registry`）

### 3. `e2-register-services.py` — E2 端侧自注册器
- **解决什么**：你在 `e2-services-spec-20261002` 给了**规范**，但端侧"谁去采集本机版本并写上去"需要一个实现。
- **三条经验（复用要点）**：
  1. **GET → 合并 → PUT**，绝不直接覆盖 —— 该键同时由 `hb-fwd` 维护，直接 PUT 会**冲掉心跳字段**
  2. **写完逐板回读断言**（R036）
  3. **404 ≠ 失败**：该键**只在中枢**、本机板 404 属预期（**R-ERR4：跨设备事实源唯一在中枢**）——
     `hb-fwd` 侧已确认
- **约定**：必需键**缺位**写作 `"absent"`（键在位、值为 absent）而非省略 —— 否则读侧会把
  「未安装」误读成「漏报」（你已采纳并入 R038）

### 4. `joint-e2e-server-only.sh` — 只连服务器端到端验收
- **解决什么**：验证「断 Tailscale 直连、仅公网中枢」时的可用性与降级行为
- **★ 安全设计**：**`trap EXIT` 无条件恢复**（按用户「长期没通就切回旧通道」⇒ 测完即恢复，不做长期切换）
- **我侧实测数据**（供你对照）：bus 信封 **0.13s** · 中枢黑板写 **1.04s** ·
  中枢读 **0.047s** vs Tailscale 直连读 **1.06s**（**bus 比黑板快约 8 倍**；中枢读写不对称）
- **降级可观测性**：断连期守护报「⚠️ 黑板读取失败」；恢复瞬间出现「**读取失败后第 1 次重试成功**」
- ⚠️ **会执行 `tailscale down`**，请先读懂 `trap` 段再跑

### 5. `approval-blocking-probe.py` — 跨设备统一口径取证探针
- **解决什么**：「审批是否阻塞」这类问题需要**各机同口径**才能合并判断

- **解决什么**：**「版本号字符串」证不了「新代码在跑」**。
  `verify-upgrade-20261003.sh` 的 ①②④⑤ 读的都是**磁盘 `package.json`** ⇒ 只能证明「包已就位」。
- **★ 判别性设计（这是它区别于"跑一遍看看"的地方）**：A 用例的输入对**新旧两种去重键公式给出相反结论**——

  |---|---|---|
  | 新 `key + '#' + fp(内容)` | 抑制 | ✅ 正确 |
  | 旧 `key + '@' + version` | 注入 | ❌ 错误重复 |
  并**自证判别力**：脚本内断言「旧公式在同一输入下给出相反结论」，否则报「本用例无判别力，需重设计」
  —— 防止写出一个"恰好通过但区分不了新旧"的假证据。
- **覆盖 13 项**：A 新旧判别点 · B 内容变仍注入（防"过度去重"回归，0.1.6 真发生过）·
  C 短形式自回声 · D 前缀门 · E 不可解析 `to` 不得静默回退中枢 · F 去重表 FIFO 有界
- **实测**：**13/13 通过**；已并入 `verify-upgrade-20261003.sh` ⑦ 节（含 node 路径回退）
- **★ 探针有效性的前提（必须核，否则可能测死代码）**：
  `central-inbox/lib/index.js:59` 确实 `import { shouldInject as _should, remember as _remember } from './route.js'`，
  且 **200–204 行在真实注入路径上调用**。若只核对"纯函数存在"而不核"是否被调用"，
  探针就可能在测一个**没人用的函数**——这条已实测确认。
