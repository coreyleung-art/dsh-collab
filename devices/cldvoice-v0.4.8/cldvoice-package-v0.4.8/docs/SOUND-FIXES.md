# 语音链路排错记录（SOUND-FIXES）

> 本文记录 CLD 悬浮球语音记录器从"完全没声音"到"稳定工作"的完整排错链。
> 全部问题均已在 v0.3.5 → v0.4.7 修复并实机验证。**根子在客户端/桥的音频处理，不在模型。**

## 症状演进与根因

| 版本 | 症状 | 根因 | 修复 |
|------|------|------|------|
| v0.3.4 | 完全没有声音 | ①若只看 CDP/无法 attach renderer；②面板诊断"收0KB"误导 | 加诊断面板(收KB/播次/ctx/错误) |
| v0.3.5 | 没有声音 | **base64 拼接**：每个 audio_delta 分片各自带 `=` padding，整段拼接后一次 atob 抛 `Invalid character` → 40万+ 字节静默丢弃 | **逐片解码**累积 Float32 |
| v0.3.6 | 打断叠音 | flushAi 创建 BufferSource 但不记录/停止，新旧声叠加 | 播放源追踪 + 开播前 stop + 打断发 cancel |
| v0.3.8 | "3把声音" | flushAi 按 2s 切块多 start()，分段接缝产生异音感 | **单 buffer 无缝播放** |
| v0.3.7 | 一句话4次录入/4人回 | **回声自我循环**：AI 声音被麦克风采到→模型重复回应 | (初版 micOff 送静音) |
| v0.3.9 | 偶发"只回文字没语音" | **micOff 送静音**干扰模型对用户语音判断，模型有时只回文字 | 弃用 micOff → **硬件 echoCancellation** |
| v0.4.6 | 球放大被"方框"裁切 | canvas 280(半宽140) < 最大光晕 R*1.5≈213 → 溢出裁出硬边 | canvas/box → 460(半宽230)，R 计算重调 |
| v0.4.7 | 默认声音偏小 | 播放路径无增益，音量=火山默认(偏低) | 加全局 playGain(默认1.35) + 面板"音量"滑块(30%~250%) |
| 终局 | 偶发"整轮纯文字没语音" | 火山 Seeduplex 对开场/短句偶发只回文字(audio bytes=0) | **强化 instructions"必须用语音回答"** + 兜底 TTS(用 _resp_had_audio 判, 仅真·无音频才触发) |

## 关键结论
1. **链路本身是通的**：backend→bridge→GUI 转发 405KB+ 音频/轮，实测多次。问题都在音频**处理与收发时序**。
2. **诊断面板是定位利器**：`收KB/播次/ctx状态/错误` 让"收没收到 / 播没播 / 是否被挂起 / 是否报错"一目了然，几轮就能二分定位。
3. **不要给模型喂静音**：v0.3.7 为防回声给模型送静音，实际干扰了模型对用户语音的感知，反致偶发不产语音。正确做法是**硬件 echoCancellation**，持续送真实麦克风。
4. **bridge 转发日志**：`audio_done, this-response audio bytes=N` 能立刻区分"模型没产音频" vs "桥没转发"。
5. **"偶发纯文字"= 模型行为**：火山 Seeduplex 对部分对话偶发只回文字(0 字节音频)，非我方链路 bug。缓解：①强化 instructions 促其语音；②若需 100% 有声需**独立火山 TTS 凭证**(appid+access_token)做稳定兜底。

## 排查方法论
1. 先证明**后端→桥→GUI** 是否收到音频（用诊断面板 + bridge 日志）。
2. 再证明**解码**是否成功（逐片 vs 整段 atob）。
3. 再证明**播放**是否真的出声（ctx 状态 + 是否报错）。
4. 最后才是**交互时序**（打断/回声/叠音）。

## 复用建议
任何"语音链路（WS 音频流 + 播放）"遇到无声/叠音/重复，按上面 4 步排查；尤其**避免把多段 b64 拼接后一次性 decode** 和**避免给模型喂静音**这两个坑。
