# 治理报告：脚本判定恒 true 缺陷——「无论是否报名成功都返回成功」

> 编号：GOV-2026-0901-01 | 提交：知了（学习引擎 a3bc8cba）
> 抄送：星桥（fa1f9150 协调者）/ 司库-HR（2a15e6b1）/ 明鉴（f38244df 蓝图规划师）
> 触发：老板质疑「店长查不到报名记录」→ 复查发现 8/31 教师节报名上报「5 店 applied=true」全部为虚假确认

---

## 一、缺陷描述（事实）

**脚本**：`scripts/teacherday-signup.js`（教师节活动 80125527 报名执行器）

**缺陷代码（第 51 行）**：
```js
const applied = await ev(`[...document.querySelectorAll('*')].some(e=>/80125527/.test(e.innerText||''))`);
```

**缺陷本质**：`applied` 判定 = 「页面上任意元素的文本包含活动 ID '80125527'」→ 返回 true。
而活动卡本身就**永远显示**「活动ID：80125527」→ **无论报名是否成功，判定恒为 true**。

**实际后果**（2026-08-31）：
- 上报「5 店全部报名成功」（初蘅/客村/江南西/佛山/守白）
- 实际：**5 店均未报名**（守白实测 `enterTime=0`、`enteredStatus=canApply`；老登复核 5 店卡片均仍显示「批量报名」按钮）
- 虚假结果引发后续错误决策链：履约两难评估、T-7 备战准备、确认单谈判——全部建立在「已报名」的假前提上
- 误导老板/店长/老登三方

---

## 二、根因分析

| 层 | 根因 | 说明 |
|---|---|---|
| ① 信号选择错误 | **用 UI 文本当业务状态** | 页面元素文本 ≠ 业务真实状态。活动 ID 是「页面常量」，与「报名是否成功」零相关 |
| ② 无端到端验证 | **提交动作无响应校验** | 脚本点击「提交」后未抓取报名提交 API 的响应码（成功/失败），未二次查询状态 |
| ③ 无反向用例 | **只测「有」不测「无」** | 判定逻辑从未验证「未报名时必须返回 false」这一基本反向用例 |
| ④ 无人工复核 | **执行结果直接采信** | 高险操作（跨店写）结果未经过人工/第二智能体复核即上报 |
| ⑤ 审计留痕不足 | **只记「执行了」不记「验证了」** | 审计记录报 applied=true，但无 API 响应、无状态快照作为证据 |

## 三、同类问题面（不止报名）

此缺陷模式（**「检测到 X 的存在」误当「X 已成功」**）在本项目可能扩散：

- 批量上架/下架：检测到按钮文本 ≠ 商品真的改了状态
- 改价/改库存：页面出现价格 ≠ 保存成功（弹窗确认/响应码才是）
- 平台消息提取：抓到消息容器 ≠ 消息已落库
- IM 发送：文本进入输入框 ≠ 消息已发出（需查发送 API 响应）
- 任何「点击后无断言」的自动化操作

---

## 四、避免同类问题：六项措施（可落地）

### M1. 业务状态字段权威化（信号源纠正）
- **原则**：判定成功必须使用**业务 API 的权威字段**，禁止用 UI 文本/元素存在性
- 报名判定：`getInviteList` 返回的 `enterTime > 0` 且 `enteredStatus ≠ canApply`
- 上架判定：`batchSetSellStatus` 响应 `code=0` + 复查 `sellStatus`
- **落地**：学习侧所有「执行器」判定点，从 DOM 文本改为 API 响应 + 状态复查

### M2. 端到端验证闭环（执行→断言）
- 每个写操作执行器增加**验证阶段**：提交 → 抓响应码 → 调查询 API 复查真实状态 → 全部通过才返回成功
- 验证失败 = 返回失败（不掩盖、不默认成功）

### M3. 反向用例测试（自检）
- 每个判定逻辑配**反向用例**：未执行/未成功时必须返回 false（本次缺陷若配此用例立即暴露）
- 落地：脚本 selfcheck 模式增加断言（如「活动卡存在但未报名 → applied 必须 false」）

### M4. 高险操作结果人工复核（结合 R027/R029）
- L3 操作（批量/跨店/写）执行后，结果上报前须经**第二智能体或人工复核**
- 复核 = 独立查询状态（不信任执行器自报），与 R027 人类授权、R029 原语锁形成「授权→执行→验证→复核」四段闭环

### M5. 审计留痕含证据
- 审计记录增加**证据字段**：API 响应体、状态快照、enterTime 等
- 本次缺陷即因审计无证据而未被察觉；有证据可 8/31 当天即发现

### M6. 固化核查技能/原语
- 报名状态核查已学习完成（黑板 `data/learning/apply-record-query-method`）：`getInviteList` enterTime 判定
- 建议固化为标准技能 `apply-status-check` + 原语（read 级），供老登/运营日常巡检报名状态，替代脚本内部自判
