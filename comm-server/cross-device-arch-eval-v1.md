# 跨设备通讯架构评估与演进建议 v1（2026-09-06 · 星桥）

> 触发：i9→MBP「找不到」问题（agent_peers 本地化 vs 黑板域路由）引发对分布式通讯架构的审视
> 目标：评估现状问题 → 对比路由范式 → 给出未来分布式架构图下的推荐方案

---

## 一、现状架构问题诊断

| # | 问题 | 根因 | 影响 |
|---|---|---|---|
| P1 | i9/MBP/mac-mini 各自 agent_peers 只见本机 | CLD agent_bus 单机本地化 | 跨设备「发现会话」落空（i9 找 MBP）|
| P2 | 跨设备消息域隔离（G1：i9 只写 notes/i9/）| 域权矩阵防越权 | i9→MBP 需经 mac 转发（多一跳+依赖 mac）|
| P3 | 无全局会话发现 | 每设备独立注册/能力表（agent_profiles 仅 mac-mini 全局）| 端侧不知「谁在线/谁能做什么」|
| P4 | 无统一跨设备传输语义 | 消息走黑板键（task 卡+回写键约定不一）| 「完成」语义/ack 格式漂移（G4 门补）|
| P5 | 心跳只证进程活 | 无 agent 会话级活性 | 进程活但 agent 停 = 静默失联（曾误判）|

## 二、路由范式对比（i9→MBP 场景）

| 范式 | 路径 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| A. 域隔离+协调者转发 | i9→notes/i9/→mac 转发→notes/mbp/ | 域安全统一审计；G1 保持 | 多一跳；依赖 mac 在线；延迟+ | 低频协调消息；安全优先 |
| B. 开 i9→mbp 写权 | i9→notes/mbp/ 直写 | 低延迟去中心；无 mac 依赖 | 域隔离破坏；MBP 需信任 i9；审计难 | 高频业务直连；信任建立后 |
| C. 中枢 hub 路由 | i9→中枢→MBP 订阅中枢 | 备灾（mac 挂仍通）；hub 集中 | 需中枢路由逻辑；依赖中枢在线 | 双轨备灾主路径 |
| D. bus-bridge 总线 | i9→bus(send)→MBP(receive) | 任务/结果语义内置；队列缓冲 | 需双方接总线；额外组件 | 任务式交互（非消息流）|

## 三、未来分布式架构图逻辑（推荐分层）

```
                ┌──────────── 全局身份/能力注册表 (黑板 data/registry/agents/) ────────────┐
                │  device-资产: mac-mini(i9双写) / i9(executor) / MBP(session-164dceca)      │
                │  agent-会话: <device>/<session-id> → 在线/能力/路由可达                     │
                └──────────────────────────────┬──────────────────────────────────────────┘
                                               │ 发现查询 (谁在线/找谁路由)
   ┌──────────┐  直写(域权内)   ┌──────────────┴─────────────┐
   │ mac-mini │◄──────────────►│   黑板 (域路由层)            │
   │ (协调者) │                 │  notes/<node>/ = 目标域      │
   └──────────┘                 │  路由表: 目标会话 → 域       │
        │                       └──────┬─────────────┬───────┘
        │  hub 镜像                    │            │
   ┌────┴───────┐               ┌─────┴──────┐  ┌───┴──────┐
   │ 中枢 xingqiao│◄────────────►│   i9        │  │   MBP    │
   │ (hub-spoke) │  直连/双写     │ notes/i9/  │  │ notes/mbp/│
   └────────────┘               └────────────┘  └──────────┘

  分层:
  L1 身份层    : 黑板 data/registry/agents/ (设备+会话+能力+在线) ← 现缺, 补
  L2 传输层    : 黑板 notes/<node>/ 域 (直写域内) + 中枢 hub (跨端镜像/备灾)
  L3 路由层    : 域路由表 (目标会话→目标域) —— 域内直写; 跨域经 hub/协调者
  L4 治理层    : bb-gate 门 (G1域权/G2格式/G3双写/G4闭环/G5静默) + comm_domains 单源
  L5 语义层    : task 卡 + 回写 ack (status 闭环) —— G4 门强制

  关键设计决策:
  D1 会话发现走注册表(L1) 而非 agent_peers —— agent_peers 仅本地调试用
  D2 域权限 = 静态基线(G1) + 动态信任授予(协调者批临时写权) —— 结构门不破
  D3 跨设备消息默认域内直写; 跨域低频走协调者转发; 高频经注册表评估后开白名单直连
  D4 双写保备灾: 设备自域消息主本机+镜像中枢 (mac 挂 → 中枢接管)
  D5 活性=进程心跳 + 会话心跳 双层 (G5: agent 停摆检测)

  演进路径:
  E1 (短期): L5 语义层补强 —— G4 门 + task/ack 规范 (进行中)
  E2 (中期): L1 身份层建立 —— data/registry/agents/ 注册表 (罗盘 device-assets 扩展会话级)
  E3 (长期): L3 路由自动化 —— 注册表驱动路由 (消息写注册表→自动路由目标域), 减少手动转发
```

## 四、i9→MBP 具体建议（用户待决策项）

**推荐：短期走 A（域隔离+协调者转发），中期演进 E2 后按 D3 评估是否白名单直连**

理由：
1. i9→MBP 是低频协调消息（非高频业务流）——A 的「多一跳」代价可接受，域安全收益大
2. 域隔离是 G1 结构门——破坏需用户批 + MBP 侧信任契约（R-ERR 审计）
3. 未来注册表（E2）建立后：若 i9→MBP 成高频，注册表记录路由统计 → 数据驱动决定是否开白名单
4. 双轨备灾已保证 mac 挂时经中枢路由——A 不损备灾

**转发实现**（短期）：星桥/协调者监听 notes/i9/ 域 to=mbp 消息 → 转发 notes/mbp/（加 _relay:star-bridge 标记）；或 bus-bridge（若任务式）——两通道按场景选。

## 五、方案 A 修正（2026-09-06 用户质疑后重估）

**用户质疑成立：协调者转发存在信息风暴与堵塞风险，属中间人反模式**
1. 单点依赖：协调者(agent 会话)在线才转发——agent 忙/重启/离线 → 转发断
2. 无背压/缓冲：消息涌入转发逻辑无队列 → 积压/丢（agent-bus queued 死信教训同源）
3. 环路风险：转发无防环 → 消息循环放大成风暴
4. 性能：agent 会话逐条处理转发，非专用服务（vs hub/bus 24h+重启自愈+队列）

**修正推荐：发布-订阅替代转发（零中间人）**
- 各端消息写自域（发布）：i9 写 notes/i9/（已双写中枢）
- 目标端读目标域（订阅）：MBP 订阅/轮询 notes/i9/（读权全体，经本机黑板或直连中枢）
- i9→MBP 语义：i9 写 notes/i9/ 标注 to=mbp → MBP 读 notes/i9/ 感知 —— 无需任何转发
- 域隔离保持（G1 写权不变）；读权全体是架构基础（黑板广播读）
- 转发仅保留：低频特殊协调（星桥手动转个别），不自动化成通道

**更新后推荐矩阵**
| 场景 | 方案 |
|---|---|
| i9→MBP 消息 | 发布-订阅（MBP 订 notes/i9/）—— 零转发零风暴 |
| mac 挂机备灾 | 中枢 hub（i9 双写已在 → MBP 直连中枢读）|
| 任务式交互 | bus-bridge（队列+语义内置）|
| 高频业务直连 | 注册表评估后白名单（中期 E2）|

## 六、稳定性与资源成本补充分析（2026-09-06）

### A. 系统稳定性对比

| 维度 | 转发(方案A) | 发布-订阅 | 中枢hub(C) | bus-bridge(D) |
|---|---|---|---|---|
| 单点 | 协调者 agent（会话级，忙/重启即断）| 黑板服务（24h 常驻，可双轨镜像）| hub（systemd 24h+重启自愈）| bus 服务（systemd）|
| 背压 | 无（最差）| 无背压但写即持久（积在键不丢）| 同黑板 | 队列+consume 有界语义 |
| 重启恢复 | agent 重启丢转发中消息 | 读方重启后补拉（seen 游标）| 数据持久 | 队列持久 |
| 环路风暴 | 高（无防环）| 无（写一次多读方独立，无放大）| 无 | 无 |
| 消息不丢 | 依赖 agent 处理 | 写即持久（双写双份）| 持久 | 队列持久 |
| 故障隔离 | agent 故障→全部转发停 | 黑板挂→双轨切中枢 | hub 挂→本机直连仍通 | bus 挂→黑板兜底 |

**稳定性结论**：发布-订阅/基础设施路由的故障隔离优于 agent 转发——
黑板可双轨（本机+中枢互为镜像，一处挂另一处接管）；agent 转发是单会话依赖（最脆弱层）。

### B. 资源成本对比（关键：LLM/agent 参与度）

| 资源 | 转发(方案A) | 发布-订阅 | 说明 |
|---|---|---|---|
| **LLM/token** | 每次消息 1 次 agent 处理（~1-5k token，秒级延迟）| **0**（纯脚本/基础设施）| 量级差：agent 路由=每次消息一个 LLM 往返 |
| 网络写 | 3 次（i9→mac→处理→mbp）| 2 次（i9 双写本机+中枢；MBP 拉 1 次读）| 转发更多写+处理跳 |
| 常驻进程 | 0（借 agent）| +1 轻订阅器（轮询 ~0.1% CPU 或 SSE 长连）| 可复用 sync-down 模式 |
| 存储 | 3 份副本 | 2 份（双写）| 转发额外副本 |
| 延迟 | 秒级（agent 处理）| 毫秒级（黑板写读）| agent 处理是延迟大头 |
| 运维 | 协调者负担（占处理能力）| launchd/systemd 托管（低维护）| 转发是隐性机会成本 |

### C. 量化估算（i9→MBP 消息，假设 100 条/日）
- 转发：100 × ~2k token = ~200k token/日（LLM 成本 + 协调者处理时间占用）
- 发布-订阅：100 × 2 次 PUT（~KB 级）= ~0 token，纯带宽 ~MB 级可忽略
- 结论：**发布-订阅资源成本 ≈ 转发的 1/50-1/100**（主要省 LLM）

### D. 综合结论
1. **稳定性**：发布-订阅 + 黑板双轨 > 中枢 hub > bus-bridge > agent 转发（转发是单会话最脆弱）
2. **成本**：基础设施路由(0 LLM) ≪ agent 路由(每次 LLM)——agent 不做通用路由是成本铁律
3. **agent 角色正确定位**：agent 处理「语义」（理解/决策/回复），不做「传输」（写读/转发）——传输归黑板/hub/bus
4. 已在跑的基础设施（sync-down SSE/hb-fwd/bb-sub/服务器 comm-layer）都是发布-订阅/镜像模式——架构方向已对，补 MBP 订阅读 i9 域即可

## 七、中期跳跃评估：服务器成为基础设施（注册表/路由）——2026-09-06 用户问

### 核心区分（重新评估的关键）
**注册表(发现层) ≠ 消息路由(传输层)——服务器该中心化前者，去中心化后者**

| 层 | 中心化(服务器) | 去中心化(各端本地) | 理由 |
|---|---|---|---|
| L1 身份注册表 | ✅ 服务器 | — | 全局唯一「谁在线/找谁」；公网各端可达；24h；故障可降级本地缓存 |
| L2 消息传输 | — | ✅ 本地黑板域(发布-订阅) | 消息必经服务器 = 唯一 SPOF + 违背自治；域路由已解 |
| L3 备灾镜像 | ✅ 服务器黑板 | — | 双写保证 mac 挂时中枢接管 |
| L4 任务队列 | ✅ bus-bridge(已部署) | — | 队列语义需服务端持久 |

### 服务器角色的正确终局 = 三合一基础设施（非路由单点）
```
服务器 xingqiao（基础设施，不做消息必经点）
├─ L1 注册表 data/registry/agents/   ← 身份/发现（新增，本次实测可承载）
├─ L2/L3 黑板镜像（comm-server 双写+备灾）  ← 已有
└─ L4 bus-bridge（任务队列）         ← 已有
各端: 本地黑板(域路由自治) + 心跳代理注册到服务器 + 双写镜像
```
- **注册表中心化是安全的**（咨询点，挂了本地缓存降级，消息流不受阻）
- **消息路由中心化是危险的**（必经点 SPOF）——故服务器不做全量路由

### 注册表放服务器的理由（vs 本机黑板）
| 维度 | 服务器 | 本机黑板(mac-mini) |
|---|---|---|
| 可达性 | 公网(所有端可写读) | i9/MBP 需经 Tailscale/转发 |
| 可用性 | 24h systemd(不随 CLD 重启) | 随 mac-mini CLD 重启中断 |
| 容量 | ~300MB/957MB used，注册表 KB 级 | 已紧(3-4GB RSS 风险) |
| 角色 | 中立基础设施 | 协调者主黑板(角色混) |

### 落地路径（真实跳到中期）
1. 心跳代理(hb-fwd)扩展：推心跳时同写注册表 data/registry/agents/<device>（device/session/role/status/ts）
2. 各端 agent 启动注册 + 心跳续期（mac-mini 会话/mac executor/MBP）——活心跳=online，超时标记 offline
3. 查询工具：bb-gate registry 子命令或 dsh-tools（who-is-online --all）——任何端可查全局会话/能力
4. 注册表驱动：罗盘 device-assets 改从注册表拉（会话级扩展）
5. 高频直连评估（E3）：注册表记录路由统计 → 数据驱动白名单

### 不做的部分（诚实边界）
- 服务器不做全量消息路由中枢（避免 SPOF；发布-订阅已解消息流）
- 本机黑板仍是 mac-mini 侧主黑板（8ms 本地）——服务器是全局发现+备灾+总线，非替代
- 服务器 1G 内存约束：注册表只存元数据(KB级)，不存消息体
