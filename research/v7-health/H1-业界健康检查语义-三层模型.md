## 〇、一句话结论

> **业界从不把「健康」当成一个布尔值。**
> 它至少是**三个不同问题**（该不该重启 / 该不该给流量 / 依赖是否可用），
> 而且**任何一层的「通过」都必须在接口上写清它测的是什么**——
> Kubernetes 官方文档甚至为此在 v1.16 就把笼统的 `healthz` **弃用**，拆成 `livez` 与 `readyz`。

## 一、第一层：探针语义的三分（Kubernetes，已读原文）

来源：<https://kubernetes.io/docs/concepts/workloads/pods/probes/>

逐字原文（已读原文）：

> The kubelet can optionally perform and react to three kinds of probes on running containers, each serving a different purpose: **Startup probe / Liveness probe / Readiness probe**

| 探针 | 官方定义的**问题** | 失败时的动作 | 逐字原文（节录） |
|---|---|---|---|
| **startup** | 「应用**启动了**没有」 | 杀掉容器 | "Startup probes verify whether the application within a container is started." |
| **liveness** | 「该不该**重启**它」 | 重启容器 | "Liveness probes determine when to restart a container. For example, liveness probes could catch a deadlock, where an application is running, but unable to make progress." |
| **readiness** | 「该不该**给它流量**」 | 从 EndpointSlice 摘掉 | "Readiness probes determine when a container is ready to accept traffic." |

★★★ **对我们的三条直接含义**：

1. **`/health` 这个名字本身就是被业界淘汰的模糊词。** K8s 的 API server 有专门的弃用说明（见 H2 §3）。
2. **「活着」与「能干活」是两件事**——这与 `G3` 里那条「四十年的同一个答案」是同一件事的第二次出现（内核 watchdog 管「进程还在 pong」，而 hermes PR #91554 管「工作有没有推进」）。
3. **依赖项属于哪一层，官方给了明确答案**（逐字原文）：

> When your app has a strict dependency on back-end services, you can implement **both** a liveness and a readiness probe. **The liveness probe passes when the app itself is healthy, but the readiness probe additionally checks that each required back-end service is available.** This helps you avoid directing traffic to Pods that can only respond with error messages.

⇒ ★ **依赖项健康归 readiness（可用性），不归 liveness（存活）。** 把依赖挂进 liveness 会造成级联重启——K8s 官方在同一页有 Caution：

> Incorrect implementation of liveness probes can lead to **cascading failures**. This results in restarting of container under high load; failed client requests as your application became less scalable; and increased workload on remaining pods...

★ **反向证据（重要，说明这不是无争议的共识）**：Prometheus Operator 维护者 brancz 在 2024-11 提 issue 要求**删掉 liveness/startup 探针**（<https://github.com/prometheus-operator/prometheus-operator/issues/7096>，已读原文），逐字：

> in my soon 10 years of running Prometheus, **not once was this appropriate**, and we have countless examples of startup and liveness probes killing Prometheus servers when they shouldn't have... I think the monitoring infrastructure simply **shouldn't have liveness probes**... everyone who is genuinely worried about the alerting pipeline not working should already have a real end-to-end test with the **WatchDog** alert.

⇒ ★ **业界对「liveness 到底该不该存在」是有分歧的**；但对「readiness 必须表达可用性」没有分歧。本文件按后者给建议。

★★★ **三条可直接照搬的形态**：

| 形态 | 原文依据 | 我方可照搬之处 |
|---|---|---|
| **逐项列名** | `[+]etcd ok` | `/health` 应逐个报 `board` / `bus` / `sse` / `heartbeat`，而不是一个总布尔 |
| **`excluded: ok` 是一种独立状态** | `curl -k 'https://localhost:6443/readyz?verbose&exclude=etcd'` ⇒ `[+]etcd excluded: ok` | ★ **「没查」必须与「查了通过」在字面上可区分** |
| **单项可单独取** | `/livez/<check>`（Alpha since v1.37） | 出问题时能直接看某一通道，不必读全量 |

★ **注意官方对机器的态度**（逐字）：

> This can be useful for a human operator... **it is not intended to be consumed by a machine**

以及（针对单项端点）：

> These individual health checks **should not be consumed by machines** but can be helpful for a human operator to debug

⇒ ★★ **业界把「人读的详细报告」与「机器读的裁决位」分开**：机器只认 **HTTP 状态码**（逐字："Machines that check the healthz / livez / readyz of the API server should rely on the HTTP status code."）。**我们若让机器去 grep 人类可读文本，就是反着用。**

### 2.2 NATS：`/healthz` 带**分系统的结构化错误**（已读原文，源码）

来源：<https://raw.githubusercontent.com/nats-io/nats-server/main/server/monitor.go>（`grep -n "healthz\|Healthz"`）

未编辑原文（节录）：

```
1586:		s.basePath(HealthzPath), HealthzPath,
3511:	Errors     []HealthzError `json:"errors,omitempty"`
3514:type HealthzError struct {
3525:	HealthzErrorConn HealthZErrorType = iota
3526:	HealthzErrorBadRequest
```

⇒ ★ **一个消息中间件的健康报告，粒度是「连接 / JetStream / 账户 / 流 / 消费者」** —— 即**按子系统分类的错误**，且响应 schema 含 `status`（required）+ `status_code` + `errors[]`（<https://docs.nats.io/reference/system/monitor/healthz.md>）。

★ 这正好是 H3 要回答的：「一个通讯通道的健康怎么表达」——NATS 给的答案是**按子系统枚举 + 结构化错误数组**，不是「一个绿灯」。

### 2.3 NATS 的常规监控面：**每个面一个只读端点**

来源：<https://docs.nats.io/running-a-nats-service/nats_admin/monitoring>（已读原文）

逐字：

> Each path returns a different slice of state. The four you'll use most are **`/varz`** (the server itself), **`/connz`** (its clients), **`/routez`** (its cluster routes), and **`/jsz`** (its JetStream).

并且给了一条**判据设计教训**（逐字，直接命中「空 ≠ 无」）：

> `connections` is how many clients are **connected right now**... The `total_connections` next to it is the count **since the server started, so it only ever goes up**.

⇒ ★★ **同一个词（connections）有两种口径**：现值 vs 累计。这与本仓 `research/报数自检清单-4787d717.md` §二第 1/2 问（「对象是什么」「口径声明了吗」）是同一条。

## 三、第三层：黑盒 / 白盒，与「服务网格」的两套健康（Envoy）

来源：<https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/health_checking>（已读原文）

Envoy 明确支持**三种主动健康检查**，且对每种给了「什么样的应答算健康」：

| 类型 | 判定标准（逐字原文节录） |
|---|---|
| HTTP | "By default, it expects a **200** response if the host is healthy. **Expected and retriable response codes are configurable.**" |
| gRPC | 走 gRPC 健康检查协议（见 H2 §2） |
| **L3/L4** | "it expects the **byte buffer to be echoed** in the response if the host is to be considered healthy." |
| Redis | "Envoy will send a Redis **PING** command and expect a **PONG** response." |
| Thrift | "expect a success response" |

★★★ **最重要的一条设计先例**（逐字）：

> L3/L4 : During L3/L4 health checking, Envoy will send a **configurable byte buffer** to the upstream host. **It expects the byte buffer to be echoed in the response** if the host is to be considered healthy.

⇒ ★ **「连通性」不是 `HTTP 200`，而是「我发出去的那个东西原样回来了」。** 这是一个**身份确认**（互认），不是**可达性确认**。见 H4：本机 `drift-scan` 的 board 检查**恰好缺这一层**，实测**任何返回 200 的服务都能冒充黑板**。

且 Envoy 的健康检查有**迟滞**（"failures required before marking a host unhealthy, successes required before marking a host healthy"）——与 AWS/GCP 的连续计数同构（见 §4）。

## 四、第四层：探针的**状态机**与「空集」的显式裁决（AWS / GCP）

### 4.1 Google Cloud：probe → 状态机的显式建模（已读原文）

来源：<https://cloud.google.com/load-balancing/docs/health-check-concepts>

逐字：

> Each connection attempt is called a **probe**. Google Cloud records the success or failure of each probe. Based on a configurable number of **sequential successful or failed probes**, an overall health state is computed for each backend.

⇒ ★ **健康的定义是「连续 N 次成功的函数」，不是「最后一次的结果」**。

### 4.2 AWS ALB：**「全不健康」= fail open，且被显式写下来**（已读原文）

来源：<https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html>

逐字原文（★ 这是本文件对 Q2 最重要的一段）：

> **If a target group contains only unhealthy registered targets, the load balancer routes requests to all those targets, regardless of their health status.** This means that if all targets fail health checks at the same time in all enabled Availability Zones, **the load balancer fails open.**

以及（★ 关于「分母为 0」的显式区分）：

> Note that when you deregister a target, this **decreases `HealthyHostCount` but does not increase `UnhealthyHostCount`.**

★★★ **两条可直接照搬的语义**：

1. **「一个健康的都没有」不是「一切正常」，也不是「按不健康处理」——它是一个需要被显式命名的第三种情形**，AWS 给它起了名字（fail open）并写进了文档。
2. **「摘掉」与「不健康」是两个不同的计数**。空集**不得**被并入失败侧，也**不得**被读作成功。

★ 我方的对应：`/health` 返回 `total:0` 时，**既不是 up 也不是 down**，按 AWS 的形态它必须是一个**显式的第三种裁决**——本仓已有的名字是「**不可判**」（见 H2 §1、H5 §5）。

### 4.3 判定阈值也是参数（AWS，逐字）

> If the health checks exceed **UnhealthyThresholdCount** consecutive failures, the load balancer takes the target out of service. When the health checks exceed **HealthyThresholdCount** consecutive successes, the load balancer puts the target back in service.

⇒ ★ 恢复需要**更多**成功次数（默认 5）而非 2（默认失败 2 次即判不健康）——**恢复比判坏更保守**。我方 `drift-scan` 是单次读数即判（无迟滞、无连续计数）⇒ 见 H4。

## 五、第五层：Prometheus 的 `up` —— 「健康」被定义为**可达**，且是**逐 target 的**（已读原文）

来源：<https://prometheus.io/docs/concepts/jobs_instances/>

逐字原文：

> `up{job="", instance=""}`: **1 if the instance is healthy, i.e. reachable**, or 0 if the scrape failed.

⇒ ★★ **两个必须看清的限定**：
1. Prometheus 的 `up` 把「healthy」**定义为 reachable**——它**故意**只做黑盒可达性，不做业务正确性。这是它**声明过的局限**，不是它没想到。
2. `up` 是**每个 target 一条时间序列**，天然是**逐项的**，不是全局布尔。

★ **对我方的直接含义**：如果我们照抄 `up` 的语义（HTTP 200 = healthy），就会**精确复刻当下的假绿**——因为本机 `/health` 的失效形态**恰好也是 200**（H5 §1 实测）。`up` 之所以在 Prometheus 里成立，是因为它**还配了另外两件东西**：`absent()`（见 H2 §2）与 scrape 失败本身会**不产生样本**。

## 六、Golden Signals 与黑/白盒（Google SRE，已读原文）

来源：<https://sre.google/sre-book/monitoring-distributed-systems/>

逐字（定义）：

> **White-box monitoring** — Monitoring based on metrics **exposed by the internals** of the system...
> **Black-box monitoring** — **Testing externally visible behavior as a user would see it.**

⇒ ★★ 这两者**不是可选项而是两层**：`/health` 若只回自家进程状态，就是纯白盒（**内部视角**）；本机历史上「仪表静默死亡」（`G1`）正是**纯白盒的自指困境**——`G1` 已给出结论：「**会死的仪表不能报告自己的死亡。判定方必须在被判定对象之外。**」

## 七、汇总：「一个 `/health` 应该报告什么」的字段级规格

下表**每一行都标了来源强度**（业界成熟 / 业界有分歧 / 本机自创 / 业界有本机没有）。

| # | 应报告 | 来源 | 强度 |
|---|---|---|---|
| 1 | **逐项命名 + 逐项状态**（不是单一布尔） | K8s apiserver `?verbose`；NATS `/healthz` `errors[]` | ★★ 业界成熟 |
| 2 | **每个通道区分三层语义**：*进程活着* / *能提供服务* / *依赖可用* | K8s startup/liveness/readiness | ★★ 业界成熟 |
| 3 | **「没查」是独立状态**（`excluded: ok` / SKIP ≠ PASS） | K8s `exclude=`；本机 `beacon-check.py --selftest` 亦已自证此条 | ★★ 业界成熟 **且本机已有** |
| 4 | **空集必须显式裁决**（不并成功、不并失败） | AWS fail-open + Healthy/Unhealthy 双计数 | ★★ 业界成熟（形态有分歧，原则无分歧） |
| 5 | **观测时刻必须随读数一起给**，陈旧在**读时**判 | Prometheus 时序模型；本机 `data/health/*` 已含 `checked_at` 但**没人读时判**（H5 §5） | ★★ 业界成熟 / ★ 本机只做了写侧 |
| 6 | **连续计数 + 迟滞**（N 次失败才算坏、M 次成功才算好） | AWS / GCP / Envoy | ★★ 业界成熟，**本机完全没有** |
| 7 | **身份互认**（我发的东西回来了才算通） | Envoy L3/L4 echo buffer | ★★ 业界成熟，**本机完全没有**（H4 负控 B 实测） |
| 8 | **机器读裁决位、人读详细文本，分开** | K8s：机器只认状态码；`?verbose` "not intended to be consumed by a machine" | ★★ 业界成熟，**本机完全没有** |
| 9 | **聚合总判必须可分解**（总红 ⇒ 能指到是哪一项红） | K8s `?verbose`；NATS `errors[]` | ★★ 业界成熟 |
| 10 | **降级态 / 部分不可用**（partial） | **未在 K8s/AWS/GCP/Envoy 找到一等公民的 "degraded" 状态** —— 只有 `NOT_SERVING` / `unhealthy` / `SERVICE_UNKNOWN` 三分 | ⚠️ **业界弱**：多数体系用「逐项状态」表达部分可用，**而不是**再发明一个聚合的 degraded 值 |

★ **第 10 行是诚实的缺口**：我在 K8s probes、K8s API health、gRPC health、AWS ALB、GCP LB、Envoy health checking、Prometheus 七份一手文档中**只找到** `SERVING / NOT_SERVING / UNKNOWN / SERVICE_UNKNOWN` 这类**有限枚举**；没找到业界统一认可的 **"degraded"** 语义。**未搜到 ≠ 不存在**（见 H1 §九 阴性证据）。本机若引入 degraded，属于**自创**，须自行定义其判据与反例。

## 八、本机自创 vs 业界成熟（纪律要求：不得混淆）

| 项 | 判定 |
|---|---|
| `data/health/<key>` 心跳键 + `hb-watchdog.sh` 双板写 | ★ **本机自创**（业界对应物是 Healthchecks.io 的 ping URL，但那是外置服务） |
| `refresh_seconds` / `stale_threshold` **随读数一起存** | ★ **本机自创**（且是超前的一半，见 H5 §5） |
| 「不可判」三态（fresh / stale / undecidable） | ★ **本机自创**（业界最接近的是 Prometheus 的 `absent` 与 Healthchecks.io 的 `New` 态，见 H2） |
| **负控 / 自证矩阵**（`beacon-check.py --selftest` 逐条造反例） | ★ **本机自创且成熟**（业界对应物叫 mutation testing / fault injection，但很少有把「逐条证据可红」写进工具自检的） |
| liveness / readiness **分层** | ★ **业界成熟，本机没有** |
| 连续计数 + 迟滞 | ★ **业界成熟，本机没有** |
| 身份互认（echo / 挑战应答） | ★ **业界成熟，本机没有** |
| 机器裁决位与人读文本分离 | ★ **业界成熟，本机没有** |

## 十、复跑命令（本文件所有「已实测」均指 H5，此处只给外链的可复现取源）
