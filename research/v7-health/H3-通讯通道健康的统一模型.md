## 〇、直接回答

> ★ **有先例，而且不止一个 —— 但它们没有统一成一个标准，而是形成了两条可组合的路线：**
>
> | 路线 | 代表 | 形态 |
> |---|---|---|
> | **① 逐面端点（enumerate-the-faces）** | **NATS** `/varz` `/connz` `/routez` `/jsz` `/healthz` | 每个子系统一个只读端点，`/healthz` 把它**聚合成结构化 `errors[]`** |
> | **② 上游簇 + 主被动双检查（treat-as-upstream-cluster）** | **Envoy / service mesh** | 把每个对端当作 upstream cluster member：**主动探 + 被动观测（outlier detection）**，健康是**成员级**属性 |
>
> ★★ **两条路线的共同点才是可照搬的**：
> **健康不是「通道」的属性，是「**这条通道 + 这一次通话**」的属性**；
> 且**必须同时有主动面（我主动去问）和被动面（它自己来没来）**。

## 一、先定对象：本机的「通讯通道」到底有几条？

★ 本仓 `drift-scan` 的期望矩阵（`~/dsh-plugin-drift-scan/lib/channel-matrix.json`，单一来源指向 `docs/comm-channel-rules-v2-20261002.md §2`）列了 **12 项**。
★ 但「12 项检查」**不等于**「12 条通道」——其中有进程、有 launchd、有文件权限、有注册卡。
⇒ 按「**通道**」而不是「**检查项**」重列，本机是 **6 条通道 + 6 项配套断言**：

| # | 通道 | 载体 | 实测（2026-10-12T19:54，见 H5 §7） |
|---|---|---|---|
| C1 | **板（本地）** | `127.0.0.1:8792` | HTTP 200 · `/notes` 32,510,382 bytes / 0.583 s |
| C2 | **板（中央）** | `xingqiao.meetfunbp.com:8792` | 200（drift-scan 实测） |
| C3 | **SSE 事件桥** | `:8803/events` | `event: hello` + `event: change`，`id: 498036` |
| C4 | **总线桥 bus** | `:8791`（`/bus/receive`） | ★ 根路径 **HTTP 401**（需 token，属预期） |
| C5 | **跨设备直连** | Tailscale + Funnel | 对端均 active（drift-scan 实测） |
| C6 | **心跳** | 板键 `data/health/hb-*` | mac-mini age **18.7 s** · mbp age **73.6 s** |

★★★ **一条必须写进健康报告的实测事实**（见 H5 §7 原始输出）：

```
$ lsof -nP -iTCP -sTCP:LISTEN | grep -E "8792|8803|8791"
node       1218 coreyleung   12u  IPv4 ... TCP *:8791 (LISTEN)
rust-blac  1221 coreyleung    3u  IPv4 ... TCP *:8792 (LISTEN)
rust-blac  1221 coreyleung    4u  IPv4 ... TCP *:8803 (LISTEN)
```

⇒ ★★ **C1（板）与 C3（SSE）是【同一个进程 pid 1221】。**

★★ **这条不是运维细节，是健康模型的输入**：
**板与 SSE 是「同命」的**——它们**不可能**一个健康一个不健康。
一份把 C1 与 C3 列为两个独立绿灯的健康报告，**在结构上就说错了**；
更坏的是它会让读者以为「SSE 绿 ⇒ SSE 这条路通」，而事实上**它绿只是因为板绿**。

★ 这正是 v7 计划 §二里点名 **S-4「拆单点」（8803 与 8792 同进程）**的理由；
★ 但本文件要指出：**即使不拆单点，健康报告也必须显式表达「同命」**——
否定形式是：**若 C1 与 C3 的状态在任意时刻不同，那份报告就是自相矛盾的。**

## 二、路线 ①：逐面端点 + 结构化聚合（NATS）

来源：<https://docs.nats.io/running-a-nats-service/nats_admin/monitoring>（已读原文）

逐字：

> Each path returns a different slice of state. The four you'll use most are **`/varz`** (the server itself), **`/connz`** (its clients), **`/routez`** (its cluster routes), and **`/jsz`** (its JetStream). Each one is an HTTP path, not a call into a client library, so **any HTTP tool can reach it**.

> Each endpoint takes query parameters... `/connz?acc=ORDERS&subs=true&auth=true`

★ 每个连接返回的字段（逐字）：

> Each entry names one client: its connection id (`cid`), the account and user it authenticated as, its round-trip time (`rtt`), and how many bytes are queued for it (`pending_bytes`).

★★ 三条可直接照搬的设计：

| 设计 | NATS 的做法 | 我方可照搬 |
|---|---|---|
| **分层端点** | `/varz`（自己）→ `/connz`（客户端）→ `/routez`（簇路由）→ `/jsz`（JetStream） | 板（自己）→ 通道（对端）→ 心跳 → 队列 |
| **`rtt` 是逐连接的一等字段** | `/connz` 每个连接带 `rtt` | ★★ **我方心跳只记「在不在」，不记「多快」** —— 这是缺口 |
| **`pending_bytes` 是逐连接的一等字段** | 同上 | ★ 我方 `~/.dsh/bus-queue` / inbox 无此读数（`E0` 已点名「平铺、无上限、无 ack、无游标」） |

★ 一条**判据设计教训**原文（逐字）：

> Three counters are worth a second look. `connections` is how many clients are **connected right now**: here, the four Acme services. The `total_connections` next to it is the count since the server started, so **it only ever goes up**. And `slow_consumers` is the number of clients the server has **disconnected for not keeping up**; on a healthy node it stays at 0.

⇒ ★★ **`slow_consumers`（"被踢掉的不跟趟的消费者"）是我方完全没有的一个健康信号**，
  而它**恰好量的是**我方反复出问题的那个东西（背压 / 注入风暴 / 队列）。
  ★ `research/agent-comm-paths/E0-...对照表.md` §二⑦ 已把「背压/熔断/优先级」列为「我们缺的」，本文件只补：**它是一个健康指标，不只是治理机制。**

### 2.1 NATS `/healthz`：把逐面聚合成**结构化错误**

来源：源码 <https://raw.githubusercontent.com/nats-io/nats-server/main/server/monitor.go> · schema <https://docs.nats.io/reference/system/monitor/healthz.md>

未编辑原文（源码 grep）：

```
1586:		s.basePath(HealthzPath), HealthzPath,
3511:	Errors     []HealthzError `json:"errors,omitempty"`
3525:	HealthzErrorConn HealthZErrorType = iota
3526:	HealthzErrorBadRequest
3527:	HealthzErrorJetStream
3528:	HealthzErrorAccount
3529:	HealthzErrorStream
3530:	HealthzErrorConsumer
```

未编辑原文（schema）：

```
error     string
errors    object[]  ▶
status    string    required
status_code integer
```

★★★ **这就是「一个通讯通道健康的统一表达」的最好先例**：

```
status       : 总判（必填）
errors[]     : ★ 逐子系统的结构化错误数组（不是一句 ok）
  └ type     : Conn / JetStream / Account / Stream / Consumer   ← 分类枚举
```

★ **注意 `errors` 是 `omitempty`** ⇒ 健康时**字段缺席**。
⇒ ★★ **这带来一个必须防的坑（与我方「空 ≠ 无」直接相关）**：
**「`errors` 缺席」必须与「`errors` 为空数组」区分吗？** 在 NATS 里二者同义（都表示无错），
**因为在 NATS 的模型里 `status` 是必填的、独立的**——**总判不靠 `errors` 反推**。
⇒ ★★ **可照搬的铁律**：
> **总判必须是一个独立字段，绝不能从「明细为空」反推出来。**
> 本机 `/health` 的错，正是**没有总判字段**，于是下游只能拿 `total:0` 当总判用。

## 三、路线 ②：主被动双检查 + 成员级健康（Envoy / service mesh）

来源：<https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/health_checking>（已读原文）

逐字：

> **Active** health checking can be configured on a **per upstream cluster basis**... Envoy supports three different types of health checking along with various settings (**check interval, failures required before marking a host unhealthy, successes required before marking a host healthy**, etc.)

★ 主动检查的五种协议与判定（见 H1 §3 表），其中**最值得照搬的一条**逐字：

> L3/L4 : During L3/L4 health checking, Envoy will send a **configurable byte buffer** to the upstream host. It expects the **byte buffer to be echoed** in the response if the host is to be considered healthy.

⇒ ★★★ **「通道健康」的强形式 = 互认（challenge-response），不是可达（HTTP 200）。**
★ 本机 `drift-scan` 的 endpoint 类检查**只有可达**（H4 负控 B 实测：冒牌 200 服务能冒充黑板）。

★ 关于**被动面**：Envoy 另有 **outlier detection**（被动健康检查，由实际请求的失败/延迟驱动）
—— 我**未直读其最新官方页全文**（只读到旧版 `outlier.rst.txt` 的链接，**仅见摘要**）。
⇒ ★ 本节凡涉 outlier detection 的参数与语义，**一律标「仅见摘要，未核实」**，不作为论据。

### 3.1 service mesh 给的一条关键提醒：**panic threshold**

★ 我**未能直读** Envoy/ Istio 关于 panic threshold 的一手原文（**仅见摘要**）⇒ **不作为论据**。

## 四、把两条路线合成本机可用的模型

### 4.1 每条通道必须回答的**五个字段**（缺一即「假绿位」）

| 字段 | 语义 | 业界出处 | 本机现状 |
|---|---|---|---|
| **`layer`** | 这条通道的检查**测的是哪一层**：`process` / `listener` / `protocol` / `peer-identity` | Envoy 三型（HTTP/gRPC/L3L4）；K8s 三探针 | ★ **无**：`drift-scan` 有 `kind`（endpoint / sse / process-alive / launchd-loaded / tailscale-status / file-perm / registry-services），**这是传输类型，不是语义层次** |
| **`verdict`** | `pass` / `fail` / **`undecidable`** | Healthchecks.io `New`；AWS fail-open；gRPC `NOT_FOUND` | ★ **无**（`drift` 是布尔；`process-alive`/`launchd-loaded` 只有布尔） |
| **`observed_at` + `stale_after`** | 观测时刻 + 何时算陈旧 | Prometheus 时序；本机 `data/health/*` 已存 `checked_at`/`refresh_seconds`/`stale_threshold` | ⚠️ **写侧已存，读侧无人判**（H5 §5 实测：过期 1.54× 仍写 PASS） |
| **`consecutive`** | 连续 N 次才改判（迟滞） | AWS `HealthyThresholdCount`/`UnhealthyThresholdCount`；Envoy "failures required / successes required"；GCP "sequential probes" | ★ **无**（单次读数即判） |
| **`identity_proof`** | 「我发出去的那个东西回来了」 | Envoy L3/L4 echo buffer | ★ **无**（H4 负控 B） |

### 4.2 六条通道的**应有形态**（建议，非代裁）

| 通道 | 最小真检查（不是 200） | 失效时它必须变红的**具体条件** |
|---|---|---|
| **C1 板（本地）** | GET `/data/health/hb-mac-mini`，**断言 `value.node == "mac-mini"` 且 `value.app_pid` 是活的** | ★ 任何返回 200 但 `node` 字段不对（或缺失）的服务 ⇒ **红**（当前：绿） |
| **C2 板（中央）** | 同上，断言 `value.node == "mac-mini"` **且**与本地板的 `ts` 差 < N 秒 | ★ 中央板返回**别的节点的卡** ⇒ **红** |
| **C3 SSE** | 收 `event: hello` **且**在 T 秒内收到 ≥1 条 `event: change`（板在动就必然有） | ★ 只收到 hello 却 T 秒无 change、而板在动 ⇒ **红**（当前：只要首字节对就绿） |
| **C4 总线** | 带 token 的**往返**：发一条探针消息并读回 | ★ token 过期/被轮换 ⇒ **红**（当前：drift-scan 用 `expectBodyContains:"ok"`，比 401 好，但**未验证是我这条消息回来了**） |
| **C5 跨设备** | Tailscale `active` + **对端板键的 `ts` 新鲜** | ★ 对端显示 active 但它 10 分钟没写心跳 ⇒ **红**（当前：`tailscale-status` 只查 active） |
| **C6 心跳** | **读时**判 `now - ts > stale_threshold` | ★ 过期即红，**即使文件里写着 PASS**（H5 §5 实测当下是绿的） |

★★ **这张表的每一行「失效时必须变红」都对应一个可执行的反例** —— 这正是 v7 计划该有的验收形态。

## 五、本机自创 vs 业界成熟（纪律要求）

| 项 | 判定 |
|---|---|
| **按子系统聚合的 `/healthz`** | ★ **业界成熟**（NATS），本机**没有**（`/health` 是空壳） |
| **逐面只读端点**（`/varz` `/connz` `/routez` `/jsz`） | ★ **业界成熟**，本机**部分有**（板有 `/data/...` 键面、`/events` 流；**但没有「通道健康」这一面**） |
| **逐连接 `rtt` / `pending_bytes` / `slow_consumers`** | ★ **业界成熟**（NATS），本机**没有** |
| **主动探 + 被动观测（outlier detection）** | ★ 业界成熟（Envoy），本文**未直读原文**⇒ 不作为论据 |
| **连续计数 + 迟滞** | ★ 业界成熟（AWS/GCP/Envoy），本机**没有** |
| **身份互认（echo buffer）** | ★ 业界成熟（Envoy），本机**没有** |
| **`data/health/<node>` 心跳键 + `stale_threshold` 随值存** | ★ **本机自创**（业界对应物是外置的 Healthchecks.io 或 Prometheus 的 scrape 时序） |
| **12 项「存在性断言」通道矩阵 + 单一来源 json** | ★ **本机自创**（业界无对应：mesh 的期望是声明式 API，但那是运行时数据面） |
| **`--selftest` 逐条造反例** | ★ **本机自创且成熟**（`beacon-check.py` 22 条全绿，见 H4 §4） |

★ **反向（本机有、业界没有现成的）**：`E0` §三 已列出 6 项（HLC 时间轴 / X-Writer 归属审计 / 红绿灯同源互斥 / FNP 四层 / 外链分级 / SSE 事件桥）。
本文件**不重复**，只标注一点：**它们全部是「能力」，没有一条是「健康表达」**
⇒ **能力领先不等于可观测领先**；本机的短板正好在后者。
