## 〇、直接回答

**有等价共识，但不以「禁令」的形式存在。**

我在 7 份业界一手规范里**没有找到**任何一句逐字写着「0 条不得读作健康」。我找到的是**更强的东西**：

> ★★★ **业界的接口在构造上就产生不出「空 = 绿」这个读数。**
> 每一个规范都有一个**专门的、被命名的第三种状态**来接住空集：
> Healthchecks.io 叫 **`New`**、Prometheus 叫 **`absent()`**、gRPC 叫 **`NOT_FOUND` / `SERVICE_UNKNOWN`**、
> AWS 叫 **fail open**、K8s 叫 **`excluded`**。
>
> ⇒ **它们不需要禁令，因为它们的类型系统里没有「空 ⇒ 通过」这条路径。**
> 我方的问题不是「违规」，是**接口设计缺口**——`/health` 把空集**路由进了 200**。

## 一、先给定语：本机的「空值」是哪一种空？

「空」至少有四种，混为一谈就无法给判据（本仓 `报数自检清单` §二第 1 问同调）：

| 型 | 例子 | 规范上应视为什么 |
|---|---|---|
| **A 路由不存在** | `/zzznotexist` 返回 200 + 空 | ★ **不存在**，不是空 |
| **B 命名空间存在但 0 键** | 一个真命名空间暂时无内容 | ★ **空集**（须显式裁决） |
| **C 键不存在** | `/notes/xxx` 返回 404 | ★ **not found**（已有正确语义） |
| **D 读数取不到**（服务挂、超时） | `HTTP 0` | ★ **不可判**（不得当 0） |

★★★ **本机实测把 A 与 B 合并了** —— 见 §四。

## 二、五份规范各自怎么接住空集

### 2.1 Healthchecks.io：**`New` 态与 `Up` 态是两个不同的态**（已读原文）

来源：<https://healthchecks.io/docs/>

逐字原文：

> Each check is always in one of the following states, depicted by a status icon:
> - **New**. A newly created check that **has not received any pings yet**. Each new check you create will start in this state.
> - **Up**. All is well. **The last "success" signal has arrived on time.**
> - **Late**. The "success" signal is due but has not arrived yet. It is not yet late by more than the check's configured Grace Time.
> - **Down**. The "success" signal has not arrived yet, and the Grace Time has elapsed.
> - **Paused**. ...

★★★ **这就是本问题的教科书答案**：

- **「一个 ping 都没收到」⇒ `New`，绝不是 `Up`。**
- **`Up` 的定义里含时间**：「最后一个成功信号**按时**到达」——**没有「按时」就没有 Up**。
- 而且它把「还没到点（Late）」与「过期了（Down）」**分成两态**。

⇒ ★ 对应本机：`data/health/sedimentation` 的 `status:"PASS"` 是**写侧冻结的裁决**，
  它既没有「New」这个态，也没有「读时判过期」的机制 ⇒ H5 §5 实测：**它已过期 1.54 倍，值里仍写着 PASS**。

且 Healthchecks.io 明确自己是什么（逐字）：

> Healthchecks.io works as a **dead man's switch** for processes that need to run continuously or on a regular, known schedule.

⇒ 与 `G1`（看门狗 / 缺席语义）是同一族，**`G1` 已经把这条调研做过了，本文件不重做**。

### 2.2 Prometheus：**「没有样本」必须被单独表达**（已读原文）

来源：<https://prometheus.io/docs/prometheus/latest/querying/functions/>（`absent()`）

逐字原文：

> `absent(v instant-vector)` returns an **empty vector if the vector passed to it has any elements** and a **1-element vector with the value 1 if the vector passed to it has no elements**. This is useful for alerting on when **no time series exist** for a given metric name and label combination.

★★★ **这是最直接的一条**：Prometheus **专门造了一个函数**，因为「没有数据」必须在**告警层面**被表达出来。
如果「空 = 健康」，`absent()` 这个函数**根本不会存在**。

★ 与 `up` 配合看（<https://prometheus.io/docs/concepts/jobs_instances/>，逐字）：

> `up{job="", instance=""}`: **1 if the instance is healthy, i.e. reachable**, or 0 if the scrape failed.

⇒ ★ `up` **只对「抓到过」的 target 存在**。target 整个消失时，`up` 不产生样本 ⇒ **要靠 `absent()` 接住**。
**「空」在校验链上是一个必须单独处理的分支，不是默认通过。**

### 2.3 gRPC Health Checking Protocol：**「服务名没注册」⇒ `NOT_FOUND`，不是健康**（已读原文）

来源：<https://raw.githubusercontent.com/grpc/grpc/master/doc/health-checking.md>

未编辑的原文（proto 定义，逐字）：

```proto
syntax = "proto3";
package grpc.health.v1;
message HealthCheckRequest { string service = 1; }
message HealthCheckResponse {
  enum ServingStatus {
    UNKNOWN = 0;
    SERVING = 1;
    NOT_SERVING = 2;
    SERVICE_UNKNOWN = 3;  // Used only by the Watch method.
  }
  ServingStatus status = 1;
}
service Health {
  rpc Check(HealthCheckRequest) returns (HealthCheckResponse);
  rpc Watch(HealthCheckRequest) returns (stream HealthCheckResponse);
}
```

逐字（★ 最关键的两句）：

> For each request received, **if the service name can be found in the registry**, a response must be sent back with an `OK` status and the status field should be set to `SERVING` or `NOT_SERVING` accordingly. **If the service name is not registered, the server returns a `NOT_FOUND` GRPC status.**

> A client **can declare the server as unhealthy if the rpc is not finished after some amount of time**. The client **should be able to handle the case where server does not have the Health service.**

★★★ **三条可直接照搬**：

1. **「我查的那个东西不在」不是 OK，是 `NOT_FOUND`。** 一个只回答「我有注册表」、对任意服务名都回 OK 的健康端点，**违反本协议**。
2. **枚举里没有「健康」这个笼统值** —— 是 per-service 的 `SERVING/NOT_SERVING`。
3. **超时 ⇒ 客户端可判 unhealthy**；且**「服务器根本没有 Health 服务」是一种必须被处理的情形**（而不是被当成通过）。

★ 对照本机：`/health` **没有注册表概念**，对**任何**路径都给同一个 200 空体（H5 §1 实测）⇒ 它连「服务名没注册」这条分支都没有。

### 2.4 AWS ALB：**「一个健康的都没有」是一个被命名的独立裁决**（已读原文）

来源：<https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html>

逐字原文：

> **If a target group contains only unhealthy registered targets, the load balancer routes requests to all those targets, regardless of their health status.** This means that if all targets fail health checks at the same time in all enabled Availability Zones, **the load balancer fails open.**

> Note that when you deregister a target, this **decreases `HealthyHostCount` but does not increase `UnhealthyHostCount`.**

★★★ **两句话给出两个正交原则**：

| 原则 | 原文依据 |
|---|---|
| **空集要有显式的、被命名的第三种裁决**（fail open ≠ healthy，也 ≠ unhealthy） | "the load balancer fails open" |
| **「不在册」不并入「坏」**（摘掉 ≠ 不健康，两个计数分开） | HealthyHostCount ↓ 而 UnhealthyHostCount **不动** |

★ 照搬到本机：`/health` 在「**一条通道都没登记**」时，按 AWS 的形态，必须报一个**有名字的第三种状态**——
本仓已有的名字是「**不可判**」（本仓纪律「空 ≠ 无」）。

★ **同时注意 AWS 选的是 fail open（继续发流量）而不是 fail closed**。
⇒ ★ **「不可判」之后要做什么，是一个独立决策，不能从「不可判」推出来。** 见 H5 §5 的建议：本机应选 **fail closed（报红）**，理由是本机的通道是**协作基础设施**而非**用户流量入口**，且我方已有「报红由人裁」的既有形态。

### 2.5 Kubernetes：**「没查」与「查了通过」在字面上可区分**（已读原文）

来源：<https://kubernetes.io/docs/reference/using-api/health-checks/>

未编辑原文（文档示例）：

```
$ curl -k 'https://localhost:6443/readyz?verbose&exclude=etcd'
[+]ping ok
[+]log ok
[+]etcd excluded: ok
...
```

且该页逐字：

> The `healthz` endpoint is **deprecated (since Kubernetes v1.16)**, and you should use the more specific `livez` and `readyz` endpoints instead.

⇒ ★ **`excluded: ok` 是一个独立状态**：它避免了「没查」被读成「查了通过」。
⇒ ★ **`healthz` 这个词本身被官方弃用**（因为一个词要同时管「活」和「能干活」）。

★ 与 `?verbose` 里那句配套（逐字）：

> This can be useful for a human operator... **it is not intended to be consumed by a machine**

⇒ **人读的详细报告里可以出现「excluded/跳过」，机器读的裁决位（状态码）里则必须是二值** ——
两者分开，才不会让「跳过」污染「通过」。本机 `beacon-check.py --selftest` 有**逐字对应的一条**（H5 §4）：

```
PASS 跳过 ≠ 通过（无 --net 的黑板指针必须 SKIP，不得 PASS）
```

⇒ ★★ **这条已经不是我们要引入的业界做法，是本机已经实现的同一条。**

### 2.6 NATS `/healthz`：**status 必填 + errors[] 结构化**（已读原文，schema）

来源：<https://docs.nats.io/reference/system/monitor/healthz.md>

未编辑原文（schema 节录）：

```
## Response Schema
Response from healthz monitoring endpoint
error string
errors object[]      ▶
status string required
status_code integer
```

⇒ ★ **`errors` 是 `object[]`（结构化的、逐子系统的），不是一句 "ok"**。且 `HealthzError` 枚举含 `Conn / BadRequest / JetStream / Account / Stream / Consumer`（见 H1 §2.2 源码 grep 原文）。

## 三、把五份规范并成一张表

| 规范 | 空集表示为什么 | 空集能被读成「健康」吗 | 逐字依据 |
|---|---|---|---|
| **Healthchecks.io** | `New` 态 | ❌ **不能** | "A newly created check that has not received any pings yet" ⇒ 独立态 |
| **Prometheus** | 无样本 ⇒ 须 `absent()` | ❌ **不能**（否则 `absent()` 无存在理由） | "returns ... 1 if the vector passed to it has no elements. This is useful for alerting on when no time series exist" |
| **gRPC** | `NOT_FOUND` / `SERVICE_UNKNOWN` | ❌ **不能** | "If the service name is not registered, the server returns a NOT_FOUND GRPC status" |
| **AWS ALB** | **fail open**（第三种裁决） | ❌ **不能**（但也不并进 unhealthy） | "the load balancer fails open" |
| **K8s apiserver** | `excluded: ok` | ❌ **不能** | 文档示例逐字 `[+]etcd excluded: ok` |

⇒ ★★★ **五份来自四个不同厂商、三个不同层级的规范，在这一点上完全一致。**
这不是巧合，是**必要条件**：任何健康端点若把空集并入通过，它的**发布机制本身**（摘流量 / 告警 / 重启）就会在空集时**静默失效**。

## 五、「空 ≠ 无」在本项目的严格形式

本仓纪律原文（见 `docs/next-phase-plan-20261012.md` 与 `notes/xdom/log/20261012T032424-int-discipline-triple-and-to-2bd0`）：

> **「空 ≠ 无」** —— 管**读数**。分母为 0 必须报「不可判」，不得报 OK。

★★ 把它**机械化成命端点的接口约束**（本文件的落地形式）：

| 输入 | 允许的响应 | 禁止的响应 |
|---|---|---|
| 读了 N 项，全绿（N ≥ 1） | `200` + 逐项明细 + `verdict: pass` | — |
| 读了 N 项，有红 | `503` + 逐项明细 + `verdict: fail` | — |
| **读了 0 项**（分母 = 0） | ★ `503` + 逐项明细 + `verdict: **undecidable**` | ★★ **禁止 `200` / `verdict: pass`** |
| **一项都读不到**（服务挂/超时） | ★ `503` + `verdict: **undecidable**` + `reason: unreachable` | ★★ **禁止沿用上一次的 pass** |
| **某项没查**（excluded） | ★ 该项必须显式标 `excluded`，**不得标 `ok`** | ★★ 禁止把「没查」并入「通过」 |

★ **最后一行是本机已经做对的一条**（`beacon-check.py --selftest` 逐字：`PASS 跳过 ≠ 通过…`），
  ⇒ **不需要新造，只需要把它接到 `drift-scan` 与未来的 `/health` 上。**

★ **「verdict: undecidable 时返回 503（fail closed）」是我方的选择，不是业界的唯一答案**：
  AWS 在同样情形下选 **fail open**（§2.4）。我方选 fail closed 的理由是**对方是协作基础设施、不是用户流量入口**，
  且本机已有「报红由人裁」的既有形态。**这是一个需要用户确认的决策点，本文件不代裁。**
