# 概念字典向量化评估 · 2026-08-31

> 评估：HR 司库 · 对象：concept-dict.py（R019 落地载体，当前 18 概念 JSON 存储）

## 一、结论：混合双轨（JSON 权威 + 向量语义层），非替换

概念字典「适合向量化」但**不适合纯向量化**——最佳方案是双轨（复用 v1.0.363 papers-db/paper-cache 仲裁先例）：

| 轨 | 存储 | 职责 | 适用场景 |
|---|---|---|---|
| A 权威轨 | JSON（现状） | 精确定义/来源/别名/状态 | 精确查证（名词术语）、add 登记、audit 健康 |
| B 语义轨 | bge-m3 嵌入（新） | 语义相似/别名发现/混淆深度检测 | 近似表达查证、suggest 去重 |

## 二、为什么需要向量层（3 个真实价值）

1. **别名/近似查证**：用户说「客户返图特征」→ 应命中「返图特征库」——JSON 字面匹配失败，向量语义命中（现在靠人工 alias，向量化后自动）
2. **suggest 去重增强**：新概念提取时，「返图特征」「返图特征集」等变体应与已登记的「返图特征库」判为同义（相似度>阈值）→ 减少重复登记
3. **混淆深度检测**：check 时不仅查字面公共词缀（特征库），还能发现语义相近概念

## 三、为什么不能纯向量化（3 个风险）

| 风险 | 说明 |
|---|---|
| 精确性损失 | 概念定义必须精确（返图特征库 ≠ 物品特征库——向量相似但语义不同），纯向量会误判同义 |
| 权威性 | 来源/别名/状态是结构化元数据，向量嵌入存不了 |
| 成本 | 每次 query 需嵌入（bge-m3 本地零订阅但需调用）；纯 JSON 查证零成本 |

## 四、实现方案（双轨）

concept-dict.py：
- JSON 权威轨（现状）：add/query 精确/audit/list
- 向量语义轨（新增）：
  - query --semantic <词> → bge-m3 嵌入 → 与字典概念向量对比 → 语义命中 TOP-K
  - suggest 增强 → 提取候选嵌入 → 与已登记比相似度 → 判「已覆盖」跳过
  - check 增强 → 语义相近概念提示（超越字面词缀）
- 存储：概念向量缓存在 data/concept-vectors.json（add 时生成，避免每次重算）

### 向量缓存设计
- add 概念时 → bge-m3 嵌入（name+def）→ 存 data/concept-vectors.json（{name: [1024 dims]}）
- query --semantic → 嵌入查询词 → 余弦相似度 vs 缓存 → TOP-K 命中
- 字典 18 概念 → 缓存 18×1024 floats ≈ 75KB（轻量）
- 零订阅：bge-m3 本地 Ollama（已实测可用 1024 维）

## 五、落地建议

| 优先级 | 动作 | 价值 |
|---|---|---|
| P1 | query --semantic 语义查证 | 高——解决别名/近似表达（用户实际会遇到） |
| P1 | suggest 增强（向量去重） | 高——减少重复登记噪音 |
| P2 | check 语义混淆增强 | 中——超越字面词缀检测 |
| P2 | 向量缓存（add 时生成） | 基础——避免每次重算嵌入 |

**成本**：全部本地 bge-m3 零订阅；字典小（18 概念）向量计算毫秒级。
