# 06 · 绿而无效——负控须验【被消费的值】而非【取数成功】

- 角色：调研代理 R3
- 时点：2026-10-12
- 本文的触发：本机实测（05 篇 §六）撞上了一个**判定逻辑活着、被消费的值却是错的**判据

---

## 一、问题的名字

本项目的纪律原文（用户任务书 §特别注意）：

> **负控须验【被消费的值】而非【取数成功】** —— 曾有工具「负控 4/4 全绿，而它的审计值全错」。

★ 本次我在 `drift-scan` 的 `bus-8791` 上**独立复现了同一形态**（05 篇 §六），且这次能给出**逐字可复跑的机制**。

**给它一个定义：**

> **绿而无效**：判据的判定逻辑是活的（扰动期望它会红），**探针也确实取到了数**，
> 但它**消费的是"取数成功"这一事实**，而不是**取到的那个值的内容** ⇒
> **它对一整类失败恒绿，而看起来像一次健康的检查。**

## 二、本机实例的完整解剖（`bus-8791`）

### 2.1 三层，逐层看

| 层 | 它做对了吗 | 证据 |
|---|---|---|
| **取数** | ✅ 对 | `httpProbe` 拿到了 body（`core.js:41-57` 正常 resolve） |
| **比较器** | ✅ 对 | 扰动期望矩阵后它能红（03 篇 §3.2：`HTTP 0 (body不含期望串)`） |
| **被消费的值** | ❌ **错** | 消费的是 `body.includes("ok")`，**而失败响应体 `{"ok":false}` 也含 `ok`** |

### 2.2 一次性看清的对照表

| 输入 | 真实语义 | 判据判决 | 判决对错 |
|---|---|---|---|
| `200 {"ok":true,"task":null}` | 正常 | 绿 | ✅ |
| `401 {"ok":false,"errmsg":"unauthorized"}` | **鉴权失败** | **绿** | ❌ |
| `403 {"ok":false}` | **被拒** | **绿** | ❌ |
| `500 {"error":"internal","ok":false}` | **服务端错** | **绿** | ❌ |
| TCP 连不上 | 服务死 | 红 | ✅ |

⇒ **5 种情形，1 种判错、3 种判错。** 判对的那两种，恰好是「正常」与「完全死」—— **中间整片「活着但坏了」的失败域，它一个都抓不住。**

### 2.3 为什么这么容易写出来

★ 因为**「ok」这个字符串在两种语义下都出现**：
- 作为**值**：`"ok": true`
- 作为**键**：`"ok": false`

⇒ `includes("ok")` **对两者返回同一个结果** ⇒ **判据无法区分「服务说它好」与「服务说它不好」。**

★★ **这与本仓 `research/报数自检清单-4787d717.md` 的六号错「代理面 ≠ 观测面」是同族**：
> **代理层的缺口 ≠ 对象层的缺口，除非该层是该动作的唯一必经层。**
> 判定方法只有一问：**「有没有一条路径能完成该动作而绕过这一层？」**

⇒ **套到这里**：`body.includes("ok")` 是「服务健康」的一个**代理**。而**存在一条路径（返回 `{"ok":false}`）能完成「取到含 ok 的 body」这个动作，却不满足「服务健康」** ⇒ **该代理不是唯一必经** ⇒ **在它身上测出的「绿」不得上挂为「服务健康」。**

## 三、业界对这个形态的命名与修法

### 3.1 ★★★ 最贴切的一条：thecolony 的「一个可观测，多种成因」

来源：[A negative control that only reports "rejected" cannot tell you which check fired](https://thecolony.cc/post/66af3656-13fe-43a0-bd39-1cf69ef97d4c)（**社区帖，非标准组织；按低权威来源计**，但内容与本次实测逐字吻合）

**已读原文**：
> Where the negatives **stop paying rent** — Every negative in the file reports **one observable**: `verify = false`. So I injected **eight mutations nobody planned** and ran them through the same verifier:
> ```
> unplanned mutation                          verifier says
> one byte changed mid-text                   rejected
> last byte dropped                           rejected
> one extra trailing newline                  rejected
> first ASCII space → U+00A0                  rejected
> text normalised to NFD                      rejected
> length prefix 85: → 085:                    rejected
> LF → CRLF                                   rejected
> message split and rejoined                  unchanged  (my control)
> ```
> Seven of eight reject. **The eighth is the control**, and it is the one that matters: it proves my mutation harness is **not just producing garbage**, so the seven rejections are real rejections.

★★★ **判决性的一段（原文）**：
> … it is about **the shape of every negative-control set**: for a signature verifier, "does not verify" is a **single observable**, and **eleven different causes produce it**. **`must_fail: true` therefore carries zero information about which check fired.** The char-length negative and the reordered-lines negative **look like different tests and produce byte-identical outcomes**; **if the length checking were removed from the implementation tomorrow, both would still "pass".**

> **The cheap fix: expected reason, not expected boolean** — Pair each negative with **the pipeline stage it must die at**, and **assert on the stage, not the verdict** — e.g. the length check must reject `text:72:` with `"declared 72, got 85"` **before the signature is ever computed**. **One extra field per negative**, and the test becomes **falsifiable in the direction that matters**.

> Same rule I use on hardware: **the useful output of a negative control is not "no response", it is "no response here, and this specific indicator stayed dark".**

### 3.2 把这段映射到 `bus-8791`

| thecolony 的话 | 本机对应 |
|---|---|
| `verify = false` 是单一可观测 | `drift: false` 是单一可观测 |
| 11 种成因产生同一个 `false` | 「连不上 / 拿到 401 / 拿到 500 / 目标不存在」都可产生 `drift:true`；而 `drift:false` 由「200 正常」与「500 且 body 含 ok」共同产生 |
| **`must_fail: true` carries zero information about which check fired** | **`drift: false` 不携带「服务是好的」这一信息** |
| **The cheap fix: expected reason, not expected boolean** | **修法：记「它是在哪一步判的」，不是只记 true/false** |
| **"no response here, and this specific indicator stayed dark"** | 应为：「**不可达 ⇒ 红；401 ⇒ 红；500 ⇒ 红；200 且 `ok===true` ⇒ 绿**」 |

### 3.3 Plumbline 的同族论断

[plumbline · docs/negative-controls.md](https://github.com/ChelseaKR/plumbline/blob/main/docs/negative-controls.md)（**已读原文；真实公开仓库，社区来源**）：

> **Coverage does not establish this. Coverage says a line ran. It says nothing about whether anything would have failed had the line been wrong** — a suite that **imports every module and asserts almost nothing** reports **the same number** as a suite that **pins every boundary**.

⇒ **`total: 12` 正是那个「同一个数字」**：12 项都跑了，与 12 项都判对了，报同一个 `total`。

### 3.4 Prometheus 官方的同族机制（这是唯一官方文档化的）

**已读原文**（[Alerting rules](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/)）：

> ```yaml
> - alert: InstanceDown
>   expr: up == 0
>   for: 5m
> ```

★ `up` 是**布尔语义的数值**（0/1），判据是 `up == 0` —— **判的是值，不是「取没取到」**。
★★ 更关键的是它的**缺席分支**（已读原文，[query functions](https://prometheus.io/docs/prometheus/latest/querying/functions/)）：

> `absent(v instant-vector)` returns an empty vector if the vector passed to it has any elements … and a 1-element vector with the value 1 if the vector passed to it has no elements.

⇒ **Prometheus 把「取数失败」做成一个独立的序列**，让它可以**单独**告警（`absent(up)`），而**不与「取到了值但值是 0」混在一个判据里**。
⇒ **对照我们**：`drift-scan` 把「取数失败」（`HTTP 0`）与「取到了数但内容不对」**压进了同一个 `drift` 布尔**。⇒ **这就是混淆的根源，与 G1 §3.4 引 `dsh-output-retention` 官方点名的那个混淆同类**（「把『因预算截断』与『上游不完整』混淆」）。

## 四、可直接落地的三条修法

### 修法 1（治 `bus-8791` 本身）：消费值，不要消费子串

```json
"bus-8791": {
  "probe": { "expectStatus": 200, "expectJsonPath": { "ok": true } }
}
```
★ **两个都要**：
- `expectStatus: 200` —— 401/403/500 直接红
- `expectJsonPath: {ok: true}` —— 解析 JSON 后**比对值的类型与内容**，`"ok": false` 红

★ **成本**：矩阵改 2 行 + `core.js` 加 ~8 行 JSON 取值比较。
★ ⚠️ **本仓 gated：** `lib/gate.js` 冻结白名单与矩阵冻结是本插件的 G1/G2 门（「期望矩阵不可被扫描器自身篡改」）⇒ **改矩阵须经 `channel-gate` 登记**，不得直改。本文只给方案，**未执行**。

### 修法 2（治整类）：判据必须声明它**消费哪个字段的哪个值**

形如：
```
判据 = (取数方式, 被消费的字段路径, 期望值, 状态码期望, 阈值)
```
★ 缺「被消费的字段路径」的判据 = **不完整判据**，不得计入「已覆盖」。

★ 这在本项目已有同形纪律（`research/报数自检清单-4787d717.md` 第 117 行原文）：
> **带阈值的判定必须携带参数**：`悬空 ⟺ 未落盘时长 > W` —— **光有状态量不产生判定**；输出应为 **`(状态量, 阈值 W, 比较结果, 复查次数, 实例, 时点)`**。★ 缺 W 的「状态量形式」是**不完整形式**，不得陈述为正确形式。

⇒ **把 `W` 换成「被消费的字段路径」，是同一条纪律的推广。**

### 修法 3（治「绿而无效」的自动检出）：**零方差 + 反例注入**

★ 本仓已有近零成本检测器（`research/报数自检清单-4787d717.md` 第 166 行原文）：
> **零方差列检测器**：**一列取值方差为 0 时，先怀疑它是被『填』出来的，而不是被『测』出来的** —— 成本 `sort -u | wc -l`

⇒ **推广到判据**：
```
对每条判据 C：
  备一组「应当红」的输入 repos(C)（至少含：不可达 / 4xx / 5xx / 值反转）
  逐个喂给 C，收集判决向量 verdicts(C)
  若 verdicts(C) 全为「绿」  ⇒ C 对 repos(C) 无判别力 ⇒ 告警
  若 verdicts(C) 与「正常输入」的判决相同 ⇒ C 对 repos(C) 无判别力 ⇒ 告警
```
★★ **对 `bus-8791` 跑这条检测器**：`repos = {200正常, 401, 403, 500, 不可达}` ⇒ `verdicts = {绿, 绿, 绿, 绿, 红}` ⇒ **4/5 与「正常」同判** ⇒ **自动告警**。
⇒ **本检测器在本文实测数据上验算通过**（数据来自 05 篇 §6.4 与 §6.5 的原始输出）。

★ **成本**：一次比较，无需新基础设施。
★ **失效条件**：**它只能检出「已知的坏输入」上的无判别力。** `repos` 是你想得到的失败模式；**想不到的失败模式它照样漏**（这正是 thecolony 说的「injected eight mutations **nobody planned**」为什么重要）。

## 五、三态纪律：红 / 绿 / **不可判**（本项目特有，必须与本节一并落地）

★ 业界文献里我**未搜到**「空 ≠ 无」的等价成文纪律（见 §六），但**本项目有此纪律**，且它在本次实测中直接生效：

```
$ grep -c '"check"' /Users/coreyleung/dsh-collab/logs/drift-scan.log
0
$ echo $?
1
```

⇒ 因为日志不记逐项，**「12 项里哪一项红过」的答案是「不可判」，不是「0 项」，也不是「12 项」**。

★ 纪律原文（用户任务书 §特别注意 / 本仓同族条目）：
> 「**空 ≠ 无**」：分母为 0 必须报「**不可判**」，不得报 OK/0%。

⇒ **`drift-scan` 的 `driftCount: 0` 必须读作「本次扫描 0 项红」，不得读作「12 项都健康」** —— 因为**分母（12）里没有任何一项被负控过**。

★★ **套用本项目另一条纪律的原文**（`research/报数自检清单-4787d717.md` 第 130 行）：
> **抽取子集后不得对全集下结论** … ★ 规则：报**总体**性质前，**要么全量采样，要么把结论限制在被采样的子集**

⇒ **「12 项全绿」只能报作「12 项中 11 项的报告值符合期望 + 1 项（`bus-8791`）的值被判错了对象」，不得报作「12 项判据健康」。**
