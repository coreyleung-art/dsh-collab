# 03 · 一条检查怎么被证明「能红」——安全造红输入的六种手法

- 角色：调研代理 R3
- 时点：2026-10-12
- 核心交付：**本次实际在本机跑了一遍负控**，命令与原始输出见 §三、§四

---

## 一、直答：证明一条检查「能红」= 造一个它**理应抓住**的输入，看它是否真的红

**关键区分（本文最重要的一条）：**

> ★★★ **扰动「期望」≠ 扰动「世界」。**

| 手法 | 扰动了什么 | 证明了什么 | 证不了什么 |
|---|---|---|---|
| **扰动期望矩阵** | 「我们认为什么是对的」 | **判定逻辑（比较器）会红** | 观测通道是否真的读到了世界 |
| **扰动被观测的世界** | 「世界本身」 | **整条链路（观测+判定）会红** | 昂贵、有副作用、可能影响生产 |

★ **只做前者会得到虚假的安全感**：一个「永远返回 200」的探针，配上一个再正确的比较器，也永远不红。
★ **只做后者会伤生产。** 所以正确做法是**两个都做，且只对「无副作用可注入」的那几项做后者**。

## 二、六种安全造红输入的手法（按本机可行性排序）

| # | 手法 | 副作用 | 本机适用性 |
|---|---|---|---|
| 1 | **影子副本 + 扰动期望矩阵** | 无（不碰生产） | ✅ **本次已用** |
| 2 | **指向死端口 / 不存在的对象名** | 无 | ✅ **本次已用** |
| 3 | **git 基线 + hash 证明破坏落地** | 无 | ⚠️ 本次未用（影子跑在 `/tmp`，非 git 仓） |
| 4 | **注入假数据（synthetic series / fixture）** | 无 | ✅ 业界标准手法（`promtool` 的 `input_series`） |
| 5 | **shadow 模式（同一探针同时打生产与影子目标）** | 无 | ⚠️ 需要探针支持双目标 |
| 6 | **dry-run** | 无 | ⚠️ **危险，见 §六·陷阱** |

### 2.1 手法的业界依据

- **#4 注入假数据**：`promtool` 的 `input_series` 就是官方形式的假数据注入（已读原文，见 02 篇 §二）。**这是唯一被 Prometheus 官方文档化的安全造红手法。**
- **#3 git 基线**：Plumbline 的六步规程，第 2 步「**Apply the sabotage, then PROVE it landed**」（已读原文，见 02 篇 §5.1）。
- **chaos engineering** 的对照组：principlesofchaos.org 第 4 步要求「look for a difference in **steady state between the control group and the experimental group**」（已读原文，见 01 篇 §2.4）。★ **对照组就是负控的学术名字。**

### 2.2 ★ 陷阱：dry-run 可能整体跳过被检对象

**这条不用上网查 —— 本项目已有实测教训**，出自 `research/报数自检清单-4787d717.md`（第 91 行，原文）：

> **测试模式可能跳过被检对象**（我第 14 条已发布错）：我用 `--dry-run` 断言『客户端不校验发送方身份』—— ★ 而**源码里归属守卫在 dry-run 下被整体跳过**（`if not force and not (dry_run or …)`）⇒ **该测试从未触到守卫**。★ 规则：**用某个运行模式做「某检查是否存在」的测试前，先确认该模式不跳过该检查**；否则测试结果只是模式的属性。

⇒ **dry-run 作为「安全造红」手段，其安全性正是它的危险**：模式本身可能绕过被判据检查的那段逻辑。
⇒ **判据：用 dry-run 造红之前，必须先证明「该模式不跳过被检逻辑」。**

## 三、本次实际做的负控实验（条件 1：扰动期望矩阵）

### 3.1 复跑命令

```bash
# 1) 建影子副本（不碰生产）
rm -rf /tmp/negctl && mkdir -p /tmp/negctl
cp -r /Users/coreyleung/dsh-plugin-drift-scan/lib /tmp/negctl/lib
cp /Users/coreyleung/dsh-plugin-drift-scan/package.json /tmp/negctl/

# 2) 逐项注入「应当变红」的期望值，跑扫描
cd /tmp/negctl && HOME=/tmp/negctl /opt/homebrew/bin/node negctl.mjs
```

★ 驱动脚本 `/tmp/negctl/negctl.mjs` 的扰动定义（对 12 项逐条）：
- `board-local` / `board-central` / `funnel-public` → `expect` 改指 `http://127.0.0.1:9`（**死端口**）
- `sse-8803` → 同上
- `bus-8791` → 同上
- `node-bridge` → `expect` 改为 `['--node-id NO-SUCH-NODE-XYZ']`
- `sync-from-central` / `device-daemon` → 改为 `no-such-process-xyz.py`
- `hb-fwd` → 改为 `com.dsh.NO-SUCH-JOB-XYZ`
- `tailscale-direct` → 改为 `['no-such-peer-xyz']`
- `e2-registry-services` → `requiredKeys` 改为 `['no-such-component-xyz']`
- `bus-8791 token 权限` → `tokenFile` 改为 `~/.dsh/no-such-token-xyz`

### 3.3 结论（第一条）

> ★★ **12/12 项的判定逻辑都能红。没有一项是「无论输入如何都不会红」的 A 类恒真。**

⇒ **但** —— 这个实验**只证明了比较器**，§四将说明**观测通道**仍有未验部分，而 **`bus-8791` 有一个更深的问题：它比较的对象是错的**（见 06 篇）。

## 四、本次实验的**边界**：我证了什么、没证什么

★ 这是本文最需要读者看清的一段。

| 层 | 本次证了吗 | 依据 |
|---|---|---|
| **判定逻辑**（期望 vs 实测 → drift 布尔） | ✅ **12/12 已证能红** | §3.2 |
| **观测通道 · HTTP 探针** | ⚠️ **部分**：指向死端口得 `HTTP 0` 并变红 ⇒ 探针**至少能报告「连不上」** | §3.2 的 `HTTP 0` |
| **观测通道 · 外部命令**（`ps`/`launchctl`/`tailscale`） | ❌ **未证** | 我用的是「不存在的对象名」，证的是**比对能红**；没有构造「命令返回垃圾/被劫持」的输入 |
| **观测通道 · 值被正确解读** | ❌ **未证，且已发现反例** | `bus-8791`，见 06 篇 |
| **端到端（真把服务停掉）** | ❌ **未做**（会伤生产） | — |

★★ **一句要紧的话**：
> 我证明了「**比较器**活着」，**没有**证明「**探针读到的是真东西**」。

⇒ **这正是本项目那条纪律的落点**：「**负控须验【被消费的值】而非【取数成功】」**（出处：用户本轮任务书 §特别注意；本仓 `research/报数自检清单-4787d717.md` 有同族条目多条）。

## 五、条件 2：如果要扰动「世界」——安全做法

对 12 项逐条评估「能不能安全地在世界上造红」：

| 项 | 世界侧造红手法 | 安全吗 |
|---|---|---|
| `board-local` / `board-central` | 停板 = 伤生产 | ❌ 不可 |
| `sse-8803` | 同上 | ❌ 不可 |
| `bus-8791` | 同上 | ❌ 不可 |
| `node-bridge` | 改 argv 需重启进程 | ❌ 不可 |
| `sync-from-central` | 停进程 | ❌ 不可 |
| `hb-fwd` | `launchctl unload` | ⚠️ 可逆但扰生产 |
| `device-daemon` | 停进程 | ❌ 不可 |
| `tailscale-direct` | 断对端 | ❌ 不可 |
| `funnel-public` | 关 Funnel | ❌ 不可 |
| `e2-registry-services` | 往注册表写缺组件的**影子键** | ✅ **可**（写一个新键，不改现键） |
| `bus-8791 token 权限` | `chmod` 再改回 | ⚠️ 可逆但碰真凭据 |

★ 结论：**12 项里，只有 1 项（`e2-registry-services`）能在「世界侧」无副作用造红**（向黑板写一个缺 `requiredKeys` 的影子键，指向它）。
★ 其余 11 项，**世界侧负控只能走「影子目标」路线**：把探针指到一个**专门搭的坏目标**（如起一个返回 500 的本地 HTTP 服务、起一个假进程名），而不是破坏生产目标。

⇒ **这正是 05 篇「最小可执行方案」的设计依据。**
