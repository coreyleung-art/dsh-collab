## 一、直答

**业界有一套成熟做法，但它没有一个统一的名字，而且没有「每条检查必须有一个会失败的测试用例」这条成文标准。**

四个最接近的名字，按成熟度排序：

| # | 名字 | 载体 | 是否成文标准 |
|---|---|---|---|
| 1 | **alert rule unit testing** | `promtool test rules`（Prometheus 官方文档） | ✅ **官方文档化** |
| 2 | **alert rule validation（分层）** | QASkills 指南 | ⚠️ 实践文章 |
| 3 | **negative control / defect matrix** | Plumbline 规程 | ⚠️ 社区仓库 |
| 4 | **rule sanity / vacuity / tautology check** | Certora `rule_sanity` | ✅ **官方文档化（形式验证域）** |

★ **重要区分**：
- **#1、#4 是官方文档化的机制**，可以直接抄。
- **#3 是社区规程**，最贴近我们「一个断言若从未红过，它就不是判据」这条纪律，但它**不是标准**。
- **没有**任何标准要求「每条检查必须有一个会失败的测试用例」。这条要求**以等价形态存在于 `promtool` 的 `exp_alerts: []` 与 Certora 的 vacuity check 里，但从未被写成一条通用强制条款。**

## 二、`promtool test rules` —— 官方文档化的告警单元测试

**已读原文**（[Unit testing for rules | Prometheus](https://prometheus.io/docs/prometheus/latest/configuration/unit_testing_rules/)）：

> You can use **`promtool`** to test your rules.
> ```bash
> # For a single test file.
> ./promtool test rules test.yml
> ```

测试文件结构（原文格式）：`rule_files` / `evaluation_interval` / `input_series` / **`alert_rule_test`** / `promql_expr_test`。

### ★★★ 最关键的一段：批注式负向断言

**已读原文**：

> Prometheus allows you to have same alertname for different alerting rules. … you have to list the union of all the firing alerts for the alertname under a single `<alert_test_case>`.
> ```
> # The time elapsed from start_timestamp when the alerts have to be checked.
> eval_time: <duration>
> # Name of the alert to be tested.
> alertname: <string>
> # List of expected alerts which are firing under the given alertname at
> # given evaluation time. **If you want to test if an alerting rule should
> # not be firing, then you can mention the above fields and leave
> # 'exp_alerts' empty.**
> exp_alerts:
>   [ - <alert> ]
> ```

★★★ **`exp_alerts: []` 就是「它必须不响」的官方写法。**

⇒ 这给了我们**直接可抄的判据形状**：
```
一条检查 = 两个测试用例
  用例 A：喂入该检查存在的那个缺陷  ⇒ 断言它必须红（exp_alerts 非空）
  用例 B：喂入无关输入              ⇒ 断言它必须不红（exp_alerts 留空）
```
⇒ **只写用例 A 是不够的**：那样「一个把所有输入都判红的坏检查」也会通过。这正是 03 篇 §四「双重断言」的来源。

## 四、QASkills 的「分层验证」——把一口气的检查拆成 6 层

**已读原文**（[Observability Testing for Alert Rule Validation: From PromQL to Paging](https://qaskills.sh/blog/observability-testing-alert-rule-validation)，2026-08-08，**社区技术文章，非标准组织**）：

> **Observability testing alert rule validation** is the practice of treating **every alert as executable production logic**. Parse and lint the rule, evaluate it against **synthetic time series**, test the **pending-to-firing boundary**, validate labels and annotations, check notification routing, and then exercise the metric pipeline in a controlled environment.

原文给出的分层表（逐字转述）：

| Layer | Catches | Cadence | Failure owner |
|---|---|---|---|
| Parse and syntax | Invalid rule files, malformed expressions | Every change | Rule author |
| **Evaluation unit test** | **Threshold, grouping, timing, label output** | Every change | Service and observability owners |
| Static policy check | Missing runbook, unknown severity, naming violations | Every change | Platform policy owner |
| Integration check | Scrape labels, recording rules, real evaluation | Pre-merge | Telemetry pipeline owner |
| Routing check | Matcher, grouping, receiver selection | Every routing change | On-call platform owner |
| Delivery exercise | Transport and receiver integration | Scheduled and controlled | Incident tooling owner |

★★ 两条可直接照抄的判断（原文）：

> These layers **should not all send notifications**. Unit tests and policy checks operate on files.
> What people get wrong is calling a **successful test notification** an alert-rule test. A manually sent payload **can prove that a receiver accepts a message, but it does not evaluate the PromQL expression, preserve the `for` state, or prove that production metric labels reach the rule**. **Delivery is the last link, not a substitute for earlier layers.**

★★★ 最后一段**逐字命中我们的处境**：
- 我们做过「发一张测试卡」= **delivery exercise**
- 我们**没做过**「阈值/分组/时序/标签是否被判对」= **evaluation unit test**
- 且我们连「哪一层失败了」都分不出来 —— 因为 12 项共用一个 `drift` 布尔

★ 另一条原文（可作为我们写判据时的方向）：
> **Never infer a page threshold from a dashboard's red color.** Dashboards support exploration, while alerts interrupt people and therefore need an explicit action.
> The alert name should describe **a condition**, not an assumed root cause. `CheckoutHighErrorRatio` is testable from request metrics. `CheckoutDatabaseBroken` **overclaims** unless the expression directly and reliably measures the database failure.

⇒ **判据命名必须描述「被观测的条件」，不得描述「推测的根因」。** 对照我们的 `sync-from-central`（描述条件：进程在跑）与 `e2-registry-services`（描述条件：key 在位）——**命名方向是对的**；但 `drift: false` 这个**总判决名**描述的不是条件，是结论。

## 五、Plumbline 的负控规程 —— 与我们的纪律几乎逐字同构

**已读原文**（[ChelseaKR/plumbline · docs/negative-controls.md](https://github.com/ChelseaKR/plumbline/blob/main/docs/negative-controls.md)；仓库真实性已核：GitHub API 返回 `"id": 1335380919, "private": false`，**真实公开仓库**；作者非标准组织，**按社区来源计**）：

> **Observed failing, or it is not a gate**
> A suite that has **never been observed failing** is **indistinguishable from a suite that cannot fail**, and a **wall of green ticks proves nothing** about which one you have.

★★★ 这一句与我们的纪律「**一个断言若从未红过，它就不是判据**」**是同一条**，但它是 2026 年社区文档，**不是来源**。⇒ **我们的纪律不是抄来的，是独立得出的；但也确实不是我们的独创。** 引用时须写：*与社区实践同构，非本项目独创，也非业界标准。*

### 5.1 六条可抄的规程细节（原文）

1. **双重断言（每行断言两次）**
   > It **asserts twice per row**. The suite under test **must fail**, and the suites that **should be indifferent must keep passing**. **Without the second assertion a sabotage crude enough to trip everything reads as a clean row.**

2. **先跑未破坏对照并断言它通过**
   > It **runs an unsabotaged control first, and asserts it passes**. Without that, every suite would "fail on its defect" because every suite was already failing, and the matrix would be a **wall of green rows meaning nothing**.

3. **证明破坏真的落地了（不是「我试图破坏了」）**
   > ```bash
   > # 0. Commit first. A committed baseline survives a process death; a copy does not.
   > git add path/to/file.py && git commit -m "baseline before control"
   > # 1. Take the baseline as an object hash.
   > git hash-object path/to/file.py      # -> BASE
   > # 2. Apply the sabotage, then PROVE it landed.
   > git hash-object path/to/file.py      # -> must NOT equal BASE
   > # 3. Run the suite. Confirm it goes red on exactly the tests you expect,
   > #    and that the tests you expect to be indifferent stay green.
   > # 4. Clear stale bytecode before you trust anything about the restore.
   > find . -name __pycache__ -type d -prune -exec rm -rf {} +
   > # 5. Restore, and assert the hash matches BASE exactly.
   > git checkout -- path/to/file.py && git hash-object path/to/file.py  # -> must equal BASE
   > ```
   > **Step 2 is the one people skip** and the one that earn[s]…

4. **对对照本身再做一次对照（control on the control）**
   > The same file also **plants a case declaring the wrong suite**, to establish that a row which stops holding is **reported rather than absorbed**.

5. **变异「证据」而非「测试夹具」**
   > It **mutates the evidence, not the harness**. Every planted defect is an edit to **what the target is recorded as having said**. The defects arrive **through the front door**, the way a real one would.

6. **覆盖率不能替代负控**（原文）
   > **Coverage does not establish this. Coverage says a line ran. It says nothing about whether anything would have failed had the line been wrong** — a suite that imports every module and asserts almost nothing reports **the same number** as a suite that pins every boundary.

★ 第 6 条直接对应我们的处境：`drift-scan` 的 `total: 12` 是**覆盖率数字**（12 项都跑了），它**不告诉你任何一项判错时会不会红**。

### 5.2 与我们的纪律逐条对照

| Plumbline 规程 | 我们的等价纪律（出处） | 本机有没有做到 |
|---|---|---|
| 必须先观察到失败 | 「一个断言若从未红过，它就不是判据」 | ❌ 12 项无逐项红记录 |
| 双重断言（该红的红、该绿的绿） | 未见于本仓 | ❌ 无 |
| 先跑未破坏对照 | 报数自检清单「阳性对照」（`research/报数自检清单-4787d717.md` §二·6） | ❌ drift-scan 无 |
| 证明破坏落地（hash 比对） | 报数自检清单「写操作与观测分离」（`trae:E20/E23`） | ❌ 无 |
| control on the control | 未见于本仓 | ❌ 无 |
| 覆盖率 ≠ 负控 | 报数自检清单「零方差列检测器」 | ⚠️ **有同类思想，未施加到 drift-scan** |
