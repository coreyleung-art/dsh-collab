## 一、先给结论

**业界保证「监控自身是活的」用的不是「更强的监控」，而是三类互相独立的结构：**

| 类 | 机制 | 判定方在哪 | 关键性质 |
|---|---|---|---|
| **A · 缺席语义** | dead man's switch / watchdog alert / heartbeat | **在被监控对象之外** | 「信号停止」本身就是事件 |
| **B · 外部黑盒探针** | synthetic monitoring / blackbox exporter / canary | **在探针进程之外** | 从用户视角测，不依赖被测系统自报 |
| **C · 稳态假设实验** | chaos engineering | **在控制系统之外** | 先定义稳态，再主动破坏，看稳态是否被察觉 |

★ 三类的共同点：**判定方都不在「被判定对象」内部**。这与 G1 §2.2 已读原文的结论一致（PromLabs：「Even if you build the most reliable internal meta-monitoring infrastructure, something can still go wrong」）。

## 二、术语逐条（附一手来源与等级）

### 2.1 dead man's switch / watchdog / heartbeat —— 缺席语义

**已读原文**（[healthchecks.io/docs](https://healthchecks.io/docs/)，本次重读确认）：

> It **keeps silent as long as pings arrive on time**. It **raises an alert as soon as a ping does not arrive on time**.
> … works as a **dead man's switch** for processes that need to run continuously or on a regular, known schedule.

★ 状态机（原文逐字）：`New` / `Up` / **`Late`** / `Down` / `Paused`，外加 **`Grace Time`**。
★ **`Late` 是把「还没到」与「坏了」分开的中间态** —— 没有它，只有「完全没反应」才能被发现。

**已读原文**（[paulsprogrammingnotes.com 2026-07-05](https://www.paulsprogrammingnotes.com/2026/07/dead-mans-switch-single-host-monitoring.html)）—— 单机监控栈的同类实践，与我们的拓扑形态最接近：

> Prometheus **once sat dead for two days before I noticed**, and only because a dashboard had gone blank.
> The fix is a dead man's switch: **an alert that fires constantly**, routed to an outside service that **complains when it stops arriving**. Every other alert fires when something breaks; **this one fires all the time, and silence is the failure signal**.
> The rule is just `vector(1)` … `send_resolved: false` so the "resolved" call doesn't muddy the heartbeat.

★ 两条我此前未记录的实操细节：**`send_resolved: false`**（否则 resolved 回调会污染心跳）与 **ping URL 存 git-ignored 文件**。

**已读原文（转引，本仓 G1 已取）**：kube-prometheus `Watchdog` 的 `expr: vector(1)`、`severity: none`；PromLabs 的「watchdog alert (also sometimes called a "dead man's switch", sentinel alert, beacon alert, or heartbeat alert)」。**本文不重复引用，见 G1 §2.1。**

### 2.2 `up` 指标与 `absent()` —— 缺席在 PromQL 里的表达

**已读原文**（[Prometheus querying/functions](https://prometheus.io/docs/prometheus/latest/querying/functions/)）：

> `absent(v instant-vector)` returns an empty vector if the vector passed to it has any elements … and **a 1-element vector with the value 1 if the vector passed to it has no elements**. **This is useful for alerting on when no time series exist** for a given metric name and label combination.

★ 关键机制：**`absent()` 让「系列不存在」变成一个可被 `> 0` 判定的数**。缺席从「没有数据」变成「有一个值为 1 的点」。

**已读原文**（[Prometheus alerting rules](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/)）：

> An alert for any instance that is unreachable … `- alert: InstanceDown  expr: up == 0  for: 5m`

★ 注意 `up == 0` 与 `absent(up)` 是**两种不同的缺席**：
- `up == 0` = 抓取发生了，但目标不健康
- `absent(up)` = **抓取本身没发生**（多用于「Prometheus 自己没在抓」）
★ 我们的 12 项目前**只覆盖前者（目标不健康），完全不覆盖后者（探针没在跑）**。

### 2.3 synthetic monitoring / blackbox exporter / canary —— 外部黑盒探针

**已读原文**（[prometheus/blackbox_exporter](https://github.com/prometheus/blackbox_exporter)）：

> The blackbox exporter allows **blackbox probing of endpoints** over HTTP, HTTPS, DNS, TCP, ICMP and gRPC.
> `http://localhost:9115/probe?target=google.com&module=http_2xx` will return metrics for a HTTP probe … The **`probe_success`** metric indicates if the probe succeeded.
> **Metrics concerning the operation of the exporter itself are available at the endpoint `http://localhost:9115/metrics`.**

★★ 最后一句是最有价值的一条：**被探测对象的指标与探测器自身的指标分开暴露**。
- `/probe` = 「目标活没活」
- `/metrics` = 「**探测器自己活没活**」

⇒ **业界把「目标健康」与「仪器健康」做成两个不同的序列**，于是 `probe_success == 0` 与 `up{job="blackbox"} == 0` 是两件事，可分别告警。**我们的 12 项把两者混成了一个 `drift: false`。**

★ synthetic monitoring / canary 的术语我本轮**未取到一手定义页**（见 §五·阴性证据）。Grafana/Backbox 文档只给了黑盒探针形态，未给「canary」的规范定义。

### 2.4 chaos engineering 的「稳态假设」

**已读原文**（[principlesofchaos.org](https://principlesofchaos.org/)，Last Update 2019-03）：

> These experiments follow four steps:
> 1. Start by defining **'steady state'** as some measurable output of a system that indicates normal behavior.
> 2. **Hypothesize that this steady state will continue** in both the control group and the experimental group.
> 3. **Introduce variables** that reflect real world events like servers that crash, hard drives that malfunction, network connections that are severed, etc.
> 4. **Try to disprove the hypothesis** by looking for a difference in steady state between the control group and the experimental group.

> **Build a Hypothesis around Steady State Behavior** — Focus on the **measurable output** of a system, rather than internal attributes of the system.
> … Chaos verifies that **the system does work**, rather than trying to **validate how it works**.

★★★ 对我们最要紧的是第 1 步与「control group」这个概念：
> **实验必须同时有对照组（control group）与实验组（experimental group）。**

⇒ 这**就是负控的学术名字**：**对照组**。
⇒ 我们的 12 项 `drift-scan` 天天跑，**只有实验组（生产矩阵），从来没有对照组（故意造坏的矩阵）**。所以 553 条日志全部是「实验组」的读数，没有一条是「对照组」的读数 ⇒ **无法区分「稳态真的被维持」与「测量本身失灵」**。

★ 注意：chaos engineering 的「P4 Try to disprove the hypothesis」与我们的纪律「一个断言若从未红过，它就不是判据」**同构但不等同** —— 它要求的是**主动造破坏去否证**，我们要求的是**观察它红过没有**。前者更强。

## 三、把术语映射到本机 12 项（本文的增量）

| 业界机制 | 本机 12 项里有没有 | 证据 |
|---|---|---|
| 缺席语义（dead man's switch） | ❌ **没有** | 12 项全是「存在/可达」类判据，无一项是「本该出现但没出现」 |
| `Late` 中间态 + Grace Time | ❌ 没有 | 只有二值 `drift: true/false` |
| 仪器自身指标与目标指标分离 | ❌ **没有** | 12 项共用一个 `drift` 布尔，仪器好坏与目标好坏不可分 |
| 外部黑盒探针（判定方在外） | ⚠️ **部分** | `funnel-public` 探公网入口，算「从外测」；但探针仍在本机 |
| 对照组（control group） | ❌ **没有** | 见 §四 |
| 稳态假设 + 主动否证 | ❌ 没有 | 只做被动读数 |

★ 结论：**12 项里，一条缺席语义都没有；而 G1 已指出「我们缺的不是更好的监控，而是缺席语义」。本文从「判据负控」这个角度独立复现了 G1 的结论。**

## 四、本机实测：没有对照组（复跑命令 + 原始输出 + 退出码）

```bash
$ cd /Users/coreyleung/dsh-collab
$ grep -o '"result":"[A-Z]*"' logs/drift-scan.log | sort | uniq -c
    156 "result":"CLEAN"
    397 "result":"DRIFT"
$ echo "EXIT=$?"
EXIT=0
```

```bash
$ wc -l < logs/drift-scan.log
562
$ echo $?
0
```

★ 553 条（写作时点为 562，其间另有并发写入者，见 05 篇）日志里 **397 次 DRIFT**。这**否证了「从未红过」这一假设**——`drift-scan` 作为**整体**红过。

★★ **但**：

```bash
$ grep -c '"check"' logs/drift-scan.log
0
$ echo $?
1
```

⇒ **日志每行只有 `at / action / result / driftCount / total` 五个字段，`"check"` 出现 0 次。**
⇒ **「12 项里哪一项红过」在日志里根本不存在。**
⇒ 397 次 DRIFT 里，**每一次的 red 项是无法回查的**。

★ **这正是一条「绿而无效」**：我们**有**红的历史记录（397 条），却**无法回答**「哪条判据红过」—— 那正是我们要问的问题。**记录了判决，没记录判决的对象。**
