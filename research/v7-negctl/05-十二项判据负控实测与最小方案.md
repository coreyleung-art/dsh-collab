## 六、★ 已实测的「绿而无效」实例：`bus-8791`

### 6.1 判据原文（`lib/channel-matrix.json`）

```json
"bus-8791": {
  "kind": "endpoint-token",
  "expect": "http://xingqiao.meetfunbp.com:8791/bus/receive?target=mac-mini",
  "tokenFile": "~/.dsh/bus-bridge-token",
  "tokenPerm": "0600",
  "probe": { "expectBodyContains": "ok" }
}
```
★ **注意：没有 `expectStatus`。** 唯一判据是 `expectBodyContains: "ok"`。
★ `core.js:84-88`：`const hit = r.body.includes(spec.probe.expectBodyContains);`

### 6.2 影子副本实测：判据在 **HTTP 401** 下判绿

隔离跑（`HOME=/tmp/negctl`）原始输出：
```
green  bus-8791                 | HTTP 401 (body含期望串)
```
⇒ **状态码 401（鉴权失败）被判为 `drift: false`。**

### 6.3 为什么：`"ok"` 是**子串**，而失败响应体里也有 `ok`

```bash
$ curl -s -i --max-time 8 "http://xingqiao.meetfunbp.com:8791/bus/receive?target=mac-mini"
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{"ok":false,"errmsg":"unauthorized"}
$ echo "EXIT=$?"
EXIT=0
```
⇒ 响应体是 `{"ok":false,...}`，**而 `body.includes("ok")` 对 `"ok":false` 中的键名 `ok` 成立 ⇒ 命中 ⇒ 判绿。**

### 6.4 子串恒真范围（直接验算，原始输出）

```bash
$ /opt/homebrew/bin/node -e "
const cases = {
  '401失败体 {\"ok\":false,\"errmsg\":\"unauthorized\"}': '{\"ok\":false,\"errmsg\":\"unauthorized\"}',
  '403失败体 {\"ok\":false}': '{\"ok\":false}',
  '500错误页 {\"error\":\"internal\",\"ok\":false}': '{\"error\":\"internal\",\"ok\":false}',
  '真实不可达 HTML 404': '<html><body>404 Not Found</body></html>',
};
for (const [k,v] of Object.entries(cases)) console.log((v.includes('ok')?'绿(通过)':'红(拦截)')+'  <=  '+k);
"
绿(通过)  <=  401失败体 {"ok":false,"errmsg":"unauthorized"}
绿(通过)  <=  403失败体 {"ok":false}
绿(通过)  <=  500错误页 {"error":"internal","ok":false}
红(拦截)  <=  真实不可达 HTML 404
$ echo "EXIT=$?"
EXIT=0
```

### 6.5 真实成功响应对照

```bash
$ TOKEN=$(cat ~/.dsh/bus-bridge-token)
$ curl -s -o /tmp/negctl/bus-body.txt -w "HTTP=%{http_code}\n" --max-time 8 \
    -H "X-Webhook-Token: $TOKEN" "http://xingqiao.meetfunbp.com:8791/bus/receive?target=mac-mini"
HTTP=200
$ cat /tmp/negctl/bus-body.txt
{"ok":true,"task":null}
$ echo "EXIT=$?"
EXIT=0
```

### 6.6 ★★★ 结论

| 输入 | 真实含义 | `bus-8791` 判决 |
|---|---|---|
| `HTTP 200 {"ok":true,"task":null}` | 服务正常 | **绿** |
| `HTTP 401 {"ok":false,"errmsg":"unauthorized"}` | **鉴权失败** | **绿** |
| `HTTP 403 {"ok":false}` | **被拒** | **绿** |
| `HTTP 500 {"error":"internal","ok":false}` | **服务端错** | **绿** |
| 完全不可达 | 服务死 | 红 |

⇒ **该判据对「服务坏了」这一整类失败**（401/403/500）**零判别力**；只在「完全不可达」时才红。
⇒ **它就是本项目的「绿而无效」定义**：**取数成功了（拿到了 body），被消费的值却读错了**（读的是「body 里出没出现过 `ok` 这三个字母」，而不是「`ok` 的值是不是 `true`」）。

★ **与 03 篇的关系**：03 篇只扰动**期望矩阵**，`bus-8791` 照样能红（改成死端口就红）。**是我把**真实**的失败响应喂给它，才暴露了这个缺陷。** ⇒ **这证明了 03 篇 §四 那条边界是真边界，不是免责条款。**

★ 详细机制与业界对照见 **06 篇**。

## 七、★ 最小可执行方案（Q5 直答）

### 7.1 如果只能做一件事

> ### 给 12 项**逐项**记一条「首次负控记录」，并把日志升级为**逐项**记录。

**不做**：不加新监控、不加新守护、不改矩阵、不改探针。
**只做**：① 日志加 `check` 字段；② 12 项各跑一次负控，把「红过」这件事**留成制品**。

### 7.2 为什么是这两件（而不是别的）

| 候选动作 | 为什么不是它 |
|---|---|
| 加一个 watchdog / dead man's switch | ❌ 治的是「缺席」，**治不了**「有值但值错」（§六 的 `bus-8791` 有值、有判决、全绿） |
| 把 12 项都改成 `expectStatus` | ⚠️ 只治 `bus-8791` 一类，且**仍不产生负控记录** |
| 跑一次全量世界侧负控 | ❌ 11/12 项无安全注入面（03 篇 §五） |
| **逐项日志 + 首次负控制档** | ✅ **成本最低、且它使「A/B/C 三类」第一次可判** |

★ 依据（02 篇 §5.1 已读原文，Plumbline）：
> **Coverage says a line ran. It says nothing about whether anything would have failed had the line been wrong.**

⇒ **`total: 12` 是覆盖率数字。`check: "xxx", drift: true` 才是判据数字。** 我们缺的是后者。

### 7.3 成本

| 项 | 估算 | 说明 |
|---|---|---|
| 日志加 `check` 字段 | **~5 行代码** | `core.js:184` 的 `logLine({...})` 改成循环逐项写 |
| 12 项首次负控 | **~1 人时** | 03 篇的 `/tmp/negctl/negctl.mjs` **已跑通，可直接复用**（脚本在 `/tmp`，需固化进仓） |
| 逐项红记录落盘 | **~0** | 复用现有 `logLine` |
| **合计** | **半天内** | 不含世界侧负控 |

### 7.4 ★★ 失效条件（这一栏不写就是「我已经加了保护」的错觉）

依本仓 `research/报数自检清单-4787d717.md` 第 97 行纪律：
> **凡提出判据，须同时给【它防哪个失效模式】与【它不防哪个失效模式】两栏。**

| 它防 | 它不防 |
|---|---|
| 「哪一项红过」不可查 | ❌ **不防 §六 的「绿而无效」**：`bus-8791` 会留下 `drift:false` 的记录，**看起来像一次成功的负控** |
| 「从未红过」与「不能红」不可分（B 类可判） | ❌ **不防 A 类**：若某判据恒真，逐项日志只会忠实记录它**一直绿** |
| 多写入者无标识导致读数混淆 | ❌ **不防观测通道被劫持**（`ps` 返回垃圾） |
| — | ❌ **不防「负控脚本本身跳过了被检逻辑」**（03 篇 §2.2 的 dry-run 陷阱） |

★★ **最要紧的一条失效条件（必须写进方案）**：
> **日志逐项化 + 跑一次负控，会产出一张「12/12 已负控」的绿表。**
> **而 03 篇已证：这张表只覆盖「比较器」，不覆盖「探针读到的是真值」。**
> ⇒ **方案若被读成「12 项已验证」，它造成的危害比不做更大** —— 因为**带阳性对照的错误否定判断更可信**（本仓 `research/报数自检清单-4787d717.md` 第 137 行原文：「**不完整的格套比没有格套更危险**」）。

### 7.5 因此方案的**第二个必带字段**

每条负控记录必须**同时**记三样，缺一不得发布：

```
{ check: "<项名>",
  negctl_input: "<注入的坏输入>",
  expected_red: true,        // 该输入下本该红
  observed: "red|green",     // 实际
  observed_reason: "<红在哪一步/绿在哪一步>",   // ★ 这一栏是防「绿而无效」的
  at: "<ISO>", instance: "<哪台机>" }
```
★ `observed_reason` 是**本方案唯一的真正防线**：它逼回答「**它是在哪一步判的**」。
⇒ 就 `bus-8791` 而言，若强制填这一栏，填的人必须写下「因为 body 含子串 `ok`」 —— **这句话一写出来，缺陷就自己暴露了。**

★ 依据（社区来源，见 06 篇 §三）：
> **the useful output of a negative control is not "no response", it is "no response here, and this specific indicator stayed dark".**
