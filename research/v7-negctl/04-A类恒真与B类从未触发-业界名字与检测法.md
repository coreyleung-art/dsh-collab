# 04 · A 类（恒真）与 B 类（从未触发）怎么区分——业界的名字与检测法

- 角色：调研代理 R3
- 时点：2026-10-12
- 证据等级：**已读原文** / 仅见摘要 / **未查证**

---

## 一、直答：业界有两套独立命名，分别来自形式验证与软件测试

| 本项目的说法 | 形式验证的名字（Certora） | 软件测试的名字（mutation testing） |
|---|---|---|
| **A 类 · 恒真**（无论输入如何都不红） | **assert tautology** / **trivial invariant** | **weak test**（never kills a mutant） / **equivalent mutant** |
| **B 类 · 从未触发**（逻辑上会红，只是没赶上） | **vacuous rule**（规则把输入空间排除空了） | **dead code / unreachable branch** |

★★ **关键结论：A 与 B 的区分法，业界不是「等它红一次」，而是「用工具自动判定」。**

★ Certora 的 `rule_sanity` **就是为这个目的造的**：它不问「这条规则红过没有」，它**直接检查这条规则是不是恒真的、是不是真空的**。

## 二、形式验证侧：Certora `rule_sanity`（已读原文）

来源：<https://docs.certora.com/en/latest/docs/prover/checking/sanity.html>

### 2.1 原文（逐字）

> The **`rule_sanity`** option enables some automatic checks that can warn users about certain classes of mistakes in specifications. There are several kinds of sanity checks:
> - **Vacuity checks** determines whether rules **pass vacuously because they rule out all models**.
> - **Trivial invariant checks** detects invariants that **hold in all states, rather than just reachable states**.
> - **Assert tautology checks** determines whether individual **assert statements are tautologies**.
> - **Assertion structure checks** detects unnecessarily complex assert statements.
> - **Redundant require checks** detects unnecessary require statements.
>
> The `rule_sanity` option may get one of the `none`, `basic`, or `advanced` values …
> - When not using the `rule_sanity` option at all, or when using it with the value `basic`, the **vacuity and trivial invariant checks** are performed.
> - When using the value `none`, no sanity checks are performed.
> - When using the value `advanced`, all sanity checks will be performed for all invariants and rules.

★ 注意默认值：**`basic`（不做任何设置时）= 跑 vacuity + trivial invariant**。
⇒ **业界把「A/B 检测」放在了默认开启的位置**，不是可选的额外功夫。

### 2.2 Vacuity checks（原文）

> The **vacuity** sanity check ensures that **even when ignoring all the user-provided assertions, the end of the rule is reachable**. This check ensures that the combination of `require` statements **does not rule out all possible counterexamples**. Rules that rule out all possible counterexamples are called **vacuous rules**. **Since they don't actually check any assertions, they are almost certainly incorrect.**

固定例（原文）：
```
rule vacuous {
    uint x;
    require x > 2;
    require x < 1;        // ← 与上一条矛盾 ⇒ 输入空间为空
    assert f(x) == 2, "f must return 2";
}
```
★ **`require x > 2` 与 `require x < 1` 同时成立 ⇒ 没有模型 ⇒ 断言从未被真正检验 ⇒ 规则永远「通过」。**

★★ **这就是 B 类的严格形式**：**不是「输入没赶上」，而是「输入空间被自己的前置条件排空了」**。
⇒ 对我们的意义：**如果一条判据的前置条件本身把「会红的输入」排除了，它就是一个 vacuous 判据** —— 它**永远绿**，但**不是**因为对象健康，而是因为**它从不去看会坏的那种情形**。

### 2.3 Trivial invariant checks（原文）

> **Trivial invariant checks** detects invariants that **hold in all states, rather than just reachable states**.

★★ **这就是 A 类的严格形式**：「在所有状态都成立」⇒ **它在任何输入下都为真 ⇒ 零判别力**。

★ 注意 Certora 的用词很精确：**不是「恒真」，而是「在所有状态包括不可达状态都成立」**。一个真正有用的不变量**只应在可达状态成立**。

### 2.4 Assert tautology checks（原文）

> **Assert tautology checks** determines whether individual **assert statements are tautologies**.

★ 力度比 trivial invariant 更细：**逐条断言**判定它是不是恒真。**这可以直接映射到我们「逐项判据」的粒度** —— 12 项应该逐项做这件事，而不是只看总判决。

## 三、软件测试侧：mutation testing（已读原文）

来源：<https://en.wikipedia.org/wiki/Mutation_testing>（**百科，非一手标准；但术语定义清晰，作为术语来源可接受**）

### 3.1 原文关键段

> Mutation testing … is used to design new software tests and to **evaluate the quality of existing software tests**. Mutation testing involves making **small changes to the program being tested**. Each changed version is called a **mutant**. A test **detects, and therefore rejects, a mutant upon test failure** … Rejection is called **killing the mutant**. The value of a test suite is measured by **the percentage of mutants that it kills**.

> … it can also indicate that **the mutation introduces no faults**. That is, the mutation is a **valid change** … One (common) way a mutant can be valid is that the code that has been changed is **"dead code" that is never executed**.

> **Goals** … identify weakly tested pieces of code (those for which mutants are not killed); **identify weak tests (those that never kill mutants)**; compute the **mutation score**.

### 3.2 ★★★ 最强的一条映射

> **identify weak tests (those that never kill mutants)**

⇒ **「从未杀死任何变异体的测试」就是 B 类的严格对应物。**
⇒ 而且它**清楚地说明了为什么不能由「没红过」判它无效**：**一个测试没杀死变异体，可能是测试弱（A 类），也可能是那个变异体是等价的/死代码（B 类）。**

★ 维基原文甚至直接点名了这层混淆的哲学名字：
> (This technological problem is itself an instance of a deeper philosophical problem named **"Quis custodiet ipsos custodes?"** ["Who will guard the guards?"].)

★★ **这正是本仓 G3 §七已记录但「本轮未找到权威一手来源」的那一条** —— **G3 说「『谁会看住看门人』的递归终止，未找到权威一手来源，不编」。**
⇒ **本条可回填 G3**：mutation testing 用「**变异体必须被杀**」给出了这个递归的**工程终止条件** ——
> **不需要无限递归，只需要一个「由外部造出的、已知应当被抓住的坏输入」，看它有没有被抓住。**

## 四、可操作的判别法（本文的直接产出）

给定一条从未红过的判据 `C`：

```
第 1 步：造一个「C 理应抓住」的坏输入 I。
第 2 步：跑 C(I)。
    ├─ C(I) = 红  ⇒  C 有断言力。此前未红属 B 类（历史原因）⇒ 记录本次为首次负控。
    └─ C(I) = 绿  ⇒  进入第 3 步。
第 3 步：区分「坏输入没进得去」还是「进去了却不被判」。
    检查 I 是否真的到达了 C 的判定点（例如：I 是否被前置条件/短路/模式开关拦掉了）。
    ├─ I 没进去（被测对象没收到 I）  ⇒  B 类·输入空间被排空（= Certora 的 vacuous rule）
    │                                  修法：改前置条件，让 I 能到达判定点。
    └─ I 进去了但没被判                    ⇒  A 类·恒真/无判别力（= trivial invariant）
                                       修法：改写断言本身（换被消费的值、加状态码、加阈值）。
第 4 步：只有在第 3 步「I 确实到了判定点且没被判」时，才可判 A 类。
        ★ 缺第 3 步就对 A 类下判断 = 把一个 B 类误判为 A 类而改写掉一条本来有效的判据。
```

★ **第 3 步是本项目既有纪律的落点**（`research/报数自检清单-4787d717.md` 第 91 行原文）：
> **测试模式可能跳过被检对象** … ★ 规则：**用某个运行模式做「某检查是否存在」的测试前，先确认该模式不跳过该检查**；否则**测试结果只是模式的属性**。

⇒ **「被测对象根本没收到输入」与「收到了却没判」在观测上都是『绿』** —— 这与该清单 §二·6 的「否定判断不自证手段」是同一族缺陷。

## 五、把 A/B 映射到本机 12 项（用 03 篇的实测数据）

03 篇实测：**12/12 判定逻辑能红** ⇒ **没有任何一项是 A 类（恒真）**。

★ **但这**不**意味着 12 项都健康**，因为 §三·3.2 的映射提示还有第三种形态：

| 形态 | 本机实例 | 判据 |
|---|---|---|
| A 类 · 恒真（无判别力） | **本机未发现** | 03 篇 12/12 能红 |
| B 类 · 从未触发 | **无法判定，且不可判** | 见下 |
| **C 类 · 判别对象错**（新发现） | **`bus-8791`**，见 06 篇 | 判定逻辑活，但被消费的值是错的 ⇒ **对最可能的失败模式恒绿** |

★★★ **B 类在本机为什么「不可判」**（这条很重要）：
```bash
$ grep -c '"check"' /Users/coreyleung/dsh-collab/logs/drift-scan.log
0
$ echo $?
1
```
⇒ 日志**不记逐项**，所以「某一条判据历史上红过没有」**在现有制品里查不到**。
⇒ 按本项目纪律（「**空 ≠ 无**：分母为 0 必须报『不可判』，不得报 OK/0%」），
> **本机 12 项的 B 类状态 = 不可判**，**不是**「0 项曾红过」，**也不是**「全部曾红过」。

## 七、边界声明

1. Certora 是**形式验证工具**的文档，其 vacuity/tautology 概念**定义在数理逻辑语义上**；本文把它映射到「运维判据」是**类比**，**不是原文主张**。原文**没有**讨论监控判据。
2. 维基条目是**二手**，非一手标准；mutation testing 的原始文献（DeMillo/Lipton/Sayward 1978 等）**本轮未取**。
3. **未复跑** Certora 或任何 mutation testing 工具（本机无）。
4. §四 的判别法**是本文综合出来的，未经实测**；它尚未在本机 12 项上完整跑过第 3 步（因需构造「能到达判定点的坏输入」，本次只做到「坏输入被判定点看到」这一层）。
