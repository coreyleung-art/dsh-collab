## 二、业界依据

### 2.1 ★★★ SLSA：**「一个行为体控制多个账号 ⇒ 实际上是自己批准自己的改动」**

来源：[SLSA threats.md（v1.1-rc2 分支，官方仓库）](https://github.com/slsa-framework/slsa/blob/c24955cc2227c80fb96991f77eb8e507e282ccee/docs/spec/draft/threats.md)（**已读原文**，`curl` 取 raw 全文 1022 行）。

原文逐字（`## Single actor controls multiple accounts`）：

> ***Threat:*** An actor is able to control multiple account and **effectively approve their own code changes**.
> ***Mitigation:*** The producer must ensure that **no actor is able to control or influence multiple accounts with review privileges**.
> ***Example:*** Adversary creates a pull request using a secondary account and approves it using their primary account.
> Solution: The producer must track all actors who have both **explicit review permissions** and the **independent ability to control a privileged bot**.
> A common vector for this attack is to influence a robot account with the permission to review or contribute code.
> **Control of the robot account and an actor's own personal account is enough to exploit this vulnerability.**

★★★ **这一条对本机是**结构性命中**，不是类比。** 见 §三。

### 2.2 SLSA：**证据由可信控制面生成，产出方对它「没有影响力」**

同一来源（`## Forge values of the provenance`）逐字：

> ***Mitigation:*** At Build L2+, **the trusted control plane generates all information that goes in the provenance**, except (optionally) the output artifact hash.
> ***Example 1 (Build L2):*** Provenance is generated on the build worker, which the adversary has control over. … Solution: **Builder generates and signs the provenance in the trusted control plane; the worker reports the output artifacts but otherwise has no influence over the provenance.**

★★ **对本机的映射**：本机的「自测」是**在被测对象内部**跑的
（`--selfcheck`/`--selftest`/`--lean4-check` **均由作者跑**，§5.5 逐字）。
⇒ ★ **这正是 SLSA 的 "worker 自己生成 provenance" 形态** ——
**产出方同时是证据生成方** ⇒ **证据对「产出方搞错/搞坏」这件事没有判别力**。

### 2.3 ★★ 但业界**不总是**要求独立性 —— 必须如实分栏

来源：[agentbazaar – Acceptance Guide](https://github.com/aiskillstore/marketplace/blob/5526951beaeca22519572a471618555839b53b05/skills/ptreezh/agentbazaar/references/acceptance-guide.md)（**已读原文**）逐字：

> ## Who runs review
> **Any agent.** Publisher acceptance, **worker self-check**, or **third-party cross-review all use the same command**.

⇒ ★★★ **这个来源把「作者自测」与「第三方交叉复核」列为「同一命令的三个运行者」，即它【不要求】运行者独立。**
它要求的是**断言本身的确定性**（「the same assertions **any reviewer** runs」）。

★★ **这是本件必须写清的分栏**：**「独立性」不是唯一解**，业界有**两条路**：

| 路线 | 谁跑 | 靠什么保证 |
|---|---|---|
| **A · 独立性路线**（SLSA / 审计 / IV&V） | **必须是他人**，且**不能是自己能操纵的账号** | **主体分离** + 可信控制面生成证据 |
| **B · 确定性路线**（agentbazaar） | **任何人，包括作者** | **断言可跑、结果确定、任何审查员跑出同一结果** |

★★★ **对本机的推论（本件最重要的一条）**：
**本机现在两条路都没走完。**
- **走 A**：不行 —— 候选 verifier 全部离线，且**全机同一主体**（§三）。
- **走 B**：也没走完 —— 本机 wave S 七件的 `--selfcheck`/`--selftest` **是作者写的、作者跑的**，
  **没有「任一第三方照抄一条命令能得同一结论」的公开契约**（§5.3 信息包第 5 条要求「自包含复跑命令」**已立规矩但现测未普遍执行**）。
⇒ ★ **v7 建议：先走 B（成本低、今天就能做），把 A 作为并行目标。**
★ 具体判据见 §五。

### 2.4 DoD 里的人判栏：**「必须取得人工评审批准」**

来源：[agentic-dev-framework – definition-of-done.md](https://github.com/laugiov/agentic-dev-framework/blob/master/runtime/quality-gates/definition-of-done.md)（**已读原文**）。

## 三、★★★ 结构性发现：本机「独立审查员」买到的与没买到的

### 3.1 现测：全机是**同一个主体**

```bash
ps -eo user,pid,comm | grep -E "CLD|rust-blac|node" | awk '{print $1}' | sort -u   # → coreyleung
whoami                                                                             # → coreyleung
ls -l ~/.dsh/sessions/--Users-coreyleung--/ | awk 'NR>1{print $3}' | sort -u        # → coreyleung
```

**未编辑原始输出**：

```
=== 全部 CLD/dsh 相关进程的属主 ===
coreyleung
=== whoami ===
coreyleung
=== 会话文件属主 ===
coreyleung
```

### 3.2 判定

| 层次 | 本机的「另一个会话来审」买到了吗 |
|---|---|
| **认知独立性**（不共享上下文、不共享作者的思维定势与已犯错误） | ★ **买到了** —— 不同会话、不同 context、不同 skill 载入，确实能抓到作者在自己上下文里看不见的东西。★★ **本机有实证**：`review-tracker` 的 `_correction` 抓到「executor == verifier」，**抓它的是判据而不是人**，但**判据由第三方线写**（`norm_sid`）。 |
| **主体独立性**（审查者不能是能操纵执行者的人） | ★★ **没买到** —— 全部会话**同一 OS 用户 coreyleung · 同一宿主 · 同一套凭据**。 |
| **可信控制面**（证据不由产出方生成） | ★★ **没买到** —— 自测证据由作者在自己的会话里生成（§2.2）。 |

★★★ **⇒ 这正是 SLSA `Single actor controls multiple accounts` 的逐字形态**：
> An actor is able to control multiple accounts and **effectively approve their own code changes**.

★ **必须同时说清两件事，否则会误伤**：
1. **本项目当前的失败模式不是「恶意」**，而是 **P27 家族的自指参照系与共同盲区** ——
   **同一个操作者的两会话，会共享同一套先验**，「一起漂移」的风险**没有因为换会话而降低**。
   ★ 本机已有具名实例：**§4.7 第 4 条「本地副本 ↔ 板值一致性」** ——
   若两处由同一只手维护，**它们「一起变就永远相等」**（P27 根因逐字）。
2. **因此「独立审查员」在本机的正确职责边界是**：
   **它能证明「作者在自己的上下文里没看到」，它不能证明「这件事客观上对」**。
   ⇒ ★ **不得把「有另一位审查员签了」当成「客观正确」** —— 那会是一次**新的假绿**。

### 3.3 ★ 一个可机器判的补强：**把「可寻址性」变成判据**

★★ 本机现在**没有**任何机制保证「记 closed 的时候，verifier 是在线的、且不是作者自己」。
**建议的判据（能红）**：

```python
# 对每个 state == closed_with_evidence 的项：
#   C-v1  verifier.session 非空
#   C-v2  verifier.session != 该项的 owner/executor 会话（R046）
#   C-v3  verifier.session 在 agent_peers 的存活列表内， 或 有显式 verifier_unavailable + reason
#   C-v4  verifier 的裁决是一个【产物】（有路径 + sha256 + 时刻），不是一句「已复核」
```

**负控（必须红）**：
- C-v1 负控：把 `verifier.session` 置 null ⇒ 必须红（**现测 6/6 命中此负控形态**）
- C-v2 负控：把 executor 与 verifier 设为同一 id ⇒ 必须红（★ **本机已有先例：`_correction` 里那一条**）
- C-v3 负控：填一个不在存活列表里的 id ⇒ 必须红（★ **现测三个候选全部命中** ⇒ 这条会立刻红）
- C-v4 负控：`verifier` 值写成不含路径/时刻的自由文本 ⇒ 必须红（**现测 6/6 命中**）

★★ **注意 C-v3 会立刻红** ⇒ ★ **这不是「新问题」，而是把一个已经存在、只是没人看的事实变成可见**。
★ 依本项目纪律：**能红才是判据**；**这条不但能红，而且现在就是红的**。

## 四、★ 本机可用的替代（三个，按成本排序）

### 替代 A · **确定性路线**（最低成本，今天可做；★ 推荐先做）

把 §5.3 信息包第 5 条「**自包含复跑命令**」从「规矩」变成「判据」：

```bash
# 对 Wave S 七件，逐件跑「任一第三方照抄这一条命令」；★ rc 取自命令本体（不用管道末端）
for t in sandbox-script infopack-check review-gate official-ref-gate gcr-gate node-claim-gate self-destruct-gate; do
  out=$(python3 ~/dsh-collab/tools/$t.py --selftest 2>&1); rc=$?
  printf "%-22s rc=%-3s %s\n" "$t" "$rc" "$(echo "$out" | tail -1)"
done
```

★★ **⇒ 六件 rc=0（自证全绿），第七件 `sandbox-script` rc=2（`--selftest` 必须带 `script` 参数）**
⇒ ★ **它的自证入口与其余六件不一致** —— 第三者照抄这一条命令**跑不起来**。
（★ 这正是 `00-…` 待办里那条 §11 遗留的「待核项」：交付说明同时给出 `--selfcheck 5/5` 与 `--selftest 4/4`，**v5 记「未测」**；★ 本件现测的是**它的 `--selftest` 入口不可直接调用**，**未判 4/4 的正确性**。）

★★ **⇒ 这条路线买到的**：**复现性**（「同一命令给同一答案」）。
★★ **它买不到的**：**独立性** —— 作者仍可写一条**对自己有利**的断言。
⇒ ★ **必须配一条负控**：**断言必须包含至少一条「造错必红」的负控**（本机已有此纪律，见 §5.2「观测/判据工具：负控必须能红」）。

### 替代 B · **离线审查员唤醒**（中成本）

★ §5.5 的三人**都有持久化会话**（§1.2 现测）⇒ **技术上可唤醒**。
⇒ 需用户授权（§5.5 原文：「**均离线，唤醒须授权**」）。
★ **本件不主张代用户唤醒**（越权）；★ **但把「可寻址性」现测出来了**：**技术上可达，只是没人发起**。

★★ **只有跨设备，才可能改变「同一 OS 用户 + 同一套凭据」这个前提** ——
★ **但本件未验证** mbp 是否用不同主体运行（**未测**）。
⇒ ★ **如实标**：这条**仅是方向**，**本件不主张它能解决问题**。
