## 二、业界做法（一手来源）

### 2.1 核心概念：**half-life 不是**一个数

最相关的一手来源：[Audit Evidence Half-Life: When Compliance Evidence Goes Stale](https://secportal.io/research/audit-evidence-half-life)（**已读原文**）。

原文开篇逐字：

> When a security leader asks how long audit evidence is valid, the question **collapses three separate sub-questions into one sentence**.

三个子问题（**本件最重要的借镜**）：

| 子问题 | 原文要点 |
|---|---|
| **① 节奏问题（cadence）** | 框架期望该控制**多久运行一次** |
| **② 观测问题（observation）** | **审计覆盖哪个窗口**，证据**是否落在窗口内** |
| **③ 变更问题（change）** | 采集之后，**底层控制或资产是否发生了变化，以至于证据的主张不再成立** |

原文的判断：

> Programmes that answer one of these three at the cost of the others end up with **confident-looking artefacts that fail the audit read**.

★★ **对映到本机**：本机 `guard/gate-state.json` 的 24h 阈值**只回答了 ①（节奏）**，
**②（窗口）**体现在 `official-ref-gate.py` 的「`--target` 才判」，**③（变更）完全没有**。
⇒ ★★ **典型形态**：「带着自信外观的产物，在细读下失败」—— 这与本机 `§11 「声明面 > 证据面」`的半修形态**同源**。

### 2.2 三问的具体口径（原文表格摘录）

| 框架 | 观测窗口 | 节奏形态 |
|---|---|---|
| **SOC 2 Type 2** | **在委托书里具名**，常见 6–12 个月。**窗口外的证据不是「部分证据」，是「结构上无效」** | 期望持续运行；证据必须**填满整个周期**，不能堆在审计周 |
| **ISO 27001:2022** | 监督审核间隔（年度）+ 三年再认证 | Annex A 各控制**各有期望节奏**；记在 ISMS 里，**按间隔内产生的产物核验** |
| **PCI DSS v4.0** | 年度评估；**按条款各自挂节奏** | 每日（10.4 日志复核）· 每周（5.3 反恶意软件）· 每季（11.3 扫描）· 每年（11.4 渗透、12.3 风险评估） |
| **NIST CSF 2.0 / SP 800-53** | 持续；控制评估频率由组织定义 | AU-11 定**保留期**；**节奏由系统安全计划逐控制设定** |

原文的共享模式逐字：

> The shared pattern is that **cadence is per-control rather than per-programme**.

★★★ **对映到本机**：本机的「24h」是一个**全局单值**，挂在**所有** dsh 设计项上。
⇒ 按业界模式，**「24h」应当是「每控制各自一个 cadence」**：
`app.asar 崩溃看门狗`、`cordis patch config`、`session persistence 读路径契约` 的**变化速率天差地别**，
用一个 24h 卡全部 ⇒ **要么过度（噪声），要么不足（漏）**。

### 2.3 另一个 ISO 27001 视角：**跨周期抽样，不是时点快照**

来源：[ISO 27001 audit evidence: what auditors ask for](https://www.cloudsoul.net/resources/blog/evidence-that-assembles-itself/)（**已读原文**）。

> ISO 27001 auditors **sample dated records from across the audited period, not a snapshot taken the month before**.
> A folder assembled the month before **shows the current state and invites questions about every other month**.

原文给了一张「**各控制区各自的证据与过期速度**」表，摘三条与本研究最相关的：

| 控制区 | 证据 | **何时过期（原文措辞）** |
|---|---|---|
| 认证与配置（A.8.5, A.8.9） | MFA 覆盖、基线、漂移报告 | **持续：一个新管理员账号就会改写它** |
| 日志与监控（A.8.15, A.8.16） | 保留设置、告警工单、复核记录 | **持续** |
| 变更（A.8.32） | 变更工单 / 带批准的 PR | **每次变更** |

★★★ **「持续：一个新管理员账号就会改写它」** 这一句，**正是本机缺的第 ③ 问（变更问题）**。
⇒ 对本机最直接的推论：**`app.asar` 或 `cordis.patch.yml` 一旦被改动，此前那条留证当场失效 —— 与它有多新无关。**
★ 本机已有**一个弱化的同向实现**：`beacon-check.py` 的「**锚点指纹未变（改了正文须同时升 state_version 并重盖章）**」
—— **思路是对的，但只用在锚点文档上，没有用在留证上**。

### 2.4 厂商实践：**给每个证据项一个默认间隔 + 到期标 `Expired` 而不归档**

来源：[Secureframe – Default Intervals](https://support.secureframe.com/en/articles/15972003-default-intervals)（**已读原文**，2026-08-03 上线）。

原文逐字（这段几乎是为本机写的）：

> Previously, an Upload Test **could stay Passing indefinitely, even when its evidence was long out of date**, because many tests had **no interval set**. That led to **stale evidence going unnoticed and surprises at audit time**.

三条改动：

1. **Default intervals**：**每个测试都拿到一个默认间隔**（多数默认年度；渗透测试默认季度）。
   「**You cannot remove the interval entirely.**」⇒ **不允许「没有间隔」这个状态存在**。
2. **Completion-date evaluation**：按证据的**活动完成日**评估，**不是上传日**。
   原文给的例子：3/15 做渗透测试、4/10 上传 ⇒ **下次到期是 6/15（从 3/15 起算三个月），不是从 4/10**。
   原文强调：「**Setting the completion date accurately on every upload is the single most important thing your team can do**」。
3. **`Expired` 状态**：到期证据**标 ⚠ Expired，而不是自动归档** ——
   ★ **因为它必须「stays visible to auditors」**。

★★★ **对映到本机**：

| 业界做法 | ★ 本机现状（现测） | 差距 |
|---|---|---|
| 每项必须有 interval | **全局一个 24h**（`official-ref-gate.py:FRESH_HOURS=24`，源码自注「取自锚点原文，本工具不判断该时长是否合理」） | ★ 无 per-control cadence |
| 不允许「没有间隔」 | ★ **本机 `_day` 停在 `20260905`** ⇒ 台账事实上**停更**（新条目仍能追加，但「今天有没有查」没有状态位） | ★ **缺「区间」状态本身** |
| 按**活动完成日**评估 | 本机 `gate-state.json` 的 `ts` 是**写入时刻**（写台账那一秒） | ★ 若补证发生在读文档之后数日，会**虚高新鲜度** |
| 到期标 `Expired` 且**保持可见** | 本机是**运行期现算**（`age_hours > 24` ⇒ NO-GO），**台账里不留「已过期」痕迹** | ★ **过期这件事没有留痕** ⇒ 事后无法统计「有多少天处于无留证状态」 |

## 三、★ v7 可落地的形态（把上面四条变成可机器判）

### 3.1 留证台账的最小 schema

```jsonc
{
  "schema": "official-ref-evidence/v2",
  "records": [{
    "id": "sha256-prefix",
    "topic": "session persistence inspect loadStored …",
    "domain": "dsh",                       // ★ per-control cadence 的分桶键
    "target_paths": ["<runtime>/…/lib/index.js"],
    "activity_completed_at": "2026-09-05T16:16:31+08:00",   // ★ 业界口径：活动完成日
    "recorded_at":           "2026-09-05T16:20:00+08:00",   // ★ 写入时刻（另存，不混用）
    "cadence_hours": 24,                   // ★ per-control，不是全局
    "expires_at": "2026-09-06T16:16:31+08:00",              // ★ 落盘时就算好
    "status": "expired",                   // ★ 四态之一：fresh|expired|superseded|invalidated
    "invalidated_by": null,                // ★ 变更问题的钩子：被哪次改动作废
    "source": {"mirror_hits": 0, "mirror_age_days": 41, "web_evidence": "https://…"},
    "source_reject_reason": null           // ★ 见 3.2 的假证剔除
  }]
}
```

### 3.2 ★ 三条能红的判据（每条都配负控）

| 判据 | 正向 | **负控（必须红）** |
|---|---|---|
| **C1 · 时效** | 该 `domain` 存在 `status=fresh` 且 `expires_at > now` 的记录 | 把 `expires_at` 改成过去 ⇒ 必须红（★ **本机已有**：`official-ref-gate --selftest` 的「合成·留证 48h 前 ⇒ 过期」，4/4） |
| **C2 · 假证剔除** | `source.web_evidence` 的 host **不在保留域名表**内（`example.com`/`example.org`/`example.net`/`localhost`/`invalid`） | ★★ **注入一条 `https://example.com` 留证 ⇒ 必须红** —— **本机现在没有这条判据**（因为两条假证已在台账里躺了 912h） |
| **C3 · 变更作废** | 每条留证的 `target_paths` 的 **mtime ≤ `activity_completed_at`** | ★★ **touch 一个 target 文件 ⇒ 该留证必须立刻转 `invalidated`** —— 这条**本机完全没有** |

★★ **C2/C3 是新造的**，且**都能红**（造得出反例）。★ **按本项目纪律：能红才算判据。**
★ C1 是**沿用**（`official-ref-gate.py` 已在位，`--selftest` 4/4 全绿）。

### 3.3 ★ 「到期不归档、保持可见」的本机实现

业界（Secureframe）的 `Expired` 之所以**不归档**，是因为**必须让审计员看得见**。
本机对应的形态很简单：**不要用「删除」表达「过期」**，而是**在台账里保留并置 `status=expired`**。
★ 本机现在**做不到**这一点是因为台账是**运行期现算**（`age_hours > 24`），**过期本身不留痕**。
⇒ **v7 要加的是「每日一次的落盘评估」**：每天把每条的评估结果写回一个 `evidence-health.jsonl`，
这样**「本季度有多少天处于无留证状态」变成一个可算的数** —— 而它才是真正的 SLO 指标（见 `02` 的窗口纪律）。

### 3.4 ★ 与 §6.1 第 4 条的关系（本机既有条款，值得保留）

锚点 §6.1 第 4 条原文：

> ★ **留证过期即视为无留证** …… 本条要求**长期处于失效状态**，v5 起按事实判定，不再按名义判定。

★★ **这一条与业界完全一致**，而且是本机**做得对的一处**：
它把「名下有 9 条留证」与「有 1 条可用留证」分开了。
⇒ ★ v7 **应当保留这条原文**，并把「按事实判定」升级为 §3.2 的三条机器判据。
