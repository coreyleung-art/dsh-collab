# 02 · SLO 阈值怎么定才不是「事后编的」

> **调研代理**：R-M4M5 · **出件时刻**：2026-10-12T20:2x+0800
> **问题**：① 阈值怎么定才不是事后编的？② **样本为 0 时报什么？**
> ★ 本件区分 **业界做法** 与 **本机现状**，**不把「本机已有」写成「业界最新」**。
> ★ 外部来源均给链接；★ **未读原文的** 单独标「仅见摘要」。

---

## 〇、一句话

★★ **业界的答案不是「怎么定阈值」，而是「阈值定在哪一层」**：

```
事件层     →  合成一个比值（SLI）        ← 这一层定「测什么」
 SLO 层     →  目标 + 窗口                ← 这一层定「多好 / 多久内」
 策略层     →  error budget + burn rate   ← 这一层定「快到什么程度要动手」
 数据健康层 →  有样本吗 / 采样面还活着吗   ← ★ 本机完全缺这一层
```

★★★ **本机 14 条指标全部把四层压成了一行**（例：「真积压 ≤10 / 去重漏判 0 / 风暴发现自动提前 ≥10 分钟」**一行三个指标**）。
⇒ **压层的直接后果**：**分母无处声明，窗口无处声明，数据健康无处声明** ⇒ **读数不可比**。

## 一、业界做法（一手来源）

### 1.1 三层定义（SRE book / workbook）

- **SLI**：测量本身，如「成功请求 / 全部请求」。
- **SLO target**：目标，如 99.9%。
- **Window**：目标覆盖的周期，**通常滚动 28 或 30 天**。
- **Error budget** = `(1 − SLO) × 窗口内事件数或时间`。
- **Burn rate** = `观测错误率 / (1 − SLO)`。burn rate = 1 ⇒ 窗口结束时刚好用完预算。

来源：[Last9 – Error Budgets: How to Calculate and Alert on Burn Rate](https://last9.io/blog/error-budget/)（**已读原文**）。

★ **对我们的直接映射**：本机的指标**没有一条写了 window**。
「官方校对留证」写了 24h（**这是唯一写了窗口的**）；「闭环率 ≥80%」**没写窗口**；「真积压 ≤10」**没写**。
⇒ **没有窗口的 SLO 不可复跑**：同一份数据，窗口取 1h / 24h / 全量会给出**三个不同答案**。
★ **本机已实测到这一点**（`v7-baseline-m1-m4-20261012.md:69-76`）：
`drift-alert` 到达率 **1h=不可判(样本 0) · 3/6h=100%(n=1) · 24h=90.91%(n=11) · 全量=16.48%(n=58)** —— **同一指标四个答案**。

### 1.2 多窗口多燃尽率（multiwindow, multi-burn-rate）

Google 建议**长窗 + 短窗成对**（短窗 = 长窗的 1/12）：

| 长窗 | 短窗 | 消耗预算 | burn rate 阈值（99.9% · 30 天窗） |
|---|---|---|---|
| 1 小时 | 5 分钟 | 2% | **14.4** |
| 6 小时 | 30 分钟 | 5% | **6** |

来源：[Splunk Observability Cloud – Burn rate alerts](https://help-preview.splunk.com/en/splunk-observability-cloud/create-alerts-detectors-and-service-level-objectives/create-service-level-objectives-slos/burn-rate-alerts)（**已读原文**；原文明确「short windows are 1/12 of the long windows, as suggested by Google」）。

★ **为什么成对**：**长窗判「真的在烧」，短窗判「还在烧吗」** —— 短窗负责**快速复位**，
避免「事故已结束但长窗还挂着」导致的**告警滞留**。

★★ 对我们的映射：**本机所有指标都是「单点快照」**（`du -sh`、`ls | wc -l`、`--status` 一次）。
**没有一条是「窗口 + 成对」** ⇒ **一次抖动就会被当成「现状」**。
★★★ **本机已有实证**：`gcr-gate` 的 **G-CR1 在 20:05:39 判 ❌、20:11:26 判 ✅**（见 `01` §六）。
**同一命令、相隔 6 分钟、两个结论** —— 若把它接进 SLO，这个 SLO **会在 6 分钟内跳变**。

### 1.3 ★★ 样本为 0 时报什么（本件的核心问题）

**业界的主流答案是：不许合并，必须单列「无观测」态。**

一手来源：[No Traffic or Broken Telemetry? How Missing Data Should Affect an SLO](https://oneuptime.com/blog/post/2026-08-29-no-traffic-or-broken-telemetry-how-missing-data-should-affect-an-slo/view)（**已读原文**）。

**原文的三条关键主张**：

1. **「无流量」与「遥测坏了」都会产生空图，但含义完全不同。**
   - 健康的、已初始化的计数器 + 无流量 ⇒ **观测到的分母 = 0**；
   - **遥测坏了 ⇒ 分母本身未知**。
2. ★★ **「两者都不得被静默转成 100% 成功」**。原文给的 SLO 状态机是**四态**：
   `compliant` · `noncompliant` · **`idle / no observation`** · **`unknown`**。
3. **禁止在 SLI 查询里强制消解缺席**。原文点名两个危险写法：

```
# Dangerous: a completely absent aggregate ratio falls back to perfect service.
(sum(good) / sum(total)) or vector(1)
```

   并指出 `or vector(0)` **在另一个方向上同样误导**；且**分子分母都在、但没有增量**时，比值是 **0/0 ⇒ 仍是 NaN**。

原文还给出**检测采集失败的专用原语**：

```
absent_over_time(api_requests_total{service="orders"}[10m])
# 仅当整个选择器在区间内**一个样本都没有**时返回 1
```

★ 注意它自己声明的**局限**：**它认不出「一组 label 缺失而同选择器的其它序列还在」** —— 那种情形要**逐序列显式选择**或**与清单对账**。

★ **旁证（社区实践，含历史错误）**：[pyrra-dev/pyrra discussion #1246](https://github.com/pyrra-dev/pyrra/discussions/1246)（**已读原文**）。
报告人自陈 Sloth 曾用两个 hack：`or on() vector(0)`（补错误侧）与 `or on() vector(1)`（补总量侧），
并**自评第二个 hack「a bit more doubtful」**；另一位的做法是给分母 `+ 0.0000000001`，
**自陈「This query is a bit lying」**。
⇒ ★★ **业界自己也栽过这个坑，且留下的补丁是「说谎但让图好看」** —— 这条对我们**特别相关**：
**本机的 `/health` 返回 `{"total":0}` 被读作「健康」，正是一个 `or vector(1)` 的等价物。**

## 二、★ 本机的「空 ≠ 无」纪律 vs 业界四态

本项目的纪律（用户给的题面）：

> 「**空 ≠ 无**」：分母为 0 必须报「不可判」，不得报 OK/0%。
> 「**一个断言若从未红过，它就不是判据**」。

★★ **业界四态 ↔ 本机两态的映射（本件的建议）**：

| 业界态 | 含义 | ★ 本机应当怎么报 |
|---|---|---|
| `compliant` | 有样本且达标 | 绿（并报分子/分母/窗口） |
| `noncompliant` | 有样本且不达标 | 红（并报分子/分母/窗口） |
| `idle / no observation` | **采样面活着，但没有事件** | ★ **「不可判（无观测）」** —— 与「绿」显式不同 |
| `unknown` | **采样面本身死了** | ★ **「不可判（采集失败）」** —— 与上一条**也必须不同** |

★★★ **本机的漏洞在第三、四态被合并成一个「不可判」**。
而这两态**处置完全不同**：`idle` 什么都不用做，`unknown` **要报警**。
⇒ **v7 必须把「不可判」再拆两态**，否则「分母为 0」这个信号会**同时**掩盖「一切正常」与「仪器已死」。

★ **本机已具名的实例**（v6.1 `:236` H-1）：**「C7 遮蔽扫描 0 包报 OK · drift 跨机 401 只打印成功侧 · 有界重试 822 次恒记 1/3」**
—— 三例都是**把 `unknown` 当成 `compliant`**。
★ 本轮**又新增第 4 例**（见 `01` §三）：`official-ref-gate.py` **不带 `--target` 时**打印 `✅ GO` 且 rc=0，
而**12 条留证 24h 内 0 条** ⇒ **正是「未做判定 ⇒ 报绿」**。

## 三、★ 阈值怎么定才不是「事后编的」—— 四条可操作的纪律

从上面的一手来源 + 本机的两处活标本（`probe-activation-counters.py` 判据改了四代；
`v7-baseline` 里 drift 到达率四个窗口四个答案），我提炼四条：

### 纪律 1 · **阈值必须先于读数存在，且改动要留两代**

★ 本机的**活标本**（`01` §十）：同一个事实（本机有没有「机制激活计数器」），
判据改了四代，答案分别是 **47 / 41 / 30 / 0**。
⇒ ★★ **凡改判据，必须同时重报「旧判据值 / 新判据值 / 改的理由」**，否则**任意数字都可以有据**。

**建议的机器形态**（写进 v7）：

```jsonc
{
  "metric": "机制激活可观测",
  "criterion_history": [
    {"gen": 1, "rule": "文件名含 activation|counter", "value": 47, "rejected_because": "全是 counterexample，语义不同"},
    {"gen": 2, "rule": "剔 counterexample",        "value": 41, "rejected_because": "仍有 counter-test 同病"},
    {"gen": 3, "rule": "名尾 count(s).json 或含 activation", "value": 30, "rejected_because": "全是 node_modules vendor"},
    {"gen": 4, "rule": "再剔 vendor 路径",           "value": 0,  "rejected_because": null}
  ],
  "threshold": 0,
  "threshold_set_at": "2026-10-12T20:07:31+08:00",
  "threshold_set_by": "R-M4M5",
  "★": "阈值先于读数固定：本条 threshold=0 沿用锚点 §12 原文，非本轮事后择定"
}
```

### 纪律 2 · **每个阈值必须挂「窗口 + 分子定义 + 分母定义」三件**

★ 反例（本机）：`drift-alert` 到达率 —— **窗口换一次，答案从 100% 变 16.48%**。
⇒ v7 里任何阈值**写成三件套**，缺一即**不可复跑**：

```jsonc
{"metric":"双板到达率","window":"rolling 24h","numerator":"boardsMatch===true 的 send 行",
 "denominator":"action=send 且含 result 字段的行","threshold":1.0,"direction":"≥"}
```

### 纪律 3 · ★★ **样本为 0 时不得评估阈值，必须输出第四态**

**机器形态**：

```python
if denominator == 0:
    return {"state": "UNDECIDABLE", "reason": "NO_OBSERVATION" if probe_alive else "COLLECTION_FAILED",
            "threshold_evaluated": False}
```

★ **且必须再配一条负控**：**造一个空分母 ⇒ 该判据必须红**（本项目已具名此为 H-1 的复现谓词）。
★★ 本机**已有的正确实现**（值得 v7 直接沿用）：
`beacon-check.py` 的 `SKIP`/`PEND` 与 `beacon-cover-check.py` 的 `WARN`/`SKIP` ——
`beacon-cover-check` 的原文即：「**WARN 不等于 PASS；SKIP 不等于通过 —— 本门不把「没查」算成「绿」**」。
此外 [G1 调研](agent-comm-paths/G1-仪表静默死亡-市场调研与DSH官方对照.md) 已把这条讲透：
「**会死的仪表不能报告自己的死亡**」「我们缺的不是更好的监控，而是**缺席语义**」，
并给出业界标准解 **watchdog / dead-man's-switch**（kube-prometheus 的 `Watchdog` 告警 `expr: vector(1)`，**永远在响**；
一旦不响就由**外部服务**发现）。★ 本机这层**仍缺**（见 `01` §三：无自动失效、无外部读者）。

### 纪律 4 · ★ **阈值要能红，且要能证明「红过」**

本项目纪律：「**一个断言若从未红过，它就不是判据**」。
★ 本机的活标本：`review-tracker.json` 的 `_correction` 记着**唯一一次红**：
「**移除一条违规登记：executor 与 verifier 同为 session-1ffded95（R046 禁 verifier=executor）**」。
⇒ ★★ **这是本地唯一一处「自审门真的红过」的证据** ⇒ **它把「六者齐备」从口号变成了判据**。
反过来：**S13（机制激活可观测）从未红过、也永远红不了**（没有计数器 ⇒ 不存在「漏记」） ⇒ **按此纪律它不是判据**。

## 四、★ 「不可能验证的目标」要改写，不是保留

本机有两条目标**结构上不可能用其字面判据验证**（`01` §九、§十一）：

| 目标字面 | 为什么不可能 | ★ 建议的改写 |
|---|---|---|
| **端口固定：3 次重启地址不变** | 重启打断在役会话（R035），调研阶段无权限 | 改为**两条可判**：①`profile` 里是否写死 `port`（静态可判）②**端口变更事件计数 = 0**（从 `startup` 日志按窗口统计，**不改判据也能事后判**） |
| **去重漏判 = 0** | 无独立标注集 ⇒ 重算同一函数得同一答案（**自指参照系**） | 改为**构造性判据**：造 N 组**半重复**合成消息注入 ⇒ **必须被抑制**；负控 = 造不重复消息 ⇒ **必须放行**。★ 这才是「能红」的形态 |

★★ 一般原则（从上面两条提炼）：
> **当原始目标要求的观测手段在本环境不可得时，改写为「合成输入 + 必红负控」，
> 而不是保留一个永远无法执行的阈值。**
> 这与本机 §5.2「观测/判据工具：合成输入正例+负例+边界；**负控必须能红**」**完全一致** ——
> 差别只是**适用范围扩到 SLO 指标本身**。
