# 04 · 「读者自身坏了」怎么防——watchdog / dead man's switch / `absent()` / meta-monitoring

## 〇、一句话结论

★★★ **业界防「读者自身坏了」只有一招，且它要求【判定方在对象之外】**：
> **不看「有没有人读」，看「本该出现的信号有没有出现」——即缺席语义（absence semantics）。**

★★ **★ 而这一招有一个本报告要强调的硬边界**（G1 未展开）：
> **`absent()` 能证明「信号消失了」，【不能】证明「信号被读过」。**
> 一个从未被读过的告警，从缺席语义看，**与一个被认真读过的告警完全一样** —— 因为**两者都没有「已读」这条时间序列**。
> ⇒ **缺席语义防的是「读者死掉」，防不了「读者压根没接线」。** 后者要靠 **02 篇的 `consumer:` 字段**（创建时填）。

## 一、业界的三种结构（含逐字依据）

### 1.1 「always firing」告警：把「管道仍在」变成一个会消失的信号

**kube-prometheus 的 `Watchdog`**（逐字，见 [PromLabs 培训页](https://training.promlabs.com/training/monitoring-and-debugging-prometheus/metrics-based-meta-monitoring/end-to-end-watchdog-alerts/)）：

```
- alert: Watchdog
  annotations:
    description: |
      This is an alert meant to ensure that the entire alerting pipeline is functional.
      This alert is always firing, therefore it should always be firing in Alertmanager
      and always fire against a receiver. There are integrations with various notification
      mechanisms that send a notification when this alert is not firing.
      For example the "DeadMansSnitch" integration in PagerDuty.
  expr: vector(1)
  labels: severity: none
```

★ PromLabs 把三步写清楚了（逐字）：
1. `Configuring an alerting rule that is **always firing**, e.g. using the PromQL expression **vector(1)**`
2. `Configuring Alertmanager to route the resulting alert notification to an **external service** with a repeat interval of only a few (x) minutes`
3. `Configuring the **external service** to expect an incoming alert notification every x minutes (plus some slack time) or to send you an alert notification otherwise`

★★★ **三个结构点，缺一不可**：
1. 信号是**恒真**的（不检测任何指标）⇒ **它的信息量 100% 在「出现与否」上**；
2. 周期**很短**（x 分钟）⇒ 失效被发现的延迟有界；
3. ★★ **接收方在【系统之外】**（third-party dead-man's-snitch）⇒ **管道整体死亡时，通知仍能发出**。

★ 官方同时给了**为什么必须外部**（同页逐字）：
> Even if you build the most reliable internal meta-monitoring infrastructure, something can still go wrong: the meta-monitoring setup might have a **systematic error** that causes it to break, the **Alertmanager through which notifications are supposed to get delivered might be down**, or your **entire organization's network might be disconnected from the internet!**

### 1.2 `absent()` / `absent_over_time()`：缺席语义的**语言层实现**

Prometheus 官方（[Query functions](https://prometheus.io/docs/prometheus/latest/querying/functions/)，逐字）：

> `absent(v)` returns an **empty vector if the vector passed to it has any elements** and a **1-element vector with the value 1 if the vector passed to it has no elements**. This is useful for **alerting on when no time series exist for a given metric name and label combination**.

★★ **判据形态**：`absent(某指标)` ⇒ **红**。这是把「**本该有，实际没有**」直接写成一个触发条件。

★ **边界（本文重点）**：它问的是 **「这条时间序列存在吗」**。它**不问「有没有人处理过」**。
⇒ **本机若把 `absent()` 用在本机告警面上，得到的是「本轮没有新告警卡」= 绿** —— ★ **而那正是 19:23 归档后得到的那个绿**（现测：`drift-delivery-failure` 带归档过滤 n=0 ⇒ PASS；见 07 篇负控③）。
⇒ **`absent()` 给不了比「看目录空不空」更多的东西。** ★ **这一点必须写下来，否则团队会以为引入了 `absent()` 就升级了。**

### 1.3 meta-monitoring：把监控基础设施自身当被监控对象

Google SRE 逐字（[Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)）：

> **Metamonitoring**: It is important to have confidence that monitoring is working. Accordingly, **have alerts to ensure that Prometheus servers, Alertmanagers, PushGateways, and other monitoring infrastructure are available and running correctly.**
> As always, if it is possible to alert on symptoms rather than causes, this helps to reduce noise. For example, **a blackbox test that alerts are getting from PushGateway to Prometheus to Alertmanager to email is better than individual alerts on each.**
> Supplementing the whitebox monitoring of Prometheus with **external blackbox monitoring** can catch problems that are otherwise invisible, and also **serves as a fallback in case internal systems completely fail**.

★★★ **⇒ 关键判据是【端到端探针】**（`PushGateway → Prometheus → Alertmanager → email` 走通一条），**不是给每一跳各配一条告警**。理由逐字：**"better than individual alerts on each"**。

★ 同一节还有一句对本机格外贴（[Prometheus TIL · self-monitoring](https://github.com/ntk148v/til/blob/7495cf25ee3d5f0ff6376ea98dbe167d632ad7d0/prometheus/scaling/self-monitoring.md) 逐字）：

> `The one thing it won't catch is a production machine that hasn't been added to our Prometheus configuration.`
> `we check to make sure that these files aren't too stale through the node_textfile_mtime_seconds metric`

⇒ ★★ **「太陈旧」（staleness）是缺席语义在文件层的标准实现**：不看内容，看 **mtime**。

## 三、★★ 递归的终止条件：为什么最终必须有一个「系统之外」的判定方

把上面的结构递归展开：

```
告警卡 (data/ops/*)          ← 读者 A（beacon-check，手工）
       ▲ 谁保证 A 被跑？
watchdog（hb-watchdog，60s）  ← 读者 B（？）
       ▲ 谁保证 B 在跑 / B 的失败被看到？
……                            ← 读者 C（？）
```

★★ **本机现测的答案链**：
- A 无调度 ⇒ **A 的存活依赖「有人记得」**（人/会话）。
- B 有调度（launchd 现测 loaded）⇒ **B 的存活有保证**；但 **B 的输出无读者** ⇒ **B 的失败依赖「有人记得看 peer-watchdog.log」**。
- ⇒ **两条链都终止在「有人记得」上。** 而**「有人记得」本身不是机制**（它无法被判据化）。

★★★ **业界对这一层的回答是唯一的：把最后一跳放到【自己控制不到的系统】上**（PagerDuty DeadMansSnitch / 外部 heartbeat 服务）。**理由就是上面 PromLabs 那句**：元监控可能有 `systematic error`、Alertmanager 可能整体挂、**整个组织的网络可能断网**。

★ **本机的现实**：**没有「组织外部」**（本机是一个单用户 + 多设备 + 一个中枢服务器的自建网络；中枢 `xingqiao.meetfunbp.com` 与各设备**同属一个人控制**）。
⇒ **严格意义上的终止条件【本机不存在】。** ★ 这一点**必须如实登记为限制**，不得用「对端设备」冒充「组织外部」。

★ **但本机有一个业界认可的次优形态，且现测是活的**：**对端设备互保**（`hb-watchdog` 的 ①②③④：写本机心跳 + 读对端心跳 + 换代则结 ticket + 超窗则写升级卡）。
- 现测 `data/health/hb-mbp` **新鲜**（20:29:30）⇒ 对端写者活；
- 现测板上 `notes/collab/peer-up-*` **有 3 张**（`peer-up-mbp-rn-*`）⇒ **本机确实读到过对端换代并落了卡** ⇒ ★ **这是一条【真的红过/真的触发过】的判据**（符合本项目纪律「一个断言若从未红过，它就不是判据」）。
- ★ 但 `peer-down-escalation` 卡现测 **0 张** ⇒ **「超窗未回」这一支【从未红过】** ⇒ 按纪律，**它不是判据**。

★★ **⇒ 次优形态的准确表述**：**对端设备可以防「本机整体死亡」，但防不了「两台设备同时坏/同一个人的两台设备同时被同一个原因影响」**（如：同一账号、同一网络、同一个中枢）。★ 这是**相关性风险**，不是覆盖率问题。

## 五、★ 落到本机的三条（本文的结论）

1. **缺席语义要抓的是「读者自己的运行记录」，不是「告警目录的内容」。**
   ⇒ 读者每次运行**必须留下一个心跳键**（单键覆盖写，形如现有 `data/ops/drift-heartbeat/current`），判定方看它的 **staleness**，**不看内容**。
   ★ 理由：这是唯一能让「读者没跑」与「没有告警」**在读数上分开**的量（03 篇 §一.5 的 M1）。

2. **`absent()` 不能替代 `consumer:` 字段。**
   ⇒ 「读者死了」用 staleness 判；「读者从没接线」用**创建时填的具名字段**判（02 篇）。**两者不可互替。**

3. **本机不存在「组织外部」，故终止条件是【声明性的】，不是【技术性的】。**
   ⇒ 必须**显式登记**：「本机的最外层判定方 = 用户本人 / 对端设备」，并**写清它能防什么、防不了什么**（防单机死亡；防不了同源相关失效）。★ **把这一条当成已完成的安全网，就是 02 篇里 `security theater` 的定义。**
