## ① `CREATED` 与 `QUEUED` 是否合并

**现状（v1.0 原文，三处不一致）**：
- §4 L78：`CREATED→ASSIGNED→RUNNING→DONE/FAILED/TIMEOUT`
- §7.2 L148：`"state": "QUEUED|RUNNING|DONE|FAILED|TIMEOUT"`
- §7.3 L152：`QUEUED → RUNNING → …→ FAILED → (retry≤max) → QUEUED`
- §12 L222–231：`[*] --> CREATED / CREATED --> ASSIGNED / … / FAILED --> QUEUED : retry<max`

**v1.2 当前处置**：**取三处并集超集**（7 值），**不引入新状态、不替裁**。

| 备选 | 做法 | 影响 |
|---|---|---|
| **A** | **合并为一个**（如统一为 `QUEUED`，删 `CREATED`/`ASSIGNED`） | ✅ 最简；❌ 丢失「已创建未委派」与「已委派未开始」的区分 ⇒ **无法表达「卡已生成但还没指派给人」** |
| **B ★ 我的倾向** | **保留两者，明确分域**：`CREATED`＝**任务卡已生成、尚未入队**；`QUEUED`＝**已入队、等待执行**（`ASSIGNED` 保留为「已指派」） | ✅ 保住四处的语义且不丢信息；❌ 需在 §7.3 说明 `CREATED→QUEUED` 的转移条件 |
| **C** | **保留但标记 `CREATED`/`ASSIGNED` 为可选**（简化实现只需 `QUEUED`…） | ✅ 兼容两种实现；❌ **「可选状态」= 又一个静默兼容条款**（正是我们本轮在封堵的形态） |

**★ 我的倾向 B 的理由（推断）**：**A 会丢语义**（v1.0 三处并存说明确实需要区分）；**C 会新造一个静默条款**。⇒ **⇒ 若采用 B，需补一句转移条件**（这是我建议的最小代价）。

## ② `COLLAB` 为何是 0.8

**现状**：§4 给 `COLLAB` 权重 **0.8**，而 §5.2 的通道权重里**没有 COLLAB**；`COLLAB` 走 `p2p（线程内）`，而 **p2p 通道价 = 1.0**。

| 备选 | 做法 | 影响 |
|---|---|---|
| **A ★ 我的倾向** | **承认 0.8，补理由**（如「线程内多轮协商，单次成本被摊薄」） | ✅ 不改数值、不改预算模型；✅ 消除「无对应通道」的歧义 |
| **B** | **改为 1.0**（与它的通道 p2p 一致） | ✅ 与通道权重对齐；❌ **若 0.8 是有意的成本估计，改 1.0 会高估 COLLAB 成本 25%** |
| **C** | **列为 p2p 的【类型级折扣】**（写明「p2p 基准 1.0；COLLAB 类型折扣 0.8」） | ✅ 保留折扣且解释来源；❌ 引入「通道价 × 类型折扣」的合成规则（**而 v1.0 未定义合成**） |

**★ 关键提问（需所有者答）**：**0.8 是【设计】还是【笔误】？** ⇒ **⇒ 我无法从文档判断**（v1.0 未给理由）。

## ③ `ACK` 成本：0.05 vs 黑板写 0.1（**裁判核出的实质问题**）

**现状**：§4 L81 `ACK … blackboard … 0.05`；而 §5.2 的 **黑板写 = 0.1**。⇒ **ACK 走黑板写却按 0.05 计 ⇒ 低估 2×**。

| 备选 | 做法 | 影响 |
|---|---|---|
| **A** | **保留 0.05**，为 ACK 定义**独立的轻量写路径**并说明其成本依据 | ✅ 保住低成本目标（§1.1 动机正是 ack 风暴）；❌ **需新定义一条路径**（等于新增一个通道） |
| **B ★ 我的倾向** | **改为 0.1**（承认它走黑板写） | ✅ 与 §5.2 一致、预算不低估；❌ **ACK 成本翻倍** ⇒ 可能影响「ACK 去耦」这一核心设计目标 |
| **C** | **保留 0.05 但在 §4 标注「本期未校准」** | ✅ 诚实；❌ **又一个「声明了但没定」的静默项** |

**★ 我的倾向 B 的理由（推断）**：**§1.1 的动机是「61.8% 工具调用为 ack 风暴」⇒ ACK 的低成本是【设计目标】而非笔误** ⇒ 若如此则应选 **A**（保留 0.05 但补路径）。**⇒ 所以我建议所有者先答一个问题：ACK 的低价是【激励】还是【实测】？**

## ④ `dedup_key` 两套构造

**现状**：
- §8.3（**事件域**）：`dedup_key = 源事件指纹（如 SHA256(payload)）`
- 附录 A（**示例**）：`"dedup_key": "task:phoneuse-lookup"` / `"task:phoneuse-lookup:status"`（**结构化命名式**）

| 备选 | 做法 | 影响 |
|---|---|---|
| **A ★ 我的倾向** | **保留两套、划清域**：**事件类**用指纹式（内容寻址）；**任务/状态类**用结构式（语义寻址） | ✅ 两者各有适用场景（指纹防重放、结构式可读可查）；❌ 需在 §3 说明「何时用哪个」 |
| **B** | **统一为指纹式** | ✅ 唯一构造；❌ **结构式的可读性丢失**（`task:xxx` 能被人读懂，SHA256 不能） |
| **C** | **统一为结构式** | ✅ 可读；❌ **内容级防重放失效**（payload 变了但 key 不变 ⇒ 漏去重） |

**★ 我的倾向 A 的理由（推断）**：**二者解决的不是同一个问题**（一个是「内容相同」、一个是「语义相同」）⇒ **⇒ 合成一套必然牺牲一侧**。

## ⑤ `thread` 与 `task_id` 的关系

**现状**：§3 L61 有 `thread`（信封字段）；§7.2 L147 有 `task_id`（任务卡字段）；**两处均未说明关系**。附录 A 同时使用两者。

**v1.2 当前处置**：加了**暂定声明**（「一 thread 可含多 task」），标为待裁。

| 备选 | 做法 | 影响 |
|---|---|---|
| **A ★ 我的倾向** | **一 thread 可含多 task**（thread = 会话级聚合；task = 任务级唯一） | ✅ 与「多轮协商（COLLAB）在一个 thread 内」相容；✅ §7.2 的 `envelope` 可携带 `thread` 支持此解 |
| **B** | **thread 与 task 一对一**（同一物的两个名字） | ✅ 最简；❌ **无法表达「一个会话里委派了多个任务」** |
| **C** | **多对多**（一个 task 可跨 thread） | ✅ 灵活；❌ 需定义 join 语义，**复杂度高且 v1.0 无任何暗示** |

**★ 我的倾向 A 的理由（推断）**：**依据 §7.2 的 `envelope` 内含 §3 信封 ⇒ 可携带 `thread`** ⇒ **⇒ 该结构本身就暗示了「task 属于某 thread」的从属关系**（而非一对一）。
