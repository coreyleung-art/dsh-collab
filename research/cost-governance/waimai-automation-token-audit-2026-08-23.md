# 外卖自动化恢复 · token 消耗量化评估

> 日期：2026-08-23 · 协调者 fa1f9150 · im-duty 成本优化后评估
> 依据：实测脚本模型调用扫描（grep 全部脚本）+ 恢复链路清单

## 一、核心结论

**外卖侧恢复的全部自动化 = 零订阅 token 消耗。** 实测所有脚本（差评采集/评价分析/日报/客服值守/digest）均无 LLM 模型调用——纯本地采集 + 规则聚合 + HTTP 推送。外卖自动化「不烧 token」已达成，符合成本最优。

## 二、各环节 token 消耗总表（实测）

| 环节 | 脚本 | 模型调用 | token 成本 | 频率 |
|---|---|---|---|---|
| 差评采集 | bad-review-scheduler.js | ❌ 无（本地页面采集） | 0 | 每日 10:00 |
| 评价分析+发群 | daily-review-push.js | ❌ 无（规则聚合） | 0 | 每日 11:00 |

**总 token 消耗：≈ 0 / 天**（全部本地环节）

## 三、im-duty 优化对比（60s 轮询 → SSE 事件驱动）

| 维度 | 60s 轮询（旧） | SSE 事件驱动（新，已上线） | 优化 |
|---|---|---|---|
| HTTP 请求量 | 1440 次/天（60s×24h） | 按新消息触发（假设日均 50 条 → 50 次） | **省 ~97% HTTP** |
| token 消耗 | 0（本地查询） | 0（本地事件） | 持平（都零） |
| 触发时效 | 最长 60s 延迟 | 消息到达即时 | 更即时 |
| 空闲成本 | 恒定（每 60s 一次查询） | 零（长连接待事件） | 空闲零成本 |

> 注：im-duty 的「轮询」是本地 HTTP 查询（/api/im/timeout），**本身不消耗 token**；优化的价值在 HTTP 请求量/资源/时效，token 维度两者都为零。

## 四、成本治理符合性

1. **零订阅 token**：外卖自动化全部本地环节，不消耗订阅模型
2. **HTTP 优化**：im-duty 从轮询改事件驱动，省 97% HTTP 请求
3. **本地优先**：采集/分析/推送全部本地（8787 面板 + 脚本），无外部 API 订阅
4. **门控**：客服确认卡每卡用户确认才发（天然门禁），P2 digest low LLM（实际零 LLM）

## 五、局限

- 本次评估聚焦「自动化脚本」的模型调用；agent 会话的「值班/协调对话」token 未计入（那部分取决于 agent 活动量，非自动化固定成本）
- P2 digest 若未来接入 LLM 摘要（当前纯规则聚合），成本另计

## 六、结论

外卖自动化恢复 **零 token 增量**——所有环节本地化，im-duty 事件驱动优化再省 97% HTTP。成本治理停令下的「外卖放行」证明是**无 token 代价的放行**（本地资源成本）。
