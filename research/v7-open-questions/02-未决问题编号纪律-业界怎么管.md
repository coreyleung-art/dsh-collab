## §1 业界怎么管这类编号一致性（四层，逐层给来源）

> ★ **来源分级**：本件只把**标准组织 / 政府标准 / 官方仓库**当一类依据；二手转述标为二类。
> ★ **★ 本机无任何「业界标准」代称** —— 下面每条都附可点链接。

### 层 1 · **登记表（Registry）本身的治理规程** —— IETF / IANA，BCP 26

**来源**：[RFC 8126 · Guidelines for Writing an IANA Considerations Section in RFCs](https://www.rfc-editor.org/rfc/rfc8126.txt)（**BCP 26 · 2017-06 · IETF 官方**，obsoletes RFC 5226）

这是**业界唯一一份把「编号登记表怎么管」写成标准**的文件。逐条对应本机的病灶：

| RFC 8126 的条款 | 原文（摘） | 本机对应 |
|---|---|---|
| **§2.2 登记表的文档要求** | 「Documents that create a new namespace … **must provide clear instructions** on details of the namespace」；须写明 **the name of the registry**、**Required information for registrations** | 本机 `open_questions` 的字段只有 `id`/`ask`/`owner`（+偶发 `state`/`note`/`voided`）⇒ **没有「登记必填字段」的定义** ⇒ 每条的形状各不相同（现测：17 条里只有 2 条带 `state`） |
| **§4 登记策略（10 种）** | Private Use / Experimental / Hierarchical / **First Come First Served** / **Expert Review** / Specification Required / RFC Required / IETF Review / Standards Action / IESG Approval | 本机**没有**声明「Q-x 号按哪种策略分配」。★ 从 §17.7 的实证看，实际策略是**先到先得** —— 而先到先得**必须配套一个可查的已占号清单**，而本机**没有**独立的已占号清单（占号信息散在索引 `open_questions` + 锚点 §15 + 台账，**三处**） |
| **§9.4 回收已分配值** | 「**Reclaiming previously assigned values for reuse is tricky**, because doing so can lead to interoperability problems with deployed systems still using the assigned values.」并给出三条最低要求（联系原被分配方 / 无原请求方同意不得重分配 / 必要时走正式流程） | ★ **本机在 `open_questions` 里做了一次「作废」（Q-F `voided=true`、Q-P `voided=true`）** —— 现测**两条都保留了原条目并附 `voided_reason`**（★ **做法符合 §9.4 的精神：不删、留痕**）。★★ **但本机没有「不得复用已作废号」的明文** —— 这是一条**应当补上的一句** |
| **§9.6 关闭/废弃登记表** | 给出关闭登记表与单条登记的规定路径 | 本机**无**「Q-x 号段的关闭/归档」条款 |

★ **⇒ 层 1 的结论**：**「先对表，再编号」在业界不是一句纪律，是一张有名字的登记表 + 一种明写的分配策略 + 一条「不得复用」的红线。** 本机**只有中间那句纪律**。

### 层 2 · **决策编号的成文格式** —— ADR / MADR

**来源**：
- [Michael Nygard · Documenting Architecture Decisions（2011，GDS 引为业界通例）](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)
- [UK GDS Way · Documenting architecture decisions（英国政府数字服务标准）](https://raw.githubusercontent.com/alphagov/gds-way/acc80bb8e30bca3c8823300a0d3a1637af99a691/source/standards/architecture-decisions.html.md.erb)
- [MADR v3 文档（adr/madr 官方仓库）](https://raw.githubusercontent.com/adr/madr/refs/heads/release/v3/docs/index.md)
- [AWS Prescriptive Guidance · Best practices for using architectural decision records](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/best-practices.html)

**GDS Way 逐字**（政府标准，一类依据）：

> Architecture decisions should be stored **in version control** so there is a record of **what was changed, who by, and when**. … as a summary it consists of the following sections: **Title · Status**（eg Proposed, Accepted, **Superseded**）· **Context** · **Decision** · **Consequences**.

**AWS Prescriptive Guidance 逐字**：

> **Preserve ADR history.** ADRs should have a change history, and each change should have an owner. When the ADR owner updates the ADR, they should change the status of the old ADR to **Superseded**, note their changes in the change history of the new ADR, and **keep the old ADR in the decision log**.

**MADR 的编号做法逐字**（官方仓库）：

> 1. Copy `docs/decisions/adr-template.md` to `docs/decisions/**NNNN**-title-with-dashes.md`, where `NNNN` indicates **the next number in sequence**.

★ **⇒ 层 2 的结论（三条可直接搬的机制）**：
1. **编号 = 单调递增序号**（`NNNN`），**不是语义字母**（本机 Q-A…Q-Q 混用了「序号语义」与「字母序」，且 `Q-M` 的漏载使字母序**看起来连续、实际断档**）。
2. **状态是第一条必填字段**（Proposed / Accepted / **Superseded** / Deprecated）。
3. **旧条目永不删，只改状态**（AWS 逐字：「keep the old ADR in the decision log」）。
4. **MADR 还提供 `Lint ADRs`** —— 即**编号/格式一致性有工具**，不靠人记。

★★ **对照本机现测**：`open_questions` 17 条里 —— **有 `state` 的只有 2 条**（Q-G `answered`、Q-P `answered`）；有 `voided` 的 2 条。★ **⇒ 15/17 条没有状态字段** ⇒ 「这条是 proposed 还是 accepted」**读不出来**。★ 这正是 §1 里「Q-G/Q-P 锚点写未决、登记表写 answered」能在**两边同时成立**的结构原因。

### 层 3 · **引用完整性（Referential Integrity）** —— 名字寻址，不是位置寻址

**来源分级**：★ **本层是数据库/规范工程的通例**（SQL 外键、URI/URN 持久标识），本件**未能取到一份单点权威文档**（见 §3 阴性证据）⇒ ★ **本条按「通例 + 本机实证」写，不按「标准原文」写。**

**通例**：
- 记录之间互相引用时，**用稳定标识（nominal reference）**，**不用位置（positional reference）**。
- 位置寻址的失效模式是**静默错指**（silent mis-reference）：插入一条，后面全部右移，**读数看起来正常但对象换了**。

★ **⇒ 层 3 的结论**：本机与「业界通例」的差距**不在纪律，在寻址方式**：

## §4 把「编号纪律」变成**可裁**的形态

> ★ 依本件任务边界：**把问题变成可裁形态，不代裁。**

### 问题是什么

「起草任何带编号的新条目之前，必须先读现有登记表并逐条比对占号」（§17.7）—— ★ **这条纪律要落成什么？**

### 可选项（★ 三档，成本递增）

| 选项 | 内容 | 参照（一类来源） |
|---|---|---|
| **(a) 只补纪律文本** | 把 §17.7 扩写，加入「不得复用已作废号」等句 | ★ 无外部参照；★ **本机已有前例：这类「只写规则」的做法已被证伪一次**（§17.7 **自己就是**上一轮的产物，而 **v6.1 期间又发生了一次同族事故**：`R18` 被两条线各写一次 ⇒ 见 §17.8） |
| **(b) 纪律 + 一支只读校验器** | 一支读三处（锚点 §15 / 索引 `open_questions` / 台账）出**集合对账**的脚本：缺号、撞号、单向存在 ⇒ **exit≠0** | [MADR 的 `Lint ADRs`](https://raw.githubusercontent.com/adr/madr/refs/heads/release/v3/docs/index.md)（格式一致性有工具）· [RFC 8126 §2.2](https://www.rfc-editor.org/rfc/rfc8126.txt)（登记表须有文档要求） |
| **(c) (b) + 给 `open_questions` 加「登记必填字段 + 分配策略」** | 每条 `Q-x` 必带 `id`/`status`(Proposed\|Accepted\|Superseded\|Voided)/`owner`/`opened_at`；并明写号段策略（先到先得 / 指定保留段） | [GDS Way 的 ADR 五段（含 **Status**）](https://raw.githubusercontent.com/alphagov/gds-way/acc80bb8e30bca3c8823300a0d3a1637af99a691/source/standards/architecture-decisions.html.md.erb) · [AWS「旧 ADR 标 Superseded 并保留」](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/best-practices.html) · [RFC 8126 §4 登记策略 / §9.4 回收](https://www.rfc-editor.org/rfc/rfc8126.txt) |

### 每选项的代价与后果

- **(a)** 成本 ≈ 0。★ **后果具名**：**v7 是大规模新增编号的版本**（大纲要求逐章清点并登记），**(a) 等于把同一个坑再踩一次**。★ 实证：现测 `rules-integrity.py` **红着**，且它是**上一轮「补了工具」**才有的 —— ⇒ **连「有工具」都会退，(a) 更会退**。
- **(b)** 成本 = 1 支只读脚本 + 负控（★★ **负控必须含「反向对照」**：合法集合 ⇒ 必须绿，照搬 §2.2 的 M5 形态）。★ **后果**：`Q-x` 面的「先撞号后察觉」变成「**撞号时 exit 1**」。★ **不改任何写入方 ⇒ 零风险**（与 §3 投入顺序第 1 条 W8.1 的论证同形）。
- **(c)** 成本 = **(b) + 17 条存量补齐 + 一次索引写入**（★ 改的是**外部第三方的索引** ⇒ **按 S3 / Q-N，起草方不代改**）。★ **后果**：**一次性把 §0.2 里「锚点写未决、登记表写 answered」这类分叉消除** —— 因为 `status` 变成**必填**，两边不一致会**当场可判**。★ **依赖**：须先有 Q-N 的**路由结论**。

### 裁它需要什么信息（★ 缺什么）

1. ★★ **缺：谁拥有 `open_questions` 的写入权。** ★ 现测：B8/B9/B10 逐字记「**索引 writer = 外部第三方（Claude Code 会话）**」，而 §7.8 又记「本地副本 ↔ 板值」两写入方（Q-Q）。⇒ **在「谁写」没定之前，(c) 落不了地。**
2. ★★ **缺：号段策略的一句话**（先到先得 / 保留段）。★ RFC 8126 §4 给了 10 种现成策略 ⇒ **只需挑一种**。
3. ★ **缺（本件未能提供）：锚点 §15 与索引之间「谁为准」的裁定** —— ★ 这是 **Q-Q** 与 **Q-P/Q-G** 的交点。
4. ★ **缺：「不得复用已作废号」是否照搬 RFC 8126 §9.4**（★ 本机已有两条 `voided` 先例，做法与 §9.4 一致，但**无明文**）。
