## 一、数据扩大方向评估（6 个方向，按 ROI 排序）

### P0：补齐时间与品种缺口（成本最低，收益确定）

| 缺口 | 现状 | 扩大路径 | 数据源 | 成本 |
|---|---|---|---|---|
| **2026-07~08 数据** | 库内最新 2026-06-01 | 增量采集 2 个月 | 昆明市农业农村局日价（nyncj.km.gov.cn，URL 规律 `c/日期/ID.shtml`） | 免费，脚本化 |
| **2023 年前月度明细** | 月度表从 2022-09 起 | 回溯补 2019-2022 | 呈贡区月度统计表（kmcg.gov.cn/sjkf/） | 免费 |
| **品种标准化** | 82 品种有 raw_name/standard_name 混用 | 统一标准品名映射表 | 库内自建 | 内部 |

**预期收益**：补 2 个月 ≈ +3000 行；回溯 3 年 ≈ +10000 行；品种标准化提升查询质量。

### P1：增加数据源维度（用 Coze 调研成果直接落地）

| 数据源 | 内容 | 状态 |
|---|---|---|

| 花易宝平台行情 | 日/历史趋势，需注册，⭐⭐⭐ | 待注册评估 |

**预期收益**：多源交叉验证（同一品种多源比价），价格可信度提升；KIFA 供给量接入后可与价格做联动分析。

### P1：价格因子数据接入（从「价格库」升级为「定价引擎」）

| 因子群 | 数据源 | 用途 |
|---|---|---|
| 节日需求 | OneAPI 节假日接口（免费） | 节日-价格联动（教师节/七夕/母亲节价格脉冲） |
| 气象 | 心知天气 API | 低温/暴雨 → 供应紧张 → 涨价预测 |
| 成本 | 上期所原油日行情 | 物流成本联动 |
| 出口 | 昆明海关月报 | 出口量 → 内销供给变化 |

**预期收益**：实现「提前预测价格」而非「事后记录」——这是花店 AI 运营官的核心卖点（锁价建议）。

### P2：跨市场扩展（跳出斗南单市场）

| 市场 | 数据 | 用途 |
|---|---|---|
| 广州岭南花卉市场 | 华南市场行情 | 本地化采购参考（自有店在广州） |
| 昆明 KIFA 拍卖价 | 拍卖成交价（更实时） | 高端花材定价锚 |
| 1688 批发价（已采集 90 条） | 资材/包装价格 | 成本核算完整化 |

### P2：历史数据深度清洗（质量工程）

- 2026-06 混入蔬菜市场数据（已识别 6 行脏行）→ 建清洗规则
- 价格异常值（如洋桔梗 ¥42.43 峰值）→ 波动标注 + 因子归因
- unit 标准化（元/支 vs 元/扎 vs 元/kg）

### P3：预测模型（远期）

- 基于 15970 行历史 + 节日/气象因子 → 时间序列预测（Prophet/LSTM）
- 输出：未来 7 天各品种价格区间 → 锁价建议

## 二、存储位置评估：本地 vs PC-i9

### 2.1 现状对比

| 维度 | 本机 mac-mini | PC-i9 |
|---|---|---|
| CPU | M4 / 10 核 | **i9-14900KF / 32 线程**（4 倍） |
| GPU | Metal 4（无 CUDA） | **RTX 4060 Ti 8GB**（CUDA） |
| 内存 | 24GB（交换压力高） | 32GB（WSL2 池余量充足） |
| 磁盘 | **87% 满（剩 58Gi）** | **E 盘 1.25TB 空闲** |
| 已有生态 | DSH 宿主、8787 面板 | **flower-intel Dify 栈**（竞品采集+定价+MySQL/Milvus）+ 第 3 DSH 节点 |
| 远程访问 | 本机 | Tailscale + 向日葵 MCP（已验证） |

### 2.2 方案对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 本地为主 + i9 镜像** | 查询快、与 DSH 无缝、现有管道直接用 | 本机磁盘紧（58Gi）、算力有限（预测/向量弱） | ⚠️ 短期可行，长期受限 |
| **B. i9 为主（推荐）** | E 盘 1.25TB 充足；flower-intel 已有「智能定价」定位；GPU 可跑预测/向量；卸本机负载 | 需跨设备同步/访问层（Tailscale 已通）；远程写入有延迟 | ✅ **推荐**：数据资产归 flower-intel 定价闭环 |
| **C. 混合** | 查询副本在本地（SQLite 小、快）、**主库在 i9 MySQL**、向量在 i9 Milvus | 双写复杂度 | ✅ 中远期目标 |

### 2.3 推荐方案：B（i9 为主）分阶段

```
阶段 1（现在）：本地 SQLite 继续做查询底座（15970 行仅 ~5MB，无压力）
                + flower-price.db 导出备份到 i9 E 盘（Tailscale/向日葵）
阶段 2（接入时）：flower-intel Dify 栈（i9）增加「花材价格」数据源
                → 竞品情报 + 花材成本 + 定价建议 全闭环在 i9
阶段 3（远期）：向量层入 i9 Milvus；预测模型在 i9 GPU 跑
                → 本地保留「轻量查询副本」供 DSH 会话日常用
```

### 2.4 为什么不是纯本地

1. **磁盘**：本机 87% 满（剩 58Gi），Docker/外卖采集栈/缓存都在涨，花材价格只是开始，后续跨市场/因子/预测数据会持续膨胀
2. **算力**：价格预测（Prophet/LSTM）、向量检索、多源采集调度——i9 的 GPU-CUDA 是本机没有的
3. **生态归属**：i9 已有 flower-intel「智能定价」平台（MySQL/Milvus/ChromaDB 全栈），花材价格**天然属于定价闭环**，放本地是「孤儿数据」
4. **既有先例**：Dify 栈已从本机迁移到 i9（docker-migration 评估 ✅），花材价格跟随同一逻辑

### 2.5 迁移风险与对策

| 风险 | 对策 |
|---|---|
| 跨设备访问延迟 | 本地保留轻量 SQLite 副本（现库不删），i9 做主库 |
| i9 远程写入不稳定 | 批量导入用文件传输（Tailscale SCP），不用实时 API |
| 数据一致性 | 明确主从：i9=主（权威），本地=查询副本（定期同步） |
| flower-intel 归属需确认 | 需与设备协调（5a5368af）确认 flower-intel 数据模型可否扩表 |

## 三、结论

1. **扩大方向**：P0 补时间缺口（+1.3 万行）→ P1 多源交叉 + 因子接入（从价格库升级为定价引擎）→ P2 跨市场 → P3 预测模型
2. **存储**：**推荐 i9 为主**（E 盘 1.25TB + flower-intel 定价闭环 + GPU 算力），本地保留轻量查询副本；分 3 阶段迁移，不冒险迁移
