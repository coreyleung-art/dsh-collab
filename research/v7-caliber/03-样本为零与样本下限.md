# 03 · 样本为零与样本下限：业界怎么报

> 角色：v7 调研代理 R4 · 时点：2026-10-12
> 项目纪律（硬性）：「**空 ≠ 无**」—— 分母为 0 必须报「不可判」，**不得报 0%、不得报 100%**
> 证据等级：**已读原文** / 仅见摘要 / 未查证（逐条标注）

---

## 〇、结论先

1. **「无数据」在业界是一个【独立的第三态】，不是 0 也不是 100%。** 三家独立来源同向：Prometheus `absent()`、Grafana `No Data` 四态、Prometheus staleness。
2. **「样本不足」在业界有一条【可执行的阈值】**，不是靠感觉。GitLab 生产 runbook 明写 `minimumSamplesForMonitoring`，**当前值 3600 样本**。
3. **样本不足时的行为必须是【显式选择】**：Grafana 给了 4 个选项并**点名了最危险的错配**（把 no-data 当 Normal）。
4. ★ **本项目的「空 ≠ 无」纪律与业界一致，且本机已把它做成可复跑的负控**（§四复跑 3，5/5 符合 + 2 个天真实现被抓出，`bad=0`，`EXIT=0`）。

## 一、业界一手来源

### 1.1 Prometheus：把「无元素」映射成值 1（一个独立信号）

**Prometheus 官方**（已读原文，[Query functions](https://prometheus.io/docs/prometheus/latest/querying/functions/)）逐字：

> `absent(v instant-vector)` returns an **empty vector if the vector passed to it has any elements** and a **1-element vector with the value 1 if the vector passed to it has no elements**. **This is useful for alerting on when no time series exist for a given metric name and label combination.**

> `absent_over_time(v range-vector)` returns an empty vector if the range vector passed to it **has any elements** and a 1-element vector with the value 1 if the range vector passed to it **has no elements**. This is useful for alerting on when no time series exist for a given metric name and label combination **for a certain amount of time**.

★★ **两个设计要点**：
1. **方向**：「无数据」→ 值 **`1`**（一个**可被 assert 的信号**），**不是 `0`**、**不是「跳过」**。
2. **`absent_over_time` 自带时长**：`absent_over_time(nonexistent{job="myjob"}[1h])` —— **「无数据持续多久」也是判据的一部分**。

★ 对照我们：「1 小时窗口内 0 张卡」这件事，业界形态是 `absent_over_time(...[1h])` ⇒ **它本身是一条可告警的断言**（「巡检流断了」），**而不是「到达率=无定义」**。

### 1.2 Prometheus：陈旧 ≠ 0

**Prometheus 官方**（已读原文，[Querying basics · Staleness](https://prometheus.io/docs/prometheus/latest/querying/basics/)）逐字：

> If a target scrape or rule evaluation **no longer returns a sample** for a time series that was previously present, **this time series will be marked as stale**. ... If a query is evaluated at a sampling timestamp after a time series is marked as stale, then **no value is returned** for that time series.

★ **「不返回值」与「返回 0」在 Prometheus 里是两个不同的东西。**
★ 默认 lookback **5 分钟**（逐字：`The lookback period is 5 minutes by default, but can be set with the --query.lookback-delta flag`）。

### 1.3 Grafana：No Data 是独立状态，且有 4 种显式处置

**Grafana 官方**（已读原文，[No-data and error handling](https://grafana.com/docs/learning-hub/basic-alerting/04-evaluation/12-no-data-error/)）逐字给出**无数据的三个成因**：

> - No series match the query due to an incorrect metric or label filter
> - The data source stops reporting
> - **The time window has no samples, often because the evaluation window or query range is too short for how often the data arrives**

★ 第三条**逐字命中**我们的 1h / 3h 空窗（见 02 篇 §三）。

> The query returns no data. In this case, **Grafana assigns a state of No Data**.

**四种处置（原文表，逐字）**：

| Alert state | Use this state when | What happens |
|---|---|---|
| **Alerting** | **No data means something is broken, like a heartbeat check where silence equals an outage** | Makes your own rule fire |
| **Normal** | **Gaps are expected and harmless**, like a metric that only reports during business hours | Keeps your rule quiet and healthy |
| **Keep Last State** | Gaps are **brief and self-healing**, and you want to avoid the rule **flapping on a missed scrape** | Holds whatever state your rule had before the gap |
| **No Data/Error (default)** | You want a **separate signal that the data pipeline broke**, routed apart from your rule | Leaves your rule quiet and raises a **separate alert** named `DatasourceNoData` / `DatasourceError` |

★★ **且它明确点名这个坑**（逐字）：

> **Don't set the `Alert state if no data or all values are null` option to `Normal` unless you're certain that data gaps are safe.** Otherwise **your rule stays silent during a real outage**, and you hear nothing when the underlying data source stops reporting.

★★★ **⇒ 关键区分：**
- **「空窗可能是好事」**（无 drift ⇒ 无卡）⇒ 选 `Normal` 有一点点道理
- **但 `Normal` 的代价是：真断链时也沉默**
- **业界默认是第四个选项**：**另起一条独立的告警**，而不是把空窗塞进原判据

★ 这正是**本项目该走的路**：**到达率遇 0 样本报「不可判」，而「巡检流是否在流」另立一条独立断言**。
★ 且 `m4-1-caliber-ruling` §四 已经立了这条（①c 心跳 ≤ 2×周期，现测 PASS）—— **本调研确认它符合 Grafana 的默认处置（No Data ⇒ 独立信号）。**

### 1.4 GitLab：样本下限是一个【可配置的数值】，不是「足够多」

**GitLab 生产 runbook**（已读原文，[Service-Level Monitoring](https://runbooks.gitlab-static.net/metrics-catalog/service-level-monitoring/index.html)）—— 这是本调研找到的**最直接回答「样本下限怎么定」的一手生产文档**。逐字：

> Service-Level Monitoring uses a **statistical approach** to monitoring and alerting. **As with any statistical operation, sample sizes matter.**

> The Metrics-Catalog **initially used a fixed minimum RPS rate of 1 request-per-second** for SLO alerting. **Any service not maintaining this RPS was excluded from SLO alerting** to avoid noisy alerts.

> However, our SLO Alerting implementation uses **Multi-Window, Multi-Burn-Rate alerting**, which evaluates burn rates across multiple windows, including **1h, 6h and 3d**. **In a 3d period, a 1 RPS minimum service threshold equates to 259,200 samples, but over a 1h period, this is only 3,600 samples.** A service could therefore operate just under the threshold, producing say 250,000 samples over 3d, **yet still be excluded from the minimum RPS threshold**.

> To get around this, the Metrics-Catalog has **migrated over to minimum sample size thresholds instead**. **This is currently set to 3600 samples.** This means that in a **1h** period, 3600 samples are needed (except in the case of node SLO monitoring for Gitaly, which uses **1200 samples**), over a **6h** period, 3600 samples are required and over **3d**, 3600 samples are required. **This means that low-traffic services can be monitored over long-window periods even if they are excluded from short window periods due to low sample services.**

> We have **two thresholds** to control this. **Both thresholds are optional, but both need to be met if specified**:
> - **`minimumSamplesForMonitoring`** – This is the **number of operations** needed over the whole window for an alert to be triggered.
> - **`minimumOpsRateForMonitoring`** – This is the **absolute average ops rate** needed for the window for an alert to be triggered.

★★★ **这段给了四条可直接照搬的规则：**

| # | GitLab 的规则 | 对我们的映射 |
|---|---|---|
| 1 | **不用「速率阈值」用「样本数阈值」** | 我们不该用「每小时多少卡」，该用「**窗口内至少 N 张卡**」 |
| 2 | **同一个样本下限对每个窗口分别适用** | 1h / 6h / 24h 各自都要 ≥ N，**不能用一个窗口的充足去补另一个窗口的不足** |
| 3 | **未达下限 ⇒ 【排除出告警】，不 ⇒ 报 0%** | ★ 这正是「**不可判**」的生产形态 |
| 4 | **阈值可配置，且可 per-target 覆盖**（Gitaly 用 1200） | 我们的自指卡/低频卡可能需要**单独下限** |

★ 注意 GitLab 的第 3 条用词是 **"excluded from SLO alerting"** —— **排除出告警**，不是**排除出统计**。
★ 这与 01 篇的结论互补：**排除的是「判据的 PASS/FAIL」，不是「数据本身」。**

### 1.5 Google SRE：低流量服务是【一个专章】

**Google SRE Workbook**（已读原文，[Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/)）逐字提到：

> Note that alerting can become **particularly sensitive to nonsignificant events during low-traffic periods** (discussed in **Low-Traffic Services and Error Budget Alerting**).

★ 即：**低流量下的告警会变得过度敏感**（一个失败事件就把比率打穿）。
★ 该章的评估四参数（逐字）：**Precision / Recall / Detection time / Reset time**。
★★ **⇒ 业界把「低流量」当成一个【需要专门设计的子问题】，不是「样本少所以随便看看」。**

## 二、把三者拼起来：业界对「样本为 0 / 不足」的完整处置

```
                样本充足 ──────────────►  报具体比率，判 PASS / FAIL
                     │
查询/统计 ───────────┤
                     │
                样本不足 ─────┬──► Prometheus absent_over_time：另立「无数据」断言（值 1）
                             ├──► Grafana：「No Data」独立状态，默认另起一条告警
                             ├──► GitLab：excluded from SLO alerting（不报比率）
                             └──► Google SRE：Low-Traffic 专章（防过度敏感）

                ★ 三者共同点：绝不把「样本不足」折叠成 0% 或 100%
```

★★ **⇒ 本项目的「空 ≠ 无 ⇒ 报不可判」与这条业界线完全一致。**
★ 本项目的**额外贡献**是把「不可判」明确写成**第三态**（`UNDECIDABLE`），而 Grafana 用「单独告警」、GitLab 用「排除」、Prometheus 用「值 1」——**形状不同，语义相同**。

## 三、我们的样本下限该定多少？（给判据，不代裁）

按 GitLab 方法论（`minimumSamplesForMonitoring`），需要先知道**事件到达率**：

- 巡检周期 = 1800 s（`m4-1-caliber-ruling` §四 实测 `StartInterval = 1800`）
- **★ 但「有卡」≠「有巡检」** —— 只在 `driftCount > 0` 时才写告警卡（`m4-1-caliber-ruling` §6.2 逐字：`无漂移即无告警卡`）

⇒ **告警卡的到达率不是一个固定速率，它正比于「系统有多坏」。**
⇒ ★★ **因此「窗口内样本数」本身是一个【依赖于被测状态】的量 —— 坏的时段样本多，好的时段样本少。**

★★★ **这是一个结构性发现**：
```
系统越坏  ⇒ 卡越多     ⇒ 样本充足 ⇒ 可判   ⇒ 指标有效
系统越好  ⇒ 卡越少     ⇒ 样本不足 ⇒ 不可判 ⇒ 指标失效
```
⇒ **「到达率」这个指标在系统健康时天然失效。** 这正是 Grafana 说的「不能把 no-data 当 Normal」的另一面 —— **不是我们实现错了，是这个指标形状如此。**

★ **业界对本问题的处置是【换指标】**，而不是调窗口：
- **Prometheus**：用 `absent_over_time` 直接问「**信号停了吗**」（不依赖样本量）
- **Grafana**：另立 `DatasourceNoData` 独立告警
- **我们的对应物**：**`data/ops/drift-heartbeat/`** —— 单键覆盖写，逐字自述（本机与中枢两板实读，19:34:55，见 04 篇复跑）：

> ★ 本键为【单键覆盖写】：**新鲜=巡检在跑；陈旧=巡检已停（零漂移 ≠ 健康）**

★★ **⇒ 「心跳新鲜度」才是那个【不依赖样本量】的健康判据。**「到达率」只在**有卡可数**时才有意义。

## 五、对我方（v7 计划）的直接结论

| # | 建议 | 依据 |
|---|---|---|
| 1 | **样本为 0 ⇒ 报「不可判」**（现行纪律，确认保留） | Prometheus `absent` / Grafana `No Data` / GitLab `excluded` |
| 2 | ★ **「样本不足」还要覆盖「样本少」**（不只 0） | GitLab `minimumSamplesForMonitoring = 3600`；**现测 6h 窗口 n=1 即属此列** |
| 3 | ★ **「不可判」必须是三态之一，不得回退为 0%/100%** | Grafana 点名把 no-data 当 `Normal` 的后果 |
| 4 | ★★ **「到达率」不该承担「巡检是否在跑」的职责 —— 另立心跳** | GitLab 的 excluded 语义 + Grafana 的独立告警默认项；**本机心跳已存在** |
| 5 | ★ **样本下限应写成可配置数值 + per-target 覆盖** | GitLab 双阈值 + Gitaly 1200 例外 |
| 6 | **分母为 0 与分母为负都要落到不可判** | §四复跑 3 负例 2（脏输入） |

★ **不代裁**：具体下限数值（如「24h 窗口至少 N 张」）**本文件不给**—— 需要先确定「可接受的判别力」，属属主裁决。
