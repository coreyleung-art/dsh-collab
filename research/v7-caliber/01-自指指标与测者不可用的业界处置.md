## 〇、先更正一个前提（★ 本节最重要）

题面写：

> 「一条『中枢不可达』的告警，要双板到达就得写进中枢 ⇒ **结构上不可能到达**。」

**这条被本机实测证伪了。** 复跑见 `evidence/repro-02-selfref.py`（原文输出 `repro-02-selfref.txt`）：

```
  ⇒ 自指卡 23 条，已到达 21 条，未达 2 条
  ⇒ ★ 若「结构上不可能到达」成立，应为 0 条到达；实测 21 条到达
```

**23 张自指卡里，21 张到达了中枢板（91.3%）。**

关键在于：这 23 张卡的 `actual` **全都**是 `HTTP 0`（= 报「中枢不可达」），内容形状完全一致：

```
【B】自指卡的 actual 值分布（确认它们报的是不是「中枢不可达」）
   actual='HTTP 0'     arrived=False  → 2 条
   actual='HTTP 0'     arrived=True   → 21 条
   ★ 全部 23 条 actual 均为 'HTTP 0' ⇒ 内容形状完全相同，
     故「是否自指」不是到达与否的判别式。
```

⇒ **「是否自指」不是判别式。** 同一内容形状的卡，21 张到了、2 张没到 ⇒ 差异不在「自指」，在**别的量**。

### 那 2 张为什么没到？——用邻域成片度区分

`repro-02-selfref.py` 【C】节对每张未达卡取 ±3h 邻域，数其中未达张数：

| 未达卡时刻 | ±3h 未达/总数 | 定性 |
|---|---|---|
| **10-03 21:50:06**（自指） | **6/6** | ★真断链（成片）—— 该卡同时报 **5 项** drift，含 `tailscale 失败: spawnSync ... ETIMEDOUT` |
| **10-12 00:24:07**（自指） | **1/2** | **孤立单点** |

全量统计（同一脚本尾部命令）：

```
全量未达卡: 294 条
其中【孤立单点】（±3h 内仅它一条未达）: 2 条
   2026-10-03 15:01:54  1791010914531    checks=['sse-8803']  自指=False
   2026-10-12 00:24:07  1791735847210    checks=['board-central']  自指=True
```

★★ **判决性事实有两条**：

1. **294 条未达里只有 2 条是孤立单点**；其余 **292 条全部落在成片断链窗口**内（真断链，与自指无关）。
2. **这 2 条孤立单点里，有 1 条是【非自指】的**（`sse-8803`）。

⇒ **孤立单点投递失败是一个与「自指」无关的通用现象**（非自指卡也照样发生）。
⇒ 因此「自指」既**不充分**也不**必要**。
⇒ **自指闭环在本机全量数据里只有 n=1 的候选实例**（10-12 00:24:07），**样本不足以断言「结构上不可能」**。

### 为什么 21 张自指卡能到达？—— 两个时刻被写成了一个

这是本机纪律「**凡读状态必问这是哪个时刻的**」的镜像实例：

- 卡断言的是「**扫描时刻 T1** 中枢 HTTP 0」
- 投递发生在「**写入时刻 T2**」

T1 ≠ T2。中枢可以在 T1 抖动不可达、在 T2 已恢复 ⇒ **两者不矛盾**。
把 T1 和 T2 读成同一个时刻，就会得出「它说自己不可能被送达」的假悖论。

★★★ **⇒ 要处置的不是「自指」，是【时刻坍缩】**：一条记录把「T1 时刻中枢不可达」与「T2 时刻写入中枢」两件事写成了一件事，读者据此推出悖论。
★ 与 `docs/m4-1-caliber-ruling-20261012.md` §四「无告警时落后量空转」、§6.2 板级 `ts` vs 内层 `value.ts` 差 56m46s **同族**——都是**两个量被写成一个**。

## 二、Q2：测 A 时 A 自己坏了，业界怎么处置？

业界给的不是一个手法，而是**四层手法，且方向一致：判定方必须在被判定对象之外**。

### 手法 1 · 独立探针路径（out-of-band / 外部判定方）

**PromLabs 官方培训**（已读原文，[链接](https://training.promlabs.com/training/monitoring-and-debugging-prometheus/metrics-based-meta-monitoring/end-to-end-watchdog-alerts/)）：

> **Even if you build the most reliable internal meta-monitoring infrastructure, something can still go wrong**: the meta-monitoring setup might have a systematic error that causes it to break, the Alertmanager through which notifications are supposed to get delivered to you might be down, or your entire organization's network might be disconnected from the internet!

★ **这一句直接否掉「再加一层内部监控」这条路。** 必须走到**外部**。

三步原文（同页）：
1. 配一条**永远在触发**的告警规则（`vector(1)` 或 `1`）
2. Alertmanager 路由到**外部服务**，repeat interval 只有几分钟
3. **外部服务**期望每 x 分钟收到一次，**否则给你发告警**

> When anything in your alerting pipeline breaks, the external service will then notice that **no more alert notifications are coming in** and will send you a notification about it.

**kube-prometheus 的 `Watchdog` 告警**（PromLabs 同页逐字引用，G1 亦已录）：

```
- alert: Watchdog
  expr: vector(1)
  labels: { severity: none }
```

★ `expr: vector(1)` —— **它不检测任何指标，它的存在本身就是信号；它坏掉的方式就是「不再出现」。**

**Out-of-band management**（Wikipedia，已读原文，**非一手**）：

> a process for accessing and managing devices and infrastructure at remote locations through a **management plane separate from that of the production network** ... It is contrasted to **in-band management, which requires the managed systems to be powered on and available over their operating system's networking facilities.**

★ 对我们的映射：本机板 `127.0.0.1:8792` 与中枢板 `106.53.214.108:8792` **都是 in-band**——两板都在同一条链路语义里。**目前没有 OOB 腿。**

### 手法 2 · 递归必须有界（第三条路，而非无限套娃）

**[ADR-0046: Meta-observability with bounded recursion](https://github.com/T-rav/hydraflow/blob/40087d19baa69e392714a813b7f587c2e90cc0b3/docs/adr/0046-meta-observability-bounded-recursion.md)**（已读原文，**非权威来源**，见 §五）逐字：

> **who watches the watchers?** ... That immediately raises a second question: **who watches the meta-observer?** A tempting answer is "another loop", but that recurses ... **At some level something has to watch the last watcher, and if the answer is "the same class of loop", the chain is infinite and the last layer has no observer.**

它的决定（逐字）：

> **One and only one meta-observability layer.** ... That loop is **itself watched by `HealthMonitorLoop._check_sanity_loop_staleness`**, which runs **inside the pre-existing (non-trust) health monitor** and uses a dead-man-switch pattern ... **The recursion terminates at the health monitor on purpose.**

**并且它诚实承认终点**（逐字）：

> **Negative:** ... **No observability for the dead-man's-switch itself.** A bug in `_check_sanity_loop_staleness` could leave the fleet unmonitored.

★★★ **这正是我们要的答案形状**：**递归必须显式终止，且终止层的「未被观测」要被写下来，而不是假装不存在。**
★ 对照我们的现状：**自指卡这一步没有终止声明** —— 它既没说「这条卡结构上不可达所以不计」，也没说「谁来看这条卡」。**它悬空了。**

### 手法 3 · 「测者不可用」单独计为一个状态

**Prometheus 的 `absent()` / `absent_over_time()`**（已读原文，[Query functions](https://prometheus.io/docs/prometheus/latest/querying/functions/)）逐字：

> `absent(v instant-vector)` returns an **empty vector if the vector passed to it has any elements** and a **1-element vector with the value 1 if the vector passed to it has no elements**. **This is useful for alerting on when no time series exist for a given metric name and label combination.**

★ 注意方向：**「无数据」被映射成值 `1`（一个独立的、可告警的信号），而不是映射成 `0`，也不是映射成「跳过」。**

**Prometheus 的 staleness**（已读原文，[Querying basics · Staleness](https://prometheus.io/docs/prometheus/latest/querying/basics/)）逐字：

> The lookback period is **5 minutes by default** ... If a target scrape or rule evaluation **no longer returns a sample** for a time series that was previously present, **this time series will be marked as stale**. ... If a query is evaluated at a sampling timestamp after a time series is marked as stale, then **no value is returned** for that time series.

★ **「不再被导出」是一个显式状态**，且它**不等于 0**。

**Grafana 的 No Data / Error 四态**（已读原文，[No-data and error handling](https://grafana.com/docs/learning-hub/basic-alerting/04-evaluation/12-no-data-error/)）—— 这是与我们最贴近的一张表，**四种选项各有适用语**：

> | Alert state | Use this state when | What happens |
> |---|---|---|
> | **Alerting** | **No data means something is broken, like a heartbeat check where silence equals an outage** | Makes your own rule fire |
> | **Normal** | Gaps are expected and harmless, like a metric that only reports during business hours | Keeps your rule quiet and healthy |
> | **Keep Last State** | Gaps are brief and self-healing, and you want to avoid the rule flapping on a missed scrape | Holds whatever state your rule had before the gap |
> | **No Data/Error (default)** | You want a separate signal that the data pipeline broke, routed apart from your rule | Leaves your rule quiet and raises a separate alert named `DatasourceNoData` / `DatasourceError` |

**且它明确点名了这个坑**（逐字）：

> **Don't set the `Alert state if no data or all values are null` option to `Normal` unless you're certain that data gaps are safe. Otherwise your rule stays silent during a real outage, and you hear nothing when the underlying data source stops reporting.**

★★★ **⇒ 「测者不可用」在业界是一个【有名字、有开关、有默认值】的显式状态，而不是一个空白。**
★ 且 Grafana 列出了**无数据的三个具体成因**，其中第三条**正是我们的 1h/3h 窗口问题**：

> The **time window has no samples**, often because **the evaluation window or query range is too short for how often the data arrives**

（该条在 03 篇展开。）

### 手法 4 · SLI 里把「测量系统自身的失败」排除或另立

**Google SRE Book**（已读原文，[Service Level Objectives](https://sre.google/sre-book/service-level-objectives/)）逐字：

> For maximum clarity, **SLOs should specify how they're measured and the conditions under which they're valid.**

★ 这一句是**「口径未定」问题的业界正面回答**：**生效条件（validity）是 SLO 定义的必要组成部分**，不是事后补充。

**Google SRE Workbook**（已读原文，[Implementing SLOs](https://sre.google/workbook/implementing-slos/)）把 SLI 拆成两半，逐字：

> **SLI specification** — The assessment of service outcome that you think matters to users, **independent of how it is measured**.
> **SLI implementation** — The SLI specification **and a way to measure it**.

★ **「测什么」与「怎么测」被显式分开。** 我们的「到达率」把两件事混在一句「到达率 == 100%」里 ⇒ 违反这条。

**Google SRE Workbook** 同页还列了标准的**测量窗口必须随 SLI 一起声明**（逐字）：

> Standardize Indicators — **Aggregation intervals**: "Averaged over 1 minute" · **How frequently measurements are made**: "Every 10 seconds" · **Which requests are included**: ...

### 复跑 3 · 孤立单点计数（决定性）

```bash
cd /Users/coreyleung/dsh-collab && python3 - <<'PY'
import json,urllib.request,time
def get(b,k):
    with urllib.request.urlopen(b+"/"+k,timeout=30) as r: return json.loads(r.read().decode())
```

## 五、对我方（v7 计划 D 项）的直接结论

题面给了三个选项，本调研的取证**改变了它们的权重**：

| 题面选项 | 本调研后的评价 |
|---|---|
| **1. 改判据，把「自指类告警」显式排除** | ❌ **不建议** —— 前提被证伪。自指卡 **21/23 到达**，排除它**会误伤 21 条合法到达的卡**，并使指标**对中枢真断链致盲**（自指卡恰恰是中枢最坏时的唯一信号） |
