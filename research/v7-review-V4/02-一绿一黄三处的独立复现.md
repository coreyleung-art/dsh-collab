## 三、★ 三条最小动作 —— 是否真能修掉？

### 动作 #1 · 用 `check-six-conditions.py` **替换** `beacon-check` 的两条 PASS，且退出码让 UNKNOWN 致非 0（`--strict`）

**可修性：可实现。但有代价，且该代价未被计价。**

**证据 1 · 文件可写**（`guard_check_writable` 现测）：

```json
{"path":"~/dsh-collab/tools/beacon-check.py","writable":true,"forbidden":false,"reason":""}
{"path":"~/dsh-collab/tools/official-ref-gate.py","writable":true,"forbidden":false,"reason":""}
{"path":"~/dsh-collab/data/registry/continuity-index.json","writable":true,"forbidden":false,"reason":""}
```

**证据 2 · `--strict` 存在，且我用合成 fixture 证明它【能红】**（正控，避免我误报「从未红过」）：

```bash
python3 -c "..."  # 造一个 FAIL=0 而 UNKNOWN>0 的索引到 /tmp
python3 …/check-six-conditions.py --index /tmp/v4_strict_fixture.json
python3 …/check-six-conditions.py --index /tmp/v4_strict_fixture.json --strict
```

**未编辑原始输出**：

```
args=[]         rc=0  汇总行=['  PASS 0 · FAIL 0 · UNKNOWN 1（共 1）']
args=['--strict'] rc=1  汇总行=['  PASS 0 · FAIL 0 · UNKNOWN 1（共 1）']
```

⇒ ★ **`--strict` 确实是判据（它能红）。**

**证据 3 · ★★ 但在生产索引上，它今天是【空转】**

```
python3 …/check-six-conditions.py          → rc=1
python3 …/check-six-conditions.py --strict → rc=1
```

⇒ ★★ **两者同码** ⇒ 最小动作 #1 所指定的机制，在**当前唯一的真实输入上不改变任何结果**。
⇒ 它要等到 `FAIL` 降到 0 才第一次生效 —— **也就是要等 verifier 问题被修完之后**。

**证据 4 · ★★★ 代价：`--strict` 把 UNKNOWN 与 FAIL 折叠成同一个 rc**
源码（`check-six-conditions.py:164`）逐字：

```python
rc = 1 if counts["FAIL"] else (1 if (a.strict and counts["UNKNOWN"]) else 0)
```

⇒ **`FAIL=6` ⇒ rc=1；`FAIL=0, UNKNOWN=4` ⇒ rc=1。CI 只读 rc 时【分不出】这两者。**
★★★ **而「把 规格缺失（UNKNOWN）与 规格被违反（FAIL）分开」正是 `slo/05` §四 花了整节建立的实质增量。**
⇒ **最小动作 #1 在机器可读层把它撤销了。**
⇒ **这是「两个量被写成一个」的又一次实例，且由被审文档自己的建议引入。**

**⇒ 判定：可修，但须补一条修正 —— `UNKNOWN` 与 `FAIL` 必须给不同的 rc（如 `1=FAIL`、`4=仅UNKNOWN`），否则 #1 与 §四 相冲。**

### 动作 #2 · 把「不可判」拆成 `NO_OBSERVATION` / `COLLECTION_FAILED`

**可修性：可实现（无工具依赖），但【无人验证过】。**

⇒ **#1 与 #2 必须同时定稿，否则两者互相抵消。**
