## 〇、定位：为什么这是替代代运营的核心链路

传统代运营=人盯盘+经验判断：刷单量靠感觉、推广费靠经验、品类分配靠记忆、持续稳定靠纪律。
**AI 替代的路径 = 同样的动作，但每个决策都有数据模型支撑、可回测、可实验、秒级执行**——这正是量化交易对金融市场做的事，我们把它搬到外卖运营。

## 一、总体架构（6 层）

```
L5 实验层   商品赛马 / A-B / DID / 断点回归 / 合成对照（最小成本试错）
L4 执行层   营销端自动化（改价/推广/发券/补单任务）+ 审计 + 门控（J37/确认）
L3 决策层   动态优化：预算分配（补单 vs 推广 vs 折扣）、关键词→品类分配、秒级联动策略
L2 因果层   测算模型：补单→转化 因果效应 / 推广费→进店→转化 漏斗 / 交互效应
L1 指标层   统一口径：CTR/CVR/每单成本/推广费单/补单量/关键词权重/自然流量占比
L0 数据底座 订单/曝光/点击/关键词/评价/竞争情报 秒级采集入库（多店 × 多平台）
```

## 一·A、市场调研端自动化（手机链路）——竞对情报采集

> 用户澄清（2026-08-19）：营销端自动化≠商家版后台运营（那是链路 A，纳入但不构成主体）——**核心是市场调研端自动化**：平台数据闭源无 API，传统靠人拿手机逐个刷附近店铺（排名/商品结构/销量/价格）；自动化=从「控制电脑」升级到「控制手机」（物理或虚拟），逻辑与商家版管理同构，游走于「不惊扰平台闭源保护」与「物理层自动化推进」之间。

### 1A.1 双链路同构架构

| | 链路 A：商家版管理（电脑端） | 链路 B：市场调研（手机端） |
|---|---|---|
| 控制对象 | 外卖商家版后台（电脑浏览器/客户端） | 用户版 App（美团/饿了么/京东外卖）物理或虚拟手机 |
| 自动化层 | 浏览器自动化（CDP/Playwright）+ 面板原语 | 手机自动化（ADB/Appium/AirTest/scrcpy/向日葵 MCP） |
| 采集 | 本店订单/评价/推广/关键词 | 竞对店铺排名/商品结构/销量/价格/评分/活动 |
| 大脑 | 外卖运营智能体（vision + LLM + 决策） | 同一大脑（数据归一后共用） |
| 知识库 | 运营手册/策略库 | **竞对情报库**（店铺画像/价格带/活动策略/关键词映射） |
| 输出 | 本店运营执行 | 竞对周报/价格策略/补单品类依据/推广竞价参考 |

### 1A.2 手机链路技术栈

设备层：物理真机群（iPhone/安卓）或 云手机/模拟器（多开=多城市多商圈并发）
控制层：ADB / Appium / AirTest / uiautomator2 / scrcpy / 向日葵 MCP（已有 awesun 22 工具实测打通）
采集层：用户版 App UI 自动化——附近店铺列表 → 店铺详情 → 商品/价格/销量 → 截图 + 结构化提取（vision OCR）
归一层：数据清洗 → 标准 schema（店铺/排名/商品/价格/销量/评分/活动/时间戳）
知识库：竞对情报库（入 Chroma/KB，供运营智能体查询——即「知识库体系持续管理」）
大脑层：外卖运营智能体：看截图做决策 → 反馈链路 A 执行（定价/补单品类/推广）

### 1A.3 边界设计（不惊扰平台闭源保护）

- **只做 UI 层「人肉浏览」的自动化替代**（物理操作手机屏幕）：不逆向 API、不抓包破解、不批量注册、不干扰平台服务
- **拟人节奏**：随机间隔/滚动/停留时长，防行为指纹检测
- **频率熔断**：检测到平台风控信号（验证码/限流/异常提示）即停并告警人工
- **数据范围**：仅采集「附近可见」的公开经营信息（排名/商品/价格/销量/评分），不窃取非公开数据
- **合规声明**：采集目的=自身经营决策参考；遵守平台 ToS 可接受范围；本设计同步作为合规边界评审输入（§六）

### 1A.4 科研价值（为什么这是底座关键）

- 竞对情报 = **L0 数据底座的核心外部输入**（排名/价格/销量/商品结构）——没有它，L2 因果测算的「竞争度/关键词权重/定价参考」全是盲区
- 补单品类分配、推广竞价、价格策略全部依赖竞对情报（§三 关键词权重的「竞争度」因子=竞对价格/销量数据）
- 手机链路与商家版链路同构 → 一套智能体大脑 + 两套采集执行 = 「市场调研 + 运营执行」完整闭环
- 现有资产已就绪：向日葵 MCP（awesun 22 工具：握手/搜索/详情实测打通）——物理手机控制通道已存在，waimai_scan/录制器原语可复用到手机端

### 1A.5 P0 验证路径

1. 单机试点：1 台手机（或模拟器）+ 目标商圈 10 店竞对快照（排名/TOP 商品/价格带/销量/评分）——手动触发、符合成本治理指令
2. 结构化入库：快照 → schema → 竞对情报库（Chroma）
3. 与关键词权重衔接：竞对价格/销量 → 竞争度因子 → 权重矩阵 v0.1
4. 周报输出：竞对变化（价格调整/新品/活动）→ 运营智能体建议
5. 合规评审通过后再扩到多机多商圈

## 二、核心测算模型：补单 ↔ 推广费 ↔ 转化（因果）

### 2.1 传导链（机制假设，待数据验证）

补单 S → 销量/评分/评价↑ → 搜索排名↑ → 曝光 E↑ → 进店 I↑ → 真实转化 CVR↑ → 下单 O↑
推广费 A（按进店计费）→ 曝光加成 → 进店 → 转化
交互：S 抬升 CVR → 推广费性价比（转化/每单成本）↑ → 每单成本↓

### 2.2 核心指标

| 指标 | 定义 |
|---|---|
| 进店率 CTR | 进店 I / 曝光 E |
| 转化率 CVR | 下单 O / 进店 I（区分真实/补单） |
| 推广费 A | 单价 × 进店量（按进店计费） |
| 补单量 S | 每日补单（含时间/品类/关键词） |
| 每单成本 | (A + 补单成本 + 平台抽佣) / O |
| 推广费性价比 | 转化率 ÷ 每单成本（被 S 抬升） |
| 关键词权重 | 搜索量 × 转化 × 竞争度 × 毛利 |

### 2.3 待验证的因果问题（研究假设）

1. S 增加 1 单 → 排名/曝光/真实转化变化多少？（边际效应，非线性？平台阈值断点？）
2. CVR 与 S 是否直接相关？还是通过评分/评价/从众效应间接？剂量-反应曲线形态？
3. S 与 A 是互补还是替代？（S 抬高转化 → A 的每单成本下降 → 最优 S/A 配比）
4. 不同品类/关键词的 S 边际效应差异？（→ 动态分配依据）
5. 是否存在无效投入区间（S 超阈值后边际归零甚至负效应——平台风控）？

### 2.4 建模方法

- 因果图（DAG）+ 结构方程：识别 S→CVR 的直接/间接路径
- 断点回归（RDD）：平台推荐池/排序阈值（如销量 X 单）附近补单的局部效应
- 双重差分（DID）：补单店 vs 同商圈对照店
- 剂量-反应回归：S 的分段边际效应（找拐点=最优补单量）
- 交互模型：S × A 的联合效应（预算分配依据）

## 三、关键词权重 → 动态补单品类

1. **关键词权重矩阵**（每日更新）：权重 = 搜索量 × 转化率 × 竞争度 × 毛利——数据源=订单标题/搜索词/竞品（waimai_keywords 已有雏形）
2. **分配规则**：补单预算优先投「高权重×低竞争×高毛利」关键词对应 SKU——拉升该词排名即抬升进店
3. **动态调整**：搜索热度/竞争度变化 → 权重重排 → 补单 SKU/数量调整（每日级；秒级系统上线后分钟级）
4. **品类赛马**：同品类多 SKU 并行小量测试 → 数据决定主推/弃推

## 四、秒级联动系统（量化交易式）

| 模块 | 类比量化交易 | 外卖版 |
|---|---|---|
| 行情流 | tick 数据 | 订单/曝光/关键词热度/竞争价 秒级流 |
| 信号 | 动量/均值回归 | 转化率异常、关键词热度突变、评价事件、竞争调价 |
| 策略引擎 | 规则+模型 | 预测未来 1h 订单 → 提前调推广/补单/发券 |
| 执行 | 自动下单 | 营销端 API 自动改价/调推广/补单任务（高险门控确认） |
| 风控 | 熔断/风控 | J37/红绿灯/硬预算/审计/人工确认门控 |
| 回测 | 历史回测 | 历史数据回测 → 纸面跑 → 小资金 → 放大 |

**设计原则**：先回测后实盘；实盘先低预算；每个自动动作可审计可熔断。

## 五、最小测试模型（实验体系）

- **商品赛马**：同品类 3-5 SKU 小量上架，自然/补单/推广三组并行，赢者加大投入（周级迭代）
- **分层实验**：店×时段×关键词维度正交小样本
- **因果推断**：RDD/DID/合成对照（对照店库）
- **预算纪律**：每组实验预算上限（与 token 预算同理，防实验本身烧钱）
- **输出**：效应量 + 置信区间 → 决策规则库（沉淀为策略）

## 六、合规边界与风险（客观声明）

- 补单=平台违规行为，有封店/处罚/流量降权风险——**研究目的=量化其边际效应，找到等效的合规替代手段**（真实好评激励、限量活动、老客复购、新品冷启动、内容种草）
- 研究输出分两路：① 补单效应的科学测量（知其然）② 合规等效手段的迁移（替代路径）
- 所有实验遵守平台规则底线：不批量刷单触红线、小量试探、风控熔断
- 决策系统含人工确认门控（高险动作）——与 J37/成本治理指令一致

## 八、每日 Token ROI 审查机制（颗粒度=每日）

**流程（恢复后启用，当前被动模式下手动按需）**：
1. 每日 09:00 拉取前一日精确账单（平台导出/API）——成本 C
2. 对碰当日业务产出（订单/GMV/操作数/实验组数据）——价值 V
3. 计算日 ROI：ROI_eff = (V × δ × Q − 错误成本) / C（质量加权，δ 实测前打折）
4. 异常检测：环比 >2 倍 或 >3σ 告警（归因会话/任务）
5. 输出：日审报告（消耗/产出/ROI/异常）+ 优化建议（停/降/路由）

**持续主动**：每日报告 → 周聚合 → 月度校准配额与预算。
**优化建议模板**：识别 top 消耗会话/任务 → 对照业务产出 → 建议（降频/本地路由/压缩/停）。

## 十、启动建议（P0 第一步）

1. **M0 数据底座最小集**：先落「每日级」数据（订单/转化/推广费/补单量/关键词）——不必等秒级，先跑每日模型
2. **补单-转化初步测算**：用已有历史数据（各店订单+评价+关键词）先做描述性分析（相关性与滞后相关）
3. **赛马最小实验**：选 1-2 个品类、3-5 SKU 试跑（与成本治理指令兼容：手动触发、小预算）
4. **每日 Token ROI 审查**：设计成手动脚本（成本指令下先手动、恢复后 cron）
5. **合规评审**：补单研究方案过合规边界评审（§六）后再展开
