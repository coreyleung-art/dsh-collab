## 三、三件套不够：本机现测的四个反例

下列四条**都有「命令 + 未编辑输出 + 退出码」三件套**，但**读数都不承载它声称的结论**。

### 反例 1 · `channel_gate status` 的 `changes24h` 与它自己的统一日志不互校

```
----- [P28-a] jsonl 总条数: 20 / board-central 最新 2026-10-11T17:27:32.959Z
----- [P28-b] logs/channel-gate-state.json
{"launchd-daemons":{"count24h":2,...},"board-central":{"count24h":2,...}, ...}
```

而 `channel_gate status`（工具调用，2026-10-12T11:59:57.732Z）逐条报：

```
"channel": "board-central", "changes24h": 0, "frozen": false
```

**代码级根因**（`~/dsh-plugin-channel-gate/lib/core.js` 逐行实读）：

| 行 | 内容 |
|---|---|
| `:7` | `const LOG_PATH = …'channel-changes.jsonl'` |
| `:8` | `const STATE_PATH = …'channel-gate-state.json'` |
| `:94` | `changes24h: (s.windowStart && now - s.windowStart < 86400000) ? (s.count24h \|\| 0) : 0` |

⇒ `status()` **只读 `:8` 的 STATE，从不读 `:7` 的 LOG**。
⇒ `changes24h: 0` 的真语义是「**本进程内存里那一份 state 的 24h 窗口内计数**」，**不是**「24h 内没有发生变更」。
⇒ 而 `board-central` 在 **18.5 小时前**（`2026-10-11T17:27:32.959Z`）**确有一张变更单**。

★ **这正是 P27「检查项与变化项不是同一项 / 自指参照系」的一个新实例**，而且它**通过了三件套** —— 因为三件套没有「**来源**」这一元。

### 反例 2 · 「经管道 → exit=0，不经管道 → exit=1」

```
$ python3 tools/incident-regression.py 2>&1 | tail -3 >/dev/null; echo "经管道 → exit=$?"
经管道 → exit=0
$ python3 tools/incident-regression.py >/dev/null 2>&1; echo "不经管道 → exit=$?"
不经管道 → exit=1
```

★★ **本次调研的 capture 脚本第一版就在自己的第 6 节踩了同一个坑**（写成 `… | tail -20; EX`），把真值 `1` 打印成 `exit=0`。
⇒ 已在 `capture.sh` 内**逐字留痕并标注修法**（先落文件、再取 `$?`、最后打印），重跑后 `exit=1` 正确显示。
⇒ **这正是本仓 `/tmp` 之外第二处活体实例**，也说明「三件套」里**退出码这一条本身需要一条纪律**：**退出码必须在管道之前取**。

### 反例 3 · `beacon-check --net` 有 1 项 PEND，而 `exit=0`

```
PEND closed 项审查员已到位（§11 六者之「审查员」）   << C1/C2/C3/C5/R049 记为 closed_with_evidence，而 verifier 仍是待复核 ⇒ **未验证 ≠ 已关闭**

反遗忘校验：无 FAIL，但**有 1 项记为 closed 而审查员未到位** ⇒ 不得读作『全绿』（0 条 WARN，0 条 SKIP，1 项待复核）
exit=0
----- [P27-b] raw_exit=0
```

⇒ **工具的散文面说「不得读作全绿」，机器的退出码说「绿」**。任何以 `$?` 为判据的调用方（cron、CI）读到的是绿。
⇒ 三件套里的「退出码」**在这一条上与被观测的事实相反**。

## 四、`RCP-6`：解除条件的六元组格式（本文产出）

> **定义**：一条解除条件 **E** 可判 ⟺ E 写成下面六元的合取，六元**逐字贴出**，缺一即 E 只能记 `待补判据`。

| 元 | 名称 | 必填内容 | 为什么 |
|---|---|---|---|
| **1** | **谓词 P** | 一个布尔式，且**取值域三态**：`成立` / `不成立` / **`不可判`** | 本项目纪律「空 ≠ 无」：**分母为 0 必须报不可判** |
| **2** | **复跑命令 C** | 一条可直接粘贴的命令（含 `cd`），**不改盘、不留副作用** | 「不得只给结论」 |
| **3** | **读数三元** | **未编辑输出 O** + **退出码 E** + **取值时刻 T**（`date "+%Y-%m-%dT%H:%M:%S%z"` 实读） | 「凡读状态必问这是哪个时刻的」 |
| **4** | **分母断言 D** | 明写**分母是什么**，并给**分母为 0 时的期望行为**（必须是「不可判」） | 本项目纪律「一个断言若从未红过，它就不是判据」的对偶：**分母为 0 的绿不是绿** |
| **5** | **负控 N** | **造红输入的构造方法** + **该输入下的期望输出（必须红）** + **首次实红的存档**（时刻 + 命令 + 原始输出） | 业界：*a suite that has never been observed failing is indistinguishable from a suite that cannot fail* |
| **6** | **观测窗 W** | 窗口长度 + 复跑间隔 + **样本下限**（窗口内至少跑 N 次，少于 N 次 ⇒ 不可判） | 「零复发 / 持续 / ≤X 分钟」这类**只能用窗口表达** |

### 4.1 缺元判定表（★ 直接可用于审查）

| 缺哪一元 | 该解除条件只能记 | 典型错写 |
|---|---|---|
| 缺 **4** 分母 | `待补判据` | 「0% ⇒ 不达标」（分母 0 时报不达标也是错，应是**不可判**） |
| 缺 **5** 负控 | `待补判据` | 「门全绿 ⇒ 零复发」（**9/17 条门恒 N-A**，见 M6 篇） |
| 缺 **6** 观测窗 | `待补判据` | 「零复发」「持续 100%」（无窗口即无样本） |
| 缺 **1** 三态 | `待补判据` | 二值谓词遇空分母自动落 `不成立` 或 `成立` |
| 缺 **3** 时刻 | `读数无效`（**不得入表**） | 引用 v6.1 的 10-11 读数当现状 |
| 缺 **2** 命令 | `读数无效` | 「实测支持率 96.7%」而不给命令 |

### 4.2 两条硬纪律（本次新立）

1. **退出码必须在管道之前取。** `cmd | tail` 取到的是 `tail` 的 `$?`。正确形：`cmd > /tmp/x 2>&1; rc=$?; tail /tmp/x; echo "exit=$rc"`。
2. **负控必须「造世界」而非「改期望」。** 见 M5 篇 §一 —— 本仓 `research/v7-negctl/03-证明一条检查能红-安全造红输入的六种手法.md` 已逐字给出这一区分（**本件不重造，只引用**）。

## 五、业界形态（★ 只列检索到的，标明来源与限度）

> ★ **本节的引用是「业界有这种做法」，不是「业界最新」。** 检索面与限度见 §五.4。

### 5.1 Defect matrix（种缺陷矩阵）—— 与本节结论最贴的形态

来源：[Plumbline `docs/negative-controls.md`](https://github.com/ChelseaKR/plumbline/blob/main/docs/negative-controls.md)（本次实读，`read_url` 6000 字符截断）。

逐字要点（引文为原文英文，本件不译作断言，只作**做法登记**）：

- 「**A suite that has never been observed failing is indistinguishable from a suite that *cannot* fail**, and a wall of green ticks proves nothing about which one you have.」
- 三条可抄的形式：
  1. **每行断言两次**：被测套件**必须红**，且**应当无感的套件必须保持绿**。「Without the second assertion a sabotage crude enough to trip everything reads as a clean row.」
  2. **先跑未破坏的基线并断言其通过**。「Without that, every suite would 'fail on its defect' because every suite was already failing.」
  3. **用 git 对象哈希证明「破坏真的落盘了」**：`git hash-object` 前 `BASE`、后**必须 ≠ BASE**、还原后**必须 == BASE**。「Step 2 is the one people skip and the one that earns its keep. A sabotage that silently does nothing produces a green run that reads exactly like a passing guard.」
- 其自报矩阵：**23/23 cases behaving as declared，覆盖全部 15 个 enabled suite**，并附一句「There is no suite in this configuration whose failure path is untested.」

★★ **对本仓的直接映射**：这几条**正是**本项目纪律「一个断言若从未红过，它就不是判据」的可复跑化形态，且**多了一条本仓还没有的**：**无关项必须仍绿**（防止「粗到什么都绊倒的破坏被读成干净行」）。

### 5.2 Mutation testing / mutation score

来源：[Mutation testing — fitness signal beyond "tests pass"](https://raw.githubusercontent.com/Rejnyx/cortex-x/main/standards/mutation-testing.md)、[Mutation Testing Explained](https://www.drizz.dev/post/mutation-testing-explained-how-it-improves-your-tests)、以及 `research/v7-negctl/04-A类恒真与B类从未触发-业界名字与检测法.md`（本仓既有调研）。

要点：mutation score 是**测试有效性的代理指标**；其地位是**抽样证据，不是证明**。A 类（恒真断言 / trivial invariant）与 B 类（vacuous rule / dead code）在业界有专名，且**区分法不是「等它红一次」而是工具自动判定**（本仓 v7-negctl 篇已详述，本件不重复）。

### 5.3 「全称否定」的业界处理

来源：[Google SRE — Testing Reliability](https://sre.google/sre-book/testing-reliability/)（检索命中，本次**未逐字读全文** ⇒ 标「未逐字核对」）。

## 七、给 v7 的格式条款（可直接抄）

> **§X · 里程碑解除条件的书写规格**
>
> 1. §14 每一条「解除条件」必须写成 **`RCP-6` 六元组**：谓词（三态）· 复跑命令 · 未编辑输出+退出码+取值时刻 · 分母断言 · 负控（含首红存档）· 观测窗。
> 2. **缺第 4/5/6 元**者，状态列**只能填 `待补判据`**；**不得**填 `已解除`，也不得填 `不成立`（那会把「判据缺失」误读成「事实不成立」）。
> 3. **退出码一律在管道之前取**：`cmd > /tmp/x 2>&1; rc=$?; tail /tmp/x; echo "exit=$rc"`。
> 4. 凡引用他处读数（含 v6.1、含本仓基线件），**必须重跑**；引用时**必须同时写出「引用的时刻」与「重跑的时刻」**，二者不同即**不得**合并陈述。
> 5. **凡新立一条判据，必须同时落一条负控**；负控**首次实红**的原始输出须入库（这是 §5.1 的 `hash-object` 那一步在本仓的等价物）。
> 6. **一条解除条件若其谓词涉及「持续 / 零 / ≤X」**，**必须**在第 6 元给窗口与样本下限；给不出 ⇒ `待补判据`。

★ 本件不主张任何事项已闭合（S3）。
