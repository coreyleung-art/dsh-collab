## 一、为什么这份哲学存在（历史教训）

DSH 依赖供应链反复因「第三方不可控」导致崩溃与事故：
- 08-18 六第三方插件连环崩溃
- gov schema 异常构建产物
- better-sidebar 版本不匹配（rc.7 构建 vs rc.8 宿主）
- flower-cockpit type:module 冲突
- xberg 平台包发布缺失

共性根因：**版本节奏 / 构建产物 / schema 声明 / 发布纪律全不受控，被动适配 = 崩溃反复**。

## 二、两条核心原则

### 原则 1：判断力优先（拿什么、为什么、值不值）

拿来的行为本身**没有错**——吸收外部好的技术/经验是正当的，不应否定（xberg 修复方案、CLD-004 方法论、rc 升级链的 peer 兼容分析、结构门工程范式，都是外部吸收的成功成果）。

错的是**无差别拿来 + 图快**。关键在判断力：知道「拿什么、本地化后对长远是否有帮助」。

**关键区分**：
- 吸收**知识/方法论/经验** → 永远开放吸收（对长远有帮助就学，不问来源）
- 吸收**代码/依赖** → 选择性本地化（值得才慢工自研，不值得审慎引用）

### 原则 2：慢慢来，可能更快（不图快，把基础打好）

不要追求"马上能用"，不要有"拿来即用"的倾向性。把基础打好。
稳定性 = 地基质量 × 时间，不是上线速度。

但**不是**拒绝外部经验 / 闭门造车：
- 持续吸收智慧（方法论/经验永远开放）
- 值得自研的地基才慢工（架构/测试/文档/结构门/持久化一次打对）

## 三、判断力标准（吸收什么值得本地化）

| 吸收对象 | 态度 | 判断 |
|---------|------|------|
| 知识/方法论/经验 | 永远开放吸收 | 对长远有帮助就学，不问来源 |
| 代码-长期高频依赖 | 值得本地化打牢 | 可控性重要就慢工自研 |
| 代码-一次/边缘 | 吸收用法即可 | 不必自研，审慎引用 |
| 代码-脆弱失控反复坑 | 本地化替代 | 版本/schema 失控就自研稳定版 |

## 四、落地纪律

1. **拒绝快速止血优先**：先问"地基哪里歪了"，而非"怎么最快堵上"
2. **地基一次打对**：值得自研的模块，架构合理 + 测试全 + 文档齐 + 结构门 + 持久化，不赶工
3. **先判断再吸收**：吸收前问"本地化后对长远是否有帮助"——有帮助才自研，否则审慎引用或只学方法
4. **持续吸收智慧**：外部方法论/经验/成功案例永远开放学习，不因本地化而封闭
5. **不计算"工期快"**：评估看"是否稳、是否可长期维护"，不追求上线天数短
6. **崩过的是地基信号**：每次崩溃都是地基某处没打牢的提示，值得慢下来修根，不是快堵

## 五、与既有战略关系

- 依赖本地化战略（localization-strategy.md）= 方向（第三方能力吸收为可控自研）
- 本哲学 = 怎么做（判断力取舍 + 慢而稳打地基）
- 合一：方向是本地化，方法是「判断力优先 + 慢慢来」，最终根除"第三方反复坑"病灶
