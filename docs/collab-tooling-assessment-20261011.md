### 2.1 ★ `xdom-mail` 的设计（最接近「MCP 式协作」的既实现）

```
send     投递（只写自己域的信键）
inbox    读信（含水位与球权；空 ≠ 无信）
ack      推进自己的水位（只写自己的 cursor 键）
status   状态（板可达 / 日志 / 双方水位 / 球权 / 陈旧）
```

- **两域互不相交**：`log` 键归发方 · `cursor` 键归读方
- **水位**：`cursor >= 该键` ⇒ 已读
- ★ **球权不落盘**：由**日志最后一条的 `ball` 字段派生**（设计原则：**派生量不落冗余字段**）
- **陈旧检测**：`status --stale-hours 6`

### 2.2 ★ 失败可见性体系（`starbridge-v2 ... v3.1` §四，既有高质量设计）

```
观察段  世界真是什么？   失败形态＝看不见       修法：让 X 自报 X 的状态    角色：产出方
转述段  数据里有什么？   失败形态＝有而不叙述   修法：结论附 n/distinct/覆盖 角色：转述方
决策段  我需要知道什么？ 失败形态＝维度不对口   修法：消费方先声明决策问题   角色：消费方
★ 关键性质：三段的失败【静默传递】—— 本段失败不报错，只在下一段变成【合法输入】
```

## 六、★ 本报告新发现的既有一处缺陷（与本题直接相关）

**`tools/xdom-mail.py` 的「越域写入」负控是恒真式**（★ **由外部 CU 线实测发现并告知我，我 18.9h 未读**）：

```
cmd_ack:  key = CUR_PREFIX + party;         then owns_key(key, party)   ← key 与 party 同源 ⇒ 恒真
cmd_send: key = f"{LOG_PREFIX}...-{frm}-..."; then owns_key(key, frm)   ← 同型
--selftest: chk(not owns_key(CUR_PREFIX+"int","ext"), "★ 负控：ext 写 int ⇒ 拒")  ← 只测纯函数，从未走 CLI
```

⇒ **`owns_key` 保证的是【自洽】，不是【鉴权】**；越域写入在 **CLI 面不可达** ⇒ **不可被违反、也不可被验证**。

★ **它与 v6 自立的 R060（静默失败禁止）/ R061（假绿禁止）同型** —— **负控绿在函数上，而函数不是被调用的那个对象。**

**⇒ 对本报告的启示**：★ **选项 3（通用原语）的前置条件正是「先解决这个」** —— 因为「通用 party 模型」的核心就是「谁可以写谁的键」。
