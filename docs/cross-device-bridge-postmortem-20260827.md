## 二、踩坑全记录（按严重度排序）

### 🔴 P0：CLD 崩溃 3 次（01:19 / 01:21 / 01:44）
- **现象**：起服务绑定端口测试（nohup python 实例 / kill 循环）后 CLD 崩溃；内存 free 骤降（正常 10 万+页 → 1.5 万页）
- **根因**：测试服务占用端口/资源，触发 CLD 异常
- **固化**：运维硬约束文档《禁止起服务测试》——验证只用编译 + 单测 + 静态审查 + 黑板只读
- **反省**：这是我最严重的失误。测试不能以「起服务」方式进行——教训已写入所有后续开发流程

### 🔴 P0：黑板列 API 不按 node 过滤
- **现象**：`GET /notes/<node>/` 返回全量（8777 条 / 3.2MB）
- **根因**：黑板实现问题（列接口未按 node 过滤）
- **修复**：bb-read/agent-thread 改读本地订阅 inbox 或线程索引 data/threads/
- **教训**：依赖外部 API 行为前必须实测，不能假设

### 🟠 P1：agent-bus 依赖包名不一致（cosmokit 坑）
- **现象**：MBP 部署报「缺 cosmokit」
- **根因**：MBP 装的是**官方 cordis**（依赖不带 scope 的 `cosmokit`），mac 用的是 **@deepseek-ai/cordis fork**（依赖 `@deepseek-ai/cosmokit` 带 scope）——**包名不同**导致解析失败
- **修复**：完整底座包内带依赖快照（从 mac CLD runtime 逐字拷贝），两端照抄
- **教训**：跨设备交付必须给「与源端完全一致的依赖快照」，不能假设两端 npm 解析一致

### 🟠 P1：cordis definePlugin API 漂移
- **现象**：central-inbox `import { definePlugin }` 在 cordis 4.x 报错
- **根因**：cordis 4.x 移除了 definePlugin；更隐蔽的是——mac 侧 import 了但**从未使用**，靠打包器 tree-shaking 摇掉才没崩（悬空 import 隐患）
- **修复**：删悬空 import，改约定式（export name/inject/apply）
- **教训**：①API 漂移是跨版本部署的头号风险 ②「没崩」不等于「没问题」——tree-shaking 掩盖了错误

### 🟠 P1：CLD 插件加载机制误判（i9 架构约束）
- **现象**：i9 全盘搜 runtime 找 cordis.yml 找不到
- **根因**：组合入口**不在 runtime**（mac 的 runtime 也没有 cordis.yml！），在 **profile 层** `~/.dsh/profiles/<name>/`（package.json bundles + cordis.patch.yml）
- **修复**：查证 dsh-app-boot/lib/index.js 源码，确认 profile 机制 + 自动初始化模板
- **教训**：排查跨设备问题先确认两端 CLD 版本/结构一致，不要假设

### 🟡 P2：bash 3.2 兼容性（macOS 自带 bash 不支持 declare -A）
- **现象**：check-deps.sh / install-deps.sh 用 `declare -A` 报错
- **根因**：macOS 自带 bash 3.2 不支持关联数组
- **修复**：改用 while read + grep 兼容写法
- **教训**：macOS 脚本默认兼容 bash 3.2，不能用 bash 4+ 特性

### 🟡 P2：heredoc shell 展开破坏 JSON
- **现象**：写黑板 notes/i9/full-install-guide 后 value 是空 `{}`
- **根因**：无引号 heredoc（`<<EOF`）里 `$env:`、`$(...)` 被 shell 展开破坏了 JSON → 服务器存空对象 → **i9 读到空内容**
- **修复**：改用引号 heredoc（`<<'EOF'`）
- **教训**：写含 `$`/反引号的 JSON 必须用引号 heredoc；**写黑板后必须读回验证**（这次差点导致 i9 收不到关键信息）

### 🟡 P2：agent_send 通道误用（i9 收不到我的信息）
- **现象**：用户反馈「i9 收不到你信息」
- **根因**：我用 agent_send（同宿主跨会话工具）给 i9（跨设备节点）发消息——`to="i9"` 不是本机进程内会话 id，消息 queued 永不投递（targetLive: false）
- **修复**：跨设备通知一律走黑板 notes/<node>/*（node-bridge 轮询）
- **教训**：**通道选择错误是致命**——同宿主用 agent_send，跨设备用黑板。术语要精确

### 🟡 P2：macOS date %N 问题
- **现象**：`date +%s%3N` 输出 `17877729773N`（N 字面量）
- **根因**：macOS date 不支持 GNU %N
- **修复**：时间戳用 `python3 -c "import time; print(int(time.time()*1000))"`
- **教训**：macOS/GNU 工具差异要在脚本里规避

### 🟢 P3：版本漂移误报
- **现象**：MBP 宿主 rc.8 vs 快照 rc.6，check-deps 精确比较误报「不一致」
- **根因**：精确字符串比较不识别「宿主更新」语义
- **修复**：版本比较改「宿主 ≥ 期望」（rc 感知），宿主更新算 OK 不降级
- **教训**：工具要理解业务语义（宿主更新是正常的，不是漂移）

### 🟢 P3：CLD「开不了」误判
- **现象**：用户反馈「mac 装完开不了 CLD」
- **根因**：CLD 进程实际健康（GUI 200、窗口存在）——是**窗口激活问题**（单实例锁 + 渲染器高 CPU），不是崩溃；且我改的插件在 CLD 启动之后，尚未加载
- **修复**：激活窗口 + 确认健康 + 安全重启指引
- **教训**：先确认「进程/服务是否真的挂了」再动手，不能凭用户描述直接重启

## 三、成功经验（可复用）

### ✅ 黑板协议是跨设备协作的正确抽象
- 三端共享同一黑板（8792 KV + 8803 SSE），notes/tasks/data 三类 key 语义清晰
- 事件驱动（SSE）+ 轮询兜底（node-bridge 2s/5s）双保险
- **链路**：写黑板 → 事件桥 → 注入/轮询 → 处理 → 回报黑板

### ✅ Rust 化常驻工具收益显著
- node-bridge v1.2.0：五线程 + LLM 执行器 v2（三因子门禁）单二进制
- dsh-tools v1.4.2：9 子命令单二进制，三平台交叉编译（zigbuild）
- 内存 151.8MB → 31MB（省 80%）、token 1200 → 45/条（省 96.2%）

### ✅ 部署安全机制（MBP 提案 → deploy-check 工具化）
- 三类崩溃点模式库：P1 缺传递依赖 / P2 API 漂移 / P3 解析链不可达
- deploy-check 7 类检测 + exit=0 门禁（发包自检 → 收包二次自检 → 通过才上生产）
- 这是「防止再踩坑」的机制化——**从被动修 bug 到主动防 bug**

### ✅ 一次性完整交付（用户要求「为什么一个事情要分开做」）
- 教训：碎片化交付（只给插件本体）导致两端各自踩坑
- 改进：完整底座包 = 插件 + 依赖快照 + 校验脚本 + README + 安装脚本
- **给完整能力，不让别人重复踩坑**

### ✅ 三端注入链路实证（探针验证法）
- i9 生产探针2：写黑板 → 中枢上下文自动收到 [跨会话智能体消息] → 链路实证成功
- 验证方法：探针（写黑板）+ 观察（上下文出现）——**每端单独验证，不跨端推断**

## 四、反省（诚实面对问题）

### 1. 通道选择错误（最严重）
我用 agent_send 给跨设备 i9 发消息，导致它收不到。这是我**没有把「同宿主 vs 跨设备」的通道边界想清楚**就行动。教训：发消息前先想「目标在哪」——同宿主 agent_send，跨设备黑板。

### 2. 起服务测试导致 CLD 崩溃 3 次
我反复用「起服务验证」的方式（nohup/kill），触发 CLD 崩溃 3 次才固化硬约束。**应该在第一次崩溃后就停止这种验证方式**。这是最痛的教训。

### 3. 写黑板不验证
full-install-guide 因 heredoc 展开写了空对象，i9 差点收不到。**写黑板后必须读回验证**——这个习惯现在已固化（每次 PUT 后 curl 读回）。

### 4. 碎片化交付
先给 MBP 缺依赖的包，再补；先给 i9 不完整的包，再改。用户批评「为什么一个事情要分开做」。**应该第一次就给完整底座 + 完整依赖**。

### 5. 术语不精确
早期把「轮询」说成「注入」（MBP 感知机制澄清时被用户纠正）。**注入=agentBus.send 进上下文 / 轮询=node-bridge 落盘 / 链路=消息可达**——三个概念必须严格区分。

### 6. 版本比较的语义缺失
check-deps 精确比较误报「版本漂移」（宿主 rc.8 更新其实是好事）。**工具要理解业务语义**，不能只看字符串相等。

## 五、总结（可迁移的方法论）

### 1. 三问前置（任何跨设备操作前）
- 目标在哪？（同宿主 / 跨设备 / 黑板）
- 用什么通道？（agent_send / 黑板 notes / 黑板 tasks）
- 如何验证？（读回 / 探针 / 心跳）

### 2. 部署安全三原则
- 依赖快照与源端逐字一致（防包名漂移）
- API 兼容性静态审查（防 API 漂移）
- 发包自检 + 收包二次自检 + exit=0 才上生产

### 3. 工具化门禁（踩过的坑都变成工具）
- agent_send 违规 → agent-send-gate（v2.3 门禁注入工具层）
- 部署风险 → deploy-check（7 类检测）
- 版本漂移 → check-deps --auto-adapt（宿主 ≥ 期望）
- 重启验证 → verify-watch 守护（心跳变化 → 自动探针）
- 全量追踪 → tools-registry 台账 + 日志规范

### 4. 诚实原则
- 术语精确（注入/轮询/链路）
- 验证彻底（每端单独验证，不跨端推断）
- 给完整能力（结构差异用适配非降级）
- 诚实报状态（待确认不说通）
