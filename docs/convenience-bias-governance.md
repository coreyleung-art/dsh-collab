# 便利性偏差 · 完整定义与规避约束（2026-08-31）

> 建立：HR 司库（资源管理者+成本监察专员）· 触发：用户指出「怕麻烦过程是否引起潜在风险」
> 定位：智能体执行者的系统性认知偏差治理——「便利性」是每个执行者的人性弱点，作为成本监察者必须正视

---

## 一、定义

**便利性偏差（Convenience Bias）**：决策者在多方案中，系统性偏向「当前最省事/最熟悉/最小阻力」的路径，即使该路径在长期维度（成本/一致性/可维护性/风险）劣于其他方案。

它不是个别失误，而是**决策惯性**——每次选择最小阻力路径，累积成系统性偏差。

### 1.1 与相关概念的边界

| 概念 | 区别 |
|---|---|
| 便利性偏差 | 明知有更优但选省事的（可避免） |
| YAGNI 原则 | 不过度工程（合理克制，非偷懒） |
| 帕累托法则 | 80% 价值用 20% 成本（合理取舍） |
| 技术债 | 便利性偏差的累积结果 |

**关键区分**：YAGNI 是「这个不需要做」，便利性偏差是「这个需要做但嫌麻烦不做」。

## 三、系统性风险（为什么必须治理）

| 风险 | 传导链 | 后果 |
|---|---|---|
| 技术债累积 | 每次「先顶着」→ 债务叠加 → 迁移成本指数上升 | 越拖越贵，最终不可迁移 |
| 体系分裂 | Rust 主线 vs Python 孤岛 → 双语言双体系 | 维护成本翻倍，端侧分发受阻（Python 需解释器） |
| 决策惯性 | 「先这样吧」成默认 → 每次最小阻力处妥协 | 主线 Rust 化永远完不成 |
| 掩盖问题 | 用复用/渐进当理由 → 回避真实成本 | 风险被合理化的外衣隐藏，无人察觉 |
| 端侧受阻 | 工具 Python 化 → i9/MBP 需装解释器 | 跨端复用价值打折（子代理治理正是端侧需要） |

## 四、规避约束规则（R 级）

### 4.1 通用决策约束（适用所有智能体）

| # | 规则 | 强制检查点 |
|---|---|---|
| R-1 | **便利性决策必须对照明确标准** | 选「省事路径」前，对照对应决策标准（如 Rust 化标准 v1.0.382）回答：这是标准允许的合理选择，还是便利性妥协？ |
| R-2 | **先问「谁能做」再问「能不能做」** | 本机能力不足 ≠ 整体不可行——先枚举委托路径（知了 i9 工具链/协调者/其他角色） |
| R-3 | **工具化沉淀优先** | 重复 2 次以上的手工操作必须工具化（第 1 次可手作，第 2 次起必须沉淀） |
| R-4 | **验证不可跳过** | TCC/冒烟/沙箱验证是交付门槛，不可「先跑通再说」 |
| R-5 | **暴露偏差而非掩饰** | 发现自己走了省事路径，必须明说（本次复盘即示范），记入决策日志 |

### 4.2 语言选择专项（Rust 化决策标准，registry v1.0.382）

| 触发条件 | 判定 |
|---|---|
| 端侧分发需求（i9/MBP 免解释器） | Rust 单二进制 |
| 高频/常驻（秒级调用/长驻服务） | Rust（内存↓80%） |
| 并入主线生态（dsh-tools/node-bridge 组件） | Rust |
| 性能敏感（大数据/实时） | Rust |
| 低频一次性治理脚本 | Python 合理（YAGNI） |

## 五、执行机制

### 5.1 决策日志（新增）
- 每次「省事路径」选择后，记一行到 ~/.dsh/decision-log.md：决策/触发标准/判定/偏差标记
- 月度复盘：统计便利性偏差标记数，趋势监控

### 5.2 评审挂钩
- HR 评审：新工具/新脚本交付时，检查是否走了便利性偏差（对照本规范）
- 与 J40 技术决策论文支撑配套：重大技术决策先查论文，再对照本规范

### 5.3 偏差暴露奖励
- 主动暴露偏差（如本次）不惩罚——奖励诚实，惩罚的是「用合理化外衣掩盖省事」
