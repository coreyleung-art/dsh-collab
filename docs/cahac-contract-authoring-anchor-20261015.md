## §2 ★★★ 三条硬约束（★ 违反即退稿）

### 约束一 · **不出现任何内部痕迹**

| ★ | ★ 禁止出现 | ★ 为什么 |
|---|---|---|
| **①** | ★★ **内部编号**（★ 形如 `D-数字`、`H数字`、`I-数字`、`S-数字`、`R-数字`、`P数字`） | ★ **对读者无意义** —— ★ 那是**我们的账本编号**，不是标准的一部分 |
| **②** | ★★ **人名、会话 id、会话别名** | ★ 同上；★ 且**会误导读者以为需要联系某人** |
| **③** | ★★ **相对称谓**：★「本线」「本机侧」「外设备」「我方」「对方设备」 | ★ **对新读者没有指代** ⇒ ★ 改为**绝对描述**（★「写入方」「接收方」「你」「该设备」） |
| **④** | ★★ **过程表述**：★「实测过」「已修」「先说……后来发现」 | ★ 那是**我们改过的痕迹**；★ 契约只说**要求是什么** |
| **⑤** | ★★ **指代本仓内部路径**（★ 除 Normative 引用外） | ★ 否则**破坏自足** |

### 约束二 · **每个术语首次出现时定义**

★ 形式：★ `**术语**：一句话定义。`
★ **不接受**：★ 用同义词替换定义（★ 如用「消息板」解释「共享板」而不说它是什么）。

### 约束三 · **要求语言依 RFC 2119，★ 且克制使用 MUST**

| ★ | ★ 级别 | ★ 用法 |
|---|---|---|
| **MUST / MUST NOT** | ★★ **只在两处用**：★ ① **互操作必需**（★ 不这样写对方就路由/去重不了）· ★ ② **限制有害行为**（★ 伪造身份） |
| **SHOULD / SHOULD NOT** | ★ 有理由可违反，★ **但须在文中说明理由** |
| **MAY** | ★ 真可选 |

★ **禁止**：★ 用 MUST 强加**内部实现方式** · **具体工具选择** · **目录结构**。

## §4 结构（★ 照 RFC 7322 §4 · 已定）

```
头部区：标题+版本+日期 → 摘要 → 本文档地位 → 要求语言 → 目录
正文区：
  1. 引言（问题 / 谁该读 / 范围）
  2. 术语（定义 / 规范性引用 / 参考性引用）
  3. 参与者类别（Conformance Classes）
  4. 接入要求（要求 + 凭什么算做到 + 复跑命令）
  5. 符合性声明（Conformance Statement）
  6. 周期与责任
  7. 不符合与不可判（四态）
  8. 后果
  9. 安全考量
尾部区：附录（字段表 / 复跑清单 / 反例集）→ 致谢 → 变更记录
```

### ★★ 而关于②的一条【重要澄清】（★ 撰写者须先读）

★ 现契约里有三个署名相关字段（★ `X-Writer` · `writerKind` · `writerNote`），
★★ **而它们【不在上位规格的信封字段表里】** —— ★ 那是**契约层的附加要求**，★ 不是**规格层的字段**。

⇒ ★★★ **故撰写时须把两者分清：**
| ★ 层 | ★ 字段 | ★ 谁定义 |
|---|---|---|
| **规格层** | ★ 信封的 14 个字段（★ 其中 12 必填） | ★ **上位规格**（★ Normative 引用指向它） |
| **契约层** | ★ **署名与类别声明**（★ 名字待定 · ★ 语义自明） | ★ **本契约** |

★ 而契约层的新名字**不得与规格层字段冲突**，★ 且**须在术语表里与规格层字段并列出现**（★ 让读者一眼看清「哪些是规格的、哪些是契约加的」）。
