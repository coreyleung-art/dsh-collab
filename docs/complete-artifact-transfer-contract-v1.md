# 完整体传输契约 v1.0（Complete Artifact Transfer Contract）

> 2026-08-29 星桥-mac-mini-协调者 · 用户指示：所有端对端/总线对端侧传输必须是完整体，禁止半成品让接收方二次开发，浪费资源情况不应出现
> 定位：元规则（R012）——一切传输（吸收/分发/升级/报告/消息）的交付完整性标准

## 一、原则

**发送方交付 = 接收方可直接使用的完整体**（开箱即用，零二次开发，零补全）。

半成品判定：接收方需要额外开发/猜测/补全才能使用 → 即半成品，禁止传输。

## 二、传输类型 × 完整体标准

| 传输类型 | 完整体必须包含 | 反例（已发生） |
|---------|--------------|--------------|
| **资产吸收**（端侧→中枢）| 设计文档 + 完整源码 + 版本信息 + 依赖清单 + 使用说明 | i9 health-check 只发描述无源码 |
| **二进制/插件分发**（中枢→端侧）| 可运行二进制/完整包 + 版本号 + 校验和 + release 资产 | node-bridge v1.3.2 tag 无 release 资产 404 |
| **升级包** | 二进制 + 升级说明 + 回滚方案 + 验证清单 | MBP 升级崩溃无原始日志 |
| **报告/修复说明**（端侧→中枢）| 原始证据（日志/复现步骤/崩溃报告）+ 修复 diff + 验证结果 | MBP 崩溃经转述无原始日志 |
| **消息/指令**（总线）| 完整上下文（key/value 非空 + 可执行动作）| install-playbook-guide value 空 |
| **配置/剧本** | 完整内容 + 适用环境 + 验证方法 | playbook 空 value |

## 三、完整性七要素（CHECKS）

每个传输物必须满足（CHECKS 检查）：

```
C - Complete 完整内容：无空 value、无缺文件、无 TODO 占位
H - Hash 校验：带校验和（sha256），接收方可验证
E - Executable 可执行：接收方能直接运行/使用（依赖已声明可装）
C - Context 上下文：含设计意图/背景/边界（为何这么做）
K - Known-version 版本可溯：git/tag/CHANGELOG/依赖版本
S - Self-verified 自检通过：发送方已测（测试结果/冒烟/exit 0）
S - Safe 可回滚：含备份/回滚方案（破坏性操作）
```

## 四、发送方责任（七问自检）

发送前自问：
1. 接收方能**直接使用**吗？（还是需要补全/开发？）
2. 内容**完整**吗？（无空 value/缺文件/占位符？）
3. **校验和**给了吗？（接收方可验证完整性？）
4. **版本**可溯吗？（tag/CHANGELOG/依赖？）
5. **上下文**够吗？（接收方理解设计意图？）
6. **自检**通过了吗？（发送方自己跑过测试？）
7. **回滚**可行吗？（出错能恢复？）

任一为否 → 先补全再传输。

## 五、接收方验收（拒绝半成品）

接收方收到后：
1. **验证完整性**：checksum 比对 / 解压成功 / 空值检查
2. **验证可执行**：deploy-check / restart-guard / 试运行
3. **不全即拒**：缺要素 → 打回要求补全（附缺失清单），不自行补全开发
4. **记录**：验收通过 → 登记 registry；不通过 → 踩坑档案 + 退回

## 六、工具化（CHECKS 检查器）

`checks-transfer.py <包> [--type 吸收|分发|升级|报告]`：
- 解压/读包 → 逐项验证七要素（文件完整/checksum/README/版本/自检痕迹）
- 输出 PASS/FAIL 清单
- 半成品直接 FAIL → 阻止传输

（实现：tar 检查 + 文件清单 + README 存在 + CHANGELOG/tag 检测 + checksum 文件检测）

## 七、规则账本

- **R012「完整体传输契约（CHECKS 七要素）」enforced**
- 与 R002（通道分级）配套：通道决定「走哪」，CHECKS 决定「交付什么」
- 与 R006（插件化 9 项）配套：插件交付必须满足 CHECKS（文档/版本/日志/校验）
- 与 R010 v1.1（端侧吸收）配套：吸收流程的交付物必须满足 CHECKS

## 八、触发

- 任何端对端/总线对端侧传输（吸收/分发/升级/报告/消息/配置）
- 接收方收到疑似半成品 → 按第五节拒绝 + 记录

## 九、黑板描述文档规范（Context 要素的承载）

> 2026-08-29 用户确认：黑板（notes/）可以写意图描述以及设计逻辑简要之类的描述性文档

**原则**：实体（代码/二进制）走网盘，**描述（意图/设计逻辑）写黑板 notes/**——两者配套构成完整体。

### 黑板描述文档模板（notes/<目标>/<asset>-intent-<ts>）

```json
{
  "key": "notes/mac-mini/<asset>-intent-<ts>",
  "type": "asset-intent",
  "ts": "<时间戳>",
  "from": "<发送方>",
  "title": "<资产名> 意图与设计逻辑简要",
  "intent": {
    "purpose": "解决什么问题（一句话）",
    "motivation": "为什么做（背景/触发）",
    "expected_use": "预期用途/谁用"
  },
  "design_logic": {
    "architecture": "架构/模块划分（简要）",
    "key_decisions": "关键设计决策（2-5 条）",
    "tradeoffs": "权衡/取舍",
    "boundaries": "边界/不做的事"
  },
  "asset_ref": {
    "genebank_id": "<gene_id>",       // 实体在 AI 网盘
    "version": "<vX.Y.Z>",
    "docs": "<README/设计文档路径>"
  }
}
```

### 使用场景

| 场景 | 黑板写什么 | 网盘传什么 |
|------|-----------|-----------|
| 端侧吸收（i9→中枢）| 意图 + 设计逻辑简要 | 完整源码 tar.gz |
| 中枢分发（→端侧）| 升级意图 + 设计变更说明 | 二进制/完整包 |
| 插件新增 | 插件定位 + 设计逻辑 | 插件完整目录 |

### 校验

- checks-transfer.py 的 C（Context）要素：检查配套黑板描述文档存在（key 含 intent 或 design）
- 黑板描述文档是 R012 的一部分，缺失 = 半成品（Context 要素 FAIL）

## 十、完整传输 = 实体 + 描述（双通道）

```
发送方
  ├─ 实体通道：genebank 网盘（代码/二进制/完整包）→ R012 CHECKS 校验
  └─ 描述通道：黑板 notes/（意图 + 设计逻辑简要）→ 模板见第九节
        ↓
接收方：拉实体（网盘）+ 读描述（黑板）→ 完整理解 → 评估/使用
```

**半成品判定补充**：实体齐全但无意图/设计逻辑描述 = 半成品（接收方需猜测设计意图）。
