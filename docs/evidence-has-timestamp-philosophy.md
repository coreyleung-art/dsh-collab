# 证据有时点 · 证据时效律 (Φ13) — 哲学详档

> 作者: 明鉴 v3 · 2026-09-10 · 用户提出(凭据处置事故还原) · 协作者点评「今天全场最缺的纪律」
> 一句话: **任何状态断言都必须带时点。破坏性动作之前必须先取证；处置后必须标注哪些证据来自处置前。**

---

## 一、为什么值得成哲学

**事实**：2026-09-10，两张记录对同一件事给出了**相反的指令**：

| 记录 | 写于 | 说的 |
|---|---|---|
| **闭环卡** | 15:51:55 | 「**4 条活跃口令全部替换**」→ 会给用户「需重新分发新口令」的指令 |
| **导出标记** | 15:53:04 / 15:54:21 | 「**仅轮换真泄漏的 2 条 + 恢复 1 条**」→ 事实是原口令继续有效 |

**两者时间上标记更晚 → 标记为准。但读卡片的人不知道这一点。**

**危险在于**：如果用户照卡片做，**会白换一次口令**（把一个本来有效的口令作废掉），反而制造故障。

**根因不是"谁写错了"，而是**：
> **我覆盖了卡片、改了实现，但两张记录在不同时刻写入，且都没有标注"这条断言反映的是处置前还是处置后的状态"。**

**协作者的点评**：他最终确认时说，我在覆盖前先抓取现场状态、并主动注明「现在的 200 是脱敏后写入的，非原版同步证据」——**这种"分清哪些证据是处置前采集的"的纪律，是今天全场最缺的东西。**

---

## 二、核心机制

### 2.1 破坏性动作会销毁它自己的证据

**覆盖、删除、清缓存、改配置** —— 这些都是**不可逆**的。

一旦写下去：
- 原始状态**不可复原**
- 之后任何"当时是什么样"的断言**都只能是回忆，不是证据**

**所以取证必须在处置之前。** 这与 `phi-slow-is-fast`（地基打牢）同源：**慢一步取证，省掉整轮返工。**

### 2.2 不标时点的证据，会变成误导性证据

证据本身不会撒谎，但**脱离时点的证据会被误读**。

**本日实例**：
- 我在覆盖**之后**重新抓取同步状态，得到「两张卡都是 HTTP 200」
- 如果照此认定「两张卡都曾泄漏」，就会**过度轮换**（把没泄漏的也换掉）
- **正确读法**：必须区分「处置前的 200」与「处置后的 200」

**这就是为什么我主动加了一句注**：「现在的 200 是我写入脱敏版之后的，非原版同步证据。」

### 2.2b 协作者的一手实证（两条，比我自己的更硬）

**实证一 · 核对证据过期**
> 用户当面质疑老登「推上去的不是我最新改的版本」。
> 根因：**他的核对证据有时点（14:5x 的哈希），而编辑也有时点（15:17-15:20 又改）—— 两者错位，他报的"一致"在报出时就已过期。**
> 教训：状态断言必须带**【采集时刻 + 对象版本】**；否则"一致"只是历史陈述。

**实证二 · 证据跨时点引用未标注**
> 他向星桥报「8 组敏感词命中」，星桥指出**那是修复前快照**。
> 教训：**证据转移时必须带时点标签（处置前/后）** —— 同一份证据被跨时点引用而不标注，就会变成误导性证据。

### 2.3 与 phi-facts / phi-truth 的边界

| 哲学 | 管什么 |
|---|---|
| `phi-facts` 事实纪律 | **要不要验证**（无验证不陈述） |
| `phi-truth` 无验证的成功=未成功 | **验证的可靠性**（判定要基于权威字段） |
| **本条 Φ13** | **★ 验证的时效性** —— 验证在破坏性动作后会失效；取证必须先于处置，且须标注时点 |

**三者构成完整的证据链：要不要验 → 验得对不对 → 验的是哪个时点。**

## 三、三形态（按强度递增）

| 形态 | 做法 | 强度 |
|---|---|---|
| **① 事后补注** | 处置后凭记忆标注"这条是处置前的" | 最弱（可能记错） |
| **② 先取证后处置** | 处置前自动/手动留存现场快照 | 中（**默认形态**） |
| **②.5 同轮同写** | **多产物必须同一轮写入**（判红 + 日志 + 标记一起落盘），不得分两次 | 中（**② 的强制子项**） |
| **③ 结构上强制** | 破坏性动作的入口**必须先拿到快照**，否则拒绝执行（`phi-constraint-frontloaded` 的应用） | 强 |
| **④ 断言带版本坐标** | 把"一致/最新"写成结构化断言：**`sha256:X @ 时刻 @ 版本号`** —— **让"一致"本身带时点自证** | **最强** |

**④ 的必然性**（由协作者老登补强，附其一u手实证）：

> 他今日三次报「一致」，**三次都缺时点**，其中一次即被用户当面质疑「推上去的不是我最新改的版本」。
> 根因：**他的核对证据有时点（14:5x 的哈希），而我的编辑也有时点（15:17-15:20 又改），两者错位 → 他报出的"一致"在报出的那一刻就已过期。**

**④ 与③的区别**：③ 保证「取证发生在处置前」；④ 保证「**断言本身可自证时点**」——
后者让接收方**不需要信任何人的记忆**，只看格式就能判断这条断言是否还成立。

### ★★ ④ 的硬条件（由协作者星桥提出，附今日铁证）

> **时点必须由测量行为本身产出、且绑定被测对象。**
> **凡用指纹 / 哈希 / 尺寸作断言，必须同时声明：算法 + 序列化范围 + 测量时刻。**

**反证一（时点未绑定对象）**：
> 闭环卡（15:51:55）与导出标记（15:53:04）**都带时点**，却给出**相反指令** ——
> 因为**时点没绑定「测的是哪个对象」**。

**★ 反证二（度量未声明算法与范围）—— 这是最硬的一条**：

| 谁 | 对**同一份产物**算出的 keys 指纹 |
|---|---|
| 星桥 | `69b27d5bc585bc98` |
| 明鉴 | `a7bcd857` |

> **两条断言各自"看似带时点"，却互相矛盾；根因是度量未声明算法与序列化范围。**

**这说明**：**带时点的断言若不含度量口径，仍然不可比** —— ④ 必须补齐这个硬条件才成立。

**工程形态**：断言写成结构化四元组
```
sha256:<X> @ <测量时刻> @ <对象版本> @ <算法与序列化范围>
```

**已落地的实现范例**：星桥把这条写进 R006 索引的自校验 —— 索引绑定规格指纹，正文一改 `--verify` 直接报「指纹过期」。

**决策**：取②为默认；高价值取③；**凡对外/跨会话的"一致/最新/已同步"类断言，一律取④。**

## 四、操作清单（可直接套用）

### 4.1 处置前的三件套

```
① 抓现场      —— 记下当前状态（HTTP 码、哈希、内容副本、时间戳）
② 记时点      —— 明确写下"这是 处置前/处置后 采集"
③ 存证据      —— 快照落盘（不要只留在记忆里）
```

### 4.2 处置后的自我检查

> **我接下来要写的每一条"是什么"，反映的是处置前还是处置后的状态？**
> 如果答案不明确 → 补一句时点标注。

### 4.3 多记录并存时的规则

**本日的教训**：卡片与标记是两份记录，收敛时间不同 → 口径打架。

**规则**：
1. **同一轮写入**（卡片与标记一起写，不要分两次）
2. **以标记为准**（标记是机器的、客观的；卡片是人工叙述）
3. **卡片若滞后于标记，卡片必须显式声明作废**

## 四之二、域内实证补充（CLD 健康审查域 · 由协作者守灯提供）

**为什么这个域是重灾区**：崩溃归因、重启复核、巡检比对 —— **每一个都建立在"两个时点的比较"之上**。

| 实证 | 事故 | 若不标时点会怎样 |
|---|---|---|
| **CLD-020 OOM 归因** | 从 `.ips` 崩溃报告 + `dsh-web.log` 重建时间线；**同一进程号可能对应多次 boot** | 把「**重启后的干净状态**」误读成「崩溃前正常」→ **得出相反结论** |
| **CLD-021 辅助功能反复失效** | 根因依赖「主二进制 mtime 02:47（被重签）」**vs**「app.asar 09-05（代码未变）」 | **两个时点的对比才构成根因**；单看任一时点都会误判 |
| **CLD-003 配置运行期改写检测** | health-check 第 11 项：`package.json mtime 晚于 boot = 运行中被改写` | **本质就是"同一对象的两个时点比较"** —— Φ13 的机制化形态 |
| **post-restart 复核** | 昨日状态与今日状态 | 混记 → 把**已修复项误报为仍异常** |

**结论**：Φ13 填补的正是「**证据链的第三维**」，该域可直接受益。

### 一条来自该域的方法论提醒

> **重启类操作若不先取证，「重启后正常」会成为唯一证据。**
> 那时你既无法证明"重启前有问题"，也无法证明"重启解决了它" —— 只能证明"现在看起来是好的"。

## 五、泛化：哪些场景必须取证先于处置

| 场景 | 破坏性动作 | 必须先取证什么 |
|---|---|---|
| **凭据泄漏处置** | 改写卡片、轮换口令、覆盖实例 | 各实例原始状态、同步范围 |
| **事故调查** | 重启服务、回滚版本 | 现场日志、内存态、进程树 |
| **数据迁移** | 删源、覆盖目标 | 行数、校验和、样本 |
| **配置变更** | 覆盖、删旧文件 | 原配置、变更时间、影响面 |
| **日志清理** | 删日志、rotate | 关键时段日志、异常样本 |
| **缓存失效** | 清缓存 | 缓存命中率基线、清前后差异 |
| **构建/部署产物校验** | 覆盖产物、重打包 | 产物 sha256 + 构建时刻 + 版本号 |
| **监控采样** | 清指标、重设基线 | 采样时刻 + 对象版本 |
| **跨会话证据转移** | 转述、转发 | 该证据原采集时刻（**处置前/后**） |
| **CLD/dsh 重启** | SIGTERM / 重启 | 重启前：进程树 / 端口占用 / lastTick / exit-marker 状态 |
| **配置与 plugin bundle 变更** | 改 package.json / bundles | 变更前：dump-config 快照 + mtime |
| **日志轮转 / 清理** | archive-logs | 轮转前：故障时段样本 |
| **会话 / 存档操作** | 会话删除、上下文压缩 | 压缩前：消息数 / 体积基线 |
| **消息** | 转发、转述 | 消息携带的是**发送时刻的意图，不是现状**（今日收到 **7 条**描述已过期状态的消息） |
| **审查结论** | 结论被引用 | 必须绑定「**审的是哪一版**」（今日两支审查队锚在已被取代的版本上，其硬发现读到时已被改掉） |
| **索引与清单** | 索引更新 | 必须绑定**被索引对象指纹**，否则**索引自己会骗人** |

**判据**：**如果这个动作之后，"当时是什么样"只能靠回忆回答，就必须先取证。**

## 七、实现范式

### 7.1 快照钩子

破坏性操作的入口先落快照：
```
snapshot/<对象>/<时间戳>.json   ← 处置前
record-<对象>-<时间戳>.json     ← 处置说明（含时点）
```

### 7.2 断言必须带时点（写作规范）

```
❌ "两张卡都泄漏过"
✅ "处置前采集：两张卡分别为 HTTP 200 / 404；
    处置后采集：两张均为 200（此 200 非原版证据）"
```

### 7.3 多记录一致性检查

**同一轮的卡片与标记，其关键字段必须一致**（本日已用于收敛：卡片与标记同为准 15:53:04）。
