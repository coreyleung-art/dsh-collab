# todo 价值评估框架 · 判断依据逻辑 v2(Lean4 化)

> 明鉴 v2 · 2026-09-06 · 用户要求建立可复用评估逻辑(不拍脑袋选域)
> 场景: 全蓝图 100+ todo, 需判断"先推进哪个/哪个值得/哪个已完成未标记"

## 一、评估维度与权重
| 代号 | 维度 | 判据 | 权重 |
|------|------|------|------|
| I | 完整性核对 | 空标记但已有实现?(工具/代码在) → done | 先闸 |
| R | 资源可得 | 本机可做可验? (代码/数据在 mac-mini) | 硬闸 |
| V | 业务价值 | 解决真实痛点? 离用户/钱/效率近 | .30 |
| D | 依赖位置 | 被多少下游依赖(DAG 前置先做) | .20 |
| C | 完成成本 | 小(1-2h)/中(半天)/大(多轮) | .10 |
| S | 战略对齐 | 主线: 数据/自动化/产品/平台 | .10 |

## 二、判定逻辑(两级)
1. **I 先闸**: 扫 todo 项 → 若同目录/工具有对应实现(脚本/代码/服务在) → 标"疑似已完成待核", 人工核对后 done —— 零成本真实推进
2. **R 硬闸**: 资源不可得(需业务数据/真实上线/远程/他人) → 标 backlog(不入推进列), 避免抽象标记
3. 通过 I/R 后: 总分 = V×.30 + D×.20 + (1/C)×.10 + S×.10 → 排序
   - V+D 高 & C 小 → 先做(高性价比底座/前置项)
   - V 高 & R 不可得 → backlog 等资源
   - 大 C & V 中 → 拆子步或后置

## 三、工具 bb-todo-eval.py
- `--scan` : 全蓝图 todo 扫描 + I(核对工具/代码存在)+ R(本机资源标记) → 输出分类
- `--eval BP` : 单蓝图逐项 V/D/C/S 打分(规则表) → 排序建议
- 输出: ①疑似完成(待核) ②可推进(排序) ③backlog(资源不可得)
- R006: --selfcheck/--tool-version/文档

## 四、验收
| # | 标准 |
|---|------|
| A1 | 全蓝图 todo 分类(疑似完成/可推进/backlog) |
| A2 | I 核对准确(工具在=标疑似, 不在=真待开发) |
| A3 | R 判定(本机脚本可做 vs 需业务/远程) |
| A4 | 可推进列有排序依据(非拍脑袋) |
| A5 | 输出落 data/blueprint/todo-eval/ 可追溯 |

## v2 Lean4 化要点
- I门不自动 done: 能力表命中 = suspected(需 --confirm 人工核), 带 auth+审计(audit.jsonl)
- 人工核对权威表 todo-verified.json: 人核确真的映射(仅它+user-confirm 可标 done)
- 判定类型化: suspected/actionable/backlog 构造状态, 转换需门
- 教训: 能力表关键词匹配会误报(an2-2←integrity), Lean4 核心 = 人工 Confirm 门
