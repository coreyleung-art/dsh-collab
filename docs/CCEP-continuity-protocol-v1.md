# 永续通讯协议（CCEP v1.0）· Channel Continuity Evolution Protocol

> 2026-08-28 ｜ 用户确立的根本原则 ｜ 中枢 fa1f9150
> **一句话**：通讯通道的任何迭代，都必须用旧通道投递新通道、验证可行才切换——除死机等极端情况外，保持永续通讯，永不需要人类手工重新打通。

---

## 一、原则（不可违背）

1. **永续通讯**：跨设备通道（黑板/SSE/注入）升级过程中，任何时刻至少有一条可用通道——绝不出现「全部断掉需要人工重连」。
2. **通道自举**：新版本必须通过旧通道投递（genebank/黑板 notes/playbook 提示词），端侧在旧通道上收到完整迭代信息并验证，才切换。
3. **验证先行**：任何通道变更，本地完全准备妥当（编译+测试+隔离验证）后，才投递。
   4. **沙箱先行**（2026-08-28 用户要求）：任何重启和测试之前，先跑安全沙箱验证，测试没问题不报错才跑正式生产重启（沙箱验证 → 生产切换两步分离，防重蹈崩溃）。
4. **可回滚**：每次切换保留旧版本/旧配置快照，失败可秒级回滚（重启+环境变量）。

## 二、通道迭代五步流程（CCEP 流程）

```
┌─ 步骤 1【准备】本地完成：新版本编译 + 单测 + 隔离环境验证（如带 token 的 8795 实例测试）
│   产物：二进制/完整包 + CHANGELOG + playbook 提示词 + 版本 tag
│
├─ 步骤 2【投递】用当前可用通道（旧通道）投递：
│   - genebank 上传（sha256 内容寻址）
│   - GitHub Release（双资产）
│   - 黑板 notes/<node>/<change>-<ts>（扁平 JSON，python json.dumps）
│   - playbook 提示词（端侧可执行）
│
├─ 步骤 3【端侧验证】端侧通过旧通道收到 → 安装新版本 → 自检：
│   - node-bridge：identity 生成 + 心跳 device_id
│   - central-inbox：SSE 连接 + 注入测试
│   - 回报黑板 notes/mac-mini/deploy-result-<node>
│
├─ 步骤 4【就绪确认】所有端侧回报 OK（就绪清单）→ 才切换：
│   - 确认清单：mac-mini ✅ / MBP ✅ / i9 ✅（新增节点加入）
│   - 任一未就绪 → 不切换，继续等
│
└─ 步骤 5【切换+回滚保障】确认后切换；失败回滚：
   - 切换：如启用 BLACKBOARD_TOKEN（所有端侧已带 token）
   - 回滚：黑板重启 + 清除环境变量（秒级）
   - 切换后 24h 观察（心跳/注入/无 401）
```

## 三、关键检查点（每次通道迭代必须过）

| # | 检查点 | 说明 |
|---|--------|------|
| 1 | **SSE 读端兼容** | central-inbox SSE 订阅是否受新版本影响（token/协议变化）|
| 2 | **写端兼容** | node-bridge/dsh-tools 写黑板是否带新认证 |
| 3 | **端侧就绪清单** | 所有端侧回报 OK 才切换（禁止单端先行切换）|
| 4 | **回滚路径** | 切换失败秒级回滚（环境变量+重启）|
| 5 | **双通道冗余** | 注入式 + executor 轮询并存（一条断另一条兜底）|

## 五、禁止事项

- ❌ 不验证就切换（本地未测试/端侧未回报）
- ❌ 单端先行切换（会破坏就绪清单）
- ❌ 物理复制插件（不加载，且无法通过旧通道验证）
- ❌ 依赖人类手工重连（playbook 提示词是最后手段，非常态）
- ❌ 破坏性变更不留回滚路径
