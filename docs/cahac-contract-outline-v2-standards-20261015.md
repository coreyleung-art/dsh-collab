## §1 文档骨架（★ 照 RFC 7322 §4 的结构）

```
─────────────────────────────────────────────────────────
  头部区（★ 照 RFC 7322 §4.1–4.7）
─────────────────────────────────────────────────────────
  H1  标题 + 版本 + 日期
  H2  摘要（Abstract）—— ★ 一段话：本契约让读者能做什么
  H2  本文档地位（Status of This Memo）
       ★ 草案 / 生效 / 取代谁 / 谁复核
  H2  要求语言（★ 独立小节 · RFC 7322 §4.8.2）
       ★ 声明 MUST/SHOULD/MAY 的用法依 RFC 2119
  H2  目录（Table of Contents）

─────────────────────────────────────────────────────────
  正文区（★ 结构 = 新读者需要的顺序，不是我们讨论的顺序）
─────────────────────────────────────────────────────────
  H2  1. 引言（Introduction）
       ★ 1.1 本契约解决什么问题（★ 不讲历史，只讲问题）
       ★ 1.2 谁该读它
       ★ 1.3 范围（★ 管什么 / 不管什么）
  H2  2. 术语（Terminology）
       ★ 2.1 本契约定义的术语（★ 逐个一句话）
       ★ 2.2 规范性引用（Normative References）
       ★ 2.3 参考性引用（Informative References）
  H2  3. 参与者类别（Conformance Classes）★ 对应 W3C 的 ICS
       ★ 3.1 有身份的写入方
       ★ 3.2 无身份的产出方
       ★ 3.3 接收方
       ★ 3.4 不属于任何一类时怎么办
  H2  4. 接入要求（Requirements）
       ★ 4.1 … 4.N（★ 每项：【要求（MUST/SHOULD）】+【凭什么算做到】+【复跑命令】）
  H2  5. 符合性声明（Conformance Statement）★ 对应 W3C 的 ICS
       ★ 5.1 声明什么（★ 版本 · 已接入面 · 未接入面）
       ★ 5.2 声明的形状（★ 字段表）
       ★ 5.3 声明的举证方式（★ 一个东西 + 一条命令）
  H2  6. 周期与责任（Cadence and Responsibility）
       ★ 6.1 何时声明（★ 首次 · 变更后 · 周期）
       ★ 6.2 谁声明（★ 写入方自证）
       ★ 6.3 谁核（★ 异体）
  H2  7. 不符合与不可判（Non-conformance and Undecidability）
       ★ 7.1 四态：未接入 · 未举证 · 超期 · 不可判
       ★ 7.2 每态的正确记法（★ 且注明错误记法及为什么错）
  H2  8. 后果（★ 照 RFC 2119 §7 的精神）
       ★ 8.1 不遵守 MUST 的后果（★ 具体，不抽象）
       ★ 8.2 不遵守 SHOULD 的后果
       ★ 8.3 ★★ 为什么本契约【不靠禁令】—— ★ 靠读数
  H2  9. 安全考量（Security Considerations）★ RFC 7322 要求必需
       ★ 9.1 本契约要求什么可能被滥用
       ★ 9.2 本契约【不索取】什么（★ 凭证 · 写权限 · 代码改动）
       ★ 9.3 伪造身份的后果（★ 为什么宁可声明「无身份」）

─────────────────────────────────────────────────────────
  尾部区（★ 照 RFC 7322 §4.9–4.12）
─────────────────────────────────────────────────────────
  H2  附录（Appendices）
       ★ A 举证对象的完整字段表
       ★ B 复跑命令清单
       ★ C 反例集（★ 什么是【不合格的举证】）
  H2  致谢（Acknowledgements）
  H2  变更记录（Change Log）
```

## §2 ★★ 三个【业界标准带来的关键决定】

### 决定一 · **规范性引用 vs 参考性引用**（★ 解决「自足」与「不重复」的矛盾）

| ★ | ★ 含义 | ★ 本契约怎么用 |
|---|---|---|
| **Normative（规范性）** | ★★ **读者【必须】读它才能合规** —— ★ 缺了它本契约不完整 | ★★ **极少数**：★ 只放**信封字段的权威定义**（★ 如规格文件） |
| **Informative（参考性）** | ★ 读者**可以**读它来理解背景，★ **但不读也能合规** | ★ 实现示例 · 背景说明 · 设计理由 |

> ★★★ **为什么这个区分重要**：★ 现契约的毛病是**两者混在一起** —— ★ 读者**分不清「不读它会不会不合规」**。
> ★★ **而业界标准的分法是：★ 把「必须读的」压到最少（Normative），★ 其余一律 Informative。**

### 决定二 · **要求语言用 RFC 2119 五级，★ 且【克制使用 MUST】**

★ RFC 2119 §6 逐字（★ 现查）：
> ★「Imperatives…**MUST only be used where it is actually required for interoperation
> or to limit behavior which has potential for causing harm**」
> ★★ 且：「they must not be used to **try to impose a particular method on implementors
> where the method is not required for interoperability**」

| ★ | ★ 本契约的自我约束 |
|---|---|
| **MUST 只能用在两处** | ★ **① 互操作必需**（★ 不这样写，对方就路由不了/去重不了）· ★ **② 限制有害行为**（★ 伪造身份） |
| **★ 不得用 MUST 的地方** | ★★ **内部实现方式** · ★★ **具体工具选择** · ★★ **目录结构** —— ★ 因为**那些不影响互操作** |

### 决定三 · **须写【后果】（★ RFC 2119 §7 的精神）**

> ★ RFC 2119 §7 逐字：「Document authors should take the time to **elaborate the
> security implications of not following recommendations or requirements**」

★ 故本契约须有一节（§8）**逐条说明**：★ **不遵守会怎样** —— ★ 而**不是抽象地说「重要」**。
