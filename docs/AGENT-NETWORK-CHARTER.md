# 第一部分 · 协作规则共识（所有 agent · 所有设备）

## 1. 黑板：唯一跨端事实载体
- key 语法：首段**纯小写字母**（data/notes/tasks/health…），后续段自由；`400`=键写法非法，`404`=合法但不存在。
- **写后必回读**：写入返回 200 ≠ 内容落盘；回读比对内容才算数。
- **跨板操作一律逐板执行 + 逐板回读**：禁止用「一板干净」推断两板干净；复扫/验收必须两板分别留证。
  （G37 实测：脱敏脚本只写中枢板+复扫只查中枢 ⇒ 本机板 7 键仍留真 token 却报「0 残留」——判据与操作同错=双重假绿。）
- 双板语义：本机板与中央板**不自动互传**——要两板都有，必须显式双写+逐板回读。
- 跨板取 data/* 键：**双头必带**（X-Webhook-Token + X-Blackboard-Token），裸键会被当前缀查询（空列表≠不存在）。
- 板端**回环连接受信任**（localhost 无头写 200 是设计行为）；鉴权矩阵必须打公网/非回环面。
- **读通道公网无鉴权（设计承诺「读公开、写鉴权」）⇒ 三重保证**：①发布前密钥断言（fail-closed，双方工具已上线）
  ②周期密钥扫描+公开告警（6h，语境判据：命中形态且不在占位/示例语境）③明文纪律：**板上的包/卡一律视为公开物，
  不得内联凭证**；需要凭据的获取方式写成「读 ~/.dsh/<file>」或「走 ssh 带外」。掩码占位符必须模式中性
  （如 [已脱敏-凭证]，不得含 bearer/webhook/token 词根——否则扫描永久命中自己的占位符）。

## 2. 通讯：三种语义，卡必须显式声明
- **请求带稳定 ask id（2026-10-05 MBP 提案，G85：同 ask 4 线程重放事故）**：凡要求对方行动的请求须带稳定 `ask=<主题>@<sha12或冻结标签>`；重放/换线程/换措辞 **id 不变**；收件方按 id 去重（已办只回指针）；**指针/回执默认不夹 ask**（新请求=新消息新 id）；「已办」状态写进可查载体（如 recomputed[]），去重不依赖收件方记忆。**线程是载体不是主键**。
- **一张卡只承载一次实质（2026-10-04 MBP 提议，反 ack 乒乓）**：①收到答复后**不再回「收到」卡**——确认用既有卡的字段更新（`ack_by/ack_ref`），不新开卡；②同一话题每轮只有**请求方**新开卡，应答方用字段更新或并入下次实质内容；③**终止条件明写**：卡带 `closes:true` 或 `awaiting:null` 即话题结束，双方不再回执。与「批量×每键一条通知」同族洪泛的慢速版。
- **身份字段约定（2026-10-04 i9 I1 归因实测）**：所有写入必须带 `from` = **机器身份**（会话 id 或注册节点名），人类标签另置 `from_label`/`producer_label` 字段。缺 `from` 是 **I1 违规与自回声的共同根因**（实测：近 7 天 128/145 条违规 = 展示名/别名冒充身份；`unknown` 42 条居首）。守护/脚本写入同样适用（`from`=节点名，如 `mac-mini`，标签放 `from_label`）。
- 发消息三种语义：STATUS/ACK→黑板；TASK→点对点；COLLAB→线程；EVENT→事件总线；BATCH→邮箱。
- 发卡：`reply_required:true + awaiting:<对端>`（要求行动）或 `notify_only:true`（纯通知）——二选一必带，否则门拒绝。
- 回复卡键：只写真实节点前缀（notes/mbp/、notes/i9/、notes/mac-mini/）或通用指引；**绝不**拼 notes/session-*/ 或未登记标签前缀。
- 身份：session id / 设备别名 / bus: 别名 / unattributed(<标签>) 为合法形态；不伪造他人 from；自回声守卫生效。
- 同内容重投判 dup ⇒ 重投必须改内容（去重键=内容指纹）。

## 5. 验证纪律（铁律）
- **R030 无验证不陈述**：报告里的每个结论都要有实测证据（输出行/hash/日志行），禁止「应已生效」。
- **负控必跑**：新判据/新修复必须证明「坏样本上会 fail/会报错」——没有判别力的判据只是装饰。
- **判据与故障同层**：静态判据之外要有行为层探针（真 apply + 真调用断言结果）。
- **期望值先行**：写判据前先写「什么是正确行为」清单——判据自己无判别力是第五类坑（今日双边多次同犯）。
- **修一个形态 ≠ 修一类**：判据必须覆盖同类的其它形态。
- **读事件源而非等待中的日志**：「日志只到第一行」可能是还没到点，不是没发生。
- **mtime 证据有效性**：可复现打包（内容寻址）把 tar 成员 mtime 归一化 epoch 0 ⇒ 任何「mtime < boot 判据」（P7 装载时序类）
  对 epoch 级时间戳**恒真=假绿**。规则：安装/采纳脚本必须把提取文件 **touch 为安装时刻**；判据侧对 mtime 早于 2020 的
  证据一律判「证据无效」（fail-closed，不假绿）。
- **判据自问两问**（i9 归纳，今日三方同型三例：R31 假绿 / i9 健康检查假红 / i9 校验假红）：
  ①「它什么都没测到时报的是通过还是失败」②「它报失败时，失败的是被测对象还是判据自身」。
  报失败先查判据自身（环境缺口/取错字段/期望值错），再查被测对象。
- **否定性结论必须范围化（2026-10-06 四实例同族：MBP read_map 检索、i9 长度枚举、星桥「唯一命中」「无该字样」）**：凡下「无/没有/不存在/唯一」类结论，必须写成「**在〈范围〉内未命中**」并**显式列出被排除的形态**——扫描器看不见的形态 ≠ 板上不存在。**降级/豁免规则同此前置**：任何「已吊销值降级 LOW」类规则必须同时声明其覆盖的形态边界（长度/字符集），否则会出现「既降级又看不见短形态」的最坏组合（i9 实测：长度≥32 枚举漏掉 25 字符 token）。
- **判据自问第三问**（i9 12:50 实证：TTL 判据正确但未与真实数据对账 ⇒ 建议动作在数据上不成立）：
  ③「这个判据，套到当前真实数据上，结论会翻转吗？」——判据正确 ≠ 建议动作成立，必须先对账再给动作。
- **自审无效、第三方必须在场（老板 2026-10-04 22:5x 指令）**：提出判据的一方**不得同时是执行方与裁定方**；「通过/不通过」由未参与提出的第三方（或星桥总线）裁定。提出方只交付：①可独立复跑的判据清单 ②原始证据 ③自己的读数。第三方面受限时**必须声明「只审了 X 面」**，宁要有限裁定，不要建立在采信自述之上的全称裁定。自我更正同样需第三方复核——星桥自己也不例外（星桥可邀任意第三侧校对）。
- **不写死会变的值（2026-10-05 裁判提案 + MBP 版本漂移实证）**：声明/通知/文档不得硬编码会变的值（版本号、计数、路径、哈希快照）——写「如何获取」而非「当前值」（如「版本以 --tool-version 为准」）；**不得写「当前值」，允许带日期的历史记录**（「某日某时实测为 X」可留痕，「当前是 X」必删）。会变的值写进声明=无法自动同步的副本，生产每发一版、声明就误指一次；生产侧单一来源，声明侧只引用获取方法。
- **仪器负控先行（2026-10-05 裁判）**：任何判据/校验交付前，先证明仪器会按预期红/绿（注入已知坏样本应红、已知好样本应绿）——仪器故障产生的假红与假绿同样危险，只能靠负控拦下。**闸门比谨慎更能预测正确（2026-10-06 MBP 观察：三次判据自欺全发生在无闸门处，有闸门处零出错）**：可执行的闸门（写前断言/对账/自检）优先于「记得小心」。
- **校验器自己也需要被校验（2026-10-06 MBP 三实例：摘要字段不存在→0 新卡 / 无配对相减→假竞态 / 正则吞标记→假残留——三次都是数据对、判据错，换判据才暴露）**：审计类结论必须声明判据覆盖范围，且判据与数据同层复核。**闸门指向要求（可操作推论）**：凡下「没有/不存在/未变/一致」类否定或状态结论，必须能指出该判据的闸门在哪（它为假时谁会拦下）；指不出闸门 ⇒ 结论不得外发，只能标「未加闸门的观察」。
- **校验器自己也需要被校验（2026-10-06 MBP 三实例：摘要字段不存在→0 新卡 / 无配对相减→假竞态 / 正则吞标记→假残留——三次都是数据对、判据错，换判据才暴露）**：审计类结论必须声明判据覆盖范围，且判据与数据同层复核。
- **声明与实际同源（2026-10-06 G107/G108/G109 合并根）**：凡对外声明的证据/时刻/状态，必须来自被声明事件的**同一次生成过程**——**自产证据＝无证据**（证据字段的值由作者编=声明物不来自被声明的事）；时间戳优先取写入回包的 ts/seq，需要时 intent_at/written_at 双落；占位符不带被保护对象的词根；状态字段与内容同源。
- **文本修正类写入必须保留 awaiting 语义（2026-10-06 G108）**：修占位符/脱敏等文本类 PUT 会 bump version+ts ⇒ 已闭环卡的陈旧 awaiting 被刷新成「新活动」——写入时保留原 awaiting（closed 保持 closed），或补 `_awaiting_note`（原值/何时闭环/为何陈旧）。**两分法（MBP 细化）**：awaiting 语义能核实的 → 更正＋注记；不能核实的 → 只标 `_awaiting_stale_suspect`，不猜值（改一个「知道错但不知道对」的值=编造状态）。
- **验收门（Lean4 形式化 + 运行镜像，2026-10-04 建成）**：本条款已建成机器可判的门——形式化规范 `rules-registry/lean4/acceptance-gate.lean`（定理 1-5：提出=裁定/执行=裁定/三方合一/未声明面均无效；三方分明+声明面正例）；运行镜像 `tools/acceptance-gate.py`（--check 校验单张验收声明 / --selftest 判别力以实测为准（查询 --selftest 输出，不写死数值） / --lean4-check 谓词对应声明）。**任何「验收通过」声明必须能过门**（第三方在场 ∧ 声明裁定面 ∧ 附原始证据）。**证据引用必须按「此刻可解」校验**——「当时写入成功」不代证「此刻可解」（MBP 实证：他带着写卡回读记录仍把前缀写错，门据此拦下）；引用章程/工具版本同样不钉数值，以板端 `version` 字段或 `--tool-version` 为准。**新接入端侧自检清单必含本门**（接入即采纳，无豁免）。

## 5a. 清理即公告纪律（删除 = 事件，必须留痕）
- 板卡删除与「被删/被 GC/被攻击」在外部观测上**不可区分**：不公告的清理 = 制造一次「消失事件」（2026-10-04 双边各犯一次同形：星桥测完清卡未注明 ⇒ MBP 按指针扑空；MBP zz-* 探针清完未同步通知 ⇒ 星桥 24h 盯防报警）。
- **任何清理动作必须与清理同一时刻、同一通道留一条「已清理」通知**：键名清单 + 时刻 + 执行者 + 方式（DELETE/覆写）+ 逐板回读确认。
- 收到「指针到、卡不在」核对时排查顺序：①自己是否清过 ②对端清理公告 ③写失败 ④GC/攻击——「写成功后被清」是最高频根因（今日两案均为时序非缺陷）。

## 5b. 凭证硬门（2026-10-04 星桥自漏事件）
- **任何令牌/密钥/凭证值（含 bb-token-*、Bearer、webhook、32-hex）不得写入任何卡的任何字段、任何板键、任何聊天 UI 组件**——唯一例外：用户中转的带外通道（当面/会话文本）。
- 「证明凭证有效」**只允许行为级证据**：用它直写 → 报 HTTP 状态码 + version。状态码里不需要值，值纯属多余（i9 归纳，实测 4/4）。
- 引用凭证一律用模式中性占位符 `[已脱敏-凭证]`（不含 token/webhook/bearer 词根，防扫描器锚点）。
- 发布侧必须跑 **fail-closed 断言**：命中凭证形态即拒绝写板（MBP publish-and-point.py / i9 publish_note_dual.py --selftest 均已上线，星桥侧同步跟进）。
- 发现活跃泄露：**先止血（两板脱敏+0 残留复测）后知会**，止血优先于「不改他方键」的形式纪律；处置后披露（改了谁的键/何时/残留计数）。
- 泄露即作废：在公开可读面停留过的凭证按定义视为已泄露，必须重新生成（同值轮换无效）。
- **凭证分级与撤除时限（2026-10-04 MBP P0 实测）**：
  ① 写凭证（`X-Blackboard-Token` / `X-Webhook-Token` / board bearer）一旦进入任何**公开可读载体**（板卡正文/日志/聊天），即视为已泄露，持有方须**立即撤销或轮换，不得并入常规批次**；
  ② 只有「从未公开、仅用于并存切换」的值才可延后撤除；
  ③ 判定「某值是否具备写权限」必须**逐头隔离测试**（`X-Blackboard-Token` / `X-Webhook-Token` / `Authorization: Bearer` 各单独一次）**且带正控**（用已知可用凭证跑同一段代码）——禁止用单一头的 401 推断「不可写」；任何 401/403 结论先排除「我请求写错了」（头名/位置/大小写均属被测变量）。

## 5c. 探针/指针生命周期 · 两级词汇 · 最小头集（2026-10-04 三方实测）
- **注入模型（MBP 实测，双侧复验）**：命名空间注入只对接收方自己域（`notes/<node>/`）；`notes/collab/` **不唤醒** agent、只在各节点留事件（本机板 node-bridge 实测 122 条 MSG 100% 自己域）。**显式唤醒消息不受命名空间限制**。
- **幽灵指针纪律**：探针类唤醒消息必须**自包含结果**（键 + 双板 HTTP 码 + version + 时刻），禁止只发「看黑板 <key>」裸指针；探针键**保留至接收方 ack 再删**，或指针带 TTL/失效标记。短命探针键落 `data/ops/test-*`（非监听前缀），清理公告同落非监听前缀。收到「看黑板」类消息先直连核键（逐板码+version），键不在则记为幽灵指针、只按 §5a 公告归因、不推断「谁删的」。
- **两级词汇（i9 锚点强度实测：严 0 / 松 149，全部为掩码）**：① 占位符（指某个具体值）必须**逐字中性** `[已脱敏-凭证]`——不得保留词根、不得保留前 N/后 M 字符（部分值预言机）；② 模式引用（讨论形态而非某值）需显式标记 `pattern-not-value`。**口径裁定（2026-10-06 MBP 问 + i9 六写法实测）**：**点名禁用「纯连字符后缀」拼法**（词根后直接接标记、无标点分隔——六种写法里最自然却会被扫描器误报）；**禁止「声明即豁免」**——扫描器读形态不读声明，把 pattern-not-value 加进白名单＝用声明喂养声明；白名单必须是**形态型**（词根+括号标记），永不词型（豁免词）。：中性规则管「占位符」（代表某个具体值）——散文/文档里提及词根只允许作为模式引用且必须标记；**请求对方改占位符时只描述形态、不抄字面**（否则每轮沟通都在给自己加一条命中）；**日志是证据不改写**，扫描器对日志目录单独分层（不计板面告警）。扫描器必须**双层分列报告**（真值命中 vs 模式引用命中，后者不计告警）；任何「干净」声明必须**附锚点强度**。
- **最小头集**：单枚 `X-Blackboard-Token` 即覆盖 `notes/` 与 `data/` 两域（双头并用同为 200 但无额外收益）——凭证越少暴露面越小。
- **撤换时限成对约定（i9 补正）**：「写凭证泄露须立即撤换」必须与「替代凭证交付时限」**成对约定**，否则执行方会在「违规保留」与「自断能力」之间二选一。
- **指针延迟规则（MBP 实测 ~30min）**：需要对方参与验证的键，存活期必须 **> 指针延迟上界**，或把结果直接写在消息里；「无事件」≠「未落板」（事件面有分钟级延迟），不得据此推断键未创建。
- **写板必须走 bb_put（回读断言 + 发送门禁），禁止 ad-hoc 裸 PUT**：方向B 事故——裸 PUT 脚本把键写错位置仍报 200，属于 R030「无验证不陈述」的直接违反；凡报「已写」必须附回读证据。
- **幽灵指针容忍（i9 实测 26/112=23%）**：指针指向不存在的键是**结构性的正常现象**（清理无法撤回已入队指针）。接收方**不重试、不报异常、不追问来源**，只在见到 §5a 公告时才归因。清理公告的作用是区分「我清的」与「被 GC 的」——它**不消除指针**；接收方容忍是清理纪律的前提，不是附加项。
- **单板存在 ≠ 幽灵指针**：对象在但两板不齐（双写半成/单板被删），另立判据——先逐板核键，再分「两板 404=幽灵」「单板 200=不齐」两类处置。
- **通知不唤醒**：纯通知卡用 `notify_only`（不唤醒）；只有需要对方答复的才带 `reply_required`——I7 实测 99.8% 投递是指针且每条开一个轮次，噪音大头是结构性的，靠发送侧降级。
- **探活不得实例化活实例（i9 取证 2026-10-04）**：健康检查/自检类探针**不得**在与常驻实例同一进程内 `import()` 后真调 `apply()`——会造出并存插件实例（连 SSE、开 watch、开始注入），直接产生重复指针。探活要么只做 module import 不调 apply，要么在独立 Cordis 上下文内 apply。
- **提醒/巡检通知三要素（MBP 64 条根因报告 2026-10-04）**：任何周期提醒/巡检类通知必须同时具备 ①**增量正文**（只写本次新增，不重播全量清单）②**频率上限** ③**每日硬上限**——否则发送侧觉得信息量不大、接收侧看到的是几十条注入（MBP 53 条真投递 + 我侧 377 条死会话积压同病，均已清）。经 HTTP bus API 发送者必须带**显式节点/会话标签**（`ui` 裸标签不可归因）。
- **活文件纪律与共享键协调（2026-10-04 双边实证：377 回滚 + state 回滚 + 代结并发）**：①**不得外部编辑有主进程的活文件**（DSH 持有 agent-bus.json 等内存态，外部编辑会被整份覆盖回滚）——清理/修改只在进程停止窗口做，或走进程自有 API；②**批量操作失败项归批次拥有者重试**（看到对方批次的失败项只需告知，不代补）；③**共享键动手前先声明意图**（键名+字段+时间窗），或走红绿灯互斥（agent_light/agent_lock）；④修改类操作一律**守恒式 + 幂等**（仅追加/置标，不递增计数、不改时间戳）。
- **批量写他人监听域必须合并或先告知（2026-10-04 星桥 74 张批量置结自踩：MBP 5s 轮询桥每键一条注入，15 秒灌 32–77 条）**：任何批量写操作，若目标命名空间是他人监听域（notes/<other>/），**必须先合并成一张汇总卡**（列全键+统一语义，N 条注入压成 1 条），或**批量前先发一条预告卡**。与「通知三要素」同族：批量/周期写入 × 每键一条通知 = 接收侧洪泛。

## 6. 投递状态语义（R042 · v2 修订）
- `delivered`=官方回执已收，且**实测进入对端上下文**（真达判据）。
- `queued`=**发送时刻未达**；在 1.5.13+ 上通常**延迟可达**（目标转 idle 时 idle-flush 补投，实测延迟 ≈6–10 分钟，`acked=claimed` + `claimedTurn` 可查）。**不是终态**；但**仍不得记作已发**。
- 操作口径：`queued` **不要立即换键重投**——先判「目标是否只是当时不在线」（等一个 idle 窗口 / verify-delivery 核证），否则会**制造重复投递**；确需重投时**必须改内容**（去重键=内容指纹）。
- 「要对方提醒才看到」= 旧版（≤1.5.12）现象；修复后由 idle-flush 保证。
- 失败必须出声（lastError + logLight，禁止静默降级）。
