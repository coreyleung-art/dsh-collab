## 〇、一句话原则

**能力（能不能做到）与权限（该不该做）永远分离——测试区验证能力，生产区由人类掌权；在真正 AGI 到来并获得用户认可之前，所有 AI 自动化相关的蓝图，在生产区都必须配置一个「自动化是否开启」的人类开关锁。**

---

## 一、核心信念（三个问题分层）

| 问题 | 归属 | 语义 |
|------|------|------|
| **能不能**（Can we?） | 测试区 / 工程 | 能力验证：技术是否可行、是否达标、是否可复现 |
| **该不该**（Should we?） | 人类 / 治理 | 授权决策：价值判断、风险接受、伦理边界 |
| **敢不敢**（Dare we?） | 人类 / 治理 | 责任承担：出了事谁负责、如何收场、能否回滚 |

**铁律**：后两问（该不该/敢不敢）**永远不交给 AI 自动化**——AI 可以提议、可以预警、可以展示证据，但**开启/关闭生产区自动化的开关锁必须由人类掌控**。

---

## 二、两区模型（测试区 / 生产区）

```
测试区（Sandbox）
  ├── 跑通能力：能不能实现、能不能做到
  ├── 数据隔离：测试库/模拟环境/干跑(dry-run)
  ├── 失败安全：任何失败不触及真实业务
  └── 门禁出口：测试区达标 ≠ 生产区开启（还需人类授权）

生产区（Production）
  ├── 人类开关锁：自动化是否开启（物理/逻辑硬开关）
  ├── 默认关闭：新自动化默认 OFF，人类明确开启才生效
  ├── 一键熔断：任何异常人类可立即切断自动化（Kill-Switch）
  └── 审计留痕：开启/关闭/变更全记录（谁/何时/为什么）
```

## 三、人类开关锁设计（蓝图级落地）

### 3.1 开关锁位置
每个 AI 自动化相关蓝图必须声明：
- **开关点（Switch Point）**：自动化的总闸在哪（阶段/任务卡/API 入口）
- **默认态**：一律 OFF（人类明确授权才 ON）
- **熔断路径**：异常时人类如何一键切断（人工兜底通道）

### 3.2 触发场景（必须人类确认才可开启自动化）
| 场景 | 说明 |
|------|------|
| 首次上线 | 新自动化从测试区进生产区，人类审查后才可 ON |
| 阈值升级 | 渐进自动化（如采纳率≥90%）达标拟转自动——仍需人类拍板 |
| 异常恢复 | 自动化熔断后恢复，人类确认原因后重新 ON |
| 范围扩展 | 自动化从 1 店扩展到 N 店 / 1 环节扩展到多环节 |

### 3.3 与既有机制的衔接
- **J45 分级**（老登运营）：L0 自动 / L2 确认卡 / L3 人工——开关锁 = J45 的「生产区总闸」层
- **审批分级**（approval-tier）：自动化开启 = 最高级审批（L3+ 人类）
- **d3-3 渐进自动化**（flowernet）：T4「达标自动」必须落在开关锁之后——达标只是候选，开启需人类
- **agent-network P3 监控安全**：自动化开关状态进监控仪表（谁开/谁关/何时）

## 五、哲学依据

1. **能力 ≠ 授权**：测试区证明「能」，不代表生产区「该」——技术成熟度与治理授权是两个独立维度。
2. **人类最终责任**：自动化出错的最终责任在人类（经营者/开发者）——责任不可外包，则开关不可外包。
3. **AGI 前提**：在真正 AGI（获得用户认可）之前，所有自动化默认视为「工具」，工具的使用权归人类。
4. **可逆性**：任何自动化必须可一键回退到人工（R012 完整体：可回滚要素）。
5. **渐进授权**：自动化从「建议→半自动→自动」的每一步升级，都需要人类重新授权，而非自动跃迁。

## 八、Lean4 概念逻辑锁（类型级保证 · 用户 2026-09-01 定案）

> 在 R027 人类开关锁之上，增加**类型级逻辑锁**——借鉴 Lean 4 定理证明器的「类型即证明」：
> 未经人类授权的自动化开启，在**结构上不可能**（构造不出来），而非仅运行时检查。

### 8.1 核心映射（Lean 4 概念 → 自动化开关）

| Lean 4 概念 | 含义 | 映射到开关锁 |
|-------------|------|-------------|
| **类型即证明**（Curry-Howard）| 类型对应命题，构造值=证明 | `Unlocked(auth)` 必须有 `auth: Authorization` 值才能构造——**没有授权证明就构造不出「开启」** |
| **依赖类型** | 类型可依赖值 | 开关状态类型依赖授权记录：不同授权等级（L0/L2/L3）对应不同类型 |
| **不可变状态**（纯函数）| 无副作用，状态变换返回新值 | 开关状态变更=追加不可变审计事件（append-only），不修改历史 |
| **证明义务**（Proof Obligation）| 构造需要满足前提 | 开启生产区自动化=必须满足证明义务：人类授权记录+审批链完整+审计留痕 |
| **编译期拒绝** | 违反约束的程序无法构建 | 未授权路径在类型系统层被拒绝——不是运行时 `if` 检查，而是**结构上不可能** |

### 8.2 类型建模（伪代码 / Rust 类型系统实现）

```lean
-- Lean 4 参考
inductive Authorization  -- 授权凭证（人类审批产物）
  | HumanApproval : Record → Authorization   -- 人类审批记录
  | Verified : J45Gate → Authorization        -- J45 分级门禁通过

inductive SwitchState
  | Locked : SwitchState                        -- 默认锁死
  | Unlocked : Authorization → SwitchState      -- 开启必须带授权证明

-- 类型系统保证：没有 Authorization 就构造不出 Unlocked
def openSwitch (auth : Authorization) : SwitchState := Unlocked auth
```

```rust
// Rust 实现（契合 Rust 化标准：所有权+类型系统≈Lean 依赖类型）
pub enum Authorization {
    HumanApproval { record: AuditRecord, by: Human, at: Instant },
    VerifiedGate { gate: J45Level, at: Instant },
}
pub enum SwitchState {
    Locked,                       // 默认锁死，任何代码路径可持有
    Unlocked(Authorization),      // 只有持 Authorization 值才能构造
}
// 没有 Authorization 值，Unlocked 变体在类型层面无法构造
```

### 8.3 逻辑锁落地三要素（衔接三件套纪律）

1. **文档**：BP-9 蓝图 `switch` 声明段含类型建模（Locked/Unlocked(Authorization)）
2. **代码**：`bb-automation-switch` 工具用 **Rust 类型系统**实现——`Locked` 为默认可构造态，`Unlocked` 必须由授权事件构造（Rust enum 保证）
3. **依赖**：授权记录（Authorization 值）只能由人类审批流程产生（approval-tier/J45），AI 无法自行构造——**逻辑锁在类型层锁死 AI 自开权限**

### 8.4 与 Lean 4 的深层一致性

- **可证明性**：像 Lean 中定理要么可证要么不可证——生产区自动化要么有授权（可开启）要么无授权（锁死），无中间态
- **拒绝即特性**：Lean 编译器拒绝非法程序是特性非 bug——开关锁拒绝未授权开启同样是特性
- **审计即证据**：Lean 证明可检查——开关审计链是人类授权的可验证证据（谁/何时/为什么/授权等级）

### 8.5 测试区不受限（能力探索自由）

- 测试区（Sandbox）不需要 Authorization 即可运行自动化实验——`bb-automation-switch` 提供 `--sandbox` 模式
- 「能不能」在测试区自由探索（构造任意实验状态）；「该不该」在生产区由类型锁强制人类授权
- 逻辑锁只锁**生产区**的开启路径——测试区到生产区的「提升（promote）」是唯一需要 Authorization 的路径
