# 第一部分 · #6 —— I-1 有没有更完善的语义

## §1 现用语义（★ 本线本轮实现的）

```

★ 分级：本机侧 ≥50% 且中继侧 0 ⇒ SKIP
```

## §2 ★★★ 而它有三个【结构性弱点】

| ★ | ★ 弱点 | ★ 后果 |
|---|---|---|
| **①** | ★★ **把【不同可控性的面】平均成一个数** | ★ 合成 `0.61%` 里，★ **本机侧 71% 与中继侧 0% 被混在一起** ⇒ ★ **那个数【不指向任何可行动的实体】** |

| **③** | ★ **没有【时间维度】** | ★ **今天新写的卡**与**三个月前的历史卡**在同一个分母里 ⇒ ★ **改善被历史稀释** |

## §3 ★★★★★ 更完善的语义（★ 建议）

### 建议 A · 拆成【两个独立判据】，取消合成数

| ★ 判据 | ★ 判的是什么 | ★ 建议阈值 |
|---|---|---|
| **I-1a 本机侧信封率** | ★ **我们自己写的卡** | ★★ **90%**（★ 完全可控 ⇒ 该高） |
| **I-1b 中继侧信封率** | ★ **经中继来的卡** | ★★ **90%**（★ 但分母只算【已接入设备】） |

> ★★★ **关键：★ 取消「合成数」那个指标** —— ★ 因为它**把两个可控性完全不同的面平均了**，
> ★ 而**平均出来的数【谁的账都不算】**。
> ★★ **⇒ 那正是本线今晚反复在做的事：★ 不把【不同的东西】并成一个数。**

### 建议 B · 加【时间窗分层】（★ 解决弱点 ③）

| ★ 层 | ★ 含义 |
|---|---|
| **今日窗** | ★ **今天的卡** ⇒ ★ **反映【当前状态】** |

### 建议 C · 分母【按设备分】（★ 解决弱点 ①）

```
★ 不再报「中继侧 0/340」
★★ 而报「已接入设备：mbp ✓ / i9 ✗ / star-bridge ✗」—— 逐设备
```

### ★ 四条建议的合取

> ★★★ **I-1 改判为：★「本机侧 ≥90%」** 且 **「已接入设备的信封率 ≥90%」**，

# 第二部分 · #7 三个担忧（★ 而它们其实是同一个架构问题）

## §4 担忧①：旧通道是否也该挂上去？

> ★ 您问：★「避免那些设备或者会话还一直用旧通道？」

### ★★★ 答案：**是的，而且那是【关键的一环】**

| ★ | ★ |
|---|---|
| **若【不挂旧通道】** | ★ 设备可以继续用旧格式发卡 ⇒ ★ **信封率永远上不去** ⇒ ★ **契约变成【一份没人执行的文档】** |
| **★★ 正确做法** | ★★ **把「旧格式」也纳入统计** —— ★ **让【继续用旧通道】有【代价】** |

### ★ 建议：契约加【通道版本条款】

```
★ ① v1.2 信封是【唯一【被推荐】的格式】（★ 自某日起）
★ ② 旧格式卡【仍可读】—— ★ 不破坏既有数据
★★ ③ 但【旧格式卡计入信封率的分母】⇒ ★★ 于是「继续用旧通道」会【自动拉低自己的信封率】
★ ④ 并给一个【弃用日】：★ 该日后旧格式卡【只读不回】
```

> ★★★ **⇒ 那样不靠【禁令】，靠【读数】—— ★ 因为禁令需要人去执行，★ 而读数自动生效。**

## §5 担忧②：无法签署怎么办？

> ★ 您问：★「或者无法签署？」

### ★★★ 答案：**那正是明鉴今晚教我的那个区分 —— 而它已落成代码**

| ★ | ★ |
|---|---|
| **今晚的实例** | ★ 管理器网页写的卡 ⇒ ★ 显示为 `unattributed(systemgraph-gui)` |
| **★ 真相** | ★★ **那类卡【本来就没有会话身份】**（★ 人在网页上点出来的） |
| **★★ 明鉴的处置** | ★★ **「不是补一个身份，而是【声明这一类本来就没有身份】」** ⇒ ★ 加 `writerKind:"ui"` + `writerNote` |
| **★★★ 而本线已实现** | ★★ **`declared-no-identity` 第三态**（★ `D-370`）—— ★ **它【合法】，不是缺陷** |

### ★ 故契约里该有【三种写者】而非两种

| ★ 写者 | ★ 契约要求 |
|---|---|
| **智能体会话** | ★ **须带 `X-Writer`（会话身份）** |
| ★★ **无身份的写者（UI/定时器/脚本）** | ★★ **须带【类别声明】`writerKind` + `writerNote`** |
| **两者都无** | ★★ **违约** ⇒ ★ **计入违约数** |

> ★★★ **⇒ 关键：★ 契约不该要求「所有人都签署」—— ★ 那会逼出一个【编造的签名】。**
> ★★ **而「无法签署」本身**就是一个**必须声明的事实**。

## §6 担忧③：签署登记板 + 强制回复 + 限制回复范围

> ★ 您问：★「有没有一个【签署登记板的逻辑】强制要求回复，并限制回复范围？」

### ★★★ 答案：**本仓【已有全部零件】，缺的是【把它们组装成一条链】**

| ★ 零件 | ★ 已存在 | ★ 位置 |
|---|---|---|
| **① 登记板** | ★ ✅ | ★ `data/registry/`（★ 黑板上的命名空间） |
| **② 卡必带收件人** | ★ ✅ | ★ `bb_card_send` 的 `to` **必填** + 收件人校验 |
| **③ 回复范围限制** | ★ ✅ | ★ 契约 `§4` 的 **R-1…R-5**（★ 已有） |

| **★★ 缺的是** | ★★ **把 ①…⑤ 串成【一条签署链】** | ★ |

### ★★★ 建议：契约 `§6` 新增【签署登记板规格】

```
★ 6.1 登记键
   data/onboarding/<device>/<yyyymmdd>-signoff     ← ★ 每设备一卡,一签一卡

★ 6.2 卡内必填（★ 缺一即视为【未签】）
   - device          ← ★ 设备名（★ 须与 §5.1.1 的登记一致）
   - contractVersion ← ★ 签署的契约版本（★ 如 "v1"）
   - signedAt        ← ★ 时刻
   - writerKind      ← ★ "agent" | "ui" | "script"  ← ★★ 三类
   - X-Writer        ← ★ 若 writerKind=="agent" ⇒ 【必填】
   - evidence        ← ★ 举证（★ 复跑命令 + 输出摘要）
   - scope           ← ★★ 【回复范围声明】—— 见 6.4

★ 6.3 强制回复
   ★ 用 bb_card_send 发 key 与 6.2 模板给各设备
   ★★ 而【收到不代表签了】—— ★ 只有【登记键出现】才算签
   ★★★ 超期（默认 30 日）⇒ onboarding-conformance 报 STALE

★ 6.4 ★★ 限制回复范围（★ 那正是您问的）
   ★ 契约对签署卡的【回复】规定：
     - 只接受【同为 signoff 形态】的卡（★ 不接受自由文本）
     - 回复须引【被签的登记键】（★ 防伪造对签）
     - ★★ 回复【不得】要求对方改代码/给凭证（★ 那是越界）
   ⇒ ★ 即：★★ 【回复通道是窄的，只够确认签或不签】
```

### ★★★ 而"强制"的实现方式（★ 三层）

| ★ 层 | ★ 手段 | ★ 强度 |
|---|---|---|
| **① 读数** | ★ **未签 ⇒ `I-4` 报 `SKIP`/`FAIL`** | ★★ **不靠人执行** |
| **② 代价** | ★ **未签设备的卡【信封率】上不去**（★ 见 §4） | ★★ 自动 |
| **③ 门** | ★ **契约签署前，`bb_card_send` 对未签设备【加提示】** | ★★ 可选（★ 需改工具） |

> ★★★ **本线倾向【①②】，★ 不倾向 ③** —— ★ 因为**门要改别人的工具**，
> ★ **而读数与代价【不需要任何人配合】。**
