# SystemGraph 写协议 v1（P4 · R8 并发互斥）

> **出件**：明鉴 v3 · 2026-10-12 · 对应迭代规划 **P4 = R8 并发与同源互斥**
> **规划原话**：「多人/多 AI 真开始写之后，冲突才会真实发生；★ **但协议要先定，不能等出事再补**」
> ★ 本件**不宣布任何事项已闭合**。

---

## §0 一句话

> **两层分工：乐观锁是【机械保证】（拦得住），R001 红绿灯是【协作预防】（不必拦）。**
> ★ **两层都要** —— 只靠协作 ⇒ 总有会话不守规矩；只靠乐观锁 ⇒ 每次冲突都要重试、成本高且体验差。

---

## §1 第一层 · 乐观锁（**机械保证**，在写端点内实现）

### 1.1 为什么是乐观锁而不是悲观锁
★ **被写对象是黑板键**（`data/sg-page/*` · `data/sg-graph/*`），历史 **append-only**。
乐观锁 = **只在提交时校验**，不需要长期持锁 ⇒ 与「多 AI 各自随时可写」的使用形态匹配。

### 1.2 契约：`expected_seq`

```json
POST /api/write
X-SG-Principal: <session-id>
{
  "verb": "page.set_field" | "page.add_block" | "page.rollback"
        | "relation.add_edge" | "relation.remove_edge" | "relation.restore_edge",
  "target": "page:<view>" | "graph:<name>",
  "payload": { ... },
  "expected_seq": <int>        // ★ 可选，但【建议一律带上】
}
```

| 情况 | 行为 |
|---|---|
| **不带 `expected_seq`** | 视为「我知道可能冲突，我接受」⇒ 按当前 seq 直接追加。★ **向后兼容**（P2/P3 的调用不受影响） |
| **带上且与当前 seq 相等** | ✅ 正常追加 |
| **带上但不相等** | ❌ **409 Conflict**，返回体含 **当前 seq 与当前状态**，供调用方重取后重试 |

### 1.3 冲突响应（**必须可重试，不能只说"失败了"**）

```json
{ "ok": false, "code": 409,
  "reason": "★ 冲突：expected_seq=3 但当前为 5",
  "conflict": { "expected": 3, "actual": 5 },
  "current": { ...当前状态... }     // ★ 让调用方不必再发一次读
}
```

★ 这与本晚的一条教训一致：**拒绝也要把「为什么」和「现在是什么」给足**，否则调用方只能猜。

## §2 第二层 · R001 红绿灯（**协作预防**，复用既有机制）

### 2.1 资源命名（★ 与写端点的寻址同名）
| 被写对象 | R001 资源名 |
|---|---|
| 页面 | `sg-page:<view>` |
| 关系图 | `sg-graph:<name>` |

★ **同名不是为了好看** —— 是为了让「谁在写什么」在**两套机制里是同一个词**，便于对账。

### 2.2 协作流程（写者自觉遵守）
```
1. agent_light(sg-page:<view>)      → 绿 ⇒ 直接写；红 ⇒ 进 2
2. agent_lock(sg-page:<view>, wait=true, ttlSeconds=300)
3. 写（带上 expected_seq）
4. agent_unlock(sg-page:<view>)
```

### 2.3 ★ 为什么仍需乐观锁
★ **R001 是协议，不是内核** —— 任何会话都可以不查灯直接调写端点。
⇒ **乐观锁是最后的防线**：不守规矩的写会**撞上 409**，而不会**静默覆盖**。

## §3 边界与不做的事（★ 不美化）

| 项 | 说明 |
|---|---|
| **单一写路径** | 后端**只有** `do_POST` → 动词层这一条写路径；★ 无旁门（`do_GET` 未改、无第二写端点） |
| **不做「服务端排队」** | 冲突返回 409 由**调用方**决定重试策略；★ 服务端不替调用方等 —— 否则一次慢写会占住线程 |
| **不做「自动合并」** | 两个写同一字段 ⇒ **后到者拿 409**，不尝试 3-way merge（★ 自动合并会把「谁改的」搅乱） |
| **TTL** | 建议 `ttlSeconds=300`；★ **不用 0（不过期）** —— 会话崩掉会留下永久红锁 |
| **未授权写** | 仍是 **403**（R2），**与 409 是两回事**：403 是「你不能写」，409 是「你能写但晚了」 |

## §4 验收判据（P4 的「双写一成一败」）

| # | 判据 | 测法 |
|---|---|---|
| **1** | 并发双写，**恰一个 200、一个 409** | 两个请求带**同一个** `expected_seq` |
| **2** | 409 的响应体**含 actual seq 与当前状态** | 检查响应字段 |
| **3** | 拿新 seq 重试 ⇒ **成功** | 重试应 200 |
| **4** | 不带 `expected_seq` ⇒ **仍可写**（向后兼容） | P2/P3 的调用不受影响 |
| **5** | 403 与 409 **不可混** | 未授权写应仍 403 |
| **6** | ★ **冲突也留痕** | 审计日志须记 409 |
