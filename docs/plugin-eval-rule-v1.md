# 新插件评估规则 v1.0（独立 vs 纳入已有）

> 2026-08-29 ｜ 用户确立：新插件需求必须与现有插件对比，避免重复浪费资源
> 关联规则账本（新增规则 R009）+ 插件评估工具（plugin-eval-cli）

---

## 一、原则

**任何新插件需求，先评估「独立插件」还是「纳入已有子插件」**，给出定位给用户评估——用户有足够判断依据，避免重复造轮子。

## 二、评估流程（5 步）

```
1. 需求解析：新插件要解决什么问题（功能/能力/领域）
2. 现有插件对比：扫描插件目录（自有 + 社区 + 官方），找功能重叠/相邻
3. 判定矩阵：
   - 功能唯一（无重叠）→ 独立插件
   - 功能相邻（同一领域不同能力）→ 纳入已有（子插件/子命令）
   - 功能重叠（完全重复）→ 复用已有（不新建）
4. 定位输出：给用户对比表 + 建议（独立/纳入/复用）+ 理由
5. 用户决策 → 按 R006（插件化 9 项标准）执行
```

## 三、判定矩阵

| 场景 | 判定 | 理由 |
|------|------|------|
| 功能唯一（新领域，无重叠）| **独立插件** | 领域隔离清晰 |
| 同一领域，能力补充 | **纳入已有**（子插件）| 避免碎片化 |
| 功能重叠（重复）| **复用已有** | 不造轮子 |
| 横跨多领域 | 独立 + 依赖规划 | 模块化 |

## 四、对比维度

| 维度 | 说明 |
|------|------|
| 领域 | 新插件 vs 现有的 domain 重叠度 |
| 能力 | 功能重叠/相邻/补充 |
| 依赖 | 是否可复用现有服务（agentBus/黑板/knowledge）|
| 生态 | 官方/社区是否有同类（不重复发明）|

## 五、输出格式（给用户）

```
【插件定位评估】<新插件名>
- 需求: <要解决的问题>
- 现有对比: <最接近的 N 个插件 + 重叠度>
- 判定: 独立插件 / 纳入 <已有插件> / 复用 <已有插件>
- 理由: <证据>
- 建议: <推荐路径 + 备选>
【请用户决策】
```
