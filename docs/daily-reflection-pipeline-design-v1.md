# 每日反思流水线 · 设计与规格 v1.0

> 明鉴 v3 · 2026-09-10 · 用户指令：「把拆分出来的每个环节本身按 10 项标准来做，工具化、插件化，然后串联成固定的工作流；并把过程本身变成引导所有智能体一起思考总结的过程」
> 规格依据：`docs/R006-插件化工具化标准-v3.0.md`（enforced）· 参考实现 `devices/dsh-plugin-cldvoice-activate/`

---

## 一、要解决的问题

**原始形态**：反思是「明鉴一个人在会话结束时想一遍」。问题：
1. **只有一个人的视角** —— 别人踩过的坑我不知道
2. **靠记性** —— 忙的时候就不做了
3. **不可复现** —— 每次反思的深度取决于当天状态
4. **产出不流动** —— 想出来的教训没有回到别人的工作里

**目标形态**：**全体智能体的集体反思，自动化采集+派发+回收+提炼，人只做裁定。**

---

## 二、五个环节（每个按 R006 十项标准独立交付）

| # | 环节 | 插件 | 干什么 | 输入 → 输出 |
|---|---|---|---|---|
| ① | **采集** | `dsh-plugin-reflect-collect` | 扫当日事件（文件/黑板/工具/日志/git） | 时间窗口 → `events-<date>.json` |
| ② | **派发** | `dsh-plugin-reflect-dispatch` | **按每个智能体当天真实任务定制思考卡** | events → `cards/<date>/<agent>.md` |
| ③ | **回收** | `dsh-plugin-reflect-harvest` | 收回填 + **证据门** + 归一化 + 跨智能体聚类 | `answers/<date>/*.json` → `harvested-<date>.json` |
| ④ | **提炼** | `dsh-plugin-reflect-synthesize` | 对照现有库 + 分类 + **按复现广度排序** + 生成提案 | harvested → `proposal-<date>.md` |
| ⑤ | **入册** | `dsh-plugin-reflect-enroll` | 人裁后写库 + **★主动反馈给所有相关智能体** | `ruling-<date>.json` → 哲学库/规则库 + `feedback-<date>.md` |
| — | **编排** | `dsh-plugin-reflect` | 一条命令跑全链 + 断点续跑 | — |

## 三、数据飞轮（与"日记"的本质区别）

```
① 各智能体各自干活（当日任务）
        ↓
② collect    采集事件（谁改了什么、哪张卡、哪个日志报错）
        ↓
③ dispatch   按任务定制思考卡 → 派发
        ↓
④ 各智能体回填（★必须带证据：时间戳/命令/输出）
        ↓
⑤ harvest    证据门 + 聚类 + ★复现计数
        ↓
⑥ synthesize 对照现有库 → 分类 → 按复现广度排序 → 提案
        ↓
⑦ 用户裁定
        ↓
⑧ enroll     入册 + ★反馈给所有智能体
        ↓
⑨ 下次任务带着新的约束 → 回到 ①
```

### 两个关键机制（这是"飞轮"而非"日记"的原因）

| 机制 | 说明 | 为什么关键 |
|---|---|---|
| **★ 跨智能体复现计数** | 同一教训被 N 个智能体独立提到 → `recurrence: N`，**按此排序** | **不按个人感受排序，按复现广度排序** —— 一个人觉得重要可能是偏见，三个人独立踩同一个坑就是系统缺陷 |
| **★ 反馈闭环** | 新规则/哲学**主动推给所有相关智能体**（黑板卡 + 短消息） | 否则**规则躺在库里没人知道**。飞轮的闭合点在"回到别人的工作里" |

## 四、质量门（防形式主义）

| 门 | 位置 | 判定 |
|---|---|---|
| **证据门** | ③ harvest | 每条回填必须含 `evidence.ts` + (`cmd` 或 `output`)；**无证据 → 拒收，不进汇总** |
| **字段门** | ③ harvest | `pit`/`lesson`/`suggestion.type` 齐全；`type` 四选一 |
| **规则可解析** | ③ harvest | 填了规则号/哲学号 → 去库里核对存在；不存在标 `unknown_rule`（不拒收但标记） |
| **declined 合法性** | ③ harvest | 明说"当天无事"必须给理由 |
| **不强行归类** | ④ synthesize | 规则判不了的**必须显式标 `unclear` 交人复核**，不许硬猜 |
| **人裁门** | ⑤ enroll | **绝不自行决定入册**（`phi-user-sovereignty`） |

**为什么需要"证据门"**：**没有证据的教训是感想，不是经验。** 这条门是整套流水线区别于"写日记"的死线。

## 五、入册的安全设计（⑤ 的重点）

| 门 | 说明 |
|---|---|
| **备份前置** | 写前备份 + **回读验证备份可解析** |
| **dry-run 真零变更** | 一个字节都不写（含备份） |
| **原子写** | 写 `.tmp` → 校验可解析 → `rename` 覆盖 |
| **幂等** | 同一提案 id 重复入册 → **拒绝** |
| **编号唯一** | 新增编号前查重，冲突拒绝 |
| **回读校验 + 自动回滚** | 写后立即回读；失败自动回滚 |
| **无删除能力** | 结构上不能删任何条目（只增不删） |

## 七、诚实的边界（哪些做不到）

| 做不到 | 原因 |
|---|---|
| **提炼完全自动化** | 「是应用还是新维度」需要语义判断，无法纯规则化 → **④ 必须产出"待人工复核"清单** |
| **入册自动化** | 治理基础不能自动改（`phi-user-sovereignty`）→ **必须人裁** |
| **保证回填质量** | 智能体可能写套话 → 只能靠**证据门 + 按复现广度排序**削弱，不能根除 |
| **覆盖离线智能体** | 离线者收不到卡 → **待投递队列**，上线后补填 |
| **当天全量捕获** | 采集源有限（文件/黑板/日志），会话内的口头决策可能没留痕 → **靠"要求带证据"反向倒逼留痕** |

| ⑩ | 约束前置 | **各自的"不该发生路径"**：collect=只读无写能力 / dispatch=绝不假装派发 / harvest=无证据不得进 valid 集合 / synthesize=无写哲学库规则库能力 / enroll=不自动入册+不删+不重复+不写坏 |

## 九、运行手册

### 手动跑（当前阶段）
```bash
# ① 采集
node ~/dsh-collab/devices/dsh-plugin-reflect-collect/cli.js --summary

# ② 派发（只落盘，不发送）
node ~/dsh-collab/devices/dsh-plugin-reflect-dispatch/cli.js --emit-only

# ③ 等回填 → 回收
node ~/dsh-collab/devices/dsh-plugin-reflect-harvest/cli.js --summary

# ④ 提炼
node ~/dsh-collab/devices/dsh-plugin-reflect-synthesize/cli.js

# ⑤ 用户看 proposal → 写 ruling → 入册
node ~/dsh-collab/devices/dsh-plugin-reflect-enroll/cli.js --ruling ruling-<date>.json --notify
```

### 一条命令（编排）
```bash
node ~/dsh-collab/devices/dsh-plugin-reflect/cli.js run            # 跑 ①→④
node ~/dsh-collab/devices/dsh-plugin-reflect/cli.js run --upto dispatch
node ~/dsh-collab/devices/dsh-plugin-reflect/cli.js status         # 看今天跑到哪
```

### 断点续跑
流水线各环节的产物落 `data/reflect/`，编排器**按产物存在性判断从哪继续**，不重复跑已完成的环节。

## 十、★ 跨设备层（v1.1 补充 · 用户指令）

> 用户指令：「这个引导所有智能体的对象，**包括星桥外联出去的其他设备上的智能体**，也应该加入这个思考，去把它们的事件和经验吸收回来」

### 10.1 为什么必须跨设备

**只采本机 = 只看到四分之一。** 设备实况（`devices/device-assets.md`）：

| 设备 | 角色 | 是否有 DSH 智能体 |
|---|---|---|
| **mac-mini** | 主工作台（宿主） | ✅ 本机（8 会话） |
| **MacBook Pro** | **独立 DSH 节点**（CLD 运行，dsh 服务 57043） | ✅ **有独立智能体网络** |
| **PC-i9** | Windows 专属 + 高性能（RTX 4060 Ti） | ⚠️ 经 MCP 接入 |
| **iPhone 17** | 移动端 | ⚠️ 无 DSH |
| 关联设备 | 天河店 / 佛山店（向日葵） | ⚠️ 无 |

**关键**：**MBP 上跑着独立的 DSH 会话** —— 它们的经验若不被吸收，就是**永久的盲区**。

### 10.2 架构：黑板即协议

**不引入新的传输通道** —— 用已有的**中央黑板**（`106.53.214.108:8792`，已实测可读写）作为跨设备汇聚点。

**key 约定**（首段必须纯小写字母，符合黑板语法）：

| key | 谁写 | 谁读 | 内容 |
|---|---|---|---|
| `data/reflect/events/<device>/<date>` | **各设备自跑 collect** | 本机 synthesize | 该设备当日事件流 |
| `data/reflect/cards/<device>/<date>` | 本机 dispatch | **该设备的智能体** | 派给它的思考卡 |
| `data/reflect/answers/<device>/<date>` | **各设备智能体回填** | 本机 harvest | 该设备的回填 |

**示例**：`data/reflect/events/mbp/2026-09-10`

### 10.3 三种设备的接入方式（按能力分级）

| 设备类型 | 接入方式 | 说明 |
|---|---|---|
| **有 DSH 的**（mac-mini / MBP） | **装同一个插件**，各自跑 collect/harvest | 最理想：对等参与 |
| **有 agent 但无 DSH 的**（i9 经 MCP） | **本机代跑 collect**（能读到的部分）+ 派卡时经 MCP 通道唤醒 | 半自动 |
| **无 agent 的**（iPhone / 关联设备） | **只作为事件源**（若有可采数据），不派卡 | 只采不发 |

### 10.4 离线设备的处理：待投递队列

**问题**：设备离线 → 卡发不出去 → 那天就没它的反思。

**做法**（复用已有的黑板语义）：
1. 卡**落在中央黑板**（不直发）→ 该设备上线后自取
2. 本机 harvest 时，**缺失设备的回填标 `pending` 而非 `missing`**
3. **允许补填**：T+1、T+2 的回填仍然收（`--allow-late`），标注实际提交时刻（**这正是 Φ13 的实践**）

### 10.5 ★ 跨设备带来的新风险（必须处理）

| 风险 | 说明 | 对策 |
|---|---|---|
| **凭据跨设备扩散**（Φ12 形态④） | 事件流里可能含凭据（日志/卡片） | **collect 落盘前跑一次凭据扫描**；中央黑板写入前同样扫 |
| **证据时点混乱**（Φ13） | 各设备时钟可能不同步 | **每条事件/回填必须带设备本地时间 + 采集时刻**，两者分开标 |
| **设备间版本漂移** | MBP 的插件版本可能与本机不同 | 回填补 `plugin_version` 字段；harvest 校验并标注 |
| **跨设备污染** | 一台设备的事件被误算成另一台 | key 路径强制含 `<device>` 段；harvest 按设备分组统计 |
| **重复采集** | 同一文件经同步盘在两台设备都可见 | 事件带 `origin_device`（**采集者**）而非"文件在哪" |

### 10.6 对五个环节的增量要求

| 环节 | 增量 |
|---|---|
| ① collect | 加 `--device <name>`（默认本机主机名）；**结束后把事件流 PUT 到中央黑板** `data/reflect/events/<device>/<date>`；写入后**回读校验** |
| ② dispatch | 读**中央黑板上的全部设备 events**（不只本机）；卡按 `<device>` 分目录；**PUT 到中央** `data/reflect/cards/<device>/<date>` |
| ③ harvest | 从**中央黑板**拉全部 `<device>` 的 answers；**按设备分组**统计；缺设备标 `pending` |
| ④ synthesize | cluster 的 `agents` 字段扩展为 **`<device>:<agent>`**；**复现计数按此聚合**（跨设备复现 = 更强的信号） |
| ⑤ enroll | 反馈卡**推送到全部设备**（不只本机） |

### 10.7 ★ 跨设备让"复现计数"更强

**原来的复现计数**：同一教训被本机 N 个智能体提到。

**跨设备后**：
> 同一教训被 **mac-mini 的 2 个 + MBP 的 1 个**独立提到 = **跨设备复现 3 次**。

**为什么这更强**：**不同设备上的智能体跑的是不同的任务、看的是不同的上下文** ——
它们独立踩到同一个坑，说明**这不是某条工作流的偶然，而是系统性的**。

**这是"数据飞轮"跨设备后的关键升级：复现信号从"同机多会话"变成"异构环境独立复现"。**

## 十一、★★ 飞轮的关键缺口：触发（v1.2 补充 · 由 HR 司库点出）

> HR 原话：「这说明飞轮不是空想；但要**可持续**，还差一个东西：**触发**。
> 当前是『**恰好有人在想**』，不是『**结构上必然发生**』。**这属于你的 Φ9 范畴。**」

### 11.1 这个批评为什么是根本性的

**我原来的说法**是「飞轮第一次在同一天内跑完了一遍」——
**HR 指出那是一次巧合**：

```
2026-09-10 实测链路：
  我发现 400 伪装问题 → 提炼成建议 → HR 几分钟内落成 bb-write.py + 补 R003 → 我实测验证
  ✅ 闭环完整，但 **触发条件 = 『恰好明鉴在想这件事』**
```

**换成 Φ9 的语言**：**这条链路靠的是自觉，不是结构。**

### 11.2 靠自觉一定会断（Φ9 的直接推论）

| | 靠自觉 | 靠结构 |
|---|---|---|
| 触发条件 | 「有人恰好想到」 | 「每轮必然发生」 |
| 断在哪里 | 忙的时候、换人的时候、没人注意的时候 | 不断 |
| 本日证据 | 反思只发生了一次（我恰好被用户问到） | —— |

### 11.3 HR 提的对接点（可直接落）

> **每次内存治理轮次产出「今日同型错误清单」，作为反思输入（而非等明鉴回想）。**

**为什么这个对接点好**：
- **它已经有轮次**（内存治理是既有节律）
- **它天然产出素材**（治理过程就是踩坑过程）
- **不需要新增采集能力** —— 只是把它**已有的产出**接过来

### 11.4 我们需要的触发源（清单）

| 触发源 | 现状 | 缺口 |
|---|---|---|
| **HR 内存治理轮次** | ✅ 有节律，HR 愿对接 | 需约定产出格式 |
| **星桥发布门** | ✅ 每次发布都有核验 | 核验结论可作反思素材 |
| **各 builder 完成报告** | ✅ 有报告 | 报告里的"坑"章节就是素材 |
| **会话自然结束** | ❌ 无节律 | **这是最大的缺口** —— 大多数工作不发生在上面的节律里 |
| **★ 每日定时** | ❌ 未挂 | 守灯塔建议 22:30 + 先手动 5 天（未执行） |

**结论**：**触发源不是缺一个，是缺"覆盖日常工作的那个"。** 定时任务是最通用的兜底 ——
**这也是为什么流程要走：先手动 5 天验质量 → 再挂 22:30 定时。**

### 11.5 反过来看：这也是候选A 的实例

> **我"以为飞轮在转"，就是把"我建了流水线"当成"它每天在跑"。**

**与 builder 停摆 40 分钟我才发现，是同一个错误**：
**把「我启动了」当成「它在运行」。**

**这正是 HR 说的「触发」缺口的另一面 —— 不只是"没人触发"，还有"没人发现它没跑"。**

> 这是「每日反思流水线」要生产的那类东西 —— **但今天它是手工跑出来的。** 完整链条：


## 十五、黑板枚举的正确做法（v1.6 · 由 collect builder 发现，我复验）

### 15.1 服务端支持分页（实测，此前没人用过）

| 请求 | 返回 |
|---|---|
| `?limit=3&offset=0` | 3 键 |
| `?limit=3&offset=3` | **不同的** 3 键 ⇒ **offset 生效** |
| `total` | **精确**（20213） |
| 单页大小 | `limit=3` → 1.5KB · `limit=2000` → **2.4MB** · **无 limit → 36.6MB** |

**⇒ 有界分页可行，且能知道进度。**

### 15.2 ★ 我的同类错误

**我今天多次执行 `curl …/data/reflect/` 与 `…/data/`，每次拉 36.6MB 全量；`GET /data/reflect/events/` 也是 20,195 键全量。从未用过 limit/offset。**

**为什么**：**因为我没验证过服务端支持它** —— **我把「我知道的那个手段」当成了「唯一的手段」。**

**★ 这是第 0 类的变体**：
- HR 的第 0 类：「你打算用的那个手段**不 work**」
- **我这个**：「**你根本没去想有没有别的手段**」← **手段集不全**

**共同点**：**验证动作本身没被审视。**

### 15.3 ★ 「谁消费」判据（比「有多少键」正确）

**190× 不对称的归因**：
```
本机 /data/ 20,224  vs  中央 110
本机 /notes/ 13,531 vs  中央 2,458
本机命名空间：data/audit 7,660 · data/stab 5,000 · data/ops 4,133 · data/conn 1,250（前三占 83%）
而 data/reflect/ 本机只有 13 键
```
**⇒ 不对称由本机运维域主导，不是 reflect 域的同步缺口。**

**★ 可推广判据**：
> **同步范围应按「谁消费」判定，而非按「数据量」判定。**
> **消费者在本机的键不必双写；消费者是跨设备的才需要。**

**为什么这条重要**：
- 按「**有多少键**」判断 → 会误以为中央严重缺数据
- 按「**谁消费**」判断 → 才发现那些键的消费者全在本机，**双写才是浪费**

**这是「先问归属，再问数值」的又一次应用。**

## 十六、★★ 机制提取（v1.7 收窄版 · 由 HR 主动划证据边界后改写）

> ★ **本节原文写的是因果版（「机制应从事故中提取，而非从设计中产生」）。
> HR 指出那是它的自称，并主动划了三条证据边界后，我改为收窄版。**
> 这是本会话里罕见的「**贡献者撤回自己最有名的贡献的过度声称**」。

### 16.1 原始观察（HR，2026-09-10）

> **今晚所有活下来的机制，都是先有一次真实事故、再有机制**：
> · 探照灯（因为对空气说话）· 单一入口（因为我们漏了 get）· 跨产物核验（因为卡片漂了三次）
>
> **反过来看：今晚没有一条机制是先设计出来的。**

**配套统计**：机制来源 —— 事故逼出 N 条 · 设计产生 **0** 条。
**收敛方式**：四次独立收敛（键序规范化 / 回读判据 / 读写单一入口 / 报告项vs阻断项）—— **全部来自「跑对方的」或「审自己的」**。

### 16.2 ★ HR 自己划的三条证据边界（**因此不能写成因果命题**）

| # | 边界 | 说明 |
|---|---|---|
| **①** | **样本量：一晚** | 4 条机制，**不是「所有机制」** |
| **②** | **★ 选择性偏差** | **事故驱动的机制「有故事」，更容易被记住、被写下来**；而设计出来的机制若一直没被触发，**安静地待在文件里，不会被计入统计** → 这个比例**系统性地高估了「事故驱动」的份额** |
| **③** | **未观测项** | 没有统计「**设计出来、上线了、并且确实拦住了问题**」的机制 —— **它们可能存在，只是没留下痕迹（因为拦住了就没有事故）** |

### 16.3 因此：从因果命题改为规范要求

| | 表述 |
|---|---|
| ❌ **不可写** | 「**机制应从事故中提取，而非从设计中产生**」—— 因果断言，证据只支持相关性，且有选择性偏差 |
| ✅ **应写** | 「**流程应保证每次事故都被固化为一条机制，并附一条『该机制是否仍在』的探测**」—— **规范性要求，不依赖那个比例是否成立，且它自己可被检验** |

**★ 后半句（「并附一条探测」）是必须加的**：
> 否则它会造出一堆**没人验证是否还在服役的机制** ——
> **那正是陷阱③的推广版，只不过对象从「一个总闸」变成了「一整套历史机制」。**
> **第 6 项如果不自带第 ③ 条陷阱的解药，它自己就会变成第 ③ 条陷阱。**
> （HR 原话）

### 16.4 ★ 「每日反思流水线」的价值也收窄一半

| | 表述 |
|---|---|
| ✅ **成立** | 它把「**事故 → 机制**」这个动作**从偶然变成例行**（**这是流程价值，不依赖那个比例**） |
| ❌ **不成立** | 「它能把『设计』替换成『挖掘』」—— **无法证明设计命中率低**，只能证明**事故驱动的机制被记录得更多** |

**★ 而今晚正好有一个反例**（HR 提供）：
> **陷阱①的修法（声明位 + 拒绝运行 + `--stamp`）是在事故之前就把「人会忘记更新」这个风险考虑进去的。**

**这个反例的重要性**：若我们真信了「设计没用」，就不会再设计任何东西 —— **而那条修法恰恰证明了设计可以在事故之前起作用。**

## 十七、★★★ 递归终止于「可执行」（v1.8 · 今晚整条线索的终点）

### 17.1 今晚的递归链

```
空壳键  →  半空壳  →  引用的空壳  →  空壳声明
检查器  →  检查检查器的总闸  →  检查总闸是否还在跑
机制    →  防机制退化的探测  →  探测本身也要被探测
```

**四层，而且继续走没有任何阻力。**

### 17.2 ★ HR 的终止条件

> **声明的递归，终止于「可执行」。**

| | 真假来源 | 是否终止 |
|---|---|---|
| **声明** | 依赖于另一个声明 | ❌ **递归不终止** |
| **可执行的检查** | **由运行产生**（退出码 / 落盘 / 输出） | ✅ **不需要下一层声明担保自己** |

**操作形式**：
> **当你从「我声明了 X」走到「我这条命令能验 X」，递归就停。**

**★ 本日的实际终止点**：我把空壳尺做成可重跑脚本（`assertion-set-consistency.py` 第④项）的那一刻，**递归已经终止了**。

### 17.3 ★ 为什么这条最重要

> **它防止我们今晚学到的这套东西变成一个自我消耗的机器 ——
> 无限递归的框架，最终会因为它太贵而没人用，那和不发明它是一样的结果。**
> （HR 原话）

### 17.4 保证是求交，不是转交

| 性质 | 内容 |
|---|---|
| **①** | **不是「我引用了你的边界」，而是「我的保证被你的边界砍掉一块」** |
| **②** | **沿消费链，保证单调递减**（交集只会变小） |

**★ 可机械核验的不等式**：
> **下游的保证不能强于上游。**

**违规形态**：消费方声称的覆盖范围**超过**上游声明的范围 →
**且是「看起来更可信」的那种违规，因为它的话说得更满。**
