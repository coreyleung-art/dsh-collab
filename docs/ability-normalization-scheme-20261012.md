## §3 ★ 归属边界（为什么我只出方案、不改数据）

- `abilities` / `resources` **写在每个会话自己的 `agent_profile` 里**，是**该会话的自我登记**
- **修改他人档案 = 改他人件** —— 本网络的既有纪律（S3 / 不改对方件）**不允许我单方面做**
- ⇒ 归一化必须走：**① 立词表（可共同制定）→ ② 各属主自映射 → ③ 机械校验（可共跑）**
- ★ 例外：**词表与校验器**本身是我的产物，可以我做

## §4 归一化方案（三层）

### L1 · 受控词表（taxonomy）
把能力收敛为 **`域/对象/动作`** 三段，段内取值**受控**：

```
域    ∈ { 运维, 开发, 数据, 治理, 通讯, 业务, 语音, 发布 }
对象  ∈ { 本机服务, 黑板, 插件, 会话, 仓库, 蓝图, 知识库, 设备, 文档, 模型 }
动作  ∈ { 读写, 建, 改, 删, 查, 诊断, 编排, 审计, 发布, 归并 }
```

例：
| 原文（散文） | 归一化 |
|---|---|
| `系统健康巡检（内存/swap/磁盘/服务探针）` | `运维/本机服务/诊断` |
| `黑板落卡双写双回读（含写端 Bearer 鉴权）` | `通讯/黑板/读写` |
| `R006 十项逐项机械审查` | `治理/插件/审计` |
| `插件静态打包（tsc+esbuild+profile bundles）` | `开发/插件/建` |

★ **词表必须先冻结再映射** —— 否则边映射边扩，永远收敛不了（同「先定判据再跑」）。

### L2 · 映射表（owner 自映射）
- 形态：`data/registry/ability-taxonomy.json`（词表）+ `data/registry/ability-mapping.json`（`原文 → 归一化`）
- **每个属主把自己那几行映射过来**（一行命令或一张卡）
- ★ **不删原文**：归一化是**追加一个字段**，不是替换 —— 原散文仍有信息量（同「更正要替换不是追加」的反向：这里是**叠加**）

### L3 · 校验器（可共跑，机械）
`scripts/ability-taxonomy-check.py`：
- 词表外的值 ⇒ 红（防「自己造词」把词表冲垮）
- 未映射的原文 ⇒ 黄（未完成）
- 同一 `域/对象/动作` 被多会话登记 ⇒ **这才是真的「可共享能力」**（可据此算出**真冗余/真覆盖**）

## §5 验收判据

| # | 判据 | 三态 |
|---|---|---|
| A1 | 词表冻结且**有版本号** | 成立 / 不成立 |
| A2 | **覆盖率** = 已映射原文数 / 511 | ★ 必须给**分母与截至时刻**（判据：报「0 条」须附扫过的面） |
| A3 | 归一化后**出现 ≥2 次的组合数 > 6**（现状 6） | 这是「词表真的在起作用」的直接证据 |
| A4 | 校验器**有负控**：喂一个词表外的值必须红 | 否则是空转判据 |
| A5 | ★ **不丢信息**：每行原文仍可取回 | 归一化不得成为「信息删除」 |

★ **A3 是关键判据**：如果归一化后仍然几乎全唯一，说明**词表粒度错了**（太细），须回头改词表 —— **而不是宣布归一化完成**。
