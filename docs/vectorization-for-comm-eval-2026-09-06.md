# 通讯层向量化方案评估报告（数据驱动 · HR 成本监察）

> 评估: HR 司库(成本监察) · 2026-09-06 · 命题: 「所有通讯层形成文件, 传输前必须向量化, 传输向量格式文件——是否更省资源?」
> 方法: 本地实测基准(bge-m3 embedding + 黑板消息采样), 非理论推断

═══════════════════════════════════════

## 一、实测数据

| 指标 | 值 | 说明 |
|---|---|---|
| 黑板消息均值 | 368 B | 采样 20 键 |
| 黑板总键数 | 12,024 | 通讯是元数据级 |
| bge-m3 向量 | 1024 维 | JSON 21,277 B / 二进制 4,096 B |
| embedding 延迟 | 2.39 s(首条)/ 0.02-0.04 s(热) | 本地 ollama |
| 向量 vs 原文 | 11x(二进制)/ 58x(JSON) | 膨胀非压缩 |

## 二、语义保真测试(决定性)

| 对比 | 余弦相似度 | 含义 |
|---|---|---|
| 原文 vs 原文 | 1.000 | 基准 |
| 订单#123 vs #456 | 0.847 | 关键数字无法区分 |
| 拒单 vs 接单 | 0.766 | 指令方向模糊 |
| 拒单 vs 拒单+补充 | 0.870 | 细节丢失 |

**结论**: 向量是无损不可逆的——接收方拿向量无法还原精确订单号/金额/指令细节。

## 三、结论: 不能全面替代原文传输(3 硬伤)

1. **不可逆(致命)**: 通讯核心=精确传达(订单号/金额/指令/决策), 向量全部模糊化
2. **体积反膨胀**: 368B→21KB(JSON)/4KB(二进制) = 11-58x, 通讯是元数据级非文档级
3. **延迟**: 2.39s/条 vs 毫秒级实时——实时通讯不可接受

## 四、正确架构(分层)

| 层 | 传输内容 | 向量化用途 |
|---|---|---|
| 通讯层(黑板/agent_send/事件) | **原文**(精确无损) | 不需要向量 |
| 存储层(消息落盘) | 原文 + 同步入向量库 | 未来语义检索/复盘/去重 |
| 检索层(找相关内容) | 向量查库→命中读原文 | 高效定位, 精确读取 |

**现状已做对**: rules-sync.py / guard-recall(104 文档) / 概念字典 semantic / mbp-memory-vectorize —— 都是「原文存储+向量索引」, 非「向量替代原文」。

## 五、真正省资源的通讯优化方向(替代方案)

1. **减量**: R018 防刷屏/10 分钟去重(已做)——减少不必要消息
2. **分级**: STATUS/ACK 走黑板不走消息, v2.3 门禁(已做)——内容按通道权重分流
3. **压缩**: 大文件 zstd 传输(已用于会话/镜像)——体积压缩不损语义
4. **批量**: BATCH 通道合批(已设计)——降请求次数

## 六、向量化的正当场景(勿滥用)

- 语义检索(找相关历史消息/文档) ✅
- 去重/聚类(重复内容检测) ✅
- 复盘/沉淀(消息模式归纳) ✅
- 实时精确通讯 ❌(本文结论)
