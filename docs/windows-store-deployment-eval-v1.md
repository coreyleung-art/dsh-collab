## 二、推荐架构形态

### 首选: B. 门店瘦采集 + 集中管理(分级)

```
┌─ 门店 Windows(每店) ─────────────┐
│ ① Chrome 实例(登录真实门店账号)    │  ← 登录态在门店=风控天然合理
│ ② 轻量采集器(CDP 只读: 订单/告警/  │
│    商品状态) → 定时推黑板           │
│ ③ 无自动化写操作(护栏: 只采不改)    │  ← R026/Lean4: 门店不持写权
└──────────────┬───────────────────┘
               │ 黑板 notes/store-<id>/ (R-ERR4 域规范)
┌──────────────▼───────────────────┐
│ 集中管理层(mac-mini / i9 32G)     │
│ 8787 面板(监控/告警/日报)          │
│ MTM 动作(接拒单/改价) ← 运营代理执行 │  ← 写操作留中枢+人类开关
└──────────────────────────────────┘
```

### 关键设计点
1. **登录态留门店**(Chrome profile 本地), 采集器只读 → 风控最优解(门店 IP+真实设备+常驻)
2. **写权不落门店**: 门店采集器无动作能力(Lean4 门: 结构上不含写原语)——需动作时回中枢由运营执行
3. **数据回流**: 走黑板 `notes/store-<id>/`(R-ERR2 域规范, E2 已有 store 预留)
4. **护栏跨设备**: R026/R027 只在集中层生效, 门店节点=只读传感器

### 补充: C 的适用场景
若某门店无 Windows 或不便装采集器 → i9 集中托管其账号(需评估异地登录风控, 用门店 IP 白名单/代理缓解)

## 三、风险与门

| 风险 | 缓解 |
|------|------|
| 门店员工破坏采集器 | 只读无价值目标 + 凭据不落门店 |
| 门店断网 | 采集器本地缓存 + 黑板离线队列 |
| 登录态失效 | 采集器心跳 + 集中告警(复用 8787) |
| 异地登 i9 风控 | C 形态需门店 IP 代理/白名单评估 |
| 多店管理复杂度 | 复用现有 store:N 面板 + E2 注册表会话级 |

## 四、与现有体系衔接
- 数据流: 门店采集 → notes/store-<id>/ → 8787 聚合(现有架构自然延伸)
- i9 角色: i9(32G Win)=集中算力层或代理执行层(B/C 皆可承载)
- MTM mcp-export: 若产品化, 门店瘦采集=服务商平台的前端数据源形态(呼应四栈)

## 五、MCP 融合视角(用户指示 2026-09-06: Windows 迁移应结合 MCP 服务逻辑)

### 核心洞察: Windows 门店 = 天然的 MCP 边缘节点

B 形态(门店瘦采集) 与四栈 MCP 不是两件事, 而是同一架构的两面:
- **门店 Windows = MCP 客户端节点**(部署拓扑), 不是私有协议终端
- **接入 = E2 注册 + comm-mcp 底座**(栈1) — 门店经 R-ERR4 注册成为 comm 节点
- **能力面 = waimai-mcp-core**(栈2) — 门店采集的数据 = 栈2 的数据源扩展
- **管理 = 中枢 MCP 工具面** — 监控/告警经黑板, 与现有 8787 一致

### 融合架构(修订 B)

```
┌─ 门店 Windows(每店 = MCP 节点) ────────────────┐
│ ① Chrome 实例(登录真实门店账号)                │  ← 登录态留门店(风控最优)
│ ② 门店采集器 = MCP 客户端(E2 注册 + 心跳)      │  ← 节点身份(非裸脚本)
│    - node_register → E2 → node_heartbeat(G5)   │
│    - 只读采集(订单/状态) → bb_write notes/store │
│ ③ 无写原语(lean4 门: 采集器结构不含动作)        │
└──────────────┬────────────────────────────────┘
               │ MCP/黑板(comm-mcp 栈1 底座)
┌──────────────▼────────────────────────────────┐
│ 中枢(mac-mini/i9): waimai-mcp-core(栈2) + 8787 │
│ 门店数据消费 + MTM 动作(回中枢执行 + R027)      │
│ 未来: merchant/ops 产品(栈3/4) 服务商视角       │
└───────────────────────────────────────────────┘
```

### 为什么结合更优
1. **一套协议通吃**: 门店节点/i9/MBP/未来第三方 = 都经 E2 + MCP 接入, 不造门店私有栈
2. **数据即能力面**: 门店采集数据直接成为 waimai-mcp-core 的数据源 → 栈2 能力扩展 = 未来栈3/4 产品数据飞轮
3. **护栏统一**: R-ERR4(身份) + R-ERR2(域) + lean4(门店无写) 全链复用, 不另立门店规则
4. **与妙记1 通讯桥呼应**: 分布式节点 + token 差价逻辑 = 门店节点本就是 MCP 网的一环
5. **演进路径**: 门店 MCP 节点 → 若服务商平台(栈4)落地, 就是天然的"接入端模板"

### 修订后的实施路径
1. 试点(i9 模拟 2-3 店): 门店采集器以 MCP 客户端形态接入(E2 注册 + bb_write 回流) — 验证 MCP 接入而非私有脚本
2. 验证点: E2 注册/G5 心跳/数据回流 lean4 门(无写) 
3. 铺门店: 分发=comm-layer 同款(dsh-tools win 先例)
4. 产品化衔接: 若做服务商平台, 门店节点模板 = 现成接入方案

> 修订: B 形态保持不变, 但其"门店采集器"应实现为 **MCP 节点**(E2+comm-mcp 接入), 而非独立私有脚本 —— 与四栈 MCP 规划统一
