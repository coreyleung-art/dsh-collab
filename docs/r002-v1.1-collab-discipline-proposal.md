# R002 v1.1 补充提案 · collab 广播纪律（2026-08-29）

> 提交人：星桥-mac-mini-协调者
> 状态：待 HR 资源评估 + 用户批准
> 依据：用户指示「把这条纪律固化到通道规范（R002 补充）+ 给 HR 评估是否会造成资源浪费」
> 背景：排查「node 转达消息在 MBP 侧注入」时确认——notes/collab/ 为全局通道，所有端 central-inbox 均监听并注入提示；定向消息（notes/<node>/）仅目标端注入。本提案固化「广播 vs 定向」的选择纪律。

## 一、问题

- 现状：collab 通道消息会注入**所有端**（MBP/i9/中枢），两端同时收 = 广播设计
- 风险：若本应定向的消息误写 collab → 无关端被提示打扰（噪音 + 端侧 token/上下文浪费）
- 需要：明确的写入纪律，区分「全局广播」与「定向投递」

## 二、R002 v1.1 补充条款（草案）

```
R002 v1.1 增补「collab 广播纪律」：

1. **通道选择**（写入前判断）：
   - 全局重要消息（升级指引/规则变更/跨端协作广播）→ notes/collab/（所有端感知）
   - 定向任务/消息（给特定节点或会话）→ notes/<node>/ 或 agent_send（仅目标端）

2. **collab 写入前置检查**（写前自问）：
   - 这条消息**所有端**都需要看到吗？
   - 若否 → 改定向通道（notes/<node>/ 或 agent_send）
   - 若是 → 确认这是「全局协作级」内容，写 collab

3. **广播语义认知**：
   - collab = 全局广播（各端都注入提示，这是设计）
   - 不是「随手一写」的通道，是「需要全员看到」才用

4. **防打扰**：
   - 定向能达的不用 collab（避免无关端提示噪音）
   - 端侧可选择性忽略 collab 噪音（如非本端相关）

5. **评估**：HR 评估本纪律对资源（token/上下文/端侧处理）的影响，确认无浪费后生效
```

## 三、资源影响评估（给 HR 的问题）

请司库（HR）评估：
1. **collab 广播现状的资源成本**：全端注入 = 每端一次 agentBus.send + 上下文注入，是否造成 token/上下文浪费？
2. **本纪律收紧后的资源收益**：定向消息改 notes/<node>/ 后，无关端不再收到提示 → 减少多少噪音/上下文占用？
3. **反向风险**：纪律是否会造成「过度定向」——消息该广播却只发一端，导致其他端错过全局信息？
4. **结论建议**：维持现状 / 收紧 / 折中（如 collab 只写不注入，靠端侧主动查）
