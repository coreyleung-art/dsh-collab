## 1. 类别定义：什么是 System One 模型

**Jev 引入的新类别**。与传统 LLM 的根本差别在**输出契约**：

| 维度 | 传统 LLM | System One |
|---|---|---|
| 输入 | 非结构化序列消息 | **非结构化状态 + 结构化问题** |
| 输出 | 生成的字符串，**需要解析 + 验证** | **类型化结构值**，输出空间**调用前已枚举** |
| 采样 | 逐 token 自回归 | **并行采样**，一次前向出全部判断 |
| 置信度 | 需提示，且"往往过度自信且不一致" | **每次输出都带校准概率** |
| 失败模式 | 幻觉、格式损坏、拒绝回答 | **类型上不可能越界**；但仍可能选错【关键澄清】 |

### 1.1 三种原语（primitives）

| 原语 | 回答什么 | 返回 |
|---|---|---|
| **Choice** | 从 N 个选项选一个 | 选中项 + 每个选项概率 + 置信度 |
| **Score** | 在有序刻度上打分 | 位置（**可落在刻度之间**）+ 每级概率 + 置信度 + 刻度说明 |
| **Noul** | 某陈述是否成立（是/否） | 0–1 概率（**无独立 confidence 字段**） |

### 1.2 "不会幻觉"的准确含义【务必精确】

**官方口径**："类型上不可证伪"。若 Choice 只给 billing/technical/sales 三项，**不可能**返回第四个标签，也不可能类型错误。

**但它不保证正确**：Jev 完全可能选错，也可能给错误答案分配高概率。它保证的只是**不跑到剧本外**。

> 对自动化的意义：在一条有延迟约束、多层依赖的链路里，**一个"越界的答案"比"一个偶尔选错但格式永远合法的答案"危险得多**。

### 1.3 校准置信度：这才是最关键的一环

校准契约（TypeSafe 官方文档）：

- 被赋予 **0.2** 概率的结果，应约 **20%** 的时间发生
- 被赋予 **0.8** 概率的结果，应约 **80%** 的时间发生
- 被赋予 **1.0** 概率的结果应 **100%** 发生

**官方紧接着的诚实声明**：

> "These rates describe **groups of predictions, not a guarantee about any single answer**."

这不是法律对冲，这是校准的定义。一个校准良好的 0.8 **不承诺**这次一定对；它承诺在它标记为 0.8 的所有答案中约五分之四正确。

**两个工程细节**（官方文档）：
1. **置信度是推导量，不是生成量**——模型返回完整概率分布，confidence 是从分布形状算出的统计量；文档明说"若你自己的统计量更合适，你完全可以自行计算"。
2. **RLCD 是唯一塑造权重的东西**——"Jev does not fine-tune or LoRA-adapt on customer data… the same weights serve every account"。**领域适配发生在请求里，不在每个客户的检查点里**。

### 1.4 置信度分档路由（架构级用法）

| 档位 | 系统行为 |
|---|---|
| 高置信度 | 自动执行 |
| 中置信度 | 确认 / 标记复核 / 收集更多信息后再行动 |
| 低置信度 | 不行动——转人工、请求澄清或回退其他系统 |

**官方明说**："Confidence threshold is **not one number**. Different operations in the same system should be gated at **different levels** depending on the consequences of being wrong."

> **为什么"便宜 + 校准"必须成对出现**：假设你要一条流水线自动处理有把握的大多数、把其余升级给更大模型或人。**升级的决定总得来自某处**。如果那个便宜模型对一切都报告 0.98（包括它在猜的时候），这个分支就**无从检验**，你只能全自动或全不自动。只有置信度**有信息量**的模型才能让你安全地自动化一部分——因为它能告诉你**它在哪一部分上不安全**。
>
> 官方原话："**如果一个智能系统——无论是人还是机器——无法表达诚实的不确定性，那么这个系统就不可信。**"

## 2. Jev（闭源源头）

### 2.1 背景

- 创始人 **Diogo Almeida**：前 OpenAI，**GPT-4 / ChatGPT / InstructGPT(RLHF) 论文共同作者**
- TypeSafe AI，**4000 万美元**融资，两年隐身研发，2026-09-15 发布
- 定价：**输入 $0.042/M tokens，输出完全免费**（对比模型输入 $0.20–$10/M，输出约为输入 5 倍）
- 延迟 **70–500 ms**（对比前沿模型端到端 3–329 秒）
- **Doom 演示**：约 10 次决策/秒实时操控，成本约 **$7/小时**
- **Vercel AI Gateway**：上线 24 小时内被近 **13%** 付费团队采用——**该 Gateway 史上最快采用速度**，是 GPT-5.6 系列的 2 倍、Claude Fable 5.1 的 6 倍以上（此前所有新模型满 24h 均未破 7%）
- 未公开权重与架构论文 → 发布两天内社区涌现 **≥6 个克隆项目**

### 2.2 训练方法：RLCD（Reinforcement Learning for Calibrated Decisions）

**TypeSafe 自创术语**，是继 RLHF / RLVR 之后的**第三条路**：

| | **RLHF** | **RLVR** | **RLCD** |
|---|---|---|---|
| 优化目标 | 人类偏好 | 程序可验证的正确性 | **校准**（认知诚实的概率） |
| 输入重点 | 序列消息 | 序列消息 | **结构化程序状态** |
| 输出 | 需解析+验证的字符串 | 需解析+验证的字符串 | **类型化值，输出空间预定义** |
| 采样 | 逐 token | 逐 token | **并行，单次查询生成全部输出** |
| 置信度 | 过度自信且不一致 | 过度自信且不一致 | **每次输出传达置信度与不确定性** |
| 代表产品 | ChatGPT / 市面近乎 100% 主流模型 | 推理模型 | Jev |

**TypeSafe 指认的 RLHF 故障模式**（官方入门指南原文）：

- **谄媚**——模型学会生成评分者想听的内容，与真实目标不同
- **听起来自信的幻觉**——流畅与确定即使毫无依据也被偏好机制奖励
- **模式丢弃**——偏好优化收窄输出分布，"偏向某种特定风格（如指令遵循），同时降低其他可能输出的概率"

> 关键论断："**一个输出可能对人有吸引力，却不足以可靠到用于无人值守的自动化。人类偏好和机器可信度是不同的优化目标。**"

**RLVR 的两重缺口**【这是最有价值的论证】：

1. **可验证奖励需要验证器**，而验证器要求任务有可计算的正确答案。生产系统真正会问的问题——这张工单该转账单还是技术？这笔退款合规吗？这笔交易像欺诈吗？——**没有一个有程序可核查的答案**，且**最重要的情形恰恰是资深人类意见不一的情形**。
2. **给数据集打标签来伪造验证器，会改变目标**：标签编码的是**一个决策**，不是**围绕这个决策的不确定性**。被训练来复现团队判断的模型，会**像那些标签一样自信**——即和写标签的人一样过度自信。
3. **即使有真验证器，还有第二重缺口**：验证器给答案打分，**不给所声明的置信度打分**。一个 95% 正确却对所有案例报告确定性的模型会拿满分奖励，但作为自动化组件**毫无用处**——因为那 5% 才是流水线唯一需要被告知的部分。

> 官方原话："**如果一个模型有 95% 的时间能完成某项任务，却不说自己何时处于那 5% 之中，它就无法自动化那项任务。**"

### 2.3 从外部反推的 Jev 架构【最精彩的一段实验】

因权重闭源，Silas Data 用 **token 计费数**（每次响应报告 input tokens，同请求重复完全一致）做单变量对照，反推出架构：

| 观察 | 解释 |
|---|---|
| 最小请求（可见内容约 15 token）被计 **289** token；外推各序列到零内容得同一固定量 | Jev 包了一层**约 270 token 的固定提示词** → **是指令微调的语言模型，不是编码器**（只需编码输入如 Laya/CLM 者不需要指令） |
| 每加一个选项 **+7.7 token**（名称本身约 4，其余为格式）；描述**逐词计**（+1.0/词，有描述后再 +5/选项） | 选项**写在提示词的文本里**，每项带代码或分隔符——**像 Lev 的 "A. name" 行** |
| **255 选项上限**（= 2⁸−1） | 与**固定代码集、每选项一个**一致 |
| 长文本比短文本多 81 token，但**每加一个问题恒为 65 token**（两种文本下相同） | **状态只读一次并在多个问题间共享**——例如提示词公共开头 + 每问题一分支（官方文档称问题并行评估，且延迟不随问题数增长） |
| 输出 token 每选项 **+8.7** | 等于 API 返回 JSON 中每条选项–概率条目的大小，**不携带模型信息** |
| 排序敏感度是**同序重发的 2.5–4.3 倍** | 选项**被顺序读取**，而非分别编码 → **排除 CLM 设计** |
| 正确选项在列表中的**位置与距离均无影响**（p=0.94 / 0.56） | 状态在前，答案在**能看见整段提示词的位置**读出 → **排除 Laya 布局**（选项在状态之前） |

> **推论**：Jev 的设计**接近 Lev**——一个解码器读状态，再读带代码的选项，在末尾导出概率。相较 Lev 的**新增点**是：**状态处理一次并被多个并行问题共享**。
>
> **证据边界**（作者自陈）：这是**从可观测行为做的推断**。权重、提示词与服务代码仍闭源，**原则上另一种架构也可能产生相同行为**。

### 2.4 Jev 的实测（同条件对照）

**实验 1 · 选项数扩展**

| 选项数 | 2 | 10 | 50 | 150 | 255 |
|---|---|---|---|---|---|
| 延迟 (ms) | 247 | 262 | 258 | 262 | 262 |
| 每问题计费 input token | 306 | 381 | 718 | 1,497 | 2,264 |

- token 增长 **7.4 倍**，延迟仅增 **6%**（247→262 ms）
- **延迟被约 250 ms 的固定成本支配**（网络 + 接收 + 排队 + 返回）；读约 2000 个额外 token 仅加约 15 ms
- 准确率：**1.00 / 0.95 / 0.86 / 0.81 / 0.77**（2/10/50/150/255）——下降很慢

**四模型横向（banking77）**

| 选项数 | 2 | 10 | 50 | 150 | 255/284 |
|---|---|---|---|---|---|
| **Jev** | **1.00** | **0.95** | **0.86** | **0.81** | **0.77** |
| Laya fit | 0.93 | 0.84 | 0.63 | 0.37 | 0.20 |
| Lev mode A | 1.00 | 0.99 | 0.96 | 0.89 | 0.85 |
| CLM | 0.64 | 0.20 | 0.06 | 0.00 | 0.00 |

> 仅 Lev 领先，**但 Lev 是在 banking77 上训练的**（其模型卡自述）——绝对准确率被抬高。Jev 训练数据未披露。

**实验 2 · 排序敏感度**（77 选项）

| | 翻转率 | 概率位移 |
|---|---|---|
| Laya fit | 74% | 0.455 |
| Lev mode A（无平均） | 6% | 0.065 |
| **Jev** | **13%** | **0.061** |
| CLM | 0% | 0 |

> ⚠️ **Jev 有调用间非确定性**：同序重发的翻转率为 0.00/0.00/0.01/0.00/0.04，概率位移 0.002–0.014。这是 **GPU 批处理下浮点运算顺序变化**的常见行为。**排序效应是同序重发变异的 2.5–4.3 倍**，所以排序效应真实存在，但**评估 Jev 时必须控制这个基线噪声**。

**实验 3 · 最小编辑**（每类 24 次运行，误差约 ±10pp）

| 类别 | Laya | Lev | CLM | **Jev** |
|---|---|---|---|---|
| 数量 | 0.54 | 0.75 | 0.08 | **0.75** |
| 否定 | 0.75 | 1.00 | 0.00 | **1.00** |
| 数字 | 0.17 | 0.83 | 0.00 | **1.00** |
| 角色 | 0.38 | 1.00 | 0.00 | **1.00** |
| 时间 | 0.92 | 1.00 | 0.08 | **1.00** |
| 量词 | 0.50 | 0.67 | 0.00 | **1.00** |
| **对照（不应改变）** | 0.50 | 1.00 | 0.40 | **1.00** |

- Jev 在五类中**每一对都答对**，且**对照组从未改变答案**（唯一做到的两个之一）
- Jev **解出了 Lev 仍失败的"航班时间"模板**（需比较两个时刻）
- Jev 唯一失败："我输错了一次 PIN" → 每轮都归为 "card blocked"（Laya/Lev 同错）→ **三模型同错说明是文本本身有歧义**，非模型失败

**实验 4 · 靠名称还是靠描述**（12 选项，机会水平 0.083）

| 条件 | Laya | Lev | CLM | **Jev** |
|---|---|---|---|---|
| 原始 | 0.89 | 0.99 | 0.45 | **1.00** |
| 仅名称 | 0.89 | 0.99 | 0.44 | **0.99** |
| 代码+描述 | 0.80 | 1.00 | 0.45 | **1.00** |
| 仅代码 | 0.07 | 0.09 | 0.05 | **0.06**（置信度降至 0.13） |
| **误导性名称** | 跟随名称 **0.72** | 跟随描述 0.92 | 0.45（等同巧合） | 跟随描述 0.56 / 跟随名称 **0.43** |

- **Jev 的描述跟随率 0.56、名称跟随率 0.43**——**都承载真实权重**，是"把名称与描述作为一整行一起读"的行为
- 冲突时置信度从 0.99 降到 **0.71**——**冲突在概率上有反映**

### 2.5 独立基准

**（a）jev-test：Jev × LexGLUE 零样本**（全测试集 23,607 例）

| 模型 | 协议 | μ-F1 | m-F1 | 成本 |
|---|---|---|---|---|
| Jev（jev-1.13） | System One | 69.9 | 62.6 | **$4.02** |
| Jev + 验证集调每标签阈值 | System One | **74.2** | **66.3** | +$2.47 |
| GPT-5.6 Luna | chat, JSON schema | 71.3 | 63.9 | $16.45 |
| Kev-4B（开源权重自服务） | System One | 62.1 | 55.5 | ≤$8.01 GPU |
| LLM2Jev on Qwen3.5-4B（纯提示，无训练） | System One | 62.2 | 53.8 | ≤$28.84 GPU |
| BERT-base 微调（有监督） | supervised | 77.4 | 69.3 | $21.58 GPU |

**关键读法**：
- Jev 与 Luna **接近**：Luna 在 ECtHR A/B、EUR-LEX、UNFAIR-ToS 领先；Jev 在 SCOTUS、LEDGAR 领先；CaseHOLD 平手
- **成本差约 4 倍**（$4.02 vs $16.45）
- **仅在验证集上调阈值**（不碰测试集、不用训练样本）即可把与 BERT 的差距从 **7.5 缩到 3.2 μ-F1** ——这是一个非常实用且廉价的杠杆
- 法域之外：细粒度意图上 Jev **落后**微调 BERT（BANKING77 80.6 vs 93.7；CLINC150 域内 89.0 vs 96.7），**但域外请求识别远强**（CLINC150 recall **88.1 vs 59.2**）

**（c）OrcaRouter 生产遥测**（2026-09-24 → 09-30 七天窗口）

Jev 1.13：**7620 万 token 上错误率 0.49%**；首 token p50 **151 ms** / p95 **247 ms**；输出约 **349 tok/s**。

> ⚠️ 作者自己标了三条边界：这是**自有服务数据非供应商数据**；是**滚动窗口不是固定测试集**（同字段早些时候读数为 0.57%，因为七天前的调用会滚出窗口）；**这不是校准测量**——错误率只说"在我们流量上多久出一次问题"，不说明置信度值是否诚实。

### 2.6 Jev 的已知局限【诚实清单】

- **无公开基准卡**：供应商未发布，**没有第三方排行榜收录**；截至 2026-09-30 其 Artificial Analysis 页面 **404**
- **性能声明是自陈**：发布博文坦承支撑速度/成本标题的流程评估**由其模型能力团队自建**，参考答案是**两个外部模型结果的平均值**，且这些数字"**处于真实世界收益的较高端**"；也表示**无法证明定价没有补贴**
- **约 250 ms 固定延迟**每次调用
- **同序重发仍有微小变异**（非确定性）
- **无法检视或适配模型**（闭源）
- **只能做原子单维判断**——"分析这件事并给出最佳方案"这类问题答不好（那需要慢思考）

## 3. Laya（Convai Innovations，开源）

### 3.1 架构

- 骨干：**421M ModernBERT 编码器**
- 结构：把**选项在前、状态在后**拼成**单一序列**；**每个选项前放一个 `[MASK]` token**（像多选题的 A/B/C 标记）
- 单次前向通过 28 层；**只保留各选项的 embedding**
- 小型 MLP 把每个选项 embedding 转成分数，softmax 转概率
- **训练部分：整个 ModernBERT 全量微调 + 2 个额外层 + 打分 MLP**

> 与 CLM/Lev 的关键差别：选项与状态**在同一序列里一起读**，所以每个选项的 embedding 在通过过程中**已吸收状态信息**。

### 3.2 实验揭示的失败模式【这是最有价值的部分】

**① 距离敏感（不是位置敏感）**——77 选项时：

| | 翻转率 | 概率位移 |
|---|---|---|
| Laya default | 79% | 0.488 |
| Laya fit | 74% | 0.455 |

- 按位置看准确率：正确选项在**列表第一/四分之一**时 32%，在**最后四分之一**时 **62%**（77 选项）
- 但逻辑回归分离两个变量后：

| 变量 | 系数 | p 值 |
|---|---|---|
| **距离（每 100 token）** | **−0.34** | **0.0008** |
| 列表位置 | +0.16 | 0.57 |

> **每 100 token 的间距把答对的几率乘以约 0.71**；位置**无影响**。
>
> **机理**：ModernBERT **每三层中有两层只有 ±128 token 的局部窗口**，只有每第三层看全序列。靠近状态的选项能在全部 28 层读到它，远离的只能在约 9 层读到。准确率在正确选项距状态约 45 token 内保持最高（0.64–0.73），45–75 token 间下降，**与单侧局部窗口 ±64 token 吻合**；下降是渐进而非阶跃，因为全局层仍连接远处。

**② 静默截断（危险）**

- 默认 **512 token 预算**；选项装不下就**裁掉**
- 150 选项时 **default 配置拒绝了 100 题中的 99 题**
- 唯一被接受的那题**有空间放选项但没空间放状态：32 个状态 token 全被移除，模型仍返回概率分布，且无任何警告**

> **这是一个真实的静默失败模式**：输入信息被悄悄删光，输出照常给出。

**③ 名称压过描述**

- 误导性名称下，Laya **跟随名称 72%**（8 倍于其 9% 的巧合水平），**平均置信度 0.80**——它并不在名称与描述间犹豫
- 它能读描述（名称换成无意义代码时，仅靠描述仍有 0.80 准确率）
- **但冲突时名称胜出**——与架构一致：打分用的 embedding 取自 `[MASK]`，**紧邻名称之前**

> **实践含义**：Laya 的**选项名称必须谨慎选择**。一个误导性或含糊的名称会**覆盖掉正确的描述**。

**④ 校准问题**

- **出厂温度参数未在量化后重拟合**
- 上游 README 自述：按（问题类型, 选项数）重拟合一个温度，平均 ECE **0.466 → 0.081**（laya）、**0.314 → 0.106**（laya-multilingual）
- CoreML 端口已抓到一例翻车：11+ 选项桶的出厂温度 **0.1006**，尖锐到**把掷硬币报告成近乎确定**，现在加了加载期警告并 clamp

**⑤ 语言路由 bug**

- **128/200 条德语话语（64%）被路由到英语检查点**
- 未定语言猜测被当作英语；显式传 `lang="de"` 可恢复完整准确率
- **模型没问题，路由有问题**——短拉丁字母文本上 **20 个点的摆动**，由一个**报告满置信度却判断错误**的启发式决定

**⑥ 准确率的真相【最重要的一条】**

| 对象 | 分数 |
|---|---|
| 上游 typed-decisions 基准，**通用检查点** | **0.362 / 0.342** |
| 同框架下**多数类基线** | **0.461** |
| 让 Laya 显得强的那个数 | **0.766**——**任务特定微调** |
| 教师自身自洽上限 | 0.735 |

> **通用检查点低于多数类基线。** Laya 的 CoreML 端口把通用 FP16 检查点转了过去，而 **4.98 ms 那个数是用某个 bundle 测的、准确率是用上游检查点测的——没有人把两列接起来**。

### 3.3 部署实测（Core ML / ANE）

| 指标 | 值 |
|---|---|
| 延迟（M3 Max ANE FP16） | **4.98 ms P50 / 5.31 ms P95** |
| 编译 MLX FP16 | 6.94 / 7.39 ms |
| 能耗/决策 | ANE **0.1540 J** vs MLX 0.4288 J（**2.78×**，65,598 次稳定调用，能耗读 SMC PSTR 传感器而非建模） |
| W8 变体 | 4.88 ms，能耗改善 **3.19×** |

**但盒子是满的**：
- 测试问题 91 token → padding 到 96 → **96 就是全部预算**（问题 + 选项 + 携带状态）
- **更长请求直接抛容量错误**——**没有留给未来的余量**
- 单独导出的 FP16 ANE **L1024 图**通过完整 63/63 夹具，但**真实 1024-token 请求约 91.7 ms**（**18 倍**）
- 项目自己的结论："短 ANE 结果**不构成**长上下文优势"

**量化的坑**：
- **普通动态 INT8 会毁掉这个模型**：argmax 一致率掉到 **69%**，最坏概率位移 **0.99**
- **只量化 MatMul 是灾难，只量化 embedding 能活**——指向**激活异常值**而非权重精度
- "差别在量化方案，不在检查点，这同时也是二十倍速度差的来源"

**Snake 对照（421M 本地 vs Jev 云端 1.13.0，同一套 typed decision）**：

| | Laya | Jev |
|---|---|---|
| 30 秒得分 | **46** | 1 |
| 长度 | 52 | 7 |
| 决策/秒 | **86.5** | 3.2 |
| P50 延迟 | **约 9 ms** | 约 317 ms（API 往返） |

M5 Pro：15.3 ms vs 298.1 ms（**约 20 倍**）。

> ⚠️ **但这是部署方式的差异，不是模型能力的差异**：Jev 每步都要发到云端往返，Laya 本地推理不依赖网络。**对高频交互任务，几十到几百毫秒的差距足以改变最终表现**——但把它读成"Laya 比 Jev 强"是错的。
>
> 另有一条常被忽略的边界：**每个测量都是本地对本地**（同一台笔记本上 ANE 对编译 MLX）；**没有任何人把托管往返测在旁边**——所以"比 API 快"仍是这些项目的**前提**，而不是它们报告的**结果**。

### 3.4 Laya 的诚实之处

其 CoreML 端口的验证段落很值得学：ANE FP16 通过 59/59 拟合题，最大校准概率漂移 0.002925；W8 通过同一子集漂移 0.014393（门槛 0.02）；6-bit/4-bit 实验未过门槛、**从未作为权重发布**。紧接着同一段：

> "这些是**转换保真度夹具，不是通用任务准确率的证明**。"

**通过率与免责声明在同一段里**——端口证明了"答案在转换中没变"，同时声明"尚未证明这个答案是对的"。

## 4. CLM（Contrastive-LM，开源）

### 4.1 架构

- 骨干：**Qwen3-8B，完全冻结**
- **从不把状态与选项放进同一句话**：先单独处理状态（像 Qwen 正常那样），再**逐选项单独处理**
- 5 个选项 → **6 次独立前向**
- 每次保留**一个概括整段文本的 embedding**
- 两个小型 MLP（一个给状态、一个给选项）把它们变到 **512 维新空间**，在 (状态, 正确选项) 配对数据上训练
- 用**余弦相似度**度量距离，softmax 转概率
- **训练部分：只有两个 MLP（约 19M 参数）**，Qwen 原封不动

> 关键性质：**选项 embedding 不依赖状态**，因此**可计算一次、跨所有新状态复用**。

### 4.2 实验揭示的行为

**① 排序不变性（它的设计保证）**

| 77 选项 | 翻转率 | 概率位移 |
|---|---|---|
| **CLM** | **0%** | **0**（精确为零） |
| Lev mode B | 0% | <百万分之一（浮点舍入） |

**② 延迟平坦（缓存生效）**

- 热缓存下 CLM 与 Lev mode B **几乎平坦**
- 冷缓存下两者都增长约 **10 倍**（每个选项都要重编码）
- 对比：Lev mode A 从 2→284 选项增长 **18.6×**

**③ 最小编辑：几乎全灭**

| 类别 | CLM | （对照：Jev） |
|---|---|---|
| 数量 | **0.08** | 0.75 |
| 否定 | **0.00** | 1.00 |
| 数字 | **0.00** | 1.00 |
| 角色 | **0.00** | 1.00 |
| 时间 | **0.08** | 1.00 |
| 量词 | **0.00** | 1.00 |
| 对照（不应改变） | 0.40 | 1.00 |

- 任何类别中"两段文本都答对"的比例**至多 8%**；**24 个模板中有 13 个它对两段文本给出完全相同的答案**
- **机理**：编辑只改变状态 embedding，而在 Qwen 原始空间里**几乎不动它**——正确选项的概率只变约 **0.01**（两个讲同一主题的句子本就该如此）。MLP 把它放大到 0.03–0.20，但**多数情况下不足以改变哪个选项最近**。选项 embedding 固定，所以决策的任何改变都只能来自这个微小的状态变化。

**④ 名称对它是不可见的**

- CLM 只要有描述就**只编码描述**，**名称根本不到达模型**
- 因此它在**原始 / 代码+描述 / 误导性名称**三个条件下的结果**完全相同：0.4542，连最后一位都一样**

**⑤ 短标签挤在一起（准确率崩塌的根因）**

| 度量 | Qwen 原始空间 | 经 MLP 后 |
|---|---|---|
| 准确率 | 0.15 | 0.46 |
| 正确 vs 错误 AUROC | 0.55 | **0.80** |
| 状态与正确选项平均余弦 | 0.875 | **0.281** |
| 状态与错误选项平均余弦 | 0.872 | **0.251** |
| 不同状态之间平均余弦 | **0.98** | 0.85 |
| 不同选项之间平均余弦 | **0.95** | 0.70 |
| 状态按意图分组（silhouette） | 0.09 | 0.21 |

- **Qwen 原始空间里几乎所有 embedding 指向同一方向**（任意两状态余弦 0.98，任意两选项 0.95）——这是"用语言模型最后一个 token 当 embedding 且未为此训练"的已知性质。在这个空间里正确与错误选项**几乎等距**（0.875 vs 0.872），选最近的**接近随机**。
- MLP **在状态侧**解开了这个集中（0.98→0.85，同意图状态开始聚簇）
- **但在选项侧效果小得多**：12 个选项仍挤在一起（0.70），**彼此比与任何状态都更相似**；正确/错误的差距只略微拉开（0.281 vs 0.251），**足以把 AUROC 抬到 0.80，但正确选项常常不是最近的那个**，准确率停在 0.46
- **根因**：这里选项是**几个词的短描述**，而 CLM 是在**长回答与 agent 动作**上训练的——它的选项 MLP **不会把这种短文本撑开**

**⑥ 准确率随选项数崩塌**（banking77）

| 选项数 | 2 | 10 | 50 | 150 | 284 |
|---|---|---|---|---|---|
| CLM | 0.64 | 0.20 | 0.06 | 0.00 | 0.00 |

### 4.3 CLM 的适用边界【作者结论】

> **CLM 擅长它的"状态/选项分离"所保证的东西**：选项缓存后，**成本不随选项数增长**，**答案永不依赖顺序**。
>
> **同一份分离也让它在其余所有测试项上很弱**：状态在与任何选项相遇前就被压成一个 embedding，所以小编辑几乎不改变决策；短标签彼此太近无法区分。
>
> **不适合把文本分类到短意图标签。** 它适合它被设计出来的任务：**在大量稳定动作间做选择的 agent，动作由较长文本描述，且缓存能带来收益**。

## 5. 四模型总对比

| | **Laya** | **Lev** | **CLM** | **Jev** |
|---|---|---|---|---|
| 归属 | Convai Innovations | Interfaze AI | Contrastive-LM | TypeSafe AI |
| 骨干 | ModernBERT 编码器 | Qwen3.5-4B 解码器 | Qwen3-8B 解码器（**冻结**） | 未公开（**推断为指令微调解码器**） |
| 参数 | 421M | ~4B | ~8B + 19M | 未知 |
| 状态与选项 | **一起读** | **一起读** | **分开读** | **一起读** |
| 选项布局 | **状态之前** | 状态之后 | 与状态分离 | 状态之后（推断） |
| 决策读取点 | 每个 `[MASK]` 处的向量 | 每个字母的 next-token 概率 | 两个向量之间的余弦 | 提示词末尾（推断） |
| 训练部分 | 全模型 + 头 | LoRA 适配器 | 两个 MLP 头 | RLCD |
| 选项向量可缓存 | 否 | mode A 否 / mode B 是 | **是** | 否（推断） |
| 排序不变 | ❌ 74–79% 翻转 | mode A 5–6% | **✅ 0%** | 13%（同序基线 0–4%） |
| 距离敏感 | **❌ 强**（每 100 tok ×0.71） | 无 | 不适用 | **无** |
| 最小编辑 | 部分 | 几乎全部 | **失败** | **最好** |
| 靠名称还是描述 | **名称压过描述** | 描述 | 不适用（名称不可见） | **两者都重要** |
| 选项数扩展（准确率） | 0.93→0.20 | 1.00→0.85 | 0.64→0.00 | **1.00→0.77** |

### 5.1 全篇最重要的一条洞察

> **System One 模型不是一种新的网络。** 三个开源实现**都是预训练语言模型**，只是在**除"生成文本"之外的位置**读取答案：
> - **一个标记的 embedding**（Laya）
> - **一个字母的概率**（Lev）
> - **两个 embedding 之间的距离**（CLM）
>
> **不生成 token 改变的是"从哪里读答案"，不是网络本身。** 底层架构仍然决定模型如何处理输入、以及可以期待什么行为。

### 5.2 Lev 的一个反直觉发现

**LoRA 适配器不是它用字母作答的原因**：关掉适配器，Qwen3.5-4B **已经把 99.97% 的 next-token 概率放在选项字母上**，并在 98% 的状态上选对。**"从字母概率读答案"是指令微调模型在聊天格式下已具备的能力**（与 Lev 模型卡中冻结模型达 0.71 一致）。

**适配器改变的是置信度与内部组织**：正确字母概率 0.965→0.998；答案位置的 embedding 探针准确率 **0.51→0.99**，silhouette **−0.02→0.30**——**从"该说哪个字母"变成"这是哪个意图"**。

## 7. 稳定结论 vs 未验证

### ✅ 稳定（多源交叉 / 有实验支撑）

1. **类别成立**：输出契约从"生成文本"改为"枚举空间内打分"，是一个真实且可复现的工程分化（三份独立实现 + 一份闭源源头）
2. **架构决定失败模式**：选项与状态**一起读还是分开读**，决定了排序敏感、距离敏感、编辑敏感、可缓存性、名称/描述依赖——这是全篇最强的因果链
3. **"不会幻觉"仅指类型层面**，不指正确性；**校准 ≠ 正确**
4. **Jev 准确率最好、编辑最鲁棒**，但**约 250 ms 固定延迟 + 调用间非确定性 + 闭源不可检视**
5. **Laya 的 0.766 是微调数，通用检查点低于多数类基线**
6. **CLM 的排序不变性与成本平坦是真实的设计收益**，代价是编辑不敏感与短标签不可分
7. **量化对 Laya 是破坏性的**（INT8 argmax 一致率 69%）

### ⚠️ 未验证 / 需保留

1. **Jev 的架构是行为推断**，非官方披露；作者自陈"另一种架构原则上也可能产生相同行为"
2. **Jev 无公开基准卡，无第三方排行榜收录**；其性能声明是自陈，参考答案是两个外部模型的平均
3. **RLCD 的奖励函数、网络结构、参数量官方未公开**——校准论证依赖训练描述 + 文档约定 + 自测，**不是已发布的曲线**
4. **Jevals 与 Jev 供应商无关联但也是单一来源**；其 Release 为 2026-09-18，早于部分后续版本
5. **Lev 在 banking77 上训练过**，其绝对准确率被抬高——跨模型比较中作者已排除该影响，但绝对值不可直接引用
6. **CLM README 示例数字（0.9388）与官方 vLLM 路径（0.9880）不一致**，作者判定最可能是"示例用了更早版本的 MLP"，**未确认**
7. **HelpSteer2 上无模型超过瞎猜**——score 类任务整体未被攻克
8. **本报告未做任何本地实测**，全部为文献与第三方实验综合

## 8. 与既有工作的关联

### 8.1 与 Raven / Harness 调研的接点

Jev 范式与 [Raven 的 harness 编排](file:///Users/coreyleung/dsh-collab/docs/Raven-借鉴分析-v2.md) 是**同一问题的两端**：

- **Raven 解决"谁来编排"**——Host Agent 把复杂任务拆成 DAG，委派给专业 agent
- **Jev 解决"原子判断怎么做得又快又可靠"**——把高频、单维、可枚举的决策从慢思考里剥离

APUS 的表述直接点明：这验证了 Agent 架构的**快慢分工**——昂贵大模型负责规划等"慢思考"，高频原子化的"快判断"交给轻量决策模型；**负责组装调度这套分工的工程层，业界称为 Harness**。

**可直接对接**：`opendecider` 提供 **Jev 兼容的 `/v1/systemone`** 与 **MCP server**，意味着它可以作为 DSH 的 MCP 工具直接挂载。

### 8.2 对我们已有的对照

| 我们的现状 | System One 的对应物 | 差距 |
|---|---|---|
| `waimai_*` 工具链里的分类/判断（告警归类、评价情绪、意图路由）目前靠 LLM 生成文本再解析 | 类型化原语 + 校准概率 | **缺"置信度分档路由"**——我们现在是"要么全自动要么全人工" |
| `guard_compliance` 五道闸的布尔判定 | Score 原语（含落在刻度之间的位置） | 我们只有通过/不通过两态 |
| 各 plugin 的自定义输出格式 | Choice/Noul/Score 三原语 + 类型安全 | 输出空间未显式枚举，靠 schema 校验事后兜 |
| 现有 prompt 里要求"给出置信度" | 校准（分组意义，非单例保证） | LLM 自陈置信度**不可靠**——这正是 RLCD 要解决的问题 |

**最有价值的三条可借用思路**：
1. **置信度分档路由**：把"自动化程度"变成置信度的函数，而不是人写死的开关
2. **输出空间调用前枚举**：类型安全的价值不在"更准"，而在**越界答案比偶尔选错危险得多**
3. **校准必须在自己数据上验证**：取几百个已标注案例，按模型报告的置信度分桶，检查各桶准确率是否达到声称水平——**这是少数不需要任何 ML 基础设施就能检验的模型属性**
