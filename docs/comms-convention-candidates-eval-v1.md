## 一、本地已有 5 条通讯规则 → 公约覆盖现状

| 本地规则 | 公约是否覆盖 | 缺口 |
|---|---|---|
| R002 通道分级 | 部分(§1.1 通道分层) | 设备内 vs 跨设备分级不完整 |
| R003 JSON body | ✅(G-C8 信封 schema) | — |
| R018 噪音治理 | ❌ 未覆盖 | 跨设备噪音无上报机制 |
| R033 通道治理+群聊 | ❌ G1-G4 未入公约 | 群聊约束仅设备内 |
| R034 探照灯 | 部分(§1.2-4 队列零积压≈黄灯) | 无完整三灯/黄灯转黑板 |

## 二、候选纳入公约(成本治理项评估)

### 候选 1: G-C11 跨设备「看黑板」短指引(已提, 高优先)
- 内容: 跨设备信封 text>50 字 → 先落黑板 notes/<target>/, 信封只带「看黑板 <key>」
- 理由: 本地 R002/R003 已防, 跨设备黑卡片 content 带全文 = 同浪费跨设备版
- 适用服务器端: ✅ 完全适用(bus 信封→黑卡片→注入, 正是全文注入点)

### 候选 2: G-C12 跨设备噪音上报(R018 泛化)
- 内容: 收到无关跨设备消息 → noise 上报(黑板 data/audit/noise-reports/ + node 字段)
- 理由: R018 已治设备内噪音, 跨设备(服务器总线)噪音无上报——污染源难追溯
- 适用: ✅ 适用(信封有 from device 可溯源)

### 候选 3: G-C13 跨设备重试风暴熔断(R034 延伸)
- 内容: 同目标跨设备重发 10min>5 次 → 熔断转死信
- 理由: 服务器 S3 重试×2 已防单条, 但发送方重复发同内容(风暴)未防
- 适用: ✅ 适用(服务器可统计同 from+target+action 频率)

### 候选 4: 群聊跨设备约束(R033 G1-G4 泛化)
- 内容: 跨设备群聊(多设备多角色)同样 ≤5-8 人/收敛即散
- 理由: 跨设备群聊放大更严重(每消息经服务器→多设备注入)
- 适用: ⚠️ 部分适用——需评估服务器是否支持多设备群聊

### 候选 5: 心跳驱动的离线降级(已有 G-C2/C4 覆盖)
- 内容: 目标离线时发送方降级(黄灯转黑板)
- 现状: 公约 G-C4 队列零积压已要求; 缺"发送方黄灯响应"条款
- 适用: ✅ 建议补充发送方侧义务(非仅服务器侧)

## 三、本地桥泛化服务器端的适用性评估(核心问题)

### 结论: 大部分适用, 3 类需改造

| 本地机制 | 泛化服务器 | 适用性 | 原因 |
|---|---|---|---|
| agent_send(设备内) | bus/send 信封 | ✅ 已泛化(S2) | 同构: 定向投递+队列 |
| 黑板 KV(本地 8792) | 服务器黑板(106.53:8792) | ✅ 适用 | 同 API |
| 红绿灯锁(agent_light) | 服务器锁 | ⚠️ 需改造 | 锁语义跨设备复杂(全局锁 vs 本地锁) |
| 群聊线程 | 跨设备群聊 | ⚠️ 需评估 | 服务器多设备线程支持未知 |
| 去重(10min 同内容) | 服务器去重 | ✅ 适用 | 服务器可全局去重 |
| 噪音上报(R018) | 跨设备噪音 | ✅ 适用(候选2) | 信封可溯源 |
| 风暴熔断 | 服务器熔断 | ✅ 适用(候选3) | 服务器可统计 |
| 纯确认不回 | 跨设备同样适用 | ✅ | 语义不变 |
| 探照灯(查状态) | E2 发现层 | ✅ 已规划(R-ERR4) | 服务器注册表=谁在线 |

### 不适用的 2 类(需注意)
1. **红绿灯锁全局化**: 本地锁是进程内互斥(agent_light 查 agent-bus), 跨设备全局锁语义不同——建议跨设备用"任务归属"而非锁(设备自治)
2. **实时黑板推送 vs 服务器**: 本地 SSE 8803(TS 直连) vs 服务器推送(bus/events 公网)——通道独立设计(TS 断不影响 bus), 不可混用

## 四、建议(优先级排序)

1. **G-C11 跨设备看黑板**(已提, 用户问的缺口)——立即补入公约
2. **G-C12 跨设备噪音上报**(R018 泛化)——高价值, 治跨设备污染
3. **G-C13 风暴熔断**(R034 延伸)——服务器可统计, 成本低
4. **G-C14 发送方黄灯义务**——补全探照灯(服务器侧 G-C4 已有, 发送侧缺)
5. 红绿灯锁不做全局化(保持设备自治)——记录为边界
