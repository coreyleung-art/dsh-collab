# 通信通道规则 v2 · 通道矩阵明确化 + 变更爆破治理（2026-10-02 草案）

> 用户观察（原话转述）：「端侧为了通讯而无限爆破，也会改掉原本的基础方式；或者不断更换通道，而让最开始能行的通道变成故障。」
> 本文把该观察补成可执行规则，并与《server-degrade-discipline-v1》（故障时行为）、《agent-comm-substrate-v3》（实测基线）构成通道治理三部。
> **v1 管「故障时怎么办」；v2 管「变更前凭什么动手」**——共同目标：通道状态只由事实探测驱动，不由能动性驱动。

---

## 1 · 现象定性（用户观察 + 今日四例实测证据）

**一句话定性**：以「改善通讯」为名的**主动变更**（换通道 / 改参数 / 停启服务 / 改鉴权 / 降频），本身是无界动作——没有「先证明现在坏了」的前置、没有回滚点、没有留痕。每次变更都是潜在破坏，无限爆破的终点就是把本来健康的通道改坏。

| 证据 | 场景 | 教训 |
|---|---|---|
| E1（今日·我侧） | 测试脚本 shell 变量未 export ⇒ 读空 token ⇒ 401 ⇒ 误判「服务器 send 通道坏了」，差点去改服务器鉴权 | **误判会驱动对健康通道的破坏性变更**；负向证据（401）逼出复测才避免。判据：动手修通道前，必须有「对照探测证明它坏」+「排除自己的测试错误」。 |
| E2（今日·MBP 侧） | 资源紧张时手动停 launchd job（4 个静默未加载、无告警）⇒ 守护「聋了 13.5 小时」 | 以「省资源」为名的停用=隐性爆破；plist 在而 job 未加载是**静默故障**（launchd-scan 已工具化检测）。 |
| E3（今日·我侧） | D2 `--once` 验证 ⇒ 全量回灌 500 张历史卡 ⇒ 注入风暴刷屏会话流 | 一次验证性变更的副作用即成风暴；修法：`--warm` 预热 + 变更前评估爆炸半径。 |
| E4（历史·双方） | 服务器暂错时「各自重试/换通道/绕过守护」（见降级纪律 v1） | 通道矩阵不唯一 ⇒ 每个 agent 各自猜 ⇒ 冲突与双倍成本。 |

## 2 · 通道矩阵（唯一权威，2026-10-02 实测口径）

> 每一类消息的通道是**固定的**；矩阵变更=规则修订（协调者起草+用户批），**端侧不得自行切换**。

| 消息类别 | 主用通道 | 兜底通道 | 禁用 |
|---|---|---|---|
| 同机会话间（agent_send/threads） | L0 agent-bus（进程内） | agent-bus.json 落盘兜底 | 不得走黑板/服务器（R031 本地优先） |
| 跨设备内容卡 | 黑板双写（mac-mini 127.0.0.1:8792 经 Tailscale + 中枢 xingqiao:8792） | 仅中枢（断 TS 时；sync v1.1 镜像收口） | 不得只写单板（collab 类必须双写+回读断言） |
| 跨设备任务/信封 | 服务器 bus-bridge 8791（token 鉴权） | 黑板卡+指针 | 不得明文 token 进卡/日志 |
| 「看黑板」指针 | bus 注入（wake=inject，不唤醒） | 黑板卡自身（SSE 推送） | 不得全文重发 |
| 要求回复的信封 | reply_required=true（唤醒语义，I7a） | — | 不得用通知语义要求回复 |
| 心跳/注册/版本 | 服务器 8792（hb-fwd 写时变更 + G5 判定） | 本机黑板镜像 | 不得由会话直写注册表（R-ERR4：仅心跳代理） |
| 服务器故障时 | 按降级纪律 v1 状态机（黄灯黑板留痕/红灯缓存） | 人类求救通道（v1 §五） | 不得自行换通道当备胎 |

## 3 · 变更爆破治理（本规则的硬约束）

**R-C1 变更前自证损坏**：对任何通道/守护动手前，必须同时具备——①一条对照探测证明「现在确实坏」（同一动作对已知健康对象做对照）；②排除了自己侧的错误（测试脚本/环境变量/本地配置）。两者缺一 ⇒ **禁止变更**。「感觉慢了/换一个试试/重启一下再说」不构成动手依据。

**R-C2 变更三步**：公告（写 `data/ops/channel-changes/` 声明意图+判据）→ 双跑/灰度（新旧并行，观察无回归）→ 验收（判据数字）。缺一步即违规。

**R-C3 变更必可回滚**：任何变更前留回滚点（备份/旧二进制/旧配置路径），回滚点写进公告。无回滚点的变更禁止执行。

**R-C4 爆破熔断**：同一通道 24 小时内变更次数 ≤2；第 3 次起冻结该通道 24 小时并上报协调者裁决。判据可机械核验：`data/ops/channel-changes/` 按通道聚合计数。

**R-C5 通道切换=矩阵修订**：主用通道不可端侧自行更换；确需更换走「协调者起草 → 用户批 → 公告 → 双跑 → 验收」全流程（即修订 §2 矩阵本身）。

**R-C6 停用=变更**：任何「先停掉省资源/避嫌」类动作同样适用 R-C1/C2/C3（E2 教训：静默停用无告警是最阴性的爆破）。

## 4 · 与既有纪律的关系

| 文档 | 管什么 | 触发 |
|---|---|---|
| 降级纪律 v1 | 服务器**已坏时**的设备行为（状态机/禁乱试/求救通道） | 探测确认故障 |
| 本文 v2 | 通道**变更前**的动手资格（自证损坏/三步/回滚/熔断） | 任何想改的念头 |
| 基座 v3 | 通道**实测现状**（矩阵数据的来源） | 持续更新 |

v1 的探照灯状态机照旧有效；v2 补的是「**黄绿灯时也不许乱动**」——今天四例证明：**故障往往不是通道自己坏的，是上一轮爆破改坏的**。

## 5 · 验收判据（可机械核验）

1. `data/ops/channel-changes/` 存在且今天所有变更（含今天的 hb-fwd v1.1、sync v1.1 等）已补记留痕。
2. 24h 内任一通道变更计数 ≤2（聚合查询）。
3. 每条留痕含回滚点字段（缺失=FAIL）。
4. 端侧守护代码中不存在「自动切换主用通道」路径（Lean4 断言，并入 convention-lean4-check）。
