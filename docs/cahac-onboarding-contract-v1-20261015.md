## 2. ① 接入清单（★ 在 portal §5 之上【增补】CAHAC 条款）

> ★ **不改 portal §5 已有条目**；★ **只增补**。★ portal 属主为协调者。

### 2.1 新设备接入时【必须】完成的 CAHAC 项

| # | 动作 | 判据（可机械核） |
|---|---|---|
| **C-1** | 声明 `cahac_version` | Agent Card 里 **有** `cahac_version` 字段，**且值 = 规格规范值**（★ 当前 `"1.2"`，★ **注意不是 `"v1.2"`** —— `D-331` 实测过这个坑） |
| **C-2** | 写卡带完整信封 | 该设备写的卡，**12 必填字段全在**：`cahac` `id` `type` `channel` `sender` `recipient` `thread` `priority` `cost_cap` `dedup_key` `ts` `payload` |
| **C-3** | 留可复跑的举证 | 该设备能给出**一条命令**，跑完后**回读自己写的卡**并打印字段齐备情况 |
| **C-4** | 声明【未接入面】 | 该设备**显式写出**它还有哪些面**未接入**（★ 依 §1.5.2「域外必须显式，不得沉默」） |

### 2.2 判据（★ 可机械核 · 每条都给复跑命令）

```bash
# ── C-1 值必须是规范值 "1.2"（★ 不是 "v1.2"）──
grep -c '"cahac": *"1.2"' <设备侧写入代码>        # ⇒ ≥1
grep -c '"cahac": *"v1.2"' <设备侧写入代码>       # ⇒ 【必须为 0】（★ D-331 的坑）

# ── C-2 12 必填字段（★ 本机侧工具已有，可复用）──
python3 ~/dsh-collab/scripts/cahac-envelope-conformance.py --tiers
#   期望：① 本机侧 = 100%

# ── C-3 举证：回读自己刚写的卡 ──
#   该设备须提供：写一张测试卡 → 回读 → 打印 12 字段齐备

# ── C-4 未接入面清单存在且非空 ──
grep -c '未接入' <该设备的接入卡>                  # ⇒ ≥1（★ 若真的全接入，须写「无」）
```

## 3. ② 举证方式（★ 从「声称」变为「实证」）

### 3.1 举证必须是【卡 + 复跑命令】，不得是【声称】

★ 依本仓纪律：**「凡报未搜到必先给阳性对照」**、**「要原始输出，不要摘要」**。

| ★ 不接受的举证 | ★ 接受的举证 |
|---|---|
| ★「我们已接入 CAHAC」 | ★ **一张卡 + 该卡自身的 `cahac` 回读值 + 复跑命令** |
| ★「我们用的是 v1.2」 | ★ **写入代码里 `grep` 到的字面值** |
| ★「应该没问题」 | ★ **`--tiers` 输出的两行数** |

### 3.2 举证卡的最小形态

```json
{
  "type": "cahac-onboarding-evidence",
  "from": "<设备/session id>",
  "cahac": "1.2",
  "cahac_version_declared": "1.2",
  "write_path": "<该设备写卡走哪个工具/脚本>",
  "evidence": {
    "self_read_cahac": "1.2",
    "probe_command": "<一条可复跑的完整命令>",
    "probe_raw_output": "<未编辑的原始输出>"
  },
  "not_onboarded": ["<未接入的面>"],
  "at": "<真实时刻>"
}
```

## 4. ③ 举证责任与周期（★ 契约的核心空白）

| # | 项 | 规定 |
|---|---|---|
| **R-1** | **谁举证** | ★ **写入方自证** —— ★ 不得由接收方代证（★ 接收方只能核，不能替写方声明） |
| **R-2** | **何时举证** | ★ **① 首次接入时**；★ **② 每次改了写入路径后**（★ 依 `D-332` 的教训：改了盘 ≠ 修好了） |
| **R-3** | **周期复核** | ★ **建议每 30 天**一条快照（★ 可挂到健康管理器的 `--publish`） |
| **R-4** | **谁核** | ★ **异体**（★ 依 S3「不可自审」）—— ★ **本机侧由本线核；设备侧由协调者或另一设备核** |
| **R-5** | **不举证怎么记** | ★ **记 `UNDECIDABLE`（不可判），★ 不得记 OK，★ 也不得记 FAIL** —— ★ 依纪律「空 ≠ 无」 |

## 7. 通道版本条款（★ 用户 2026-10-15 关切①）

> ★ 用户的担忧逐字：★**「旧通道是否也应该挂上去？避免那些设备或者会话还一直用旧通道？」**

### 7.1 为什么要这一条

| ★ | ★ |
|---|---|
| **若不挂旧通道** | ★ 设备可以继续用旧格式发卡 ⇒ ★★ **信封率永远上不去** ⇒ ★ **契约变成【一份没人执行的文档】** |
| **★★ 本线的做法** | ★★ **把「旧格式」也纳入统计** —— ★ **让【继续用旧通道】有【代价】** |

### 7.2 条款（★ 四句）

```
★ ① v1.2 信封是【唯一被推荐】的格式（★ 自本契约生效日起）
★ ② 旧格式卡【仍可读】—— ★ 不破坏既有数据，★ 不要求回溯修改
★★ ③ 但【旧格式卡计入信封率的分母】⇒ 于是「继续用旧通道」会【自动拉低自己的信封率】
★ ④ 弃用日：★ 自弃用日起，旧格式卡【只读不回】（★ 仍可查、★ 不再参与新业务）
```

### 7.3 ★★ 为什么用【读数】而不是【禁令】

> ★★★ **禁令需要人去执行；★ 而读数【自动生效】。**
> ★★ 故本条不写「禁止使用旧通道」，★ 而写「**旧通道的卡计入分母**」——
> ★ **于是不用任何人执法，★ 用旧通道的人自己会看到自己的信封率低。**

### 7.4 判据（★ 可机械核）


## 8. 三类写者（★ 用户 2026-10-15 关切②）

### 8.1 ★★★ 关键区分（★ 由明鉴 2026-10-15 实测确立）

### 8.2 条款（★ 三种写者）

> ★ **契约要的不是「所有卡都有会话身份」，★ 而是「★ 每张卡的写者身份状态【被声明过】」。**

### 9.5 ★★ 回复范围限制（★ 您问的核心）

### 9.6 为什么【限制回复范围】是必要的

> ★★★ **因为【开放回复】会把这套机制变成【另一个讨论通道】** ——
