### 二、建议的 MCP 工具族设计

#### 2.1 切分判据（为什么不是 10 个工具、也不是 1 个）

1. **粒度对齐已有 16 工具的风格**：现有工具是「1 工具 ≈ 1 个业务能力」，**不是 1 端点 = 1 工具**。已有先例：`waimai_charge` 用 `action` 折叠 `overview/records/roi`；`waimai_order_export` 用 `action` 折叠 `query/export`。
2. **同一业务对象 + 同一读写语义 → 合并**（用 `action` 分流）；**只读与写绝不合并**（写需要独占的护栏位与独立确认语义）。
3. **1:1 只在「该端点自身就是一个完整对外动作」时采用**（本例即 `send`：一次真发是一条完整业务事件，不能塞进别的工具当分支）。

⇒ **10 个端点 → 建议 5 个工具**（+1 个待裁决的可选工具）。
⇒ MCP 工具总数 **16 → 21**（含可选项则为 22）。

#### 2.2 命名（合规 + 查重，均已实测）

#### 2.3 五个建议工具（逐条）

##### ① `waimai_im_inbox` — IM 会话总览（读）
- **描述**（≤60 字）：查询 IM 客服会话列表与统筹统计（待回复/已回复/平均响应时长）。
- **schema**：`{ action?: "list"|"stats"（默认 list）、status?: string（空=全部，pending/replied/done）、storeId?: number、search?: string（会话键或客户消息关键词） }`
- **映射**：`action=list` → `GET /api/im/replies?status&storeId&search`；`action=stats` → `GET /api/im/stats`
- **返回**：list → `{sessions[], stats{}}`；stats → `{pending,replied,done,avg_latency_min,today_msgs}`
- **只读／护栏**：只读，无护栏；建议 `timeout: 30000`
- ⚠️ **不要发明端点没有的参数**：`/api/im/replies` 不接受 `limit`（内部硬编码 200）

##### ② `waimai_im_overdue` — 未回复超时清单（读）
- **描述**：查询 IM 未回复会话：实时超时、30 分钟超时、24 小时历史积压三种口径。
- **schema**：`{ action?: "timeout"|"overdue"|"backlog"（默认 timeout）、minutes?: number、hours?: number、seconds?: number、maxMin?: number、today?: boolean、storeId?: number }`
- **映射**：
  - `timeout`（默认） → `GET /api/im/timeout?minutes&hours&seconds&maxMin&today=1`
  - `overdue` → `GET /api/im/overdue?minutes&storeId`
  - `backlog` → `GET /api/im/backlog`（**无参数**，阈值硬编码 1440 分钟）
- **返回**：timeout → `{minutes,total,list[]}`（list 截 50）；overdue → `{overdue[],total,minutes}`；backlog → `{total,list[]}`
- **只读／护栏**：只读；建议 `timeout: 30000`

##### ③ `waimai_im_order_status` — 回复前查订单（读）
- **描述**：按订单号/商品/店铺关键词查询最近订单状态（客服回复前核对）。
- **schema**：`{ q?: string、storeId?: number、limit?: number（默认 20） }`
- **映射**：`GET /api/im/order-status?q&storeId&limit`
- **返回**：`{orders:[{store_id,store,order_no,item,status,amount,count,ts}], total, query}`
- **只读／护栏**：只读，无；建议 `timeout: 30000`

##### ④ `waimai_im_session_handle` — 会话处置/跳转（写）
- **描述**：标记 IM 会话为已处理，或聚焦 IM 工作台到该会话（不发消息）。
- **schema**：`{ action?: "handle"|"focus"（默认 handle）、storeId: number★、sessionKey?: string（handle 必填）、status?: "pending"|"replied"|"done"（默认 done） }`
- **映射**：`handle` → `POST /api/im/session/handle {storeId,sessionKey,status}`；`focus` → `POST /api/im/reply {storeId}`
- **返回**：handle → `{ok:true}`；focus → `{ok,focused,ensured,url}`（★ 软失败：`focused:false` 仍 200，描述里注明）
- **写属性**：本地面板状态位 + 本机窗口副作用，**不触达客户** → **沿用端点语义、不新增 `confirmed`**（与已有 `waimai_alert_handle` 的处理一致：本地软状态写不给确认位）
- **切分判据**：`focus` 与 `handle` 同属「对一个会话做处置」，且 `focus` 自身无业务数据、单独成工具的价值低于成本 ⇒ 合并；★ **替代方案**：若分发版要与 plugin 的 `waimai_focus` 粒度对齐，则拆出 `waimai_im_focus`（则总数 22）

##### ⑤ `waimai_im_send` — 发送/预填 IM 回复（★高危写）
- **描述**：向 IM 会话发送客服回复（默认演练不发送，yes=true 且带审核令牌才真发）。
- **schema**：
  ```
  { storeId: number★, sessionKey: string★, text: string★（≤500 字）,
    mode?: "send"|"prefill"（默认 send）,
    yes?: boolean（默认 false=演练）,
    confirm?: boolean（默认 false；真发需 yes && confirm）,
    approvalToken?: string, tokenTs?: string,   ★ 必须在 schema 里显式声明
    sendPort?: number }
  ```
- **映射**：`POST /api/im/send {storeId,sessionKey,text,yes,confirm,mode,approvalToken,tokenTs,sendPort}`
- **返回**：演练/预填/真发三种形态见 §一 #9，原样透传 `{ok,dryRun,verified,reason}`
- **★ 护栏（MCP 侧只做透传与显式声明，绝不削弱服务端六道闸门）**：
  | 项 | 约定 |
  |---|---|
  | 默认值 | `yes=false`（演练）——**与 `waimai_operate` 的 `yes` 完全同构** |
  | 真发前置 | 服务端要求 `yes && confirm` 双真 + 有效 `approvalToken`（HMAC 绑定 `storeId\|sessionKey\|text\|ts`，10 分钟 TTL） |
  | 令牌来源 | ★ **MCP 侧不提供任何签发工具**（`/api/approval/issue` 用的是另一把 secret `cfg.l3.approval_token`，且绑定 `"r026:"+intent`，★ **与 IM 发送的 `cfg.send.approval_token` 不是同一把**）⇒ IM 令牌只能由持 secret 的审核侧离线签发 |
  | 透传 | 完全对齐 `waimai_action` 的 `approvalToken/approvalTs` 透传写法（`mcp-core.js:524`） |
  | ★ 顺带修 | `waimai_action` 的 `inputSchema` **没声明** `approvalToken/approvalTs` 却在实现里透传（`:245-251` vs `:524`），而 `additionalProperties:false` 会让守规客户端**发不出令牌**——新工具**必须显式声明**，并可顺带补 `waimai_action`（待裁决） |

##### （可选，P3 待裁决）`waimai_im_collecting` — 采集避让状态（读）
- 描述：查询各店 IM 详情采集是否进行中（驱动浏览器前避让）。
- schema：`{}`；映射 `GET /api/im/collecting`；返回 `{collecting:{<storeId>:bool}}`
- ★ **建议默认不暴露**：`mcp-core.js:210-215` 的架构边界注释写明「本列表 = 用户侧可见的纯业务能力，**不含服务端机制**」，采集避让标记属采集器内部机制（且 `lean4Check` ⑦ 有边界守卫）；真发路径已在服务端自查避让（`im-send.js:114-119`）
- 裁决结果若为「暴露」，名字已过门：`waimai_im_collecting`

**★ 一条必须写进来的实测反证（不是判断，是事实）**：

> **分发版现在就已经带着写工具**——动作类两个：`waimai_operate`（`lib/mcp-core.js:237`）与 `waimai_action`（`:245`），分别 `POST /api/stores/:id/operate` 与 `POST /api/action`，真实改价/上下架/回复（默认演练、`yes`/`confirmed=true` 才真写）；另有状态变更类一个 `waimai_alert_handle`（`:515`，`POST /api/alerts/:id/handle`）。实测分发版 `runToolInner` 共 3 处 `method: "POST"`。

#### 2.2 情形 A：节点允许自控采集

> **对应立场**：用户目标 G4（一电脑一 agent 加载分发的 MCP）＋ 分发版已含写工具的既成事实。
> **与之冲突的既有共识**：甲（写权不落门店）、乙（只读传感器）、丙（凭据不落节点）。

##### A-1 工具设计

| 工具名 | 类型 | inputSchema | 说明 |
|---|---|---|---|
| `waimai_collect_status` | 只读 | `{storeId?: number}` | 映射 `GET /api/collect/switch`。`storeId` 缺省=本机全部 |
| `waimai_collect_switch` | **写** | `{storeId?: number, action:"on"\|"off", confirm: boolean, reason?: string}`，`required:["action","confirm"]` | 映射 `POST /api/collect/switch`；`reason` 仅入本地审计日志，**不发给后端**（后端不接受该字段） |

##### A-2 护栏（逐条对应一个真实失败面）

| # | 护栏 | 防的是什么（实测依据） |
|---|---|---|
| A2-1 | **默认演练**：`confirm !== true` 时不发 POST，只回“将执行什么 + 当前 `cdpUp/cdpTotal` + 预期影响” | 对齐 `waimai_operate`/`waimai_action` 的既有约定（`:237/:245` 描述逐字“默认演练”）；一次 LLM 幻觉调用不应停掉 10 店采集 |
| A2-2 | **写前必读**：写分支内先调一次 `GET /api/collect/switch`，把结果放进回执 | 服务端 POST 的 `results[]` 是“每步已尝试”，**不代表真的停/真的起**；关闭后需要 `cdpUp=0` 才是真停 |
| A2-3 | **幂等短路**：目标值与当前 `enabled` 相同 ⇒ 不发 POST，返回“当前已是该状态，未执行” | 端点无幂等（`server.js:399-477` 无条件重复 bootout/bootstrap）；重复 off 会对已 unload 的标签再 bootout 12 次 |
| A2-4 | **storeId 归属校验**：当传入 `storeId` 且与本节点注册的 `store_id` 不一致 ⇒ 拒绝 | ★ 端点**根本不分店**：`POST` 不接受 `storeId`（`:399-402` 只读 `action`），off 时按**机器级** pattern 杀 Chrome（`:467-469` `plat.chromeInstancePattern()` / `killByPattern`）；`GET` 则遍历 `store.listStores()` 探测全机端口（`:382`）。⇒ **一店一机时作用域恰好等于 1 店；多店残留配置时会误伤邻店**，故须由工具层补归属校验 |
| A2-5 | **回执字段收敛**：只返回 `{ok, enabled, cdpUp, cdpTotal, results}`，**不整包 dump** `r.data` | 对齐既有 `waimai_review_daily` 只取文本的写法（`:520`）；整包在 60000 字符处截断（`:85-88`）会截掉 `cdp[]` 明细 |
| A2-6 | **断档提示（★ 关键，但服务端当前无能力）**：off 的回执必须显式写明“采集已停且看门狗已被 `disable`，**不会自愈**，需人工或定时器恢复” | off 分支 `launchctl bootout` **+ `disable`** 是双保险（文档记为“仅 bootout 会被自愈重新 bootstrap”，`docs/collect-switch.md` §二/§五）⇒ **这正是“误关即断档”的机制原因** |

**★ A2-7 未决的一个真实缺口（本件只登记，不设计）**：
MCP 层无法提供“N 分钟后自动恢复”护栏——`/api/collect/switch` 没有该参数，`launchd` 侧又被 `disable` 掉了。
⇒ 若采纳情形 A，**建议同步加一个中心侧/节点侧的“采集开关租约”**（到期自动 `on`），否则“误关断档”只能靠人发现。这不是本次工具设计能覆盖的，须单独立项。

##### A-3 与既有共识的落差，如实列出

| 落差 | 程度 |
|---|---|
| 与“写权不落门店”直接冲突 | **强**（但分发版已有 2 个写工具，冲突不是本次新增） |
| 一键停采集 = 该店**全部数据源中断**（订单/评价/IM 全在 Chrome 里） | **强**（比“改错一个价”影响面大） |

##### B-1★ 建议同步补一条**结构性判据**（这是情形 B 独有、且当前完全缺失的东西）

> ★ **这正是把 D1 从“讨论”变成“可核验事实”的成本，也是它的价值所在。**

##### B-3 ★ 情形 B 的真实代价（必须写明，不能只讲好处）

> `node-executor.py` 执行任务卡时走 `subprocess.run(cmd, shell=True, ...)`（`:209`），其“动作白名单”声明为 `shell/info/status/ollama/scan/自定义`（`:28`）——**“自定义”即无封闭枚举**。

> ⇒ 所以：**“只允许中心控制”并不等于“节点能力更小”**，它等于**“把节点写权上收到中心，把爆炸半径从节点转移到中心（及其凭据）”**。
> 这个转移是 D1/D2 的实质内容（D2：节点电脑归谁），应在裁决时一并看。

##### B-4 情形 B 的爆炸半径变化

| 面 | 情形 A | 情形 B |

### 一、协议规范要点（逐条附来源 URL）

#### 1.1 协议版本与协商规则

【官方规范】MCP 版本号采用 `YYYY-MM-DD` 字符串格式，表示「最后一次发生不向后兼容变更的日期」。**只要变更保持向后兼容，版本号就不递增**。

【官方规范】版本分三态：**Draft**（草稿，不可消费）/ **Current**（当前，可继续接受向后兼容变更）/ **Final**（历史完整版，不再变更）。
**当前（Current）协议版本为 `2026-07-28`。**

来源：<https://modelcontextprotocol.io/specification/versioning>

【官方规范】规范把两个时代明确分开（术语表原文）：

| 术语 | 定义 |
|---|---|
| **Modern** | 通过**每请求元数据**（per-request metadata）传递版本、身份与能力的协议版本（`2026-07-28` 及以后） |
| **Legacy** | 用 `initialize` 握手建立会话的协议版本（`2025-11-25` 及以前） |
| **Dual-era** | 同时支持现代版与旧版握手的实现 |

【官方规范】★ **现代版没有协商握手**（原文：「There is no negotiation handshake.」）。每个请求各自携带自己的协议版本，服务器**逐个请求独立接受或拒绝**：

- 客户端在每个请求的 `_meta` 字段里声明协议版本，键名为 `io.modelcontextprotocol/protocolVersion`。
- 走 HTTP 时，同一值另放在 `MCP-Protocol-Version` 请求头。
- 服务器不支持所请求版本时，**MUST** 返回 `UnsupportedProtocolVersionError`，错误码 **`-32022`**，并在 `data.supported` 中列出自己支持的版本：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32022,
    "message": "Unsupported protocol version",
    "data": {
      "supported": ["2026-07-28", "2025-11-25"],
      "requested": "1900-01-01"
    }
  }
}
```

- 客户端 **SHOULD** 从 `supported` 列表里挑一个双方都支持的版本重试；若无可选版本则向用户报错。
- 服务器 **MUST** 实现 `server/discover`。客户端 **MAY** 在发任何其他请求前先调它，一次性拿到服务器的支持版本、能力与身份——但**不是必须**：客户端可以直接发任意 RPC，收到版本错误再处理。
- 客户端与服务器 **MAY** 同时支持多个协议版本。

来源：
<https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning>
<https://modelcontextprotocol.io/specification/2026-07-28/basic/index#meta>
<https://modelcontextprotocol.io/specification/2026-07-28/server/discover>

【官方规范】`server/discover` 是「现代版」的强制 RPC，返回服务器支持的协议版本、能力与身份。

来源：<https://modelcontextprotocol.io/specification/2026-07-28/server/discover>

#### 1.2 tools / prompts / resources 各自该装什么（官方定义）

【官方规范】官方「理解 MCP 服务器」文档给出了三分法的核心表，并以「**谁控制它**」作为分界：

| 特性 | 官方解释 | 官方举例 | 谁控制 |
|---|---|---|---|
| **Tools** | 「你的 LLM 可以主动调用、并基于用户请求自行决定何时使用的函数。工具可以写数据库、调外部 API、改文件或触发其他逻辑。」 | Search flights / Send messages / Create calendar events | **Model** |
| **Resources** | 「被动的数据源，提供对信息的只读访问作为上下文，例如文件内容、数据库 schema 或 API 文档。」 | Retrieve documents / Access knowledge bases / Read calendars | **Application** |
| **Prompts** | 「预置的指令模板，告诉模型如何配合特定的工具与资源工作。」 | Plan a vacation / Summarize my meetings / Draft an email | **User** |

来源：<https://modelcontextprotocol.io/docs/2026-07-28/learn/server-concepts>

【官方规范】tools 页进一步定义交互模型：工具是 **model-controlled**——模型可基于上下文理解与用户提示自动发现并调用。但协议本身**不强制**任何特定交互模式。

【官方规范】prompts 页：prompts 是**用户控制**的，需要**显式调用**而非自动触发；类似 resources，prompts 支持**参数补全（argument completion）**帮助用户发现合法取值。

【官方规范】resources 页：resources 支持 `resources/subscribe` 订阅与变更通知；resource templates 通过 `uriTemplate` 暴露**参数化的资源族**。

来源：
<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>
<https://modelcontextprotocol.io/specification/2026-07-28/server/prompts>
<https://modelcontextprotocol.io/specification/2026-07-28/server/resources>

【官方规范】官方对「一个工具做多少事」的措辞：工具是「schema 定义的接口」，且「**Each tool performs a single operation with clearly defined inputs and outputs**」（每个工具执行单一操作）。

#### 1.3 工具命名：官方有没有规范？

【官方规范】官方**只有一条**关于工具名（`Tool Names`）的规定，且全部是 **SHOULD**（非 MUST）：

- 长度 **SHOULD** 在 **1–128 字符**之间（含端点）。
- 工具名 **SHOULD** 被视为**大小写敏感**。
- **SHOULD** 只允许这些字符：大小写 ASCII 字母（A-Z, a-z）、数字（0-9）、下划线 `_`、连字符 `-`、点 `.`。
- 工具名 **SHOULD NOT** 含空格、逗号或其他特殊字符。
- 工具名 **SHOULD** 在单个服务器内唯一。
- 官方给出的**合法示例**（注意三种风格并列）：`getUser`、`DATA_EXPORT_v2`、`admin.tools.list`

【官方规范】★ 官方**没有**规定必须用 snake_case，也**没有**规定必须加前缀，也**没有**规定动词-名词结构。规范对命名风格是中立的。

来源：<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>（小节 `#### Tool Names`）

【官方规范】关于**跨服务器冲突**，规范明确承认并给出策略建议：

> 工具名唯一性**只在一个服务器范围内**。聚合多个服务器工具的客户端或代理 **MAY** 遇到命名冲突（例如两个服务器都暴露 `search` 工具），**SHOULD** 实现消歧策略，**例如给工具名加服务器标识前缀**。
> 服务器 `name`（来自 `serverInfo`）**不保证**跨服务器唯一，**SHOULD NOT** 依赖它做消歧。

来源：<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>

**结论**：【官方规范】只约束「字符集 + 长度 + 服务器内唯一」；**前缀与 snake_case 属于【社区惯例】，不是官方规范**。

【社区惯例】Anthropic 官方技能包的 MCP 构建指南给出的命名约定（**非 MCP 规范，属厂商生态指南**）：

- 工具名用 **snake_case**：`search_users`、`create_project`、`get_channel_info`
- **包含服务前缀**：理由原文是「Anticipate that your MCP server may be used alongside other MCP servers」——用 `slack_send_message` 而不是 `send_message`，用 `github_create_issue` 而不是 `create_issue`
- 格式：`{service}_{action}_{resource}`
- **动作为导向**：以动词开头（get、list、search、create 等）
- **具体化**：避免可能与别的服务器冲突的通用名
- 服务器命名：Python `{service}_mcp`（如 `slack_mcp`）；Node/TypeScript `{service}-mcp-server`（如 `slack-mcp-server`）；名字应通用、可从任务描述推断、**不带版本号**

来源：<https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md>

#### 1.4 错误处理规范

【官方规范】工具使用**两套**错误上报机制，分工明确：

**（1）协议错误（Protocol Errors）**——请求结构本身的问题，模型较难自行修复：

- 未知工具（unknown tool）
- 格式错误的请求（不满足 `CallToolRequest` schema）
- 服务器错误

以标准 JSON-RPC 错误返回：

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "error": {
    "code": -32602,
    "message": "Unknown tool: invalid_tool_name"
  }
}
```

**（2）工具执行错误（Tool Execution Errors）**——含可供模型自我纠正并重试的**可操作反馈**：

- API 失败
- 输入校验错误（如日期格式错、取值越界）
- 业务逻辑错误

**在工具结果里以 `isError: true` 上报**（不是协议级错误）：

```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "result": {
    "resultType": "complete",
    "content": [
      {
        "type": "text",
        "text": "Invalid departure date: must be in the future. Current date is 08/08/2025."
      }
    ],
    "isError": true
  }
}
```

【官方规范】客户端分工要求：

- 客户端 **MAY** 把协议错误提供给语言模型，但**这些错误较难带来成功恢复**。
- 客户端 **SHOULD** 把工具执行错误提供给语言模型，以**启用自我纠正**。

来源：<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>（小节 `## Error Handling`）

【官方规范】错误码分配规则（`basic/index` 原文）：

- MCP 使用标准 JSON-RPC 2.0 错误码（`-32700`、`-32600` 至 `-32603`）。
- JSON-RPC 2.0 保留 `-32000` 至 `-32099` 给实现自定义，MCP 内部再细分：
  - **`-32000` 至 `-32019`——legacy**。该子区间曾被旧版分配，新实现**不应**使用；除 `-32002` 外，接收方**（原文建议）应将其视为通用错误**。
  - **`-32020` 至 `-32099`——保留给 MCP 规范**：

| 错误码 | 名称 |
|---|---|
| `-32020` | `HeaderMismatch` |
| `-32021` | `MissingRequiredClientCapability` |
| `-32022` | `UnsupportedProtocolVersion` |

- `-32002` —— 资源未找到（`2025-11-25` 及更早使用；已被 `-32602` 取代）。规范明确要求服务器**接受** `-32002` 作为资源未找到的合法返回。

【官方规范】工具不存在时用 **`-32602`（Invalid params）**。

来源：
<https://modelcontextprotocol.io/specification/2026-07-28/basic/index>
<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>

【官方规范】prompts 的错误处理：**缺少必需参数 → `-32602`（Invalid params）**；服务器 **SHOULD** 在处理前校验 prompt 参数。

来源：<https://modelcontextprotocol.io/specification/2026-07-28/server/prompts>

【社区惯例】Anthropic 指南补充的工程建议（非规范）：使用标准 JSON-RPC 错误码；**工具错误报在结果对象内而非协议级**；提供有帮助、具体、**带下一步建议**的错误消息；不要暴露内部实现细节；出错时正确清理资源。示例：

```typescript
} catch (error) {
  return {
    isError: true,
    content: [{ type: "text",
      text: `Error: ${error.message}. Try using filter='active_only' to reduce results.` }]
  };
}
```

来源：<https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md>

#### 1.5 `annotations` 字段——这是标准吗？怎么用？

**【官方规范】是标准，且自 2025-06-18 起就在 schema 里。** 工具定义中 `annotations` 是**可选**字段，类型为 `ToolAnnotations` 接口。

【官方规范】`ToolAnnotations` 的完整字段与**默认值**（取自规范 schema 原文）：

| 字段 | 类型 | 默认值 | 官方说明（原文要点） |
|---|---|---|---|
| `title` | string | — | 工具的人类可读标题 |
| `readOnlyHint` | boolean | **false** | 若为 true，该工具**不修改其环境** |
| `destructiveHint` | boolean | **true** | 若为 true，工具可能对环境执行**破坏性更新**；若为 false，工具**只做增量更新**。（**仅当 `readOnlyHint == false` 时有意义**） |
| `idempotentHint` | boolean | **false** | 若为 true，用相同参数反复调用**对环境无额外影响**。（**仅当 `readOnlyHint == false` 时有意义**） |
| `openWorldHint` | boolean | **true** | 若为 true，该工具可能与「开放世界」的外部实体交互 |

【官方规范】★ 关键定性——**它们全是「提示（hints）」，不是保证**。规范原文：

> NOTE: all properties in `ToolAnnotations` are **hints**. ... Clients should never make tool use decisions based on `ToolAnnotations` received from untrusted servers.

【官方规范】★ 安全约束（Warning 原文）：

> 出于信任与安全考虑，**客户端 MUST 把工具注解视为不可信，除非它们来自可信服务器。**

【官方规范】显示名优先级：`title` → `annotations.title` → `name`。

来源：
<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>
<https://modelcontextprotocol.io/specification/2026-07-28/schema#toolannotations>

【社区惯例】Anthropic 指南要求「Provide tool annotations (readOnlyHint, destructiveHint, idempotentHint, openWorldHint)」，并重申：「Annotations are hints, not security guarantees. Clients should not make security-critical decisions based solely on annotations.」

来源：<https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md>

【官方规范】**resources 另有一套注解**（与工具注解不同），字段为：

- `audience`：数组，合法值 `"user"` 与 `"assistant"`，表示目标受众。
- `priority`：0.0–1.0 的数字，1 表示最重要（相当于必需），0 表示最不重要（完全可选）。
- `lastModified`：ISO 8601 时间戳，如 `"2025-01-12T15:00:58Z"`。

用途：按受众过滤资源、按优先级决定是否纳入上下文、显示修改时间或按新旧排序。

来源：<https://modelcontextprotocol.io/specification/2026-07-28/server/resources>（小节 `### Annotations`）

#### 1.6 分页（`nextCursor`）

【官方规范】`tools/list`、`prompts/list`、`resources/list`、`resources/templates/list` 均支持游标分页：

- 请求参数带可选 `cursor`。
- 响应带 `nextCursor`（无更多页时可省略）。

`tools/list` 响应示例（规范原文）：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "complete",
    "tools": [ /* ... */ ],
    "nextCursor": "next-page-cursor",
    "ttlMs": 300000,
    "cacheScope": "public"
  }
}
```

来源：
<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>
<https://modelcontextprotocol.io/specification/2026-07-28/server/resources>

【官方规范】`2026-07-28` 版新增列表**缓存元数据**：列表与读取响应可带 `ttlMs`（缓存存活毫秒）与 `cacheScope`（`"public"` / `"private"`）。resources 读取支持缓存，见 `server/utilities/caching`。

来源：<https://modelcontextprotocol.io/specification/2026-07-28/server/resources>

【官方规范】列表顺序确定性：服务器 **SHOULD** 以**确定性顺序**返回工具（底层集合未变时，跨请求顺序一致）。理由原文：确定性顺序让客户端能可靠缓存工具列表，并**在工具被纳入模型上下文时提升 LLM 的 prompt cache 命中率**。

来源：<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>

#### 1.7 版本演进 / 弃用策略

【官方规范】弃用政策由 **SEP-2596** 采纳，定义三个特性状态：

| 状态 | 含义 | 实现方预期 |
|---|---|---|
| **Active** | 属于当前规范版本 | 按该特性的规范性要求实现 |
| **Deprecated** | 仍在规范中，但已排定移除。已记录迁移路径 | 新实现不应采用；既有实现应在最早移除日之前完成迁移 |
| **Removed** | 已从 `draft` 删除，下一个 Current 版本中不存在 | 面向该下一版本实现时**不得**依赖该特性 |

【官方规范】弃用窗口硬约束：**最短弃用窗口至少十二个月**；窗口从「该特性**首次被标记为 Deprecated 的那个规范版本发布**」起算（**不是**从 SEP 转 Final 的日期起算）。另有一项**加速移除例外（expedited-removal exception）**可短至**九十天**。

【官方规范】弃用是一项规范变更，因此**需要 SEP**，且弃用 SEP 必须：按名识别特性并链接 `schema.ts` 定义；陈述理由；记录迁移路径（或明确声明无需迁移）；指定最短弃用窗口（≥12 个月）。若迁移路径指向替代特性，该替代特性必须在弃用生效的同一版本中已处于 Active。

【官方规范】弃用登记表是**派生视图**，与各特性的弃用声明及 changelog 条目保持一致——**后者才是规范性记录**。

【官方规范】SDK 例外：「Removed from the specification does not oblige an SDK to drop the feature from releases（从规范移除并不强制 SDK 从发行版中删除该特性）。」该时间线由各 SDK 自己的版本支持政策决定。

来源：
<https://modelcontextprotocol.io/community/feature-lifecycle>
<https://modelcontextprotocol.io/specification/versioning>
<https://modelcontextprotocol.io/specification/2026-07-28/deprecated>

#### 1.8 JSON-RPC 与传输基础（补充）

【官方规范】客户端与服务器间**所有**消息 **MUST** 遵循 **JSON-RPC 2.0**。请求 ID **MUST** 为字符串或整数，且**与基础 JSON-RPC 不同，ID MUST NOT 为 null**；同一会话内请求 ID **MUST NOT** 重复使用。

【官方规范】传输与鉴权：使用 HTTP 传输的实现 **SHOULD** 遵循 MCP 的 Authorization 框架；使用 **STDIO 传输的实现 SHOULD NOT 遵循该框架**，而**改从环境变量获取凭据**。

【官方规范】JSON Schema：默认方言为 **JSON Schema 2020-12**（无 `$schema` 字段时）；实现 **MUST** 至少支持 2020-12，**SHOULD** 记录额外支持的方言。`inputSchema` **MUST** 是合法 JSON Schema 对象（**不能为 `null`**）。

【官方规范】无参数工具的合法写法（官方给出两种，并**推荐前者**）：

- `{ "type": "object", "additionalProperties": false }` —— **推荐**：显式只接受空对象
- `{ "type": "object" }` —— 接受任意对象（含带属性）

来源：<https://modelcontextprotocol.io/specification/2026-07-28/basic/index>

#### 1.9 安全：官方 MUST 级要求（与错误可诊断性/限流/超时相关）

【官方规范】tools 页 `## Security Considerations` 原文：

1. 服务器 **MUST**：
   - 校验所有工具输入
   - 实现适当的访问控制
   - **对工具调用限流（Rate limit tool invocations）**
   - 清洗工具输出
2. 客户端 **SHOULD**：
   - 对敏感操作弹出用户确认
   - 调用服务器前**向用户展示工具输入**，以避免恶意或意外的数据外泄
   - 传给 LLM 前校验工具结果
   - 遵循 `$ref` 解析要求
   - **为工具调用实现超时（Implement timeouts for tool calls）**
   - **记录工具使用以用于审计**

来源：<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>（小节 `## Security Considerations`）

【官方规范】resources 页 `## Security Considerations` 原文：

1. 服务器 **MUST** 校验所有资源 URI
2. 敏感资源 **SHOULD** 实现访问控制
3. 二进制数据 **MUST** 正确编码
4. 操作前 **SHOULD** 检查资源权限
5. 服务 `file://` 资源时，服务器 **MUST** 清洗文件路径以防目录遍历攻击

来源：<https://modelcontextprotocol.io/specification/2026-07-28/server/resources>

【官方规范】tools 页 Warning：出于信任与安全，**SHOULD** 始终有一个人在环（human in the loop）并具备拒绝工具调用的能力。应用 **SHOULD**：提供 UI 明示向 AI 模型暴露了哪些工具；工具被调用时插入明确的视觉提示；对操作展示确认提示。

来源：<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>

【官方规范】官方安全最佳实践文档收录的攻击面与缓解（章节列表）：Confused Deputy Problem、Token Passthrough、Server-Side Request Forgery (SSRF)、State Handle Hijacking、Local MCP Server Compromise、OAuth Authorization URL Validation、stdio Transport Security in Proxy Scenarios、Mix-Up Attacks、Localhost Redirect URI Impersonation、CIMD Trust Policies、Scope Minimization。

【官方规范】**Scope Minimization（作用域最小化）**要点：宽泛 scope（`files:*`、`db:*`、`admin:*`）会扩大爆炸半径、提高撤销摩擦、掩盖审计轨迹、允许权限链式提升；缓解方向是最小化授予的 scope。

【官方规范】stdio 代理场景安全要求中有一条与可诊断性相关的措辞：**展示将要执行的确切命令，不得截断（without truncation）**。

来源：<https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices>

#### 1.10 大输出截断 / 限流 / 超时：官方是否有通行做法？

需要**严格区分**官方规定与社区做法：

- 【官方规范】**限流**：服务器 **MUST** 对工具调用限流（见 1.9）。这是 MUST 级要求，但规范**未规定**具体算法、阈值或错误码。
- 【官方规范】**超时**：客户端 **SHOULD** 为工具调用实现超时（见 1.9）。规范**未规定**具体时长。
- 【官方规范】**大输出截断**：★ **未找到权威来源**。规范正文中**没有**关于「工具输出过大应如何截断」「标准截断标记」「分页输出」的规范性条款。规范中唯一与「truncation」相关的措辞出现在安全文档的 stdio 代理条款里，且语义是「展示命令时**不要**截断」，与工具输出截断无关。
- 【官方规范】`basic/index` 提到：「timeout raised inside an SDK」这类情况**当前未被本规范分配错误码**——即 SDK 内部超时属于未标准化区域。

【社区惯例】Anthropic 指南对分页的工程建议（**非规范**）：实现分页用 `offset` 或游标；返回分页元数据 `has_more`、`next_offset`/`next_cursor`、`total_count`；**绝不把所有结果载入内存**；默认限制 20–50 条。

来源：<https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md>

**小结**：「大输出截断」在 MCP 中**不是**有官方规范的领域，属于实现自由度；把它当作「MCP 规定」是没有来源支撑的说法。

### 二、工具命名与粒度（官方 + 社区惯例）

#### 2.1 命名

| 维度 | 【官方规范】 | 【社区惯例（Anthropic 指南）】 |
|---|---|---|
| 命名风格 | **无规定**（仅约束字符集） | snake_case |
| 服务前缀 | **无规定**；但跨服务器冲突时客户端 **SHOULD** 加服务器标识前缀消歧 | **要求加**，格式 `{service}_{action}_{resource}` |
| 长度 | 1–128 字符（SHOULD） | 未规定 |
| 允许字符 | A-Z a-z 0-9 `_` `-` `.`（SHOULD） | 未规定 |
| 大小写 | 视为大小写敏感（SHOULD） | 未规定 |
| 唯一性 | 服务器内唯一（SHOULD）；跨服务器**不保证** | 未规定 |
| 词序 | **无规定** | 动词开头（get/list/search/create） |

官方合法示例**三种风格并列**（`getUser`、`DATA_EXPORT_v2`、`admin.tools.list`）这一事实本身说明：**官方对风格中立**。

#### 2.2 粒度

【官方规范】官方措辞：「Each tool performs a single operation with clearly defined inputs and outputs.」（每个工具执行单一操作，输入输出清晰定义。）

来源：<https://modelcontextprotocol.io/docs/2026-07-28/learn/server-concepts>

【社区惯例】Anthropic 指南：「Keep tool operations focused and atomic.」（保持工具操作聚焦且原子。）

来源：<https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md>

【个别实现的做法】但**实测显示官方参考服务器并不一致**——`sequentialthinking` 用**单个工具**承载全部功能（9 个属性参数、2781 字符描述），与「一事一工具」相反。详见第三节。

#### 2.3 描述长度

- 【官方规范】**未找到权威来源**：规范**没有**对 `description` 长度作任何数值约束。规范只要求服务器 `description` 为「Human-readable description of functionality」。
- 【社区惯例】Anthropic 指南的定性要求：「Tool descriptions must narrowly and unambiguously describe functionality（必须狭窄且无歧义地描述功能）」「Descriptions must precisely match actual functionality（必须与实际功能精确一致）」。**未给出长度数值。**
- 【个别实现的做法】实测描述长度跨度极大：Playwright 最短 14 字符（`browser_close` → 「Close the browser」），sequential-thinking 2781 字符。**不存在业界统一长度标准。**

#### 3.2 关键对照结论

**（1）官方参考服务器自己的命名风格就不统一。**
`memory` / `filesystem` / `github` 用 `snake_case`；`everything` 用 **`kebab-case`**（`get-sum`、`get-annotated-message`、`trigger-long-running-operation`）；`sequentialthinking` 是一个无分隔符单词。
→ 说明「snake_case 是 MCP 规定」是**没有依据的**；它是 Anthropic 生态指南的**惯例**。

**（2）服务前缀在官方参考服务器中普遍缺失。**
`memory`、`filesystem`、`github` 的工具名**都不带服务前缀**（`read_file`、`create_issue`），只有 `playwright`（`browser_*`）带。
→ Anthropic 指南推荐的「加服务前缀」在实际官方参考实现里**并未被一致遵守**。

**（3）只读/写入区分方式：两派，且泾渭分明。**

| 派别 | 做法 | 样本 |
|---|---|---|
| **注解派** | 用 `annotations.readOnlyHint` 区分；读工具 `ro:true`，写工具 `ro:false` + `destructiveHint` | memory、everything、filesystem、playwright |
| **裸奔派** | 完全不用注解，靠工具名动词（`get_`/`list_`/`search_` vs `create_`/`update_`/`merge_`）暗示 | github |

★ 值得注意：**注解派内部对「写」的标注也不一致**——
- `filesystem` 的读写工具**同时**给了 `ro` 与 `dh`。
- `memory` 的**读**工具 `ro:true`，**删除**工具 `ro:false`+`dh:true`+`ih:true`，而 `create_entities` 等**写**工具 `ro:false` 但 `dh:false`（属「只做增量更新」的语义）。
- `playwright` 的 `browser_close`/`browser_click` 都标 `dh:true`（把「点击」也标为潜在破坏性）；而 `browser_take_screenshot`/`browser_find` 标 `ro:true`。
- `everything` 把 `trigger-long-running-operation` 标为 `ro:true`，把 `gzip-file-as-resource` 标为 `ro:false dh:false ow:true`。

**（4）描述长度无共识**：Playwright 极简（14 字符），sequential-thinking 极繁（2781 字符），github 中庸（avg 47）。同属官方参考的 `everything`（avg ≈95）与 `sequentialthinking`（2781）差距达 29 倍。

**（5）工具数量无「标准值」**：实测跨度 1（sequentialthinking）到 26（github）。**官方从未规定工具数下限或上限。**

**（6）★ 生态时效警示：大量「知名」服务器已被归档。**
官方 `modelcontextprotocol/servers` README 明确：该仓库「只托管 MCP steering group 维护的**少量**参考服务器」，且「这些服务器**意在作为参考实现**……**不是生产就绪方案**」。
当前**活跃**参考服务器仅 **7 个**：Everything、Fetch、Filesystem、Git、Memory、Sequential Thinking、Time。
**已归档**的包括常被引用的：**GitHub、GitLab、PostgreSQL、Puppeteer、Slack、SQLite、Redis、Sentry、Google Drive、Google Maps、Brave Search、AWS KB Retrieval、EverArt**。
另注：**HTTP+SSE 传输已弃用**（见 1.2），Anthropic 指南亦称「Avoid SSE (deprecated in favor of streamable HTTP)」。

来源：
<https://github.com/modelcontextprotocol/servers>
<https://github.com/modelcontextprotocol/servers-archived>
<https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md>

**（7）prompts / resources 的实际普及率很低。**
6 个样本中，**只有 `everything` 一个**同时提供 prompts（4）与 resources（7）——而 `everything` 的定位本就是「Reference / **test** server with prompts, resources, and tools」，即专门用来演示这三类特性的测试服务器。
其余 5 个样本中 4 个是 **0 prompts / 0 resources**。
→ 【个别实现的做法】暗示：真实世界中「只做 tools」是绝大多数服务器的形态。

### 四、成熟度判据清单（可逐条打勾）

> 本节每条均标注依据来源。**MUST** 级为规范强制；**SHOULD** 级为规范建议；「生态实践」为样本实测得出的常见做法，**非规范要求**。

#### A. 协议层（官方 MUST / SHOULD）

- [ ] **A1** 【MUST】所有消息遵循 **JSON-RPC 2.0**
- [ ] **A2** 【MUST】请求 ID 为字符串或整数，**不得为 null**；同一会话内不重复使用
- [ ] **A3** 【MUST】不支持所请求协议版本时返回 `-32022` `UnsupportedProtocolVersionError`，并在 `data.supported` 列出支持版本
- [ ] **A4** 【MUST】实现 `server/discover`（现代版 `2026-07-28` 起强制）
- [ ] **A5** 【MUST】`inputSchema` 为合法 JSON Schema 对象，**不得为 `null`**
- [ ] **A6** 【MUST】支持 JSON Schema **2020-12**；使用其他方言时显式声明 `$schema`
- [ ] **A7** 【SHOULD】STDIO 传输从**环境变量**获取凭据（**不应**走 HTTP Authorization 框架）
- [ ] **A8** 【SHOULD】STDIO 传输**不向 stdout 写日志**（日志走 stderr）—— 亦为 Anthropic 指南明示

来源：<https://modelcontextprotocol.io/specification/2026-07-28/basic/index>、<https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning>、<https://modelcontextprotocol.io/specification/2026-07-28/server/discover>

#### B. 工具定义层（官方 SHOULD + schema 字段）

- [ ] **B1** 【SHOULD】工具名 1–128 字符
- [ ] **B2** 【SHOULD】工具名仅含 `A-Z a-z 0-9 _ - .`
- [ ] **B3** 【SHOULD】工具名不含空格/逗号/特殊字符
- [ ] **B4** 【SHOULD】工具名在服务器内唯一
- [ ] **B5** 【SHOULD】`tools/list` 返回**确定性顺序**（利于客户端缓存与 LLM prompt cache 命中）
- [ ] **B6** 【MUST NOT】`tools/list` 结果按连接变化或受同连接其他请求副作用影响
- [ ] **B7** 【SHOULD】每个工具含 `title`（人类可读显示名；优先级 `title` → `annotations.title` → `name`）
- [ ] **B8** 【SHOULD】每个工具含 `description`（人类可读功能描述）——【社区惯例】须「狭窄无歧义」且「与实际功能精确一致」
- [ ] **B9** 【生态实践】无参数工具用 `{ "type":"object", "additionalProperties": false }`（官方**推荐**写法）

来源：<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>

#### C. 注解与安全标注

- [ ] **C1** 【官方字段】为**每个**工具提供 `annotations`
- [ ] **C2** 【官方字段】只读工具置 `readOnlyHint: true`
- [ ] **C3** 【官方字段】写工具显式声明 `destructiveHint`——★ **注意其默认值为 `true`**，不声明即被客户端按「可能破坏」对待
- [ ] **C4** 【官方字段】幂等工具置 `idempotentHint: true`（仅当 `readOnlyHint == false` 时有意义）
- [ ] **C5** 【官方字段】与外部世界交互的工具置 `openWorldHint: true`（默认即为 `true`）
- [ ] **C6** 【官方 MUST】服务器校验所有工具输入
- [ ] **C7** 【官方 MUST】服务器实现访问控制
- [ ] **C8** 【官方 MUST】服务器**对工具调用限流**
- [ ] **C9** 【官方 MUST】服务器清洗工具输出
- [ ] **C10** 【官方 SHOULD】客户端为工具调用实现**超时**
- [ ] **C11** 【官方 SHOULD】客户端记录工具使用以**供审计**
- [ ] **C12** 【官方 SHOULD】始终保留人在环，可拒绝工具调用
- [ ] **C13** 【官方 MUST】服务 `file://` 资源时清洗路径防目录遍历
- [ ] **C14** 【官方 MUST】校验所有资源 URI
- [ ] **C15** 【官方 MUST】二进制数据正确编码

来源：<https://modelcontextprotocol.io/specification/2026-07-28/schema#toolannotations>、<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>、<https://modelcontextprotocol.io/specification/2026-07-28/server/resources>

#### D. 错误可诊断性

- [ ] **D1** 【官方规范】区分两类错误：**协议错误**用 JSON-RPC `error`；**工具执行错误**用结果内 `isError: true`
- [ ] **D2** 【官方规范】未知工具返回 `-32602`（Invalid params）
- [ ] **D3** 【官方规范】prompt 缺少必需参数返回 `-32602`
- [ ] **D4** 【官方规范】资源未找到可返回 `-32002`（legacy）或 `-32602`
- [ ] **D5** 【官方规范】自定义错误码只用 `-32020` 至 `-32099`；**不得**使用 legacy 子区间 `-32000`–`-32019`
- [ ] **D6** 【社区惯例】工具执行错误消息含**可操作的下一步建议**，便于模型自我纠正
- [ ] **D7** 【社区惯例】错误消息不暴露内部实现细节

来源：<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>、<https://modelcontextprotocol.io/specification/2026-07-28/basic/index>、<https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md>

#### E. 分页 / 缓存 / 大输出

- [ ] **E1** 【官方字段】列表接口支持 `cursor` 入参
- [ ] **E2** 【官方字段】响应在有多页时返回 `nextCursor`
- [ ] **E3** 【官方字段】列表/读取可提供 `ttlMs` 与 `cacheScope` 缓存元数据（`2026-07-28` 新增）
- [ ] **E4** 【社区惯例】列表类工具**遵守 `limit` 参数**，返回 `has_more` / `next_offset`（或 `next_cursor`）/ `total_count`，默认 20–50 条
- [ ] **E5** 【社区惯例】列表类工具**绝不把全部结果载入内存**
- [ ] **E6** 【★ 无权威来源】**大输出截断**：MCP 规范**未规定**标准做法、截断标记或输出分页协议。此项**不能**作为「合规项」判定。

来源：<https://modelcontextprotocol.io/specification/2026-07-28/server/tools>、<https://github.com/anthropics/skills/blob/main/skills/mcp-builder/reference/mcp_best_practices.md>

#### F. prompts / resources 完备度

- [ ] **F1** 【官方规范】prompts 是**用户控制**、需显式调用的模板（区别于 model-controlled 的 tools）
- [ ] **F2** 【官方规范】prompt 参数带 `required` 标记；含必需参数时校验并返回 `-32602`
- [ ] **F3** 【官方规范】resources 是**应用控制**的被动只读上下文
- [ ] **F4** 【官方字段】resources 提供 `mimeType`
- [ ] **F5** 【官方字段】resources 可用 `annotations.audience` / `priority` / `lastModified`
- [ ] **F6** 【官方字段】需要参数化资源族时用 **resource templates**（`uriTemplate`）
- [ ] **F7** 【官方规范】声明 `listChanged` 则在列表变化时发通知
- [ ] **F8** 【官方规范】prompts / resources 支持**参数补全（completion）**以帮助发现合法取值
- [ ] **★ 校准项**：**「工具数/prompts 数/resources 数」不是成熟度判据**——官方**从未**规定任何数量下限。实测 6 个样本中 5 个是 0 prompts / 0 resources，含全部官方参考实现。

#### G. 版本与演进

- [ ] **G1** 【官方规范】支持 `2026-07-28`（Modern：版本走每请求 `_meta`）
- [ ] **G2** 【官方规范】若需兼容旧客户端，同时支持 `2025-11-25` 及更早的 `initialize` 握手（Dual-era）
- [ ] **G3** 【官方规范】不使用已弃用特性：**Sampling、Roots、Logging**（均自 `2026-07-28` 弃用）、**HTTP+SSE 传输**
- [ ] **G4** 【官方规范】服务器 `name` 不保证跨服务器唯一，**不应**依赖它做消歧
- [ ] **G5** 【社区惯例】服务器命名：Python `{service}_mcp`；Node/TS `{service}-mcp-server`；**不带版本号**

### 五、对照 MTM MCP 的差距

> ★ 本节**只陈述实测事实**，不给建议、不做价值判断。
> **MTM 实测方式**：本机 `node ~/meituan-multi/server.js --mcp`（stdio，JSON-RPC 2.0），完成 `initialize` → `tools/list` / `prompts/list` / `resources/list` / `resources/templates/list` 并统计原始响应。

#### 5.1 MTM 实测基线（供对照）

| 项 | MTM 实测值 |
|---|---|
| `serverInfo` | `{ "name": "mtm-waimai", "version": "1.0.0" }` |
| `protocolVersion` | **`2025-06-18`** |
| `capabilities` | `{"tools":{},"prompts":{},"resources":{}}` |
| 工具数 | **16** |
| prompts 数 | **4** |
| resources 数 | **6** |
| resourceTemplates 数 | **0** |
| 工具名 | 15 个 `waimai_*` + 1 个 `mtm_health`；**全部 snake_case**；**16/16 带前缀** |
| 工具 `annotations` | ★ **0/16（全部为 `null`）** |
| 工具 `outputSchema` | **0/16** |
| 工具描述长度 | min 12 / ≈avg 37 / max 58 |

#### 5.2 逐条差距（事实陈述）

**差距 1 —— 工具注解（`annotations`）全部缺失。**
MTM 16/16 工具 `annotations` 为 `null`。对照：6 个实测样本中，**5 个**（memory 9/9、everything 13/13、sequentialthinking 1/1、filesystem 14/14、playwright 25/25）提供了注解；**1 个**（github 26 工具）为 0。
规范层面：`annotations` 是 `2025-06-18` 与 `2026-07-28` 两版 schema 中都存在的**官方字段**；`destructiveHint` 的**默认值为 `true`**。
事实性推论（不含建议）：MTM 中存在写能力工具——`waimai_operate`（接单/拒单）、`waimai_action`（上下架/改价/改折扣/回复）、`waimai_alert_handle`（标记告警已处理）——这些工具未声明 `readOnlyHint`/`destructiveHint`。按规范默认值，客户端会把这些工具按 `readOnlyHint: false`、`destructiveHint: true` 对待。

**差距 2 —— 协议版本停留在 Legacy 世代（`2025-06-18`）。**
MTM 声明 `protocolVersion: 2025-06-18`（握手式 initialize 世代）。
当前规范 Current 版本为 `2026-07-28`（Modern 世代，按 `basic/versioning` 术语表：`2026-07-28` 及以后为 Modern，`2025-11-25` 及以前为 Legacy）。
`2025-06-18` 早于两者。
事实性含义：Modern 世代的两项强制项——**每请求 `_meta` 声明版本**与 **`server/discover` RPC**——在 MTM 的 `2025-06-18` 世代中不存在此形态；MTM 未实现 `server/discover`（实测 `capabilities` 仅含 `tools`/`prompts`/`resources`）。

**差距 3 —— `capabilities` 均声明为空对象，`listChanged` 未声明。**
MTM 返回 `{"tools":{},"prompts":{},"resources":{}}`。规范中 `tools.listChanged` 为可选字段，用于声明服务器是否会在工具列表变化时发通知。MTM 未声明该字段。

**差距 4 —— `outputSchema` 0/16。**
规范中 `outputSchema` 为可选字段，用于定义结构化输出。MTM 16 个工具全部未提供。对照样本的数据中，此项未逐一统计（属本次实测覆盖边界）。

**差距 5 —— 分页行为：`cursor` 被静默忽略。**
实测向 `tools/list` 传入 `cursor: "x"`，MTM **未返回 JSON-RPC 错误**，而是返回完整 16 条列表且无 `nextCursor`。
规范：`cursor` 为可选入参，`nextCursor` 用于指示后续页。MTM 既未分页，也未对无法识别的 cursor 报错。
（事实陈述；16 个工具的规模下是否需要分页属实现判断，本节不作评价。）

**差距 6 —— prompts 与 resources 内容 1:1 重叠。**
MTM 的 4 个 prompt 名为 `bad-review-handling`、`daily-inspection`、`pricing-decision`、`promo-prep`；
MTM 的 6 个 resource 中，有 4 个 URI 为 `mtm-knowhow://prompts/<同名>.md`，与 4 个 prompt **逐一对应同名**。
另 2 个 resource 为 `mtm-knowhow://resources/bad-review-categories.json` 与 `mtm-knowhow://judgment/thresholds.json`。
依官方定义：prompts 是**用户控制**、需显式调用的模板；resources 是**应用控制**的被动只读上下文。MTM 中同一份知识内容以两种特性同时暴露。

**差距 7 —— prompt 参数全部为可选。**
MTM 4 个 prompt 的参数签名完全一致：`storeId`（`required: false`）+ `focus`（`required: false`）。
规范：参数可带 `required` 标记；缺必需参数时返回 `-32602`。MTM 无必需参数，故不触发该校验路径。

**差距 8 —— resource annotations 0/6。**
MTM 6 个 resource 均提供 `mimeType`，但均无 `annotations`（`audience` / `priority` / `lastModified` 三个官方字段全部未使用）。

**差距 9 —— resourceTemplates 为 0。**
实测 `resources/templates/list` 返回空。MTM 6 个 resource 均为固定 URI，无参数化资源族。
（MTM 的 prompt 参数含 `storeId`，而 resource URI 中不含门店维度。）

**差距 10 —— 描述长度分布。**
MTM 工具描述 min 12 / avg 37 / max 58 字符。
对照：github avg 47、playwright min 14、everything min 28、sequentialthinking 单工具 2781。
规范对描述长度**无**数值规定（见 2.3）。

**差距 11 —— 命名与官方/社区惯例的吻合度。**
MTM 16/16 工具为 `snake_case` 且 16/16 带服务前缀（`waimai_` / `mtm_`）。
对照 Anthropic 社区指南（snake_case + 服务前缀 + 动词开头）：MTM **吻合** snake_case 与前缀两项。
对照官方规范：官方对风格中立，仅约束字符集/长度/唯一性——MTM 16 个工具名均为小写字母+下划线，**落在合法字符集内**。

**差距 12 —— 与已弃用特性的关系。**
MTM 的 `capabilities` 中**未**声明 `sampling` 或 `roots`；实测也未暴露相关能力。
规范自 `2026-07-28` 起弃用 **Sampling、Roots、Logging** 三项。MTM 未实现这三项，即**未引入**已弃用特性。
