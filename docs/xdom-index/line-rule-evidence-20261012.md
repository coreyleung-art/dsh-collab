## 一、规则定义（★ 冻结命名 · 本件之后不得改名）

```
rule_id : infer:handoff-next-utterance-v1          ← ★ 冻结。★ 不得命名为「回复链」
定义     : 若信 A 满足 (A.reply_required ∧ A.ball == A.to)，
           则边 A →「A 之后第一封来自 A.to 的信」。
产物名   : 「顺序邻接推断」(ordering adjacency)      ← ★ 不是「回复链」
```

### ★ 先决条件读数（**先决条件，不是结论** —— 规则成立与否取决于它）

| 先决条件 | 实测 | 含义 |
|---|---|---|
| **`ball == to` 共线率** | ★ **15 / 15 = 100%** | ⇒ 「球权交接」**只是 `to` 的重述**，**不含任何独立信息** |
| `ball` 取值集 | 仅 `{ext, int}` | 本语料里**从未出现** `ball=none / ball=from / ball=第三方` |
| 参与方 | 仅 `{ext, int}` | 无第三方 |
| topic 复用 | **0 / 15** | 每封信**各起一个新 topic** ⇒ 按 topic 分帖提供不了结构 |

⇒ ★ **判据**：**共线率 100% ⇒ 本规则在本语料上无法被证伪**（它没有可区分的分支）。
★ 这正是本仓库反复记的「**空转绿**」形态 ⇒ P2 必须让 `ball≠to` 的分支**有控**（见 §七 GATE）。

## 六、★ 规则的两处硬伤（这是本件最该被读到的部分）

### 硬伤 1：`ball` 与 `to` 100% 共线 ⇒ 规则**在本语料上不可证伪**
`ball == to` 实测 **15/15**。⇒ 「**球权交接**」不含任何超出 `to` 的信息，
规则实际等价于 **`reply_required ∧ 下一封来自 to`**。
★ **风险**：一旦出现 `ball=none / ball=from / 球给第三方`，规则**从未在真实数据上跑过**
⇒ 这正是「**空转绿**」：**控是绿的，但它证明不了什么**。

### 硬伤 2：「下一封来自收件人」**≠**「回复」—— 语料自己给了反例
`#1` 与 `#2` **都**把球交给 `int`，而 `int` 只有 `#3` 一封 ⇒ 规则**同时吐出 `#1→#3` 与 `#2→#3`**
⇒ ★ **同一封信被算成两封信的回复** ⇒ 「一球一回」的**回合前提被数据本身违反**（并行话题交错）。
且 `#3→#4`（`#4` 是「v6 已生效」**新话题**）是否真回 `#3`，**规则判不了**。

⇒ ★ **结论**：本规则**可以保留为「顺序邻接」的观测**，但
★ **不得作为「欠谁一句」的判据**，★ **不得命名为「回复链」**。
