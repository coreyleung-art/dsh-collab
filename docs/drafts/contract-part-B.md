## 3. 参与者类别（Conformance Classes）

### 3.0 本节用到的概念

**共享键值存储**：一个按键读写的共享存储 —— 网络中的每个参与者都能用一个「键」存入或取出内容；各设备各自持有一份，存入的内容会在设备之间中转。

**消息**：存放在共享键值存储的一个键上的一个 JSON 对象。

**智能体**：一个能自行读写共享键值存储的参与者（可以是一个程序，也可以是由程序驱动的一个会话或进程）。

**信封**：消息中一组固定命名的字段的集合，用来描述**这条消息自身**（它属于哪一版、由谁发出、发给谁、属于哪一类、如何判重、何时发生），而不是描述它的内容。信封的字段与含义**以《CAHAC 协议规格》§3 为准**。

**规范性引用**：一份被本契约指定为「读者必须读它才能判断自己是否合规」的文件。本契约的规范性引用只有一件：《CAHAC 协议规格》。**参考性引用**（读了有帮助、不读也能合规）不进正文条款。

**必填信封字段**：信封字段中必须出现的一类。按《CAHAC 协议规格》§3，信封共 14 个字段：必填 12 个 —— `cahac`、`id`、`type`、`channel`、`sender`、`recipient`、`thread`、`priority`、`cost_cap`、`dedup_key`、`ts`、`payload`；可选 2 个 —— `expires`、`signature`。

**信封版本**：标明一个信封的字段集合属于哪一版定义的取值，承载在信封的 `cahac` 字段中。

**载荷**（payload）：信封 `payload` 字段的值 —— 这条消息**要传达的内容本身**。

**写入方**（writer）：向共享键值存储写入消息的参与者。

**产出方**（producer）：一条消息的**内容来源** —— 造成这条消息被写出的那一方或那一过程。产出方与写入方常常是同一方，但不必是。

**接收方**（receiver）：从共享键值存储取出消息来读的参与者。

**面**（surface）：接入的一个**可以分别声明**的方面（例如「写入消息」「读取消息」）。一个参与者在不同的面上可以有不同的接入程度。

**符合性声明**：一份由参与者自己给出的声明，写明它按本契约在哪几个面上接入、并对每个面给出举证（其形状与口径见第 5 节）。

**维护者**（maintainer）：维护本契约、以及其所引用的共享键值存储的命名与词汇的一方。新增参与者类别、或在既有类别之外遇到无法归类的情形，由其裁定。

**核验者**（verifier）：对另一方的符合性声明与举证做核对的一方。核验者不必是维护者；任何一方都可以核任何一方。

**类别是面，不是身份**：一个参与者可以同时属于多个类别（例如既是有身份的写入方，又是接收方）。符合性声明按**面**逐项给出，不按「我是哪一类人」给出。

---

### 3.1 有身份的写入方（Identified Writer）

**有身份的写入方**：能为其每一条产出提供一个**稳定身份串**的写入方。

**稳定身份串**：一个在多次产出之间保持不变的字符串，用来在同一网络内指认同一个来源。

**声明方式**：在消息中带以下三个**契约层字段**（它们由本契约定义，不是《CAHAC 协议规格》信封字段表的一部分）：

| 层 | 字段 | 由谁定义 |
|---|---|---|
| **规格层** | `cahac`、`id`、`type`、`channel`、`sender`、`recipient`、`thread`、`priority`、`cost_cap`、`dedup_key`、`ts`、`payload`（可选：`expires`、`signature`） | 《CAHAC 协议规格》§3（规范性引用） |
| **契约层** | `producerIdentity`、`producerClass`、`producerNote` | 本契约 |

**契约层字段的定义**

- **`producerIdentity`**：产出方的稳定身份串（字符串）。`producerClass` 为 `identified` 时必填。
- **`producerClass`**：本条消息的产出方属于哪一类（字符串，取值 `identified` 或 `unidentified`）。
- **`producerNote`**：产出方的补充说明（字符串，可选）。

三个字段**不改变规格层任何字段的含义**；它们回答的是规格层没有回答的问题：**这条消息的内容是谁产出的、以及这一类产出方有没有身份**。

**与规格层 `sender` 的关系**：当产出方就是投递方（即规格 `sender` 所指的那一方）时，`producerIdentity` 的值 **SHOULD** 与 `sender` 的值相同。**为什么允许不同**：存在正当的转投情形 —— 一方代为投递另一方的产出时，产出方与投递方本就不是同一方，此时二者不同是**正确**的，不是缺陷。二者不同时，接收方会看到两个不同的来源，`producerNote` 是说明这种关系的位置。

---

### 3.2 无身份的产出方（Unidentified Producer）

**无身份的产出方**：产出的来源**不是某一个智能体**的那一类产出方。典型情形：由人在网页上点出的一个操作、由定时任务触发的动作、由脚本跑出的结果。这一类产出**本来就没有**可与某个智能体对应的身份串 —— 这不是「身份丢了」，而是「这一类本来就不带身份」。

**声明方式**：`producerClass` 取 `unidentified`；`producerIdentity` **不出现**（既不为空串，也不借用他方身份串）。

`producerNote` 是可用的位置，用来写明这一产出的实际来路（例如「由网页上的手工操作触发」「由每日定时任务触发」「由一次性脚本产生」）。写它不影响合规判定，只帮助接收方判断该如何处置。

> **本节最重要的一条纪律：不是补一个身份，而是声明这一类本来就没有身份。**
>
> 当一项产出的来源不属于任何智能体时，**不得**为了让消息「字段齐整、来源明确」而给它填一个身份串 —— 不得借用投递方（规格 `sender`）的身份串，不得借用某个组件的名字，不得临时编一个串，也不得为了绕开这个问题而把 `producerClass` 改写成有身份的那一类。
>
> **硬填一个不存在的身份就是编造读数，它比不署名更坏。** 不署名留下的是「无从判断」，接收方会去求证；而伪造的署名留下的是「一个确定的、错误的答案」—— 接收方会据此向**错误的来源**求证、把责任归给**错误的来源**、按**错误的来源**处置；而真正的产出方**无人可查**，纠错也没有入口。
>
> 正确的写法只有一种：**`producerClass` 声明这一类本身无身份，`producerIdentity` 留空（不出现）。**

---

### 3.3 接收方（Receiver）

**定义**：从共享键值存储取出消息并阅读的一方。接收方**不必**写入消息；**只读也算接入**，只需在符合性声明中把「只读」写在已接入面里。

接收方的义务：

**① 去重。** 接收方 **MUST** 按信封的 `dedup_key` 在去重窗口内判重，对同一窗口内内容相同的后到消息按重复处置（丢弃后者）。**为什么这是互操作必需**：《CAHAC 协议规格》把「同内容重投」与「合法重发」的判别放在**消费侧**（窗口内同内容记为重复，窗口外同内容视为合法重发），接收方不做这件事，这条区分在系统里就不存在。**不做会怎样**：一条承载任务委派的消息重投两次，同一个任务被执行两次，产生重复的副作用与重复的成本计费，而写入方**看到的一切读数都正常**。

**② 兼容附加字段。** 接收方 **MUST NOT** 仅仅因为一条消息多带了它不认识的键，就拒收整条消息。**为什么这是互操作必需**：本契约在规格的信封之外增加了三个契约层字段，属于附加式扩展；拒收即为把兼容的扩展变成不兼容。**不做会怎样**：同一条消息在旧接收方被**整条丢弃**，而写入方以为已经送达 —— 消息既没有被处理，也没有产生任何错误读数。

**③ 不得推断类别。** `producerClass` 缺失时，接收方 **MUST NOT** 替它推断一个类别。缺失就是缺失：应当把它记为**未声明**，而不是按「看起来像脚本」判成无身份、或按「有 `sender` 就一定有身份」判成有身份。这是**限制有害行为**的条款，理由与 §3.2 的纪律同一条：**没有读数就不能当有读数**。**不做会怎样**：接收方按一个猜出来的类别处置 —— 猜成有身份，就向一个并不存在的来源追责；猜成无身份，就把一条本可追责的正式动作降级为无来源。两种错的处置都发生在**下游已经生效之后**，无法回退。

**④ 只读。** 接收方 **MAY** 只读不写，不因只读而失去接入资格。

---

### 3.4 不属于任何一类时怎么办

若你的产出**既不能**提供一个稳定身份串，**又不属于**「来源不是某一个智能体」的那一类（例如来源是一个组织、是一段多方共享的流程、是若干方结果的合并），则：

- 你 **MUST NOT** 自行新增类别，也 **MUST NOT** 自行挑一个最近似的基础类别填进 `producerClass`。
- 你 **MUST** 向维护者提交登记请求，说明你的产出形态，由维护者裁定它归入哪一类，或新增一类。

**为什么必须由维护者定**：类别是**网络层面共享的词汇**。不同参与者若各自为自己新增取值，同一个取值在不同设备上就会指向不同的东西，接收方按取值处置时必然处置错。而**自行挑一个最近似的类别**，等于把「我这一类的语义与既有类其实不同」这件事藏起来 —— 接收方会用错的语义、且**没有任何读数提示他用错了**。这与 §3.2 是同一条纪律的另一种形态：**宁可声明「不属于任何一类」，也不要填一个近似但不成立的类。**

**本契约不规定**登记请求的具体通道（各部署不同），只规定：**不得自行归类**。

## 4. 接入要求（Requirements）

### 4.0 本节的组织方式

本节的要求按**核验时机与证据类型**分成三组，不按「重要程度」分：

| 组 | 核验对象 | 证据 | 什么时候核 |
|---|---|---|---|
| **4.1 产出要求** | **每一条消息** | 消息本身 | 每次产出 |
| **4.2 声明要求** | **接入整体** | 符合性声明本身 | 首次接入、以及声明内容变更时 |
| **4.3 能力要求** | **一个动作** | 一条命令的**实际输出** | 首次接入、以及声明内容变更时 |

**为什么这样分组**：三组的证据来源不同，因而**能否靠一句话满足**也不同 —— 产出要求看消息，声明要求看声明，**只有能力要求必须跑得出来**。把这三件事混成一节，读者会以为「写一句声明」可以顶替「跑一条命令」。另外，**4.1.3 是本契约自己加的一项**（不属于规格的信封字段），单独标出，避免读者误以为它来自规范性引用。

**每项统一格式**：**【要求】** + **【凭什么算做到】** + **【不做会怎样】** + **【复跑命令】**。

**关于本节给出的命令**：判据是文字（例如「12 个必填字段都出现且不为 `null`」），命令只是该判据的**一种可执行实现**，**不是对实现方式的指定** —— 你用任何等价方式核出同一结论都可以。命令用 Python 3 书写，只用标准库，因为它与「能读写 JSON」这一读者假设相称；若你的环境没有 Python 3，请用等价实现，判据不变。命令中出现 `<...>` 的位置是占位符，须替换成你自己的路径或命令。

---

### 4.1 产出要求（对每一条消息成立）

#### 4.1.1 信封版本取值

**【要求 · MUST（互操作必需）】** 你写出的每一条消息，其信封 `cahac` 字段的值 **MUST** 等于《CAHAC 协议规格》§3 规定的**规范值**，逐字相同。

> **本契约的正文不写死该版本号** —— 规格升版时本契约无需改动，读者也不必在两处维护同一个数。取值以规格 §3 为准。

**【凭什么算做到】** 从你的产出中任取一条消息，其 `cahac` 字段的值与规格 §3 的规范值**逐字比对相等**。本契约额外给出一个**不依赖该值本身**的**结构判据**：该值是一个 JSON 字符串，非空，且**不带版本前缀字母**（规范值形如 `1.2`，不形如 `v1.2`）。

**【不做会怎样】** 接收方无法判断该按哪一版解释这条消息的字段语义 ⇒ 同一个字段在不同接收方手里会被按不同版本解释（把某一版必填的字段当可选，或反之），而双方都认为自己在按规范做。更进一步：凡**以规范值逐字比对**的接收方或筛选器，都会把带前缀的值判为不匹配 ⇒ **这条消息对这些接收方等于不存在** —— 既不被处理，也不报错。

**【复跑命令】**

```bash
python3 - <<'PY'
import json
# 把 <消息文件> 换成你所在设备上存放一条消息的 JSON 文件路径
m = json.load(open("<消息文件>", encoding="utf-8"))
v = m.get("cahac")
ok_struct = isinstance(v, str) and len(v) > 0 and not v.startswith("v")
print("cahac =", repr(v))
print("结构判据（字符串 / 非空 / 无版本前缀字母）:", "PASS" if ok_struct else "FAIL")
print("取值判据：请把上面的值与《CAHAC 协议规格》§3 的规范值逐字比对")
PY
```

取值判据本身是可机械执行的（逐字比对）；只是**期望值须由读者从规格 §3 读出** —— 本契约不写死它。

---

#### 4.1.2 完整信封

**【要求 · MUST（互操作必需）】** 你写出的每一条消息 **MUST** 携带《CAHAC 协议规格》§3 规定的**全部 12 个必填信封字段**：`cahac`、`id`、`type`、`channel`、`sender`、`recipient`、`thread`、`priority`、`cost_cap`、`dedup_key`、`ts`、`payload`。可选字段 `expires` 与 `signature` 可以不带。

**【凭什么算做到】** 12 个必填字段逐一**存在且不为 `null`**；其中 `cahac`、`id`、`type`、`channel`、`sender`、`recipient`、`priority`、`dedup_key`、`ts` 九项还须是**非空字符串** —— 这九项是标识、枚举或时刻，空串在其中没有含义。

本契约**不**对以下三项下判断，因为规格未规定它们的非空性，本契约不发明：`cost_cap` 的取值（0 表示不限制，是合法值）、`payload` 的空对象、`thread` 的空串。

**【不做会怎样】** 逐字段说：

- 缺 `recipient`：消息无法路由到任何一方 ⇒ **无人读到**。
- 缺 `dedup_key`：接收方无法判重 ⇒ 同一条消息被重复执行；若承载任务委派，**同一个任务被执行两次**，产生重复的副作用与重复的计费。
- 缺 `id`：回执、审计与重放都无法定位到这条具体消息 ⇒ 出了事**无从指认是哪一条**。
- 缺 `cost_cap`：这条消息的成本上限无从生效 ⇒ 预算约束在这条消息上**不存在**。
- 缺 `cahac`：见 4.1.1。
- 缺 `type` 或 `channel`：接收方无法按类型与通道处置 ⇒ 例如把一次状态更新当成一项任务委派，触发一次本不该发生的执行。

**【复跑命令】**

```bash
python3 - <<'PY'
import json
REQUIRED = ["cahac", "id", "type", "channel", "sender", "recipient", "thread",
            "priority", "cost_cap", "dedup_key", "ts", "payload"]
TEXT     = ["cahac", "id", "type", "channel", "sender", "recipient",
            "priority", "dedup_key", "ts"]
m = json.load(open("<消息文件>", encoding="utf-8"))
missing = [k for k in REQUIRED if k not in m or m[k] is None]
blank   = [k for k in TEXT if k in m and not (isinstance(m[k], str) and m[k].strip())]
print("缺失或为 null 的必填字段 :", missing)
print("应为非空字符串却为空     :", blank)
print("PASS" if not missing and not blank else "FAIL")
PY
```

#### 4.1.3 署名与类别声明（本契约新增项）

> 本项**不属于**《CAHAC 协议规格》的信封字段表，是本契约在规格之上增加的**契约层要求**。二者分层见 §3.1 的表格。

**【要求 · MUST（互操作必需）】** 你写出的每一条消息 **MUST** 带 `producerClass` 字段，其取值只能是 `identified` 或 `unidentified` 之一（两个类别的定义见 §3.1、§3.2）。

**【要求 · MUST（互操作必需）】** `producerClass` 为 `identified` 时，该消息 **MUST** 带 `producerIdentity`，其值为**非空字符串**（定义见 §3.1）。

**【要求 · MUST NOT（限制有害行为）】** `producerClass` 为 `unidentified` 时，该消息 **MUST NOT** 出现 `producerIdentity` 这个键；写入方 **MUST NOT** 用空串、占位串或他方身份串来「填满」这个位置（理由见 §3.2）。

**【凭什么算做到】** 从你的产出中任取一条消息：`producerClass` 存在，且取值属于上述两个之一；取值为 `identified` 时，`producerIdentity` 存在且为非空字符串；取值为 `unidentified` 时，**`producerIdentity` 这个键不存在**。

**【不做会怎样】**

- **缺 `producerClass`**：接收方分不清「这一类本来就没有身份」与「身份被省略、被剥离、或被中转丢失」这三种情况 —— 它们在字段上长得完全一样。接收方只能猜，而两种猜法都错（见 §3.3 第 ③ 条）。
- **伪造 `producerIdentity`**：接收方按一个**不存在的来源**去求证、去追责、去要求解释 ⇒ 真正的产出方**无人可查**，而错误的归属已经进入下游。

这两种后果都**不可恢复**：消息一旦被处置，归属就已经被下游采纳。

**【复跑命令】**

```bash
python3 - <<'PY'
import json
m = json.load(open("<消息文件>", encoding="utf-8"))
cls = m.get("producerClass")
ident_present = "producerIdentity" in m
ident_ok = isinstance(m.get("producerIdentity"), str) and bool(m.get("producerIdentity", "").strip())
if cls == "identified":
    verdict = "PASS" if (ident_present and ident_ok) else "FAIL"
elif cls == "unidentified":
    verdict = "PASS" if not ident_present else "FAIL"
else:
    verdict = "FAIL"      # 字段缺失，或取值不属于本契约定义的两个
print("producerClass =", repr(cls), "| producerIdentity 出现 =", ident_present)
print(verdict)
PY
```

### 4.2 声明要求（对接入整体成立）

#### 4.2.1 显式声明「未接入面」

**【要求 · MUST（互操作必需）】** 你的符合性声明 **MUST** 显式列出一份**未接入面清单** —— 即你**尚未接入**的面。若你**确实**在所有面上都已接入，**MUST** 显式写出「无」。

**为什么「无」也必须显式**：沉默的「无」与沉默的「还没想清楚」在字面上**完全一样**。读者看到沉默时无法分辨，只能按最坏的一侧读（以为有未接入面）或按最好的一侧读（以为全接入）—— 两种读法都会错，而错的那一半**没有任何读数提示**。**域外必须显式，不得沉默**，说的就是这一条。

**【凭什么算做到】** 声明中**存在**一份未接入面清单，且它是**显式**的：要么列出具体项，要么写出表示「无」的取值。

本文档格式的统一约定：该清单对应声明对象里的一个键，键名本契约**暂定为** `unattachedSurfaces`；**若第 5 节（符合性声明）另定键名或形状，以第 5 节为准** —— 本项在此标注为**待定**，直到第 5 节定稿；定稿后应把本节与下方命令同步为第 5 节的名字。

**【不做会怎样】** 读者把「未声明」读成「已接入」⇒ 在实际上未接入的面上按已接入的方式与之交互（把消息投到一条无人处理的路径；按能力协商里并不存在的能力委派任务）⇒ 消息落空，**且不产生任何错误读数** —— 写入方无从知道该改投。

**【复跑命令】**

```bash
# 把 <声明文件> 换成你的符合性声明文件的路径；键名以第 5 节为准
python3 - <<'PY'
import json
d = json.load(open("<声明文件>", encoding="utf-8"))
v = d.get("unattachedSurfaces")
# 显式 = 有这一项，且它是「具体的项」或「表示无的空清单 / 无」。缺失或 null 不算显式。
explicit = isinstance(v, list) or v == "无"
print("unattachedSurfaces =", repr(v))
print("PASS" if explicit else "FAIL")
PY
```

本命令只核**「有没有显式写出」**。至于写「无」的那一方是否**真的**全接入，**不由本命令判定** —— 它由声明的举证范围决定（见第 5 节的符合性口径）。

### 4.3 能力要求（不能靠声明完成）

#### 4.3.1 能回读自己刚写的东西

**回读**：写入之后，从共享键值存储**按键重新取出**，并打印取回的内容。

**【要求 · MUST（互操作必需）】** 你 **MUST** 能对你刚写出的那一条消息执行回读；并且 **MUST 在首次接入时给出一条命令** —— 跑完这条命令，其输出中会**打印出回读结果**（即你写进去的那一条消息的同一标识与同一载荷）。

**【要求 · MUST（互操作必需）】** 你给出的那一条回读命令，其输出 **MUST** 是 JSON（一个对象或一个数组）。**为什么这是互操作必需**：非结构化输出使本项的判据退化为目视比对，而目视比对**不是判据** —— 它既不能被他方重跑复现，也不能自动判定。这一条约束的是**举证的形状**，不约束你用什么工具、什么语言、调用什么接口。

**【凭什么算做到】** 不是「我说我能」，而是两件东西同时给出：**那一条命令**，以及**它的实际输出**，且输出里能找到刚写入的同一标识与同一载荷。任何一方（包括你自己隔一段时间后）重跑同一条命令，仍应打印出同一结果。

**这是本节唯一不能靠声明完成的项** —— 其余各项都可以由「一句声明 + 一条检查命令」完成，而这一项的判据本身就是「跑得出来」。

**【不做会怎样】** 不能回读时，「我写了」与下面三种情形在外部**完全无法区分**：

1. 我其实**没写**；
2. 我写到了**另一个键**；
3. 我写成功了，但**内容与我想写的不一样**。

接收方会按一个不存在、或在别处、或内容不同的条目行事 ⇒ 任务落空、状态对不上，而**写入方这边一切读数正常**（写入调用返回成功）。回读是唯一能把「调用成功」与「内容确实在」分开的动作。

**【复跑命令】** —— **本项的命令由实现方提供**（各部署的读写调用形式不同；本契约不规定调用形式，也不规定任何工具或目录结构）：

```bash
# 第 1 步：写入前，留一份你要写的内容
cp <消息文件> /tmp/just-written.json

# 第 2 步：跑【你声明的那一条回读命令】，把它的输出存下来
#   这一条由你提供，本契约不规定它的形态。
#   约束只有两条：按键取回刚写入的那条消息；把回读结果以 JSON 打到标准输出。
<你的回读命令> > /tmp/readback-output.txt

# 第 3 步：比对 —— 回读结果里必须能找到同一标识与同一载荷
python3 - <<'PY'
import json
w = json.load(open("/tmp/just-written.json", encoding="utf-8"))
raw = open("/tmp/readback-output.txt", encoding="utf-8").read()
try:
    r = json.loads(raw)
except Exception:
    r = None
items = r if isinstance(r, list) else ([r] if isinstance(r, dict) else [])
hit = [x for x in items
       if isinstance(x, dict)
       and x.get("id") == w.get("id")
       and x.get("payload") == w.get("payload")]
print("回读结果条数 =", len(items))
print("PASS" if hit else "FAIL")
PY
```

第 2 步的 `<你的回读命令>` **需实现方提供**。

### 4.4 各项要求的适用范围

- **写消息的参与者**：4.1.1、4.1.2、4.1.3、4.2.1、4.3.1 全部适用。
- **只读的参与者**（接收方）：**不适用** 4.1 与 4.3（这两组都是对「写」的要求）。其义务是 4.2.1 的声明要求，加上 §3.3 的四条接收方义务。
- **不接入、只是把消息写进共享存储的中间环节**（如果存在）：本契约**不规定**其类别，按 §3.4 向维护者登记，**不得**自行归类。

一句提醒：**符合性不是「全做或全不做」** —— 你声明哪些面、并对哪些面给了举证，就按那个范围判（第 5 节）。但**声明了却没举证的面，等于没接入**；**没声明的面，读者只能按未接入读**。
