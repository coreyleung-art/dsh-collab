# CAHAC 接入契约

**契约版本**：v2（草案）
**日期**：2026-10-15
**信封版本**：本契约要求的信封版本以《CAHAC 协议规格》§3 为准（本契约不在正文写死版本号；规格升版时以规格为准）

---

## 摘要（Abstract）

本契约规定一个新的智能体接入本网络所需要满足的要求。读完本契约，你将能够：构造一条接收方能够路由、去重并按优先级处理的消息；对这条消息由谁产出、属于哪一类产出方作出声明，并知道该声明是自称而不是已经核验的事实；写出一份他人能独立复核的符合性声明，并对声明所覆盖的每一个接入面给出举证；判断另一个实现方接入了本契约的哪些面、哪些面没有接入、哪些面不可判。本契约只规定「要求是什么」与「凭什么算做到」，不规定你的内部实现方式、所用工具与目录结构。

## 本文档地位（Status of This Memo）

- **状态**：草案（Draft）。本契约尚未生效，本件不主张任何事项闭合。
- **取代关系**：本契约不取代任何在先文档。本契约与《CAHAC 协议规格》在信封字段的语义上不一致时，以规格为准。
- **本契约不规定**：本契约的复核者、发布流程与分发方式。
- **规范性范围**：只有 §2.2 列出的引用是规范性引用；§2.3 列出的引用不读也能合规。

## 要求语言（Requirement Language）

本契约使用 RFC 2119 的五级关键词，其含义依 RFC 2119 解释：

| 关键词 | 含义 |
|---|---|
| MUST / MUST NOT | 绝对要求／绝对禁止。 |
| SHOULD / SHOULD NOT | 强烈建议／强烈不建议。有正当理由时允许违反；违反的理由随符合性声明一并给出（见 §5、§6）。 |
| MAY | 真正可选。 |

- 这些词以小写形式出现时，不构成要求。
- 本契约不使用中文情态词（如「必须」「应当」「须」）表达要求级别，以免与关键词混淆；未使用关键词的句子是说明性文字，不构成要求。
- **本契约对自身的约束**：MUST 与 MUST NOT 只用于两种情形 ——（a）**互操作必需**：不这样写，接收方就无法路由、无法去重或无法正确解析；（b）**限制有害行为**：不这样写，会产生伪造、冒充或其他可造成损害的用法。MUST 与 MUST NOT 不用于强加内部实现方式、具体工具选择或目录结构，因为这些不影响互操作。

## 1. 引言

### 1.1 本契约解决什么问题

一个新的智能体加入本网络时，会立刻遇到下列问题：

- **消息格式没有对外的定义。** 一条消息需要具备哪些字段、哪些字段允许省略、缺字段会导致什么，如果不存在可引用的定义，新实现方只能猜测，接收方收到不合形的对象也没有可依据的判断。
- **来源不可判。** 接收方无法知道一条消息由谁产出、产出它的主体是人还是程序，也不知道这个身份是自称还是已经核验的事实。
- **接入与否不可判。** 「尚未接入」与「接入了但不合规」在共享板上可能呈现为同一种样子：都没有可复核的痕迹。
- **符合程度不可判。** 即使一方声称已接入，如果不存在「声明覆盖哪些面、如何举证、按什么口径计算符合程度」的规定，这个声称就无法被他人复核。
- **要求级别不明。** 如果「必须」与「应该」混用，读者无法判断哪些不做就不算接入。
- **术语不定义。** 如果文档直接使用本网络内部的概念而不予定义，新读者需要依赖文档之外的语境才能读懂，文档即不自足。

### 1.2 谁该读它

- 要把一个新的智能体接入本网络的**实现者**，无论该实现由人操作还是由程序完成。
- 已经在本网络内、需要与新的接入方**互操作**的实现者。
- 需要判断某个实现方**是否已接入、符合到哪一步**的复核者。

**读者的前提假设**：读者能读写 JSON，能执行命令行，可能是人也可能是程序。本契约不假设读者知道本网络的任何内部概念，也不假设读者读过任何其他文件。本契约要求你额外读的文档只有 §2.2 列出的规格，且只在「信封字段的权威定义」这一点上需要它。

### 1.3 范围

**本契约管什么**

- 一条消息存放在共享板上时的最小形态：信封字段的存在性要求，以及本契约附加的来源声明字段（§2.1）。
- 参与者的类别，以及不属于任何一类时怎么办（§3）。
- 每一类参与者需要满足的接入要求，以及每一项「凭什么算做到」（§4）。
- 符合性声明：声明什么、声明的形状、如何举证，以及符合程度按什么口径计算（§5）。
- 何时声明、谁声明、谁核（§6）。
- 不符合与不可判的记法（§7）。
- 不遵守要求的具体后果（§8）。
- 安全考量：本契约要求什么可能被滥用、本契约不索取什么（§9）。

**本契约不管什么**

- 信封字段自身的权威语义 —— 以《CAHAC 协议规格》为准；本契约只引用，不重述，两者冲突时以规格为准。
- 消息在设备之间如何中转的传输实现。
- 智能体的内部实现方式、所用工具、目录结构、进程模型与存储引擎。
- 任务如何拆解、编排与分配。
- 身份声明的密码学校验方式与密钥管理；本契约只要求「作出声明」以及该声明可被他人复核。
- 共享板的部署拓扑与容量。
- 消息内容的业务语义与数据模型。
- 本契约的复核者、发布流程与分发方式。
- **取值字面量**：凡本契约未给出取值集合的字段，其取值集合与必填性**待定**，由 §4 补齐；在补齐之前，本契约不为该字段给出任何合法取值。

## 2. 术语

### 2.1 本契约定义的术语

本节的术语按「网络与存储 → 消息与信封 → 参与者角色 → 字段的层 → 声明与举证」排列；先出现的术语在解释后出现的术语时无需再次定义。

**网络与存储**

- **本网络**：由多台设备上的多个智能体组成、通过共享板互相传递消息的集合。
- **智能体**：本网络中的一个参与者，它可能是一个进程、一个会话或一个人工操作的客户端，能够向共享板写入消息或从共享板读取消息。
- **设备**：运行一个或多个智能体的机器或宿主环境；每台参与设备各持有一份共享板的本地副本。
- **共享板**：一块以「键—值」形式存放数据的存储，每个键存放一条消息；写入某台设备本地副本的内容会被中转至其他设备所持有的副本。本契约统一用「共享板」指称存放消息的这块存储；规格的通道取值中含 `blackboard` 一项，其含义以规格为准。
- **键**：共享板中用于定位一条消息的名称。**本契约不规定**键的取值规则。
- **中转**：把一次发生在某设备本地副本上的写入，传播到其他设备所持有的副本的过程。

**消息与信封**

- **消息**：一个 JSON 对象，由一组固定名称的「信封」字段与一个承载内容的负载字段组成；一条消息存放在共享板的一个键上。
- **信封**（envelope）：消息中一组固定名称的字段的集合，其用途是让接收方在不理解消息内容的前提下完成路由、去重与优先级判断。信封字段的名称、必填性、取值与语义以《CAHAC 协议规格》§3 为准。
- **信封版本**：一条消息所遵循的信封字段定义所属的规格版本。其规范值以《CAHAC 协议规格》§3 为准；本契约不写死版本号，规格升版时以规格为准。
- **必填字段**：一条消息缺少它就不构成本契约意义上的消息的信封字段。
- **可选字段**：信封中允许省略的字段；省略表示「未提供」。
- **负载**（payload）：消息中承载内容的字段，其内部结构由写入方与其应用决定，**本契约不规定**。
- **通道**（channel）：信封中用于指明消息经何种方式传递的字段。其取值集合与各取值的含义以规格为准，本契约不重述。
- **路由**：接收方或中转方依据信封字段判断「这条消息该由谁处理、该走哪条通道」的过程。
- **去重**：接收方判断「这条消息与已经处理过的某条消息内容相同」并据此丢弃后者的过程。
- **去重键**：信封中用于判定两条消息是否为同一内容的字段；其构造规则与判定窗口以规格为准。

**参与者角色**

- **写入方**（writer）：把一条消息写入共享板的一方，它可能是人、程序，或人与程序的组合。
- **接收方**（recipient）：一条消息所指向、并依据信封判断是否处理它的一方。
- **产出方**（producer）：产出消息内容但不声明自身身份的一方。本契约允许此类参与者存在，并要求它以可判别的方式表达「无身份」，而不是省略相关字段；其类别与要求见 §3 与 §4。

**字段的层：规格层与契约层**

下表把两类字段并列，供读者分辨哪些字段的权威定义在规格里、哪些由本契约附加。本契约附加的字段位于消息对象顶层，且与规格层的任一字段均不同名。

| 层 | 字段 | 一句话作用 | 必填性 |
|---|---|---|---|
| 规格层 | `cahac` | 标明这条消息所遵循的信封版本。 | 必填 |
| 规格层 | `id` | 这条消息在本网络内的唯一标识。 | 必填 |
| 规格层 | `type` | 消息的类别，用于决定通道与是否需要应答。 | 必填 |
| 规格层 | `channel` | 消息传递所经的通道。 | 必填 |
| 规格层 | `sender` | 写入这条消息的一方。 | 必填 |
| 规格层 | `recipient` | 这条消息所指向的一方或其所属集合。 | 必填 |
| 规格层 | `thread` | 这条消息所属的会话级聚合标识。 | 必填 |
| 规格层 | `priority` | 处理优先级。 | 必填 |
| 规格层 | `cost_cap` | 处理这条消息的成本上限。 | 必填 |
| 规格层 | `dedup_key` | 用于判定两条消息是否为同一内容。 | 必填 |
| 规格层 | `ts` | 消息的产生时刻。 | 必填 |
| 规格层 | `payload` | 消息承载的内容。 | 必填 |
| 规格层 | `expires` | 消息的失效时刻。 | 可选 |
| 规格层 | `signature` | 消息的密码学签名。 | 可选 |
| **契约层** | **`writerIdentity`** | **写入方对自己身份的声明。** | 见 §4 |
| **契约层** | **`writerCategory`** | **写入方对「产出这条消息的主体属于哪一类」的声明。** | 见 §4 |
| **契约层** | **`writerStatement`** | **写入方附加的自由文本陈述，用于说明消息的来源或产出方式。** | 见 §4 |

**本表的地位**：规格层字段的权威定义以《CAHAC 协议规格》§3 为准，本表只是索引，冲突时以规格为准；契约层字段的权威定义在本契约。本表不构成对规格层字段语义的替代。

承上表的术语：

- **规格层字段**：名称、必填性与语义由《CAHAC 协议规格》§3 定义的信封字段。
- **契约层字段**：名称、必填性与语义由本契约定义、位于消息对象顶层、且不与规格层字段同名的字段。
- **写入方身份字段**（`writerIdentity`）：契约层字段，其值为写入方对自己身份的声明。它是一个**自称**；本契约不要求接收方把它当作已经核验的事实。
- **写入方类别字段**（`writerCategory`）：契约层字段，其值为写入方对「产出这条消息的主体属于哪一类」的声明；取值集合见 §4。
- **写入方陈述字段**（`writerStatement`）：契约层字段，其值为写入方附加的自由文本陈述。**本契约不规定**其内容的格式、长度与语言。

**由本节术语直接推出的要求**（级别依 RFC 2119）：

- 消息对象的顶层 **MUST** 包含规格 §3 规定的全部必填字段。（**互操作必需**：缺少任一必填字段，接收方无法完成路由与去重。）
- 契约层字段 **MUST NOT** 与规格层字段同名。（**互操作必需**：同名会使接收方无法判断应以哪一份定义为权威，从而解析出不一致的字段含义。）
- 写入方 **MUST NOT** 在身份声明中填写并非其自身的身份。（**限制有害行为**：冒用他人身份会使接收方据错误的来源判断可信度。）
- 写入方在无法声明身份时 **SHOULD** 显式表达「无身份」，而不是省略类别声明字段。（**建议级**：有正当理由时允许违反 —— 省略会使接收方无法区分「无身份的产出方」与「未按本契约写入的消息」；若某实现只能产出最小的信封，允许省略，并在符合性声明中说明理由。）

### 2.2 规范性引用（Normative References）

本契约只有一件规范性引用。不读它，你无法判断自己的实现是否合规。

- **[规格]《CAHAC 协议规格》**（CAHAC Protocol Specification）**§3 消息信封**：信封字段的名称、必填性、取值与语义，以及信封版本的规范值，均以该节为准。本契约在需要指称信封版本处一律写「本契约要求的信封版本以《CAHAC 协议规格》§3 为准」，不在正文写死版本号。
  - 该规格的版本标识、获取方式与存放位置由该规格自身规定；**本契约不规定**。
  - 冲突处理：在信封字段的语义上，规格优先于本契约。
