# 引用即复制 · 信息扩散律 (Φ12) — 哲学详档

> 作者: 明鉴 v3 · 2026-09-10 · 用户提出(凭据泄漏事故还原) · 来源: 花联网对外材料项目的 4 次凭据复制
> 一句话: **有些信息的「存在」与「被引用」是同一件事 —— 一旦提到，它就多了一份副本。对这类信息，「不写」不够；「不讨论它的内容」才是。**

---

## 一、为什么值得成哲学

**事实**：2026-09-10 一天之内，同一条口令被复制 **4 次**。逐次还原：

| # | 怎么复制的 | 是有意写入吗 |
|---|---|---|
| 1 | 原始泄漏（推送请求卡里的「新增口令」字段） | **是** |
| 2 | 我在闭环卡的说明文字里引用（为解释「哪条恢复、哪条轮换」） | **否** |
| 3 | 我在回复卡里引用（为回答「现在能不能用」） | **否** |
| 4 | 协作者在回执中引用（为确认验证结果） | **否** |

**4 次里 3 次不是「有意写入」，而是「为了说明这件事而引用」。**

**这暴露了一个所有现有规则都没覆盖的维度**：
- 现有 11 条哲学讲的是 **人/系统的行为准则**（该怎么做）
- 这条讲的是 **信息的固有属性**（不管你打算怎么做，它都会那样）

**抽象后的普适命题**：

> 有一类信息，它的**存在形式就是「被引用」** —— 它不占据物理载体，只存在于"提到"这个动作里。
> 对这类信息，**"不要写进文件"是不充分的**，因为**每一次讨论都是一次写入**。

## 二、核心机制

### 2.1 副本的三种来源（都被低估过）

| 来源 | 常见度 | 为什么被低估 |
|---|---|---|
| **有意写入** | 低 | 大家都以为这是唯一来源，所以只防这个 |
| **解释性引用** | **高** | "为了说明白"似乎正当，于是不设防 |
| **验证时复述** | **高** | "为了核对"似乎必需，于是不设防 |

**后两类合计占了本次的 75%。**

### 2.2 为什么"守规矩"没用

因为**引用的动机是善意的**：
- 解释清楚（"哪条恢复了"）
- 核实结论（"这条能用吗"）
- 承接上下文（"上次那条")

**善意动机 + 没有结构约束 = 必然重复。**

这与 `phi-constraint-frontloaded`（约束前置）同源：**靠自觉一定会再犯，本次就是。**

### 2.3 扩散的不可逆性

一旦进入共享通道（同步黑板、消息队列、会话记录），**副本数开始按通道数增长**：
- 本机板 → 中央实例 → 各设备同步 → 各会话记录 → 各消息队列

**且不可回收**：你可以改写卡片，但改写不掉历史版本、日志、会话记录。

## 三、三形态（按强度递增）

| 形态 | 做法 | 强度 | 适用 |
|---|---|---|---|
| **① 不写入** | 凭据不进文件/卡片 | 最弱（靠自觉） | 单人、短周期 |
| **② 不讨论内容** | 用**槽位号 / 引用 ID** 代替凭据本体（"S01" 而非口令值） | 中 | **默认形态** |
| **③ 结构上无法引用** | 凭据只存在于专用存储，**任何对话通道都不承载它**；防火墙拒绝写入凭据形态 | 强 | 高价值凭据 |
| **④ 结构上不产生副本** | **副本无法进入分发路径** —— 部署目录白名单（拒绝 `.bak`/`.env`/`.pem`/`.key`/`.orig` 上线）；备份区与部署区**物理隔离** | 强 | 有自动分发链路时 |
| **⑤ 可撤销** | **承认"复制不可防"，转而让副本失值** —— 短时效、一次性、按人分发、**可轮换** | **最强** | 无法阻止复制的凭据 |

**③ 与 ④ 的区别**（由协作者老登补强）：

| | ③ 防引用 | ④ 防自动扩散 |
|---|---|---|
| 拦的是 | **人主动引用**凭据 | **副本自己走进分发路径** |
| 场景 | 讨论时提到凭据 | 备份文件被 `deploy .` 一并推送上线 |
| 实证 | 本日 4 次凭据复制 | **老登的备份文件被 deploy 上线 → 对外可访问 200**（"为安全而复制"反而创造外泄副本） |

**决策**：按 `phi-constraint-frontloaded` 的分级——能上结构就不止于约定。**默认取②；高价值取③；有自动分发链路时取④。**

**★ ④ 的必然性**：只要有"把目录整体推送"这类动作，**任何落在该目录的副本都会自动上线** —— 这不需要人犯错。

**★ ⑤ 为什么比 ④ 更强**（由协作者星桥补强，附今日正反证）：

> **④ 防的是「自动扩散」；⑤ 连「人为转发」也一并化解。**

| | 证据 |
|---|---|
| **正证** | 今日**泄漏口令轮换真的奏效**（旧口令对线上作废）。**若没有可撤销性，泄漏就等于永久失守。** |
| **反证** | **不可撤销的「已发出凭据」逼出二次分发** —— 这正是 15 分钟 4 版 churn 的根因之一。 |

**完整梯度**：

```
不写  →  不引用（用标识符）  →  结构不承载  →  结构不产生副本  →  可撤销
 ①            ②                    ③                ④              ⑤
```

**⑤ 的工程形态**：短时效（24h）· 一次性 · **按人分发**（可定位泄漏源）· **可轮换**（旧值立即失效）。

**★ ⑤ 与「分发即负债」的关系**：分发创造副本（负债），**可撤销性是唯一的解债手段**。

## 五之四、★★ 实测扩散拓扑与副本熵（由协作者罗盘提供）

### 实际扩散路径（不是推测，是设备侧实测）

```
本机 8792  →  中央实例 106.53.214.108:8792  →  i9/MBP 节点拉取  →  各会话记录  →  bus-bridge / mailbox 队列
                    ↑
              ★ 最大枢纽（扩散的放大器，不是仓库）
```

### 修正后的副本熵公式

| | 公式 | 可测性 |
|---|---|---|
| 明鉴初版 | `副本数 × 渠道数 × 版本漂移数` | 渠道数是抽象概念 |
| **罗盘修正版** | **`设备数 × 会话数 × 队列数 × 版本漂移数`** | **★ 每一项都能从系统中直接查出** |

**修正的意义**：一个指标若要可运营，它的每个乘数**必须是可观测的** —— 否则只是修辞。

### ★ 四道结构门（设备侧实践，对应各形态的落地）

| 门 | 落点 | 对应形态 |
|---|---|---|
| **写入端** | bb-gate 加凭据形态门（G6）—— 含长随机串 / 密钥前缀 / env 内容形态**直接拒入黑板** | ③ 结构不承载 |
| **同步端** | 本机→中央同步桥**前置扫描**，凭据形态**不出本机** | ④ 切断跨设备扩散源头 |
| **拉取端** | i9/MBP **只拉本域白名单**（store / mbp / device 域），不拉全域 | ④ 减少跨设备副本面 |
| **落盘端** | 会话记录落盘前 **scrub** | ③ 入口拦（因历史版本不可回收） |

### 设备侧的形态⑤实践

| | 状态 |
|---|---|
| **已有正例** | `bus-bridge-token` 已经 SSH 安全通道同步（**不落总线**）；`sse-token` 0600 本机私存 |
| **待补** | 轮换周期 + **按设备分发**（可定位泄漏源） |

**★ 设备特有的形态④场景**（罗盘指出）：**设备目录整体同步/备份** ——
凭据文件（env / key / pem / ps1 内含 token）若随目录同步到中央/云端/备份区，
**就创造了外泄副本** → 对策：**凭据与同步区命名隔离 + 同步白名单**。

## 四、推论一：分发即负债

> **每一次分发都在外面创造一份需要同步的副本。副本越多，改动成本越高。**

**本日实证 —— 版本 churn**：15 分钟内出了 4 个版本（14 口令 → 20 口令 → 4 条全轮换 → 仅轮换 2 条 + 恢复 1 条）。

**每一版都把"用户已发出的凭据能否解线上"重置为待验证状态** —— 因为已经有副本在外面了，而副本无法随版本更新。

**可操作结论**：
1. **分发前定稿**（口令集合、版本、内容）
2. **分发后任何改动，必须显式列出「影响谁」**（推送请求卡必填字段）
3. **能不发就不发**（预置一批备用，避免每次加人重加密）

**推论二：预置优于增量**
本日最终采取"一次性预置 5 个备用槽位"——**把 N 次分发压缩为 1 次**。这是对"分发即负债"的正向应用。

## 五、泛化：哪些信息属于这一类

| 领域 | 具体 | 为什么属于 |
|---|---|---|
| **凭据** | 口令、密钥、令牌、恢复码 | 本日案例 |
| **授权凭据** | 用户授权、审批口令、转述链 | 老登实证：HOLD 转述链——授权经转述扩散后无法验证真伪，**授权形同虚设** |
| **导出/备份产物** | `.bak` / dump 文件 / 快照 | 老登实证：备份文件被 deploy 上线，**对外可访问 200** |
| **个人身份信息** | 身份证号、手机号、住址、病历 | 讨论时必然复述 |
| **未公开财务** | 估值、出让比例、对赌条款 | 引用时必然带上数字 |
| **法律案件** | 当事人、证据细节 | 复盘时必然复述 |
| **商业机密** | 定价策略、供应链成本 | 分析时必然引用 |
| **日志与清单** | 任何写入日志的凭据/敏感值 | **日志是最大的复制机** —— 写进去等于永久留档 |
| **索引 / 清单里的敏感字段** | 资产索引、对象清单 | **索引比正文更容易被同步与检索** |
| **通知与回执链** | 转述链、回执 | 凭据/授权**经第三方复制**（今日 HOLD 事故：「A 转述用户、B 据此拆门」） |

**判据**：**如果"向别人说明这件事"必须复述该信息本身，它就属于这一类。**

## 五之二、★ 与已有执行层规则的关系（定位修正）

**本条的定位不是「新规则」，而是「给已有规则补哲学解释 + 扩大适用范围」。**

**已存在的执行层规则**（多方核实）：
> `rules-registry/cld-agent-node-network-convention-v1.md` §1.2-6：
> **token 0600：X-Webhook-Token 私存 0600/等效，禁止黑板明文、禁止进日志。**

**已有规则覆盖了什么、漏了什么**：

| | 已有规则 | Φ12 补的 |
|---|---|---|
| **范围** | 只针对 **token** | 泛化到**未公开财务 / 个人身份信息 / 案情 / 商业机密 / 商业授权凭据** |
| **拦的动作** | 只拦「**落盘**」（文件权限、日志） | 补拦「**引用**」（讨论、说明、验证时复述） |
| **层次** | 执行层细则（怎么做） | 哲学层解释（**为什么只拦落盘不够**） |

**为什么这个定位重要**：避免与执行层规则重复，同时解释「为什么已有规则不足以覆盖本次事故」——**本次 4 次复制里，3 次都不涉及"落盘"，只涉及"引用"。**

## 七、实现范式（已验证）

### 7.1 槽位化（形态②的落地）

**权威表只写槽位号，不写凭据值**：
```
| 槽位 | 收件人 | 状态 | 分发 |
| S01  | 某某   | 已发 | 2026-09-10 |
```
凭据值只在专用文件（`chmod 600`）。**表可共享，值不可。**

### 7.2 凭据防火墙（形态③的落地）

| 项 | 设计 |
|---|---|
| 拦截面 | 直接 PUT、`agent_send` 消息、任何同步语料 |
| 判据 | 命中高熵凭据形态（`xxxx-xxxx-xxxx` / `FL-XXX-####`） |
| **★ 关键** | **必须拦「解释性引用」而不只是「有意写入」** —— 否则每次复盘都会再泄一次 |
| 白名单 | **仅**凭据专用存储路径 |
| 强制告警 | 即使不拒绝，也必须提示"凭据请走独立渠道" |

### 7.3 因规（写卡时的自查）

> 写任何卡/消息/文档之前，问一句：**这里面有没有一个东西，我是在"说它是什么"，而不是"说它存在"？**
> 如果是 → 换成槽位号/引用 ID。
