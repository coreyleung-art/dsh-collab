## 0. 先立判据，再套场景

不做判据直接列场景，会退化成"什么都像"。下面是六条**适配判据**和六条**反判据**。

### 0.1 适配判据（六条全中才是甜点区）

| # | 判据 | 为什么 | 怎么验 |
|---|---|---|---|
| 1 | **输出空间可预先枚举** | 这是 System One 的定义性前提——没有封闭选项集，它就不成立 | 能否写出一个有限列表？选项数 ≤26（走 OpenAI 兼容后端时）或 ≤256（进程内）？ |
| 2 | **原子单维** | "一个有经验的人一秒能拍板"是官方给的实操标准。需要权衡多个因素就不是它 | 能否用一句话说清在判断什么？ |
| 3 | **高频或批量** | 34ms 的价值只在"跑很多次"时体现。一次性判断用 LLM 就够了 | 每天发生多少次？是否需要对全量跑而非抽样？ |
| 4 | **多数情况有站得住的答案** | 它的准确率是 0.79 量级，不是 0.99。它做的是**过滤**不是**裁定** | 人类专家之间是否大体一致？ |
| 5 | **需要"该不该自动化"的信号** | 这是它相对普通 LLM 的**唯一真实增量**——校准置信度 | 错了代价多大？是否需要分档处理？ |
| 6 | **状态是文本/JSON** | 它读文本，不读截图、不点页面 | 输入能否序列化成文本？ |

### 0.2 反判据（命中任一条即排除）

| # | 反判据 | 原因 |
|---|---|---|
| R1 | **需要生成内容** | 它不生成文本 |
| R2 | **需要多因素慢推理** | 官方明说"分析这件事并给出最佳方案"这类问题它答不好 |
| R3 | **规则可精确判定** | 能用 `if` 判的不要上模型——徒增不确定性与成本 |
| R4 | **需要精确计算** | 算术应在代码里做，官方明确建议"数值比较在调用前用代码算好" |
| R5 | **状态远超模型上下文** | 截断是静默的（Laya 实测：512 token 预算下 150 选项拒绝 99/100 题） |
| R6 | **存在"无正确选项"的情况却必须给答案** | 覆盖失效——没有正确答案时它仍会给一个高置信度答案（除非把"以上都不是"也列进选项） |

### 0.3 四象限决策框架

判断一个场景该用什么，而不是默认用 LLM：

```
                规则可精确判定
                     ▲
        ① 用规则     │     ② 用 System One
     （拒单率红线、  │   （规则难写但答案可枚举：
       超时判定、    │     公告分类、差评归因、
       阈值比较）    │     意图路由、根因归类）
   ──────────────────┼──────────────────► 答案可枚举
        ③ 用代码     │     ④ 用 LLM
     （金额计算、    │   （需要生成、需要多因素
       排序、统计、  │     推理、需要查阅资料、
       去重哈希）    │     需要写文案）
                     ▼
                规则难写/不可写
```

**关键洞察**：我们系统里**大量"看起来需要 AI"的判断，其实落在象限 ①**（规则可判）。真正属于象限 ② 的，是那些**规则写不准、但答案确实是个有限集合**的判断——这才是 System One 的目标区。

## 2. 覆盖度分层

### A 级：立即可覆盖（现成封闭枚举 + 高频 + 规则难写）

这五个是**已经有明确分类体系、且分类工作正在高频发生**的场景：

| 场景 | 现成枚举 | 为什么是甜点 |
|---|---|---|
| **1. 平台公告分类** | 9 类 | 枚举已在技能里定义；分类靠 LLM 读文本，慢且口径可能漂移 |
| **2. 差评归因** | 6 类 | 枚举已在工具描述里；每条新评价都要归类 |
| **3. 语音指令意图路由** | 工具名列表 | 选项集天然封闭；现在是**正则匹配**（`lib/index.js` 里十几条 `re:` 规则），会漏、会误匹配 |
| **4. 修复根因归类** | M1–M6 | 枚举已在 `guard_archaeology` 里；**且有历史修复报告可做回测集** |
| **5. 来源可信度分级** | 一级/权威/二手/自媒体/未查证 | 枚举已在 research-pipeline 里；调研时高频重复判断 |

**其中 4 和 5 特别有价值**，因为它们**有历史数据可回测**——可以直接用已有的历史修复报告/历史来源清单做离线验证，无需新建标注集。

### B 级：需先定枚举

告警类型归类 · IM 诉求类型 · 反馈是否值得登记 · 调价异常 · 客户流失风险 · 记忆条目类型 · 建议类型 · 报告价值分级

### C 级：边界情况

商品关键词意图（词频统计可能已够） · 节日备货紧迫度（低频） · 商品是否下架（决策代价高，不宜自动）

| 场景 | 原因 |
|---|---|
| 健康检查项判定（18 项） | 脚本可精确判定（象限①） |
| 备份 good 态判定 | 规则可判 |
| 消息去重 | 已有机械四维判重 |
| 锁冲突裁决 | FIFO 规则已定 |
| 审批单类型路由 | 调用方已显式指定 |
| 检索相关性 | 向量分数已给 |
| 是否可热重启 | 规则可判 |
| 店铺是否正常营业 | 面板字段直接可读 |
| **所有需要生成文本的场景**（回复客户、写报告、写代码） | R1 |
| **所有需要精确计算的场景**（金额、排序、统计） | R4 |

## 3. 场景 × 原语矩阵

三类原语在我们场景里的分布（这是**设计选项集时的检查表**）：

| 原语 | 我们系统里的典型用法 | 场景数 |
|---|---|---|
| **choice**（N 选一） | 分类、路由、归类、消歧 | **~25 个**（最主力） |
| **noul**（是/否概率） | 是否需介入、是否相关、是否异常、是否需回复 | ~18 个 |
| **score**（有序刻度） | 紧急度、严重度、价值分级、危险等级 | ~12 个 |

**一个此前没意识到的用法**：`score` 原语**可以落在刻度之间**（返回期望值 + 最可能级别）。我们的 `guard_compliance` 现在是布尔通过/不通过——用 score 可以升级成**风险分级**，"边界情况"不再被强行二分。

## 4. 反模式清单：这些场景**不要**用

| 反模式 | 真实反例 |
|---|---|
| 用 System One 做**最终裁定**（而非过滤） | 它的准确率是 0.79 量级，全量自动化=20% 错误率 |
| 用 System One **替代生成** | 它不生成文本 |
| 用它做**精确算术** | 官方明确建议数值比较在代码里做 |
| 选项集**不封闭**（"列出所有可能的问题"） | 定义性失败 |
| 选项集**有近义项**（"技术问题"vs"系统故障"） | CLM 实测：短标签平均余弦 0.95，不可分 |
| 选项**名称随意**（与描述不一致） | Laya 实测：误导性名称下跟随名称 72%，压过正确描述 |
| **超长状态**不检查截断 | Laya 实测：静默截断后仍返回分布且无警告 |
| 用它做**高代价不可逆决策** | 错一次代价 >> 自动化收益 |
| 用它**替代规则明确的判定** | 象限①的场景上模型是净损失 |
| 用 **LLM 自陈置信度**做分档 | 这正是 RLCD 要解决的问题——RLHF 模型系统性过度自信 |

## 5. 与现有实现的差距（这是"覆盖"的实际含义）

盘点下来，**我们系统里绝大多数判断目前是三种形态之一**：

| 现状形态 | 占比（估） | 问题 | System One 能补什么 |
|---|---|---|---|
| **正则/规则匹配** | 高 | 会漏、会误匹配、口径散落在代码里 | 意图路由的鲁棒性 |
| **LLM 读文本后自由输出** | 中 | 慢、贵、**口径会漂移**（同一输入两次可能不同类） | 口径一致性 + 校准置信度 |
| **人工判定** | 中 | 不可规模化、不一致 | 可规模化的初筛 + 分档 |
| 机械可判 | 中 | 无问题 | **不需要补** |

**最值得注意的一行是"口径漂移"**：我们用 LLM 做分类时，同一份输入在不同时间可能被归到不同类——因为我们**没有把选项集固定下来做约束**。而 System One 的选项集是**调用前枚举**的，这从机制上消除了这一类漂移。**这可能是比"快"和"便宜"更重要的收益。**

## 7. 实测探针（用我们真实的分类体系直接跑）

§1 的适配度是**纸面判断**。为了不让它停留在推测，我用 `opendecider-nano`（0.8GB，M4/MPS）**直接跑我们自己的分类体系**。以下全部为本机实测。

### 7.1 平台公告 9 分类

| 结果 | 值 |
|---|---|
| 准确率 | **6/9 (67%)** |
| **错误项的置信度** | 0.264 / 0.240 / 0.293 —— **全部偏低** |
| **正确项中高置信的** | 0.727 / 0.684 / 0.527 —— **全部正确** |

> **这正是分档路由的价值**：门槛设 0.35 时，自动化 3 条、**全部正确**。

### 7.2 差评归因 6 分类

| 配置 | 准确率 | 正确均置信 | 错误均置信 |
|---|---|---|---|
| 仅类别名 | **7/8 (87.5%)** | 0.516 | 0.639 ⚠️ |
| 类别名 + 描述 | 6/8 (75%) | 0.520 | 0.283 |

> ⚠️ 注意：**仅类别名那一档的置信度没有区分力**（错误项置信度反而更高）。n=8 太小，不足以下结论，但提醒我们**逐场景验证校准，不能假设它天然成立**。

### 7.3 中文意图路由（n=41，最有价值的一组）

用我们真实的 12 个工具名作选项，41 条真实风格中文指令：

| 指标 | 值 |
|---|---|
| **裸准确率** | **27/41 = 65.9%** |
| 正确均置信 | **0.500** |
| 错误均置信 | **0.206** |
| 预测分布 | 12 个选项**全部被用到**（无塌缩） |

**置信度分档（关键）**：

| 自动化门槛 | 自动化比例 | 其中准确率 |
|---|---|---|
| ≥ 0.0（裸用） | 100% | 65.9% |
| ≥ 0.3 | 54% | **90.9%** |
| ≥ 0.4 | **46%** | **94.7%** |
| ≥ 0.5 | 32% | **100.0%** |
| ≥ 0.6 | 22% | 100.0% |

> **读法**：裸用 65.9% 不可接受；但**门槛 0.4 时，46% 的指令可全自动且准确率 94.7%**，其余 54% 回流给 LLM 或人工。**这就是 System One 在我们场景里唯一站得住的用法。**

### 7.4 确定性（重要正面发现）

| 测试 | 结果 |
|---|---|
| 同配置连跑 5 次 | **41 条结果逐条一致**（8/10 → 8/10 → …，分布完全相同） |
| 同一条输入连跑 5 次 | 概率**到小数点后 4 位完全一致**（0.5879 × 5） |

> **结论**：opendecider-nano **完全确定**。这比 Jev 更好——Jev 有调用间非确定性（同序重发翻转率 0–4%）。
> **意义**：消除了我们做"口径一致性"改进时的一个干扰变量——**结果不一致只可能来自输入或选项集，不会来自模型抖动**。

### 7.5 选项措辞是主导变量（⚠️ 最重要的操作发现）

同一个任务、同一个模型，**只改选项描述的措辞**：

| 选项措辞 | 准确率 |
|---|---|
| 详细英文描述（"Check store online status"…） | **8/10** |
| 精简英文描述（"Check store status"…） | **3/10** |
| 裸中文名（"查询门店状态"…） | **6/10**（在 n=41 上为 65.9%） |
| 中文名 + 差异化长描述 | **4/10** |

> **两个反直觉结论**：
> 1. **选项措辞的影响 ≫ 模型选型的影响**——同一模型同一任务，措辞不同可差 50 个百分点
> 2. **"描述写得越详细越好"是错的**——加长描述反而变差（与 Laya 的"名称压过描述"现象同源：模型对选项的**呈现形式**极度敏感）
>
> ⚠️ 小样本（n=10）下 3/10 vs 8/10 的差异需谨慎；但方向一致且与 Laya 的独立实验吻合。

### 7.6 原语逐项体检

| 原语 | 实测表现 | 判断 |
|---|---|---|
| **choice** | 65.9%（n=41，12 类）；分档后 94.7% | ✅ 可用，但**必须配分档** |
| **score** | 可用。返回 `expected`（可落在刻度之间）+ `legend` + 概率分布 | ✅ 可用（注意 in-process 返回 `score` 字段而非 `level`） |
| **noul** | ⚠️ **中文短句完全失效** | ❌ 当前不可用 |

**noul 的失效细节（必须记录）**：

| 输入 | 语言 | 输出 |
|---|---|---|
| "花送过来都蔫了，叶子发黄" | 中文短 | **0.258**（错误，且低于 0.5） |
| "花很新鲜，包装也仔细，好评" | 中文短 | 0.227 |
| "还行吧，就那样" | 中文短 | 0.256 |
| —— 三条挤在 0.22–0.26，**毫无区分力** | | |
| "The flowers arrived wilted and yellow." | 英文 | **0.782** ✅ |
| "Very fresh flowers, careful packaging, great." | 英文 | **0.052** ✅ |
| 中文**长文本**（完整客诉描述） | 中文长 | **0.949 / 0.312** ✅ |

> **诊断**：noul 需要我们提供**足够长的中文语境**。短句（<15 字）下模型无法判断。这与 opendecider 训练数据形态一致——它是在**完整工单/长文本**上训练的，不是在短指令上。

### 7.7 探针结论对 §1 适配度的修正

| 原判 | 修正 |
|---|---|
| 语音指令意图路由 = A 级甜点 | ⚠️ **降为 B 级**：裸用 65.9% 不够；**必须配分档路由**才有价值 |
| 客户反馈正/负 = A 级甜点 | ❌ **降级**：中文短句下 noul 失效；**需改为长文本输入或换模型** |
| 平台公告分类 = A 级甜点 | ✅ **维持**，但需接受 67% 裸准确率 + 分档 |
| 差评 6 分类 | ⚠️ 准确率尚可（87.5%）但**置信度无区分力**，需换模型或换配置再验 |
| 所有场景 | 🔺 **新增门槛**：**输入长度**成为独立判据——短中文不可靠 |

## 8. 本报告的结论

1. **可覆盖面比预期宽**：盘出 **50 个决策点**，其中 5 个纸面 A 级；**实测后收敛为"需要配分档才成立"**。
2. **真正的增量不是"快"和"便宜"**，而是三件事：**口径一致性**（选项集调用前枚举 + 模型完全确定）、**校准置信度**（可做分档路由）、**可全量跑**。速度只是前提。
3. **实测证明分档是真的有用**：中文意图路由裸用 65.9%，**门槛 0.4 时 46% 自动化 @ 94.7%**。**这是唯一站得住的用法。**
4. **三个硬约束浮出水面**（纸面调研看不出来的）：
   - **中文短文本不可靠**（noul 完全失效、choice 掉到 65.9%）
   - **选项措辞是主导变量**，且"写详细"反而变差
   - **置信度不是普遍可用的**——差评场景上它就没有区分力
5. **一个意外的正面发现**：模型**完全确定**（5 次逐位一致），消除了做口径一致性时的抖动变量。
6. **我们系统最大的一块（规则可判的判定）不该用它**——象限 ① 用规则，这是纪律。
7. **两个场景自带回测集**（修复根因归类有历史 repair-reports；来源可信度有历史来源台账），可先离线验证。
